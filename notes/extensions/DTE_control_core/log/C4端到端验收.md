> 状态：完成。C4 DTE 门禁通过；另记录一个非阻断、非 DTE 的 P6 legacy oracle 计数问题。

## 1. 静态覆盖结论

- WorkerCore 的物理传输和异步 token 业务操作统一经 `DteControlFrontend`。
- P2P、collective 与 memory bridge 生产路径没有绕过 frontend 直接调用 `DTEUnit`/`DteAsyncTracker` 的业务方法。
- `DteOutstandingCount()` 聚合 frontend token、frontend transfer 与 P2P async token，顶层 drain 继续以该统一计数判定残留。
- memory bridge 绑定统一经 `DteControlFrontend::BindMemoryBridge()`；frontend 再根据 legacy/dedicated 模式完成后端接线。
- 删除了 `logic.cpp` 中未使用且暴露 `DteTransferContext` 的 `WaitForDteTransmitStart()` dead helper。

## 4. 非阻断旁路回归问题

最终 binary 可复现：

```bash
ctest --test-dir build -R "^program_p6_collective_runtime_matrix$" --output-on-failure -j1
```

P6 legacy matrix 前两个 case PASS，第三个
`--p6-broadcast-gather-n4-l1024-u8-none` 因 oracle `action_count` 期望 96、
运行时实际 88 而停止。该 case 明确运行在 `legacy_shared`，所有
`DTE_CTRL_STATS submitted=0`；同时 `[PROGRAM_MEMORY] dte_residual=0`、P5
endpoint/timing residual=0、P6 aggregate/admission/barrier/endpoint/timing
residual=0、`COLL_DRAIN`、router 与 D2D residual 均为 0。因此它是既有/非
DTE 的 collective action-count oracle mismatch，不计为 DTE C4 门禁失败，
但应在 P6 oracle/执行器任务中继续跟踪。
