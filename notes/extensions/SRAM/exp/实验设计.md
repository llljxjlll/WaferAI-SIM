# 单 die GEMM + Reduce-Scatter SRAM Swizzling 重叠实验设计

## 1. 实验目标

本实验验证以下生产能力：

1. 每核私有 SRAM 使用真实 storage/access 数据面。
2. 通过硬件配置手工划分输入、权重、中间结果、通信双缓冲、接收区和 scratch。
3. LSU 执行本核 HBM↔SRAM 双向搬运，并逐字节校验 round-trip。
4. GEMM 输入采用双缓冲预取；GEMM 输出执行 layout swizzle 后进入 RS 双通信缓冲。
5. 同一 die 内的 Reduce-Scatter REQUEST/ACK/DATA 与后继真实 `Compute_tile` 重叠，并给出逐操作时间 breakdown。

## 2. 拓扑与负载

- 物理拓扑：单 die、2×2 mesh；实验启用 core 0 和 core 1。
- collective group：2 个 rank，执行 2-way direct Reduce-Scatter。
- 每核计算 2 个逻辑 GEMM chunk；chunk 0 的 owner 为 core 0，chunk 1 的 owner 为 core 1。
- 每个 owner 保留本地贡献，并接收另一个 rank 的 1 份远端贡献。
- GEMM tile：4096 B，512 cycles。
- RS payload：512 B，`noc_payload_per_cycle=1`，即 32 个 DATA packet/flow。
- owner reduce：32 cycles。
- 调度窗口：core0 startup guard 128 cycles、core0 arrival 0 cycles、core1 arrival 512 cycles、core0 completion park 8192 cycles。
- `send_recv_parallel=true`，cycle NoC，真实 SRAM，behavioral distributed-HBM backend。

采用 2-way RS 是有意的实验隔离：普通 unicast endpoint 的 `MAX_BUFFER_PACKET_SIZE=3` 不适合 3 个发送者同时向一个 owner 注入多包 flow。4-way direct RS 的大包试验会把端点流控限制混入 SRAM 验证；2-way 仍完整覆盖 send/receive/reduce、双缓冲和计算通信重叠。

## 3. 手工 SRAM 划分

每核 SRAM 容量为 40 KiB（40960 B）。所有功能区均为 fixed、non-spillable；地址和权限由 `hardware.json` 显式给出。

| 区域 | byte 地址 | 预留容量 | 功能 |
|---|---:|---:|---|
| `gemm_input_a` | 0–8191 | 8192 B | 偶数 tile 当前输入/预取 |
| `gemm_input_b` | 8192–16383 | 8192 B | 奇数 tile 当前输入/预取 |
| `gemm_weight_b` | 16384–24575 | 8192 B | 常驻权重 |
| `gemm_accum` | 24576–32767 | 8192 B | 两个 4096 B GEMM 中间结果 |
| `rs_send_a` | 32768–33279 | 512 B | 偶数 chunk 通信 buffer |
| `rs_send_b` | 33280–33791 | 512 B | 奇数 chunk 通信 buffer |
| `rs_recv` | 33792–34303 | 512 B | owner 接收/规约区 |
| `scratch` | 34304–34815 | 512 B | 本 rank 最终 RS chunk |
| 未划分 | 34816–40959 | 6144 B | guard/headroom |

静态预留为 34816 B（85%），headroom 为 6144 B（15%）。估算峰值 live payload 为 22528 B（55% SRAM）：双输入 8192 B、实际权重 4096 B、两个 accumulator 8192 B、双 send payload 1024 B、recv 512 B、scratch 512 B。

## 4. 数据路径与调度

### 4.1 HBM 与双输入缓冲

每核执行 chunk 0 时：

1. 用 `gemm_input_a/b` 交替生成两个确定性 tile。
2. LSU 将两个 tile store 到该核独有的 HBM backing range。
3. LSU load chunk 0 到 `gemm_input_a` 并逐字节校验。
4. 对 `gemm_weight_b` 做 SRAM→HBM→SRAM round-trip 并校验。
5. 在 chunk 0 GEMM 开始前异步 issue chunk 1 load 到 `gemm_input_b`。
6. `ComputeTimeline::RunTile` 计算 chunk 0；结束时 wait 并校验 chunk 1 prefetch。

chunk 1 直接消费已经装入 `gemm_input_b` 的数据，因此没有串行 HBM load 位于它的 GEMM 前面。

### 4.2 GEMM、swizzle 与标签绑定

每个 chunk 的 GEMM 从当前 input region 读取 4096 B，运行 512 cycles，读取常驻权重，并将结果写入 `gemm_accum[chunk]`。随后使用步长 17 的非连续索引抽取 512 B，写入：

- 偶数 chunk → `rs_send_a`
- 奇数 chunk → `rs_send_b`

原语将 worklist 的输出标签绑定到 send buffer 的真实 byte 地址；后续 `Send_prim` 会通过统一 SRAM access unit 读取该标签对应区域。

### 4.3 2-way Reduce-Scatter Swizzling

核心时序为：

- core 1：GEMM(0) → async send chunk 0 → GEMM(1) → 512-cycle owner window → receive chunk 1 → reduce(1) → receive completion → DONE
- core 0：128-cycle startup guard → GEMM(0) → receive chunk 0 → reduce(0) → GEMM(1) → async send chunk 1 → send completion → 8192-cycle park → DONE

core0 的 startup guard 调整两核相位；最终 trace 中 core1 chunk0 DATA 为 14.011–14.335 μs，core1 chunk1 `Compute_tile` 为 14.161–15.547 μs，DATA-only 交叠 174 ns。RS 完成后 core0 从 `scratch` 向 core1 发送 tag 8000 completion flow；8192-cycle park 负责释放该 flow 尾包，两个核随后各自 DONE。core0 worklist 首部的无 SRAM guard 也保证 DONE 后短暂 refill 不会启动新的 SRAM/LSU 请求。

## 5. 时间与占用分析方法

原语输出确定性 marker：

- `GEMM_RS_TILE`：HBM store、load/prefetch、weight round-trip、GEMM、swizzle+label、checksum 和 ready time。
- `GEMM_RS_REDUCE`：owner reduce 时间、checksum 和完成时间。
- `GEMM_RS_OWNER_WINDOW`：startup、arrival 与 completion park 调度窗口。

分析器同时读取 `events.json`：

- REQUEST、ACK、DATA、阻塞 owner receive 的 B/E span。
- SRAM、LSU、Compute trace 的 B/E phase 平衡。
- 完整通信事务（REQUEST begin→DATA end）与后继 GEMM 的交集。
- DATA span 本身与后继 GEMM 的交集。

Chrome trace 的 `ts` 为微秒，分析器统一乘 1000 转成 ns。

## 6. PASS 条件

- 4 个 `GEMM_RS_TILE`、2 个 `GEMM_RS_REDUCE`、4 个 schedule window。
- 2 个 RS DATA flow + 1 个 completion DATA flow；所有 SRAM/HBM round-trip 与 swizzle/reduce checksum 非零。
- 6 个 `Compute_tile`（4 GEMM + 2 reduce）。
- SRAM、LSU、Compute staged trace 均存在且 B/E 数量平衡。
- core 1 的 chunk 0 完整通信事务和 DATA-only span 都与 core 1 chunk 1 GEMM 有正交集。
- `Catch test finished`、`router_residual=0`、`data_balanced=1 ctrl_balanced=1`，且没有 watchdog/rendezvous 失败。

## 7. 能力边界

普通 NoC DATA 当前仍携带时序/值元数据，而不是完整 tensor byte array。实验真实验证发送前的 SRAM payload、HBM↔SRAM 数据、SRAM 内 swizzle 和 NoC 时序；owner 的远端 tensor bytes 由确定性 payload 建模后写入 `rs_recv`。因此本实验不宣称完成跨核逐字节数值 Reduce-Scatter。若要做端到端数值验收，需要扩展 `Msg`/DTE remote path 携带真实 payload，并由 `Recv_prim` 写入 `rs_recv`。
