# P3 四类完整模型逻辑图与 Coverage Oracle 开发记录

日期：2026-09-14  
状态：四类多层、多步 typed 逻辑语义图与独立 coverage/state-lineage 校验完成；lowering、runtime 和 simulator canary 尚未完成。

## 1. 本切片目标与范围

本切片为 P3.1–P3.6 建立可审查的逻辑覆盖基线，先回答“一个完整负载必须包含什么”和“跨步状态如何连续”。它复用 P0 的 `WorkloadRunRequest`，但没有修改 P0 的 workload materialization 集成模块，也没有把逻辑清单冒充成可运行程序。

当前基线强制：

- 模型至少两层。
- 推理包含一次 Prefill 和至少两步 Decode。
- 训练包含至少两个完整 step，优化器为 SGD。
- Dense inference、Dense training、MoE inference、MoE training 使用同一版本化 typed graph 合同。
- graph 的 `lowering_status` 和 `runtime_status` 固定为 `NOT_MATERIALIZED`；coverage report 的 `lowering_verified` 和 `runtime_verified` 固定为 `false`。

因此，本记录表示逻辑图和独立 oracle 已完成，不表示 M1、真实 E2E 执行或模拟器支持已经完成。

## 2. 开发内容

### 2.1 Typed 逻辑图与状态版本

新增 `llm/frontend/wafer_frontend/schema/e2e_workload_graph.py`：

| 类型 | 作用 |
|---|---|
| `E2EOperationKind` | 枚举 forward、KV、routing、backward、gradient、sync、optimizer、store 和 step commit 操作 |
| `E2EWorkloadOperation` | 记录稳定语义 ID、顺序、family phase、step、layer、expert、parameter、读写 state 和依赖 |
| `E2EStateVersion` | 记录 parameter、KV、gradient 的逻辑名称、版本、producer 和全部 consumers |
| `E2EWorkloadGraph` | 绑定原始 workload request、完整 operation 序列、state lineage 及未物化状态 |

schema 校验会拒绝非连续序号、向后或未知依赖、未知 state、同一 state 多 producer、producer/consumer lineage 不闭合、跨 case 引用、陈旧稳定 ID，以及任何伪造的 lowering/runtime 完成状态。

### 2.2 四类图构建器

新增 `llm/frontend/wafer_frontend/passes/build_e2e_workload_graph.py`，入口为 `build_e2e_workload_graph()`。

四类 family 的覆盖如下：

| Family | 生成的逻辑链 |
|---|---|
| Dense inference | embedding → 每层 input norm/QKV/RoPE/KV load/attention/KV append/O/residual/MLP/residual → final norm/LM head/logits；Prefill 后连续两步 Decode |
| Dense training | 每步 parameter load → 完整 Dense forward → loss → 各层 backward → 每个可训练参数 WGRAD → gradient sync → SGD update → parameter store → step commit；连续两步 |
| MoE inference | Attention 主干加 router、冻结路由、dispatch、逐 expert forward、combine、residual 和 KV 跨步版本 |
| MoE training | 完整 MoE forward/loss，加反向 grad dispatch、逐 expert backward、dX combine、shared backward；shared/router/expert 参数分别生成 WGRAD/router gradient/expert gradient，再执行 sync/update/store |

状态连续性采用显式版本表达：

```text
Inference: KV[v] -> KV_LOAD(step=v) -> KV_APPEND(step=v) -> KV[v+1]

Training:  parameter[v] -> PARAMETER_LOAD(step=v)
           parameter[v] -> gradient producer -> GRADIENT_SYNC
                        -> SGD_UPDATE -> parameter[v+1]
                        -> PARAMETER_STORE -> next step load
```

训练中的 `STEP_COMMIT` 显式依赖该 step 的全部 parameter stores，避免只完成首个 store 就宣告 step 完成。

### 2.3 独立 Coverage Oracle

新增 `llm/frontend/wafer_frontend/passes/validate_e2e_workload_graph.py`，入口为 `validate_e2e_workload_coverage()`。

oracle 不调用 graph producer。它根据 request 独立重建：

- 每个 family、layer、step、expert 和 parameter 应存在的 operation multiset。
- 推理各层 `KV[0..decode_steps+1]` 的 producer/consumer 关系。
- 训练每个参数 `parameter[v] -> raw gradient -> synced gradient -> SGD -> parameter[v+1] -> store/load` 的 lineage。

实际清单缺操作或多操作时，先按 operation kind 给出稳定缺口，再执行 graph 自身结构校验。这样 producer 不能通过自报完成掩盖语义缺失。

## 5. P3 → materialization 集成与 happens-before 加固

`E2EWorkloadGraph` 已接入 `WorkloadMaterializationManifest` 并成为逻辑语义的单一来源。manifest 必需保存 graph 及其 canonical digest，且 graph 内嵌 request 必须与 manifest request 完全相等。P0 的粗粒度 `WorkloadLogicalOperation` 类型和 producer 已删除。materialization 每次先构建 graph，再强制运行本模块的独立 coverage oracle；oracle 拒绝时不会继续发布 preflight manifest。

独立 oracle 在 operation multiset 与 state lineage 之外新增传递依赖检查：

- Prefill logits → 第一步 Decode embedding，后续 Decode 也保持连续；
- 每层上一阶段 KV append → 下一阶段 KV load；
- 每个训练 step 的 loss → 全部 backward 操作；
- backward 按最高层到最低层逆序发生；
- 每个参数的 raw gradient → sync → SGD update → store；
- 当前 step store → 下一 step 对新参数版本的 load。

故障注入测试通过重建稳定 operation ID 和 state producer/consumer 引用，构造结构合法但缺少指定传递依赖的 graph。断开 Prefill/Decode、loss/backward、反向层序、gradient/sync 或 store/next-step-load 中任一关系，独立 oracle 都会失败。

## 6. Typed tensor/value、KV 增长、MoE 路由与梯度同步合同

### 目标与实现

为逻辑 operation/state 补齐后续 lowering 所需的显式数据合同，同时保持 P3 仍是逻辑图，不生成 transport task、schedule 或 runtime 证据。

`E2EWorkloadGraph` 现在绑定完整 P1 `ParallelPlacement`，materialization 会把同一个 placement 实例传给 graph builder，并校验 manifest placement 与 graph placement 完全一致。新增 `E2ETensorValue` 记录 rank-local shape、复用的 `DType`、精确 bytes、state ref、P1 owner domain、logical rank、TP shard，以及 producer/consumer。operation 的 state reads/writes 会自动展开为 value input/output edges；graph 和独立 oracle 都检查引用及 lineage 闭合。

状态种类增加 activation、logits、loss、route token 和 dispatch payload。参数及 FP32 梯度值按 P1 ownership domain 覆盖全部 replica rank；普通 activation 覆盖 active ranks；每个 value 的 TP shard 必须与 rank placement 一致。KV value 按 request、layer 和 version 生成，形状使用 KV-head TP 分片，缓存长度明确为 `0 → prefill_tokens → prefill_tokens + decode_tokens`，bytes 随 Decode 单调增长。

MoE 每个 forward step/layer 生成冻结的 top-1 `token → expert` trace。dispatch 和 expert output 都有逐 expert payload state/value，payload shape 与 trace 的 expert token count 一致；零 token expert 保留零 extent、零 byte typed payload，combine value 同样进入 producer/consumer 闭合。

训练 `GRADIENT_SYNC` 复用 IR0 `ReduceOp.SUM`，直接绑定参数 owner 对应的 P1 synchronization group。`normalization_denominator` 必须等于实际 group rank 数，从而明确表达 SUM 后归一化得到 MEAN；MoE shared 参数覆盖 EP×DP replica group，expert 参数覆盖各自 expert-gradient group。

独立 oracle 不调用 producer，重新推导参数/梯度/KV/activation/logits/loss/route/payload 的 shape、dtype、rank/owner 覆盖，核对 state/value edges、冻结 trace、零 token expert、payload bytes 和 P1 group SUM-to-MEAN 归一化。故障注入改变合法 route trace 时必须被 oracle 拒绝。

## 7. Logical graph 到 P1 transport 的精确绑定

P3 communication operation 现在是 materialization transport request 的唯一语义来源。QKV 对应每层、每 Prefill/Decode step 的 TP AllGather；GRADIENT_SYNC 对应每个训练 step 和参数 owner group 的 AllReduce；MoE DISPATCH/COMBINE 对应逐 expert payload 的 AllToAll。每项 request 保存 operation/value 引用和 typed value 的精确 bytes，零 token expert 保留为 no-op，因此 coverage 不会因优化掉零流量而失真。

新增独立 `validate_parallel_transport_workload_bindings` oracle，不复用 producer 的 request 集合：它从 graph 重新枚举预期通信点，验证 P1 group/owner、value rank、bytes、case/digest 和 phase/step/layer，并在存在 plan 时调用严格 send/recv 配对校验。伪造 payload bytes 的故障注入会失败。

四 family 测试覆盖 Prefill 与两个 Decode step、逐层 TP、两个训练 step 的 gradient sync、MoE dispatch/combine 和 inference 零 token no-op。联合聚焦回归 40/40 通过。该切片仍只到 transport plan，未生成 simulator program 或 runtime 成功证据。

## 与 P0 legacy Dense backend 的集成审计

统一 P3 graph 当前要求 inference 至少覆盖两层、Prefill 与 2 个 Decode step。对 production `compile_rect_mesh(AUTO)` 的实测表明，其 `naive_fixed/v1` 下游 `build_ir0` 拒绝 mixed Prefill/Decode static profile，错误为无法唯一确定 attention work。因此 P0 compatibility gate 将 P3 完整请求明确标为 `unsupported`，不会把 legacy 静态单 phase 编译结果标为 P3 graph lowering。

独立 legacy 纯 Prefill compiler canary 可以真实编译并生成 linked manifest，但 capability report 仍为 `standard_chain_complete=false`、`dense_workload_complete=false`。该结果只记录为 `legacy_static_profile/motif`，`full_model_ready=false`。P3 后续接 backend 的前置条件是 production lowerer 直接消费并覆盖 `E2EWorkloadGraph` 的全部 operation/value/route，而不是按相近 shape 复用 legacy profile。

## P3.1：Dense E2E compile-only 多 profile sequence

### 目标

解除 P3 Dense inference 完整图无法交给 legacy mixed-profile compiler 的第一个阻断。把统一 graph 的 `Prefill → Decode-1 → Decode-2` 拆为三个纯静态 profile，分别复用真实 production `compile_rect_mesh`，并用一个版本化 sequence artifact 证明 segment、graph operation 与 KV 状态连续性。此阶段不拼接三个 linked program，也不发布 runtime 或完整 E2E 支持。

### 实现

新增 `schema/dense_compile_sequence.py`，定义 `wafer_frontend.dense_compile_sequence/v1alpha1`：

- `DenseCompileSequence` 嵌入原始 `WorkloadMaterializationManifest`，绑定 materialization 和 logical graph digest；
- 固定三个 `DenseCompileSegment`，timeline 必须为 `(prefill, step=0) → (decode, step=1) → (decode, step=2)`；
- 每个 segment 嵌入派生后的 legacy `ExperimentSpec`、当前 step 的全部 P3 operation refs、全部 layer binding、production compiler capability report、非空 `LinkedProgramManifest` 及其内容 digest；
- 每个 layer/rank 建立 `DenseKvSegmentBinding`，显式记录 input/output KV version、P3 state ref、HBM address 和 reserved bytes；
- KV 地址从 materialization memory plan 中每个 rank 的 resident KV allocation 按 layer 稳定切片。相邻 segment 必须复用同一 layer/rank 地址与容量，且前一段 output state/version 必须精确等于后一段 input；
- `one_shot_workload_end` 只允许最后一个 Decode segment 为 true；
- compile 状态固定为 `independent_linked_programs`，runtime 状态固定为 `runtime_not_materialized`。

新增 `passes/dense_compile_sequence.py`。production pass 只接受 Dense inference、resident HBM、baseline timing-only、至少两层、恰好两个 decode step、DP/EP/PP=1、TP 覆盖完整 row-major RectMesh、单 legacy instance、model 精确一致且每 Die 有 HBM address space 的请求。它派生：

1. Prefill profile：统一请求的全部 prefill token；
2. Decode-1 profile：每个 request 一个 query token，context 为 prefill+1；
3. Decode-2 profile：每个 request 一个 query token，context 为 prefill+2。

三个 profile 分别调用真实 `compile_rect_mesh(AUTO)`。每次编译必须得到一个非空 linked program，并保持 `naive_fixed/v1`、`executable_baseline=true`、`standard_chain_complete=false`、`dense_workload_complete=false`。任何 capability 漂移都会拒绝 sequence。

### 真实 compiler canary

当前 production profile MVP 还有两个组合约束：Prefill 必须 `num_seqs=1`；TP>1 又要求 sequence parallel，而纯 Decode token 数必须能被 TP 整除。因此 TP2、单 request 的统一 P3 case 在编译前明确拒绝，理由为 `request.decode_tokens_must_be_divisible_by_tp`；增加 request count 又会与 Prefill 单序列约束冲突。

首个合法 canary 因此使用 1×1 RectMesh、TP1、两层、Prefill=4、Decode steps=2、request count=1。三段 production 编译全部通过：

- Prefill linked manifest：44 fragments；
- Decode-1 linked manifest：48 fragments；
- Decode-2 linked manifest：48 fragments；
- 三个 linked manifest digest 各不相同；
- sequence END 标记为 `false / false / true`；
- 最终状态仍为 `runtime_not_materialized`。

### 限制与下一步

每个 legacy linked manifest 都是独立 program，拥有自己的本地 control envelope。sequence artifact 只定义统一 workload timeline 和最终 one-shot END 语义，尚未重写或链接中间 program 的 control envelope，也没有把上一段 KV 实际 simulator memory 映射为下一段 ProgramIO 输入。因此三个 compile 结果不能直接作为连续 runtime 执行，且不能成为 full-model runtime evidence。

下一步需要 production sequence linker：删除或重写中间 local END，统一 runtime symbol/address namespace，把 `DenseKvSegmentBinding` 转为跨段 persistent ProgramIO/state ABI，并对最终组合 artifact 运行 finalizer、resolver 与两次独立 simulator canary。在这些检查完成前必须保持 `runtime_not_materialized`。

## P3.2：Dense training 两步 compile/lower 基础

### 复用路径审计

现有通用 `train_n6` 只覆盖 forward train；`lite_train` 的真实 backward/SGD 链只覆盖 LM-head motif，不能代表 P3 的全部 17 个两层 Dense 参数。可复用的完整参数路径是：

```text
flexible_dense_train plan
  → production train forward lower/link
  → flexible_dense_backward IR/projection/schedule/global DAG
  → flexible_dense_backward[_multi] lower/link
  → LinkedProgramManifest
```

该 backward linker 对每个 legacy parameter 已生成真实非空 records：HBM parameter load、WGRAD MATMUL、DP>1 tree DTE sync/local reduce、SGD_UPDATE 和 HBM store。其 carrier 的 `runtime_verified` 固定为 false；旧 `FlexibleDenseTrainPlan.backward_lower_link_status=out_of_scope` 仍是早期 plan 能力字段，新的 linked carrier 在旁路中补齐了实际 lower/link，但尚未形成 P3 原生端到端 runtime。

### Versioned sequence 与参数绑定

新增：

- `schema/dense_training_compile_sequence.py`
- `passes/dense_training_compile_sequence.py`
- `test/frontend/unit/test_dense_training_compile_sequence.py`

`DenseTrainingCompileSequence` 嵌入 P3 materialization 和两个 training segment。production pass 只接受两层及以上、恰好两个 step、SGD、resident HBM、baseline timing-only、Dense、PP/EP=1、全 row-major active mesh，并要求 P3 TP=mesh columns、DP=mesh rows；legacy model、batch/sequence、parallel、fabric 和 HBM spaces 必须精确匹配。

pass 先通过现有 production 路径生成一个真实的一步 `FlexibleDenseBackwardLinkedProgram`，再把这个稳定 compiled template 绑定到 P3 step 0/1。每个 step 的 17 个 P3 trainable parameter 都显式记录：

- PARAMETER_LOAD、WGRAD、GRADIENT_SYNC、SGD_UPDATE、PARAMETER_STORE operation refs；
- input/raw-gradient/synced-gradient/output state refs；
- 参数版本 `0→1`、`1→2`，以及 step 0 output 等于 step 1 input；
- 每个 TP shard 的 P3 owner ranks、精确 logical bytes；
- legacy parameter/state、load/WGRAD/sync/SGD/store action refs；
- linked manifest StateABI、HBM address 和 byte slice。

P3 的 MLP gate/up 是两个参数，而 legacy 使用融合 `w_gate_up`。绑定将二者限制为同一 legacy buffer 的两个等长、不重叠半区。TP2 下 legacy 对 embedding/norm/LM-head 使用完整 carrier，P3 使用 TP shard；绑定显式记录 `tp_shard × logical_bytes` 的精确 slice。其他参数必须完整覆盖一个 legacy shard。DP1 的逻辑 sync 明确降为 singleton no-op；DP2 绑定真实 reduce/broadcast tree action 与 DTE records。

sequence 状态为 `reused_real_one_step_linked_program`，runtime 固定为 `runtime_not_materialized`。只有最后一个 P3 step 具有 one-shot workload end 语义。

相邻 P3 graph 与 flexible Dense backward 代表回归 11/11 通过，用时 35.260 秒。

### 当前限制

两个 P3 step 当前复用同一个真实的一步 linked program 模板；尚未把两个 step 合并为一个 control envelope，也未证明第一个 program 的 HBM store 会在同一 simulator 时间线成为第二步 load 的实际输入。legacy fused/replicated carrier 的 byte slice 是严格 compile binding，但现有 records 仍按 legacy 完整 carrier 执行。因此本切片证明真实非空 lower/link 与 P3 全参数/版本合同已闭合，不构成两步 runtime 或数值训练成功证据。

下一步需要 P3-native sequence linker/ProgramIO：将 step version 映射为跨段 persistent StateABI，处理中间 END、runtime symbol/session epoch，并运行 finalizer、resolver、两次连续 NpuSim canary。在此之前 capability 不得提升。

## P3.1-R：Dense Prefill→Decode→Decode 同实例 runtime sequence

### 目标与能力边界

把 P3.1 的三个真实 production linked program 放到同一个 NpuSim/SystemC 实例、同一套 WorkerCore、HBM backing 和时间线上连续执行。段边界只暂停供 host 校验和装载下一段，前两段不得停止 workload；第三段才执行一次最终 drain。本切片严格限定为 1×1 Mesh、TP1、两层 Dense inference、resident-only、baseline timing ProgramIO，不改变 `DenseCompileSequence.runtime_status=runtime_not_materialized`，也不把该 canary 提升为任意 Mesh、数值功能或 full-model readiness。

### Persistent KV StateABI

新增版本化 `PersistentStateReservationPolicy`。placement 对 KV binding 仍记录该段真实 tensor bytes，但分配游标按最终 Decode 的保留槽前进；默认无 policy 时保持原有地址与 digest 行为。三段 compiler 透传同一策略，因此每层 KV 在 Prefill、Decode-1、Decode-2 中地址稳定，真实 extent 分别增长，且不会与下一层状态重叠。sequence validation 还要求每段恰好覆盖全部物理 KV StateABI，逐 layer/rank 的 kind、die、address 不变，size 与本段 P3 KV version 精确一致。

### 同实例 sequence runtime

新增 `config_helper_program_sequence`，顺序加载三个 finalized Program artifact。它要求每段 ACK/DONE core 集一致；每个中间完整 DONE 集只生成 segment marker、加载下一段并 `sc_pause()`，最终完整 DONE 集才生成 one-shot drain marker并 `sc_stop()`。`MemInterface` 在 sequence 的非最终 DONE 边界把 DATAFLOW phase 从上段结束的 `PRO_START` 精确恢复为 `PRO_CONF`，确保下一段严格经过 CONFIG→WEIGHT DATA→START；该分支不作用于普通单 Program、不完整 DONE 集或最终 DONE。

ProgramIO 新增 `ApplyBeforeSequenceSegment`：首段正常初始化；后续段在 `SC_PAUSED` 边界刷新 SRAM，但保留已有 HBM byte，只对尚未出现的 KV tail subrange 做归一化、事务式补零。SRAM/HBM debug boundary API 允许 elaboration 或 paused，仍拒绝 active simulation。每段恢复运行前由同一 `Bindings` 复用同一个 `HbmRuntime`，每段结束后先执行 typed output probe，再读取该段全部真实 KV StateABI byte 并输出聚合 SHA-256。

`npusim` 增加成对的三段参数：`--program-sequence`、`--linked-manifest-sequence`、`--program-io-sequence`。preflight 对每段执行 artifact decode、finalizer 重建闭合、ProgramIO resolve，并验证两层四个物理 KV ABI 的地址连续和 extent 严格增长。运行结束后的统一 Program memory 报告从 sequence helper 读取最终 decoded artifact；同一进程只输出一个 `SIM_RESULT`。

### 限制与下一步

当前证据证明的是 production compiler/finalizer/resolver 产物在同一 timing simulator 实例上的两层 Dense、1×1/TP1 三段连续执行，以及 KV 物理地址和 byte presence 连续。ProgramIO probe 仍是 timing-only，KV 内容由 behavioral execution/缺失 tail 初始化形成，尚无参考框架的逐值数值比对；只运行一次 canary，也未达到 capability builder 要求的两次独立执行证据。因此 capability 必须继续 fail closed。下一步应生成独立、版本化 runtime evidence carrier，执行两次隔离 canary并核对 artifact/marker/KV digest，然后扩到 TP>1/多 Die 和真实 functional oracle。
