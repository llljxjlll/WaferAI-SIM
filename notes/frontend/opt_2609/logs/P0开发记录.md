# P0 开发记录：统一负载运行请求与能力合同

日期：2026-09-14

## 本次切片目标

建立可供后续编译、运行与证据模块共同使用的生产侧输入合同，统一描述以下四类端到端负载：

- Dense 推理：`dense_inference_e2e`
- Dense 训练：`dense_training_e2e`
- MoE 推理：`moe_inference_e2e`
- MoE 训练：`moe_training_e2e`

本切片同时建立机器可读的能力合同，避免将 schema 可表达、motif 可运行或未测量能力自动提升为完整模型运行能力。

## 实现内容

新增 `llm/frontend/wafer_frontend/schema/workload_run.py`，包含两个独立版本的顶层合同：

- `wafer_frontend.workload_run_request/v1alpha1`
- `wafer_frontend.workload_run_capability/v1alpha1`

`WorkloadRunRequest` 统一包含：

- family 与 Dense/MoE 模型维度；
- 推理 Prefill/Decode 步骤或训练 step/batch/microbatch/sequence 配置；
- 不受当前 10×10 验证范围硬编码限制的矩形 mesh 描述；
- TP/DP/EP/PP 逻辑并行度，以及可选的逻辑 rank 到 active die 顺序；
- resident HBM、remote HBM、external offload 三种内存策略意图；
- SGD/AdamW 优化器参数；
- timing/functional、独立重复次数和 baseline/optimized 执行策略。

请求校验覆盖模型维度关系、Dense/MoE family 一致性、推理/训练步骤互斥、训练 global batch 公式、optimizer 使用范围、TP/EP 整除、active die 唯一性与边界、序列上限、PP 当前限制，以及 external tier 引用条件。

每个请求使用完整规范化语义生成 `workload_case_<digest-prefix>`。反序列化后会重算并校验 case ID；任一模型、步骤、映射、内存或执行字段变化都会改变 ID，旧 ID 不能绑定新输入。

`WorkloadRunCapability` 要求四个 family 按固定顺序完整出现，并分别报告：

- full-model 与 motif；
- baseline 与 optimized；
- lowering 与 runtime；
- timing 与 functional；
- capacity、multi-step、remote HBM、external offload；
- SGD、AdamW 和 repeatability。

状态使用 `unsupported`、`schema_only`、`not_measured`、`supported`，只有 `supported` 满足运行请求。能力之间有依赖校验，例如 runtime 必须建立在 lowering 上，functional/multi-step/repeatability 必须建立在 runtime 上，offload 必须同时有 capacity 与 runtime 支持。

能力合同单独声明已支持的最大行、列和 rank 数。输入 schema 因而可以描述 12×12 等后续目标，而当前 10×10 capability 会明确拒绝该请求，不会把“可序列化”等同于“已验证可运行”。

新增合同已从 `llm.frontend.wafer_frontend.schema` 和 `llm.frontend.wafer_frontend` 公共包导出。

## 兼容性与当前限制

- 本次是 P0 可合入基础切片，没有替换既有 `ExperimentSpec` 或 `FlexibleMeshWorkloadSpec`，旧入口行为保持不变。

- 本切片验证 schema 和能力门控，没有生成 manifest，也不构成四类 full-model runtime 已通过的证据。

## P0.3 统一 preflight/materialization 集成切片

### 目标

将 `WorkloadRunRequest` 转换为可复核的 P1 placement/ownership、通信请求、可选物理 transport plan 和 P2 `MemoryPlan`，并用稳定 typed manifest 绑定输入与结果。本切片不生成 linked program 或 runtime evidence。

### 实现

新增 `schema/workload_materialization.py`、`passes/workload_materialization.py` 和对应单元测试。生产入口为 `materialize_workload_preflight(request, capability, capacities=..., fabric=...)`。

入口完成以下转换：

1. 复用 P1 Dense/MoE builder 生成 `ParallelPlacement`、groups 和 ownership domains。
2. 四类 family 均生成非空逻辑操作清单：Dense 推理覆盖逐层前向和 logits；Dense 训练增加 loss、backward/WGRAD、梯度同步、optimizer/store；MoE 推理增加 router/dispatch/expert/combine；MoE 训练增加 expert backward 和反向 dispatch/combine。
3. 按 ownership 生成参数 shard/replica state，并加入 KV、gradient、optimizer、activation、communication 和 MoE buffer inventory。
4. 按 TP/DP/EP group 生成 typed collective requests；提供 fabric 时调用 P1 transport builder 生成 core binding、XY route、transfer 和 endpoint。
5. 将完整 state inventory 转换为 P2 state/version/allocation request，调用真实 hierarchical planner 生成 allocation、residency 和 peak。
6. manifest 绑定 request/capability/placement/transport/memory digest，反序列化后重新检查引用闭合、并行度、transport placement 和 memory state 完整覆盖。

`WorkloadMaterializationManifest.status` 只有 `partial` 与 `unsupported`。`lowering_status` 和 `runtime_status` 固定为 `not_materialized`，因此 preflight 不会被提升为 E2E complete。

remote HBM 的重新放置和 staging 尚未完成，当前 fail closed。external 模式可以产生 P2 external allocation，但保持 `schema_only_external`，不构成 offload runtime 证据。

### 测试

执行：

```bash

  -s llm/test/frontend/unit -p 'test_workload_materialization.py' -v
```

结果：8 项通过。覆盖四 family 真实 typed manifest、严格 serde/digest、schema-only capability、可选真实 transport、HBM 容量不足、缺 capacity、remote HBM 拒绝、空 inventory/伪造 digest，以及 external schema-only。

### 当前边界

- logical inventory 与 state size 是按模型维度、ownership 和 steps 计算的 P0 preflight，不替代 P3 完整 DAG lowerer。
- transport payload 和 transient lifetime 是确定性 preflight 合同，后续由真实逐算子 schedule 细化。
- 本切片没有 finalizer、ProgramIO、NpuSim 或 evidence；`partial` 不能解释为 runtime 通过。



## P0.4 统一运行器 API 切片

### 目标

在 P0.3 preflight/materialization 之上建立一个生产侧公共运行入口，统一管理运行目录、输入绑定、阶段产物、失败诊断、严格 resume 和一次或两次独立执行。当前没有接入真实 simulator backend，因此任何路径都不能发布 `SUCCESS` 或 `complete`。

### 实现

新增 `llm/frontend/wafer_frontend/workload_runner.py`，公共入口为：

```python
run_workload(
    request,
    capability,
    capacities=...,
    output_dir=...,
    fabric=None,
    adapter=None,
    resume=False,
)
```

每个新工作目录先写入：

- `request.json`：完整 `WorkloadRunRequest`；
- `input_binding.json`：绑定 request、capability、canonical capacities、可选 fabric、adapter ID 和后端 toolchain digest 的稳定 digest；
- `manifest.json`：P0.3 产生的 typed materialization manifest；
- `status.json`：只允许 `partial`、`unsupported` 或 `failed`；
- `error.json`：失败阶段、输入绑定 digest、异常类型和消息。

提供 `WorkloadBackendAdapter` typed adapter，使用四个注入 callable 明确表示 adapter、finalize、resolve 和 runtime 边界。每个 callable 必须返回 `WorkloadStageArtifact`，runner 会检查阶段、输入 digest、输出 digest 和稳定 ID。前一阶段的输出 digest 是后一阶段的输入 digest。runtime 是唯一允许 `one_shot_workload_end=true` 的阶段，其他阶段携带该标志会被严格拒绝。

`request.execution.independent_repeats` 驱动独立的 `execution_0/`、`execution_1/` 工作目录。重复执行各自重新经历 adapter/finalize/resolve/runtime，最终 runtime digest 必须完全一致，否则以 `workload_repeatability_mismatch` 失败，且 status 不发布 execution digests。

resume 会重新计算并精确比较输入 binding，因而 request、capability、capacity、fabric、adapter ID 或后端 toolchain/binary digest 的变化都会以 `workload_resume_stale` 拒绝。它同时重新反序列化 request、manifest 和 status，核对 request/binding/manifest 的交叉 digest。失败工作目录被保留，但不能作为已完成结果 resume。

能力门控为 fail closed：若 P0.3 manifest 是 `unsupported`，runner 不会调用任何 backend adapter。没有 adapter 时只完成 materialize 并返回 `partial`。即使注入 adapter 的全部四阶段执行完成，当前 status 仍是 `partial`，`runtime_evidence_materialized=false`，且从不创建 `SUCCESS`。只有后续接入真实 simulator、验证其协议和生成 runtime evidence 后，才允许建立完成发布路径。

公共类型和 `run_workload` 已从 `llm.frontend.wafer_frontend` 导出。

## P0.4 补充：阶段产物可信度修复

### 目标

修复 typed adapter 只声明任意对象摘要、未把摘要绑定到实际文件的问题。阶段完成、双独立执行比较和 resume 都必须从工作目录重新读取产物，缺失、篡改或截断文件一律 fail closed。

### 实现

`WorkloadStageArtifact` 升级到 `wafer_frontend.workload_stage_artifact/v1alpha2`，其内容包括：

- 阶段类型与上一阶段输入 digest；
- 非空且按相对路径规范排序的 `WorkloadStageFile` 清单；
- 每个文件的规范化相对 POSIX 路径、实际字节数和内容 SHA-256；
- 由阶段、输入 digest 和完整文件清单计算的阶段输出 digest；
- 只允许 runtime 阶段为 true 的 `one_shot_workload_end`。

adapter callback 先把真实产物写入其独立 execution 工作目录，再调用 `WorkloadStageArtifact.create(..., work_dir=..., relative_paths=...)` 捕获文件清单。捕获和验证拒绝绝对路径、`..`、非规范路径、符号链接、工作目录外文件、缺失文件和非普通文件。内容 SHA-256 使用 1 MiB 分块流式读取，可处理大型 simulator 输出而不把整个文件装入内存。

runner 在三个边界重新验证：

1. callback 返回后立即从磁盘重算文件大小与 SHA-256；写入阶段 manifest 后重新反序列化并再次验证；
2. 所有独立执行结束后，按 adapter→finalize→resolve→runtime 顺序重新加载四个阶段 manifest，核对输入/输出 digest 链并重算全部文件摘要；
3. resume 时重新枚举预期 execution 目录，再加载每个阶段 manifest、重算文件摘要和最终 execution digest，并与 `status.json` 精确比较。

双执行的一致性因此建立在实际文件内容和完整阶段链上，而不是 adapter 自报的抽象对象。adapter ID 与 toolchain/binary digest 仍保留在 `input_binding.json` 中。

## P0.5 补充：证据派生 capability 与 runner readiness

### 目标

消除调用方直接构造 `WorkloadRunCapability(... supported ...)` 即可进入 backend 的可信度缺口。capability 的报告值与 runner 的执行资格必须来自版本化、可交叉校验的真实 case 证据；full-model、motif 和缺失证据不能混为一类。

### 实现

新增独立生产模块 `llm/frontend/wafer_frontend/workload_capability_evidence.py`。模块提供唯一生产 builder：

```python
build_workload_capability_from_evidence(
    evidence,
    max_mesh_rows=...,
    max_mesh_columns=...,
    max_mesh_ranks=...,
)
```

证据链包含三个版本化合同：

- `WorkloadCapabilityArtifact`：按 lowering、runtime、functional、capacity 四种角色引用具体 artifact digest；
- `WorkloadCapabilityEvidence`：绑定完整 `WorkloadRunRequest`、request digest、family、case ID、full-model/motif scope、source digest、binary digest、toolchain digest、artifact 清单和独立执行 digest；
- `WorkloadCapabilityDerivation`：同时保存规范排序的 evidence 集合和由该集合计算出的 `WorkloadRunCapability`，反序列化后重新派生 capability 并精确比较，拒绝调用方替换为自行构造的 supported capability。

builder 对四个 family 分别聚合证据。只有 full-model scope 且存在 lowering artifact 的 case 才能派生 `full_model/lowering=supported`；runtime、functional、capacity、multi-step、optimizer、memory mode 和 repeatability 分别从对应 artifact、请求语义和独立执行结果派生。motif-only evidence 只能提升 motif，不会提升 full-model。

runner binding/status 升级后显式记录：

- capability derivation digest；
- adapter source、binary 与 toolchain digest；
- `ready` / `non_ready` readiness；
- 稳定、排序且机器可读的 readiness reasons。

runner 会重新验证 derivation 确实由生产 builder 规则派生，并要求 evidence 与当前 request 的 family、case ID、request digest 和完整请求完全一致。进入 adapter 还必须满足：

1. full-model evidence；
2. lowering、runtime、capacity artifact 齐全；
3. functional 请求具有 functional artifact；
4. source、binary、toolchain digest 与 adapter 完全一致；
5. 至少两次独立执行，且执行 digest 一致；请求要求更多重复时按更大值检查。

没有 adapter、没有 evidence derivation、只有调用方自建 supported capability、跨 case evidence 或证据不完整时，runner 在 materialize 后返回 `partial + non_ready`，不创建 execution 目录，也不调用 adapter。materialization 本身 unsupported 时仍返回 `unsupported + non_ready`。合法 evidence 只把 runner 置为 `ready` 并允许进入 typed adapter；当前运行结果仍保持 `partial`、`runtime_evidence_materialized=false`，不会提升为 complete 或发布 `SUCCESS`。

完整 derivation 会写入运行目录的 `capability_derivation.json`，并纳入 resume binding。resume 会严格反序列化并核对 derivation digest，因此替换或截断 capability evidence 不能复用旧目录。

### 测试

新增 `test_workload_capability_evidence.py`，7 项测试覆盖：

- 合法 full-model evidence 严格序列化往返、派生 capability 和 exact-case readiness；
- 跨 case evidence 不能使另一个请求 ready；

- 单次执行不会提升 repeatability/readiness；
- functional 或 capacity artifact 缺失时 fail closed；
- 调用方把 derivation 内 capability 替换成自行构造的 supported capability 会被拒绝。

结果：builder 专项测试 7/7 通过，相关生产与测试文件 `py_compile` 通过。

runner 增加伪造 supported capability 的非 ready 测试，并将原 backend/failure/artifact 测试迁移到合法 exact-case evidence。P3 接口迁移前 runner 11/11 通过。随后 P3 将 `E2EWorkloadGraph.create` 扩展为 placement、tensor values 和 route traces 必填，而其 builder 当时仍在同步迁移，导致 runner 测试在 materialize 前置阶段被暂时阻断；这不是 readiness 或 adapter 失败。按主线安排，P3 收敛后的联合回归由主线统一执行。

## P0 补充：materialization 的 workload-bound transport

materialization 不再按 TP/DP/EP group 各生成一个占位 collective。它遍历 P3 graph 的实际通信 operation，并为每个 workload phase、step、layer、group 和 tensor value 生成稳定的 P1 request。request 显式绑定 case ID、request digest、logical operation、payload value refs 和精确 bytes；零 token MoE payload保留为显式 no-op。

materialization 在 transport plan 创建前后都运行独立绑定 oracle。真实 simulator lowering/runtime backend 仍未接入，manifest 的 lowering/runtime 状态没有提升。

与 P1/P3 联合回归共 40 项通过，其中 materialization+runner 22 项通过。

## P0.6 补充：统一请求到 legacy Dense backend 的严格边界

### 目标

验证统一 `WorkloadRunRequest`/materialization 是否已经能安全接入现有 `compile_rect_mesh` production 路径，并在能力不足时保持 fail closed。此切片只建立可审计的第一条 backend 边界，不把 legacy 静态 profile 结果提升为 P3 完整端到端能力。

### 实现

新增独立生产模块 `llm/frontend/wafer_frontend/legacy_dense_backend.py`，未修改 P1 transport、P3 schema/materialization、P4 或公共导出。模块提供版本化 `LegacyDenseBackendCompatibility` 和唯一检查入口 `assess_legacy_dense_backend()` / `require_legacy_dense_backend()`，严格绑定 request、materialization manifest、legacy `ExperimentSpec` 与 `PhysicalFabric` digest。

兼容门控要求 Dense inference、resident HBM、baseline timing-only、DP/EP/PP=1、TP 覆盖完整矩形 Mesh、完整 row-major Die 映射、单 legacy instance、单 static profile，以及 model/profile shape 与统一请求精确匹配。训练、MoE、remote/external memory、部分 Mesh、functional/optimized 和输入漂移均明确拒绝。

审计发现 P3 materializer 当前要求 inference graph 至少包含两层和 2 个 decode step，而 production `build_ir0` 明确拒绝同一个 static profile 同时包含 Prefill 与 Decode。因此当前没有可以同时满足 P3 manifest 与 legacy compiler 的统一 Dense inference 请求。门控将该组合标记为 `unsupported`，理由为 `legacy.mixed_prefill_decode_unsupported`；`full_model_ready` 在 compatibility schema 中恒为 `false`，不能由调用方改成 true。

为保留真实生产链基线，新增 `run_legacy_dense_compiler_canary()`：它仅运行 legacy 单阶段 static profile motif，经真实 `compile_rect_mesh(AUTO)` 进入 `naive_fixed/v1`，并校验 compiler capability report 必须满足 `executable_baseline=true`、`standard_chain_complete=false`、`dense_workload_complete=false`。canary 输出 compatibility scope、完整 compilation、linked manifest 和 capability report，全部通过 `WorkloadStageArtifact` 记录相对路径、大小、文件 digest 与阶段输出 digest并立即复验。

没有为当前不兼容的 P3 请求调用 finalizer/resolver/simulator，也没有生成 `SUCCESS`、full-model evidence 或 runner READY。先运行 legacy simulator 再把结果关联到 P3 manifest 会伪造端到端覆盖，因此此切片在 compiler 边界停止。

### 测试

新增 `llm/test/frontend/unit/test_legacy_dense_backend.py`，覆盖：

- 真实 production `compile_rect_mesh` 的两层、纯 Prefill legacy static-profile canary；
- 四个落盘文件均由 `WorkloadStageArtifact` 复验，截断任一文件后验证失败；
- P3 两层 Prefill+2 Decode 请求明确为 unsupported，且不能设置 full-model readiness；
- Dense training、MoE inference、remote HBM 与部分 Mesh 路径 fail closed；
- 新增模块和测试文件 `py_compile` 通过。

聚焦命令：

```bash
PYTHONPATH=. python3 -m unittest llm.test.frontend.unit.test_legacy_dense_backend -v
```

真实 compiler canary 单项通过，用时约 58 秒；完整三项聚焦套件在同一配置下验证。

### 限制与下一步

要接通第一个统一请求的真实 simulator canary，需先提供能消费 P3 多层 Prefill+Decode graph 的 production lowerer，或定义一个不会被误认作 P3 full-model 的独立 phase/motif request contract。完成该 lowerer 后，再把 finalizer、resolver 和 simulator 分别实现为文件清单化 `WorkloadStageArtifact`，由现有 runner 的 evidence/readiness gate 在两次独立执行一致后评估；当前 legacy canary 不构成这类证据。
