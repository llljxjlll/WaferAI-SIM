# P3.4-R1：EP2 共享反向源与物理 OwnerRank

日期：2026-09-18。源码提交 `ae83e1f7`。本切片推进 M1 MoE 两层、两步、TP1×EP2 的真实训练图，但仍未完成 expert 反向、同步、SGD 或原生运行。

## 目标与开发

现有 EP2 两层前向源与 HBM owner 证明已存在，但 CE、LM-head、final norm/residual 的反向 pass 只接收 EP1。本次使三个 pass 接收经过原有前向校验的 EP1/EP2 图，沿真实 CE dLoss→dLogits→head dX→final norm dX→residual2 dCombined 建立共享反向来源。新增 `build_moe_ep_shared_reverse_ir1_candidate`：内部从源前向重建这条反向链，用原有 EP owner 证明与 HBM manifest 放置到物理 IR1，核对节点、值、依赖、状态访问和 profile 元数据，并调用公开 `IR1.validate`。

另一个被 IR2 投影暴露的真实问题是，原有 EP2 expert1 参数 StateAccess 虽然 HBM home 在 Die1，却写成 rank0。现在 EP 拥有的参数读使用其真正的 EP owner rank；IR0、IR1 与独立前向 oracle 都验证这一身份。伪造 owner1→rank0 的状态访问在 IR0/IR1 层拒绝。

## 测试与实际边界

- 六个受影响的 MoE 源图、放置、CE/head/共享反向测试模块完整重跑：**96 项通过**。补严 IR1 profile 来源绑定后，双步 EP2 定向测试再次通过。MoE forward ProgramIO 回归：**21 项通过**。
- Step0/step1 各自产生 38 个源/物理 IR1 节点、16 条 EP owner 证明、29 个 HBM 绑定；两个 step 的候选 ID 不同。用正式 `placement` 身份进入 `partition_ir1` 与 `NaiveProjectToIR2`，每步均产生 **2 个 Die DAG、106 个语义任务**，并通过 `validate_against`。
- 进一步尝试 64 KiB wire 地址限制下的 `NaiveIntraDiePolicy.schedule`，当前仍在 `naive ordinary sharding requires a one-axis physical group or exact TP1/EP1 singleton` 处拒绝。**这不是原生执行通过**：普通共享算子目前会按整个 EP group 复制，而共享参数只驻留 rank0。必须增加按节点选择计算 rank 的放置与真实跨 Die dispatch/return，不能仅把 2D group 放开以绕过检查。
- 更后续的 `MOE_COMBINE_BACKWARD` schema 与 0x28 lowering 只接受一个 expert 返回缓冲区；EP2 的两个 expert token 数可能不同，需要真实的双 dExpert、dScore 和反向通信合同。本次未放宽其 EP1 门禁，不能称为完整 MoE backward 或 M1/M2 训练完成。
