## 精确阻断

1. 原 canonical runner 以 `--mesh-size 11x11` 实测 exit2 `invalid choice`；canonical matrix `_shape` 和正式 hardware specializer也只接受每轴1..10。聚焦负测核对100个 release shapes完全不变。这是发布边界，不应直接放宽。
2. 扩展 probe 不经过上述 CLI 限制，真实 `materialize_workload_preflight` 通过，但 `compile_moe_full_model_inference_sequence` 返回 `moe_full_model_compile_sequence_unsupported`：`manifest.full_mesh_required`、`request.ep_must_cover_mesh`、`request.experts_must_cover_mesh`、`request.full_mesh_required`。这是当前固定100专家、100活跃/121物理 Die 的第一道生产阻断。
3. 独立直接调用 MoE block `compile_moe_sequence`，又返回 `moe_compile_sequence_unsupported`：`manifest.full_row_major_mesh_required`、`request.ep_experts_must_cover_mesh`、`request.full_row_major_mesh_required`。因此仅绕开 full-model 的首个 validator 仍不能生成可执行专家 blocks。没有 linked manifest、NPUP、ProgramIO、native stdout 或物理包流量，更不能计两次 Fresh。

后续需要**版本化的稀疏 EP→物理 Die 放置语义**：在 full-model 与 block compile 两道合同中显式接受100个活跃 rank 和121个 Fabric Die，把请求的 rank→Die 映射保持到专家计划、HBM StateABI、runtime core、D2D 物理路由与 linker，再定义扩展硬件特化器和 auditor，使收据同时审计全部121物理 Die及仅100个可执行 Die。不能只去掉 `EP==mesh.rank_count` 检查，否则会把专家 rank、物理 Die ID 和 NpuSim 路由偷偷混为一谈。完成这些共享编译器/后端修改且有相应负测后，才可用独立扩展 runner 做两次完整 production compile→finalizer→ProgramIO→NpuSim，并检查21空闲 Die、100活跃 Die、真实逐链路流量和三段KV。
