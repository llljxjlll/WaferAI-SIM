# P3.3-R4：MoE ProgramIO 双 Fresh 矩阵与严格续跑

日期：2026-09-16

## 目标

在 P3.3-R2/R3 的矩形 full-model 与单 Rank GATE 修复之上，为 Prefill → Decode → Decode 增加显式 ProgramIO resolver、源码/工具/产物绑定和机器可读收据；提供确定性分片、双 Fresh、逐产物 reopen 与严格 resume 的 native mesh matrix。

## 实现

1. full-model runner 对三个 segment 分别执行 materialize/compile、finalizer、ProgramIO 构造和 `npusim_program_io_selftest --resolve`。每份 resolver 输出必须与 sidecar 的 contract id、initialization 数量和 probe 数量精确相等，然后才进入 NpuSim。
2. `source_tool_binding.json` 绑定运行入口与退出时实际加载的 repo Python、finalizer/resolver/NpuSim/simulation bytes、NpuSim resolved executable/cwd、17 个执行产物、rank→runtime core、KV 边界和所有期望 D2D 跳数。运行期间源或工具 byte 漂移即失败。
3. `compiled_receipt.json` 记录 source binding/runtime log SHA、mesh、全部 active/compiled Die、前端与原生核网格、阶段耗时和资源指标。
4. matrix driver 默认 canonical M1 八形状：`1x1, 1x4, 4x1, 2x2, 2x3, 3x2, 3x3, 10x10`；另支持 1..10 的 100 个 release shape、稳定顺序分片和 `--resume`。
5. 每个 case 必须从两个独立子进程重新 materialize/finalize/resolve/simulate。reopen 会重读当前工作树的 entry/additional 两张 Python SHA map、实际 NpuSim executable/cwd、全部 17 个产物及其身份闭合，并复核 PROGRAM_MEMORY、P2P drain、三段/KV/ProgramIO marker、makespan 和逐有向 D2D link。双 Fresh 只允许 wall/RSS/runtime log 等观测值变化。
6. NpuSim 从 resolved tool parent 执行，使硬件配置中的 `../DRAMSys` 依赖有固定语义；cwd 同时写入 binding。matrix binding 全部使用 JSON 原生类型，resume 会拒绝 tuple 等内存态伪造和任何 binding 漂移。
