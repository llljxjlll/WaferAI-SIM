# P2：容量审计、分层分配与状态连续性底座开发记录

日期：2026-09-14  
对应计划：[矩形 Die Mesh 端到端训练与推理负载支持完善开发计划](../plans/矩形DieMesh端到端训练与推理负载支持完善开发计划.md)

## 1. 本次目标和完成范围

本次交付是 P2 的可合入基础切片，目标是建立后续完整训练/推理负载可复用的统一内存规划合同，并保持已有 placement 和 runtime 行为不变。

已完成：

- 定义 SRAM、HBM 和 external 三层统一容量及分配 schema。
- 定义与物理地址解耦的逻辑 state version、predecessor lineage、clean/dirty residency。
- 实现按半开生命周期区间进行的确定性 first-fit 分配；不重叠生命周期可以复用同一地址。
- 实现对齐、固定地址、地址范围、同时存活对象空间冲突、逐 location 容量及峰值的闭环校验。
- 为所有 schema 产物生成稳定 ID，并支持严格 JSON 往返。
- 提供现有 PersistentStateManifest 到新 HBM memory plan 的无损适配器，保留既有 die、地址和 tensor 大小。
- external tier 可以参与 schema 与容量规划，但任何使用 external allocation 的计划都会标记为 schema_only_external。

本次没有修改现有 placement.py 的 canonical 64-byte HBM first-fit，没有把新 planner 接入编译主链，因此冻结 baseline 不受影响。

## 2. 具体开发内容

### 2.1 分层内存 schema

新增 schema/memory_plan.py，核心结构如下：

| 结构 | 作用 |
|---|---|
| MemoryTierCapacity | 描述一个 tier/location 的基址、容量和最小对齐 |
| MemoryStateVersion | 描述逻辑状态的 generation、可写性和前驱版本 |
| MemoryAllocationRequest | 描述状态版本在指定 tier/location 的大小、生命周期、对齐和可选固定地址 |
| MemoryAllocation | 描述实际地址和保留字节数 |
| MemoryResidency | 描述状态版本在 allocation 上有效的区间及 clean/dirty 状态 |
| MemoryPeak | 记录逐 capacity 的峰值时刻、峰值字节和活跃 allocation |
| MemoryPlan | 对上述对象做引用闭合、稳定顺序、容量和交叉一致性校验 |

状态地址没有进入 MemoryStateVersion 的 identity。同一逻辑状态可在后续阶段迁移或产生新 residency，而无需改变状态身份。

状态版本校验要求：

- generation 0 没有 predecessor。
- 非零 generation 必须引用同一 state 的前一代。
- 只读状态不能产生新 generation，也不能标为 dirty。
- request 与 allocation 必须一一闭合；每个 allocation 的一个或多个 residency segment 必须无缝覆盖完整 lifetime，不允许悬空、间隙或重叠。

内存对象种类覆盖 parameter、KV、activation、gradient、optimizer、MoE buffer、communication 和 workspace，供 Dense/MoE 推理与训练共用。

### 2.2 确定性 planner

新增 passes/memory_plan.py：

- plan_hierarchical_memory() 对每个 tier/location 独立规划。
- 固定地址请求优先，普通请求按稳定 key 排序。
- 只有空间和生命周期同时重叠才构成冲突；生命周期采用 [start, end)，结束 tick 可立即复用。
- 分配失败返回稳定错误码 memory_capacity_exceeded，诊断包含 tier、location、request、所需字节和总容量。
- 峰值从 allocation 的实际保留字节和生命周期重新计算，MemoryPlan.validate() 再独立复核。
- 结果与输入 tuple 顺序无关，同一语义输入产生相同计划和 digest。

新增 plan_persistent_hbm() 作为兼容适配器：

- 从现有 HbmAddressSpace 生成 HBM capacities。
- 从 PersistentStateDecl 生成 generation 0 的逻辑版本。
- 从 HbmBinding 生成 pinned requests。
- 保留已有 physical address，不重新解释已有 placement。

### 2.3 外部内存边界

本次只定义 external tier 的容量、allocation 和 peak schema。只要计划包含 external request，MemoryPlan.execution 就必须为 schema_only_external。

当前没有实现：

- HBM 与 external 之间的搬运 action。
- controller、带宽、延迟、队列和争用模型。
- prefetch、evict、restore、等待依赖。
- external allocation 到 NpuSim runtime 的 lowering。

因此本次交付不能表述为 offload runtime 已完成，也不能用 external schema 计划作为“超 HBM 负载已运行”的证据。这些属于 P4。

## 3. 测试内容与结果

新增 llm/test/frontend/unit/test_memory_plan.py，覆盖 7 组行为：

1. 不相交生命周期地址复用、重叠对象隔离及峰值时刻/字节。
2. 同时存活对象超过容量时 fail closed，并检查稳定错误码。
3. alignment padding、容量恰好放下及 pinned 地址冲突。
4. state generation 前驱链、跨 state 错误前驱及只读 dirty 拒绝。
5. external allocation 自动降级为 schema-only。
6. 既有 persistent HBM manifest 无地址变化适配。
7. 对伪造峰值和超出 allocation lifetime 的 residency 做交叉校验。

## 6. 已知限制

- 当前 planner 输入是显式 request，不会自行从完整模型 DAG 推导生命周期。
- peak 按同一 capacity 上同时活跃 allocation 的保留字节求和；尚未输出全 tier 聚合峰值和 tensor 级诊断报告。
- P4.3 已扩展为同一 allocation 可承载同一 state 的连续 generation residency；跨 tier 迁移、异步双缓冲和取消仍需后续搬运合同。
- 当前只完成 Python frontend 合同，没有修改 ISA、finalizer、ProgramIO 或 C++ backend。
