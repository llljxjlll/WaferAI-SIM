# P5.1-R4：TP9 计算地址窗口与 SRAM 生命周期重用

日期：2026-09-15。延续 [R3 全九 Die 运行期对齐修正](P5.1-R3-全九Die双Fresh运行期SRAM对齐失败与物理Profile修复.md)。R3 的新 word-aligned 模型在真正生产调度中暴露另一项限制；本记录冻结它的失败并接入已有的有界地址窗口重用策略，**尚未确认 native full run 成功**。

## 实际编译拒绝

隔离工作树固定 `506e83ee04cde5f93af0518900a014ebecc509f3`，工具 finalizer/resolver/NpuSim/SIM SHA 与 R3 相同，从空目录 `/tmp/m1-dense-scaled-all9-3x3-word32-fresh0` 物化两层 TP9/H144/I144/NH9/KVH9/DH16 Dense Prefill1→Decode1→Decode1。其 source case ID 为 `workload_case_08e8a2359dead3c4`。实际生产编译在 16.460s、前端峰值 482,600 KiB 处拒绝：`schema_error at schedule.die_0.core_0.sram_region_0: SRAM capacity exceeded for named region 'sram': required=65696, available=65536, value='temp.fused_op_skeleton_6c937dae55956b42.chunk.1.rank.0.a', size=288, lifetime=(106,107)`。收据在 `/tmp/m1-dense-scaled-all9-3x3-word32-fresh0/compile_failure.json`；没有 linked/NPUP/ProgramIO/NpuSim。第二轮尚未启动，不能把预留的 fresh1 目录当作实际执行。

`naive_intra_die` 默认的 sequential append 在该临时值处超过原64KiB named region，但它已经有受生命周期约束的 gap-search 模式：开启 `intra_die_wire_address_limit_bytes=65536` 后，仅在合法空隙且无并发占用时安置缓存，所有 fixed SRAM 起始地址还被拿来和生产 Fabric allocation alignment 比对。计算 record 的绝对 SRAM wire 地址是 uint16，所以单纯把物理 SRAM 限额改大并不能构成可运行修复。

## 源修正与预期核验

`--scaled-all-dies` 主 profile 对全部 1..10×1..10 固定每 Die 128KiB 物理 SRAM、32B allocation alignment，但生产 compile 同时固定64KiB绝对计算 wire 窗口；native hardware 的 SRAM容量和对齐与 Fabric 精确相同。调度器只有在真实 lifetime 允许时复用窗口内的地址，否者保留 `wire-addressable SRAM liveness capacity exceeded` 失败，不绕过编码限制。固定模型旧 runner 的原 profile 与既有 TP6/128KiB/64KiB wire 配置保持原规则。

3×3 和10×10 source 的 Fabric 容量/对齐及三段 `build_ir0→logical_expand` 定点测试 **2/2 PASS，9.003s**。全部100源矩形和旧固定模型回归 **5/5 PASS，64.075s**。以上测试只验证输入和 IR0，不能证明调度器真的找到无重叠空隙，也不能证明所有实际 `SRAM_ALLOC_AT` 的32B/16bit合同、NPUP finalizer、ProgramIO或NpuSim。下一步冻结修正源码，重新从空目录运行TP9；生产 linked 后审计每条 fixed SRAM地址与 literal alignment，原生仿真成功后才做第二轮独立 fresh。M1/M2/M3 completion 仍为 false。
