# P4.4-R12：MoE 推理 EP6 2x3/3x2 低 HBM 生产源与分页首阻断

日期：2026-09-16。继 R10/R11 的 EP4 物理双 Fresh，本阶段对 M2 MoE inference 主矩阵中的 **2x3、3x2** 固定各自相同的六专家、两层 Prefill→Decode→Decode 生产模型，只读审计容量和真实源。两形状共享模型 SHA-256 `ec8a126d51234f6f4e7a94b828565023b311ebbda1b4a03fd27130dd2ac8c527`，各自 EP=6、六活跃 Die、原始请求/三步不缩减。这里的“相同模型”是 2x3 与 3x2 之间相同；EP4 的四专家 profile 本来不同，不能冒作同模型扩形。

每 Die 固定 HBM 1024B，六 home 仍为 `die:i`、base=`i<<30`；同一请求 resident 在 Die0 的 `requests[2]` 报 `memory_capacity_exceeded`，所需 656B，容量 1024B。派生 offload policy 后，用同样 HBM 加一个 8192B 外存，2x3/3x2 preflight 均通过，物化 ID 分别为 `workload_materialization_f8604de06e1f77d4` / `workload_materialization_8585368f8c75dcf2`，并验证 useful graph 与 resident 一致。真实 P3 外存参数分配末端为 6240B，六 Die HBM workspace 末端为 464/464/464/456/464/456B；这只是规划和槽位预算，不等于已经发生 DMA。

两形状各自从冻结生产源编译完整三段，调用原版原生 finalizer 各三次得到共六份 NPUP/报告，生成并 typed 验证六份 ProgramIO；随后独立退出、只读重开六个 manifest/NPUP/report/ProgramIO 与全部冻结源码、工具 SHA。每段源码有真实六个 runtime core `0,4,8,12,16,20`、39 个 StateABI；Prefill 为 39 fragments、51 StateOperandBindings，core 记录 `207,52,52,52,30,30`，ProgramIO 120 初始化+1 probe；两个 Decode 各 43 fragments、55 bindings，记录 `199,52,30,30,30,30`，ProgramIO 124 初始化+1 probe。每形状 Die0 有 15 个真实参数页共 1032B，远端每 Die 四页共 480B，总计 **35 个物理参数页、3432B**，另有四页 rank0 KV。远端 gate 页是 48B，不能套用 EP4 的 32B 假设；最大单页仍为 192B。2x3 与 3x2 的生产 remote flows 与 X-first 有向链路期望已写入 receipt，Die4/5 虽不在本固定 token 序列的 P2P 端点中，仍有真实 core stream 与参数状态。

**精确首阻断**：尝试将生产 EP6 manifest 输入现有 `relink_moe_inference_paged_segment_ep4`，三段都在源门禁报 `schema_error at source: two-layer EP4 full-model linked source shape changed`。这是正确的 fail-closed：EP4 的四 core、31 ABI、27 参数页、32B 远端 gate、125 DMA、四 HBM backend/Die 的 typed source/runtime/native 合同，不能仅改 `ep=6` 或 NpuSim 的 mesh 标签来接纳真实六 core、39 ABI、35 页源。下一实现阶段需新增独立 EP6 relinker 与 source-derived sidecar，把 48B gate、35 页/四页 KV、六 Die 外存 X-first 路由、逐 LSU 分页 restore/writeback、固定单外链 queue/max outstanding=2 纳入原生 typed schema，重新冻结 C++/Python 工具后再做每形状**两次独立**完整 production compile→finalizer→ProgramIO→NpuSim、退出重审及 resident 拒绝配对。当前没有 EP6 原生分页成功收据，不能计为 M2 offload 完成。
