# P5.6-R1：TP16 原生核几何失配与十六 Die 物理路由修正

## 问题与物理证据

既有 `/tmp/m3-dense-tp16-1x16-sram-fixed/` 旧 1×16 TP16 两次真实 NpuSim exit0 在源签、linked、NPUP、ProgramIO、KV 和 makespan 上确实自洽，但不能证明 16 个**物理** Die 参与。旧原生 `hardware.json` 直接显示 Die `x=16,y=1`、每 Die `x=4` 且缺 `y`，NpuSim 默认4×4核/Die；前端 `minimal_hardware` 的 Fabric 每 Die 2×2核，以 `rank×4` 生成 runtime core0,4,…,60。读取旧原生 `[PROGRAM_MEMORY]` 的16个活跃core后按原生stride16得到物理 Die仅0–3；`[D2D_LINK]` 的唯一相邻端点只有 `0↔1↔2↔3`，旧 `D2D_DATA` in/out 30,720 packets。因此旧日志所写“物理 Die0–15 全部 active”失实，保留旧 KV4096→8192→12288、349,093cycles和编译开销为硬件失配诊断，但撤销该运行的 M3真实十六 Die 结论；`P5开发记录.md` 顶部已加入显式更正。

## 修复内容

`run_extended_dense_sequence_runtime_canary.py` 的实验 native hardware 从**实际 production Fabric**绑定每 Die核网格、所有 Die 的 runtime core公式、物理 Die阵列和 C2C端口位置，使用与 M1 Dense 真运行相同的 `_bind_native_hardware_to_fabric`。针对1×16/16×1，原生 now `x=2,y=2`，NpuSim每Die4核，C2C override索引0而非旧索引2，逻辑 Die15 的 runtime core60在真正物理 Die15。源闭包显式签入共享 binder 的 Python文件。NpuSim observer进一步读取发出 LSU 的原生 `[PROGRAM_MEMORY]`，按绑定核网格计算十六个物理 Die，要求 Die0–15精确覆盖；1×16需30条有向E/W、16×1需30条有向N/S真实相邻链路，各 `data_in=data_out>0`；实际 D2D in/out packets必须相等且非零。旧profile的16个P2P logical marker即使全0残留，也不会再冒充物理十六 Die运行。

## 测试与发布边界

`python3 -m unittest llm.test.frontend.integration.test_run_extended_dense_sequence_runtime_canary -v`：13项中11 PASS、2项真实TP16测试按设计需opt-in运行而skip；聚焦断言包括前端/原生核2×2、端口idx0、logical Die15→physicalDie15、旧4×4 stride导致的物理Die0–3负例、缺Die15链路负例、16×1 N/S方向与错误方向负例、原生 SRAM 1MiB/64B alignment与错误名字/重叠区域负例。静态语法与差异检查通过。此阶段只证明**源码和原生合同**已经修复；修复后1×16/16×1完整NpuSim双独立物化仍需新目录、新硬件/源SHA、新真实 stdout，尚不发布任何超过10轴的M3扩展能力。后续优先重新真实跑1×16，再试16×1及其它受限范围，且M3总里程碑还要求四类100形状resident/offload矩阵、full-dimension和资源报告。
