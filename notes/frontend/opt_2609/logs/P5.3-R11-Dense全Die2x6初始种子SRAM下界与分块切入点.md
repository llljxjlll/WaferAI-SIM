# P5.3-R11：Dense 全 Die 2×6 初始种子 SRAM 下界与分块切入点

日期：2026-09-18。继续 M3 全 Die、两层 Dense 推理 100 形状矩阵。以当前提交 `ca770ead` 和正式 `--scaled-all-dies --mesh-size 2x6` 源在 64 KiB 可寻址 SRAM 下重现编译失败，原错误为 Die0/Core0 的 384B fused GEMM A 值无法找到一段横跨任务 0..302 的固定地址。前一轮推断为 Embedding 整表窗口阻断，本轮进一步区分瞬时任务峰值与仿真开始前 ProgramIO 必须同时初始化的输入。

在受管临时任务中只拦截原有 `_fail`，读取失败帧的已分配 buffer；未改生产源码。基线失败的 `compile_failure.json` 和 live-binding 清单 SHA256 分别为 `8c61feca36c83de97807cd962973c0bf130e71e2c6a8115930cb47d9d23e1eff` 与 `8cfedbbb7a8b136c5e5b667a5728f4b684c2b7e31f1bdf3514e6981f85ad2d8a`。生产策略文件在源码快照与阶段结束时 SHA256 均为 `e45b219cf159e7c3792486af5d3f8bc95a8570b8978d5085dc11a37a71ef5346`。

关键发现：只按任务读写时刻求和得到约 49.9 KiB，**不能**作为可行性下界，因为 NpuSim 的 ProgramIO 在首任务前初始化所有 `BORROWED` 输入。一次未提交的分配重排试验把这类输入优先放到高地址后，整张 Embedding 表仍无法放入：53 个同时预置的 borrowed buffer 共 19,972B，加 49,152B 的表至少需要 **69,124B**，超过 65,536B 窗口 **3,588B**。这一下界还未计入其他需要预置的终端输出；试验清单 SHA256 为 `7d78fced7ecee825bd397d86ee85dc078b9e2297c18d1408ce0d0ceba56c7512`，准确值以[紧凑收据](P5.3-R11-Dense全Die2x6初始种子SRAM下界收据.json)为准。重排无法合法解决，试验改动已撤回。

额外尝试直接复用 GEMM A 的源张量身份，现有 rank-local tile view 与完整源 buffer 的行主序连续性合同冲突，相关单测立即在 `P0.layer0.attention_out` 的非连续 view 拒绝。这项未提交的替换也已撤回；没有把独立 tile 的数据来源假装为同一连续 span。生产源码与进入本轮时一致，`git diff --check` 通过。

下一步需要实际减少首任务前的物理预置足迹，并保留任意输入的语义：优先给 fused GEMM A tile 建立经验证的源值→局部 tile 搬运/视图合同，避免数十个独立 `BORROWED` tile 同时预置；这至少可处理当前 2×6 的 3,588B 缺口。更大的全 Die 形状单张 Embedding 表自身就会超过 64 KiB，因此仍必须实现 HBM→SRAM Embedding 行 tile、局部索引映射、状态访问及原生 lookup 合同。完成后要用相同模型/硬件重跑 2×6、2×7 双 Fresh，再推进 100 形状矩阵。本记录只证明阻断下界，不宣称 M3 case 成功。

诊断和两个失败试验均使用 `scripts/frontend_tmp.py` 受管目录与限额；紧凑收据落盘后释放临时作业，保留仍用于运行的 `build-debug-final`。
