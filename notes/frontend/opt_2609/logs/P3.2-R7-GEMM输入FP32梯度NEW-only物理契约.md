# P3.2 R7：GEMM 输入 FP32 梯度的 NEW-only 物理契约

## 目标、来源与边界

一个 rank-local 前向 GEMM 为 `X[k,m] × W[m,n] → Y[k,n]`，真实上游 `dY[k,n]`。输入梯度数学定义为 `dX[k,m] = dY[k,n] × W[m,n]^T`。计时原语的物理读数因此仅为 FP16 权重 `2mn` 字节和 FP16 `dY` 的 `2kn` 字节，FP32 `dX` 独立目标为 `4km` 字节；`X[k,m]` 是源图和 tape geometry witness，不虚增物理读取/计算。每个 tile 需 `kmn` FMA、`2kmn` EXU FLOPs、`km` FP32 vector output work，FP32 output RMW 计 `8km` 字节。

现有完整 Dense head 反向源 `backward::T0.lm_head` 仍使用旧 `OpKind.GEMM`、`impl_ref=lm_head_dgrad`、FP16 hidden-gradient。旧 MATMUL 不能提供 FP32 dX。MoE 标准训练的 `EXPERT_DGRAD` 也仍映射旧 MATMUL；不能因为源动作叫反向就算原生 dX。完整 Dense 物理门禁已要求 absent `RecordOpcode.GEMM_DX_TIMING` 而 fail closed。WGRAD 公共 0x25 只覆盖参数导数，不覆盖 dX。

## 本阶段新增（全部 NEW-only）

- `GemmInputDxTimingTile` / `BuildGemmInputDxTimingWork`：检查正的30-bit `k,m,n`，真实前向 X/FP16 StateABI W 形状和字节数，源权重状态引用与显式加载引用/版本一致，三份 16B 对齐非空独立 W/dY/dX SRAM 的精确 dtype、跨度与 16-bit 地址上限，所有乘法/工作计数 checked overflow。单独 `gemm_input_dx_timing` NpuBase adapter 已声明 `initialize/taskCore/work`，但它明确拒绝 `serialize/deserialize`：尚未公开 PrimId、Opcode 和物理 record，不能送入 NpuSim 伪称 ISA 已支持。
- Python `GemmInputDxWorkload` 明确 FP16 前向 X、FP16 W、FP16 dY 和 FP32 dX 的形状/字节数、源 forward/state ID。NEW source witness 直接查证已经验证的真实两层 Dense IR0：`T0.lm_head` forward GEMM 的 X/W/Y、StateDecl 对权重 TensorValue 的绑定、rank0 READ StateAccess，以及 CE backward 的真实 `dLogits` 上游 producer。公共物理 gate 在 opcode、StateABI LOAD→SRAM BufferABI 与 ProgramIO 权威链存在前显式拒绝。
- 源示例为真实 `T0.lm_head`：`k=1,m=4,n=8`，StateDecl `persistent_state_decl_39ea79f06b50d172`，来源 `T0.final_norm_out` FP16 X、FP16 `T0.lm_head.weight`、`T0.cross_entropy_backward` FP16 dLogits。该来源 witness 只能证明图语义，不表明物理 StateABI/version/LOAD 已执行。
