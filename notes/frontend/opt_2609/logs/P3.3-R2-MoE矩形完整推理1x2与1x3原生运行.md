# P3.3-R2：MoE 矩形完整推理 1×2 与 1×3 原生运行

日期：2026-09-16

## 目标

把 P3.3-R1 的矩形 full-model 编译链送入真实 finalizer、ProgramIO 和 NpuSim，并用实际 Fabric 核绑定与逐跳路由审计替代旧 runner 对 core 16 和单条 0↔1 链路的写死。

## 开发内容

1. `run_moe_full_model_sequence_runtime_canary.py` 新增 `--mesh-size`，覆盖 1..10 的 row-major 矩形输入，并通过同一 workload materializer、full-model compiler 和 production linker 构造两层 Prefill → Decode → Decode。
2. NpuSim hardware 使用对应 release mesh，再由 `_bind_native_hardware_to_fabric()` 写入真实每 Die `2x2` 核网格和 C2C 端口位置。
3. runner 从三个 executable manifest 提取共同的 rank→runtime core 绑定，要求每段精确覆盖所有 rank。
4. 根据每条 dispatch/combine flow 的源、目的、logical bytes 和 16B packet payload，按 X-first 路由计算每条有向链路的 request/ack/data 期望；实际 `D2D_TYPE`、`D2D_DATA`、全部 `D2D_LINK` 必须逐项相等。
5. 同时核对每个 executable core 的 `PROGRAM_MEMORY`、P2P drain、远端 expert 三个 MATMUL 与一个 SwiGLU、Dense/MoE bridge DTE 数量、KV probe、one-shot drain 和唯一 `SIM_RESULT`。
6. 修复零工作 expert rank：state/compute fragment 和 top-level program symbol definition 仅保留实际声明与 relocation 覆盖的 symbol；required SRAM region symbol 保留。该修复解决 1×3 Decode 中 rank2 没有 token 时 finalizer 对 orphan `ABSOLUTE_ADDRESS` execution scope 的拒绝。

## 范围说明

这两次是 timing-only、单次 fresh 原生运行，证明矩形 compiler→finalizer→ProgramIO→NpuSim 链与物理路由审计可工作；尚未满足 M1 每个 case 两次独立 materialize/finalize/resolve/simulate 的正式重复性门槛。当前 runner 仍使用测试 fixture 构造输入，也尚未接入独立 ProgramIO resolver 阶段和统一双 fresh/matrix receipt。`1x3` 仍属于 mesh-scaled EP/expert 配置，不能冒充固定模型任意 mesh 支持。
