## 真实失败

从本地源码提交 `c5b9e8fe94145aacadee6f53f16bdcf8d166c2a2` 建立 `/tmp/m1-tp9-source-freeze` 隔离工作树，确认工作树干净，冻结 native finalizer/ProgramIO resolver/NpuSim/SIM 配置 SHA 分别为 `76a7e61d8b7fd4f49d225d5927d224b6198de9ddf9f1ba397dbe51d314dd25d8`、`29e8fb38cace40beca5efdfba53ae520f04e71d088ffdc4648a868f7bfb03763`、`1090f93f8eb787a117804e33622a9a53dc656b2098ccbb29e1ed612f90bab5cd`、`337f5bc3f195489e8c6ef8830d83ce709a3e79a434401bd545504bf543420afb`。从空目录 `/tmp/m1-dense-scaled-all9-3x3-fresh0` 调用实际两层 Dense Prefill+Decode+Decode runner，首次 production compile 在 0.057 s、峰值 RSS 488,784 KiB 处退出码 1。`compile_failure.json` 记录 `schema_error`：`expanded_graph.nodes[4].workload.rotary_dim: current ROPE requires even rotary_dim == head_dim`，case ID `workload_case_de3711186d0476ce`；没有 finalizer、NPUP、ProgramIO 或 NpuSim。这是 **真实编译失败 1 case，真实运行成功 0 case**。

失败根因是此前 shape-scaled 来源设 `DH=rotary_dim=1`，编译输入合同只检查参数尺寸可分片，IR0 真正展开才发现当前 ROPE primitive 的偶数配对限制。不能放宽该 validator 或用不同注意力架构偷换原模型。

## 修复与验证

新 source profile 采用 `TP=rows×columns`，`H=2×TP`、`NH=KVH=TP`、`I=4×TP`、`DH=rotary_dim=2`，仍是两层 FP16 Dense、每 Die 一 request 的 Prefill1→Decode1→Decode1 和全部 Die 行优先参与；10×10 使用 `H200/I400/NH100/KVH100/DH2`，3×3 使用 `H18/I36/NH9/KVH9/DH2`。新 3×3 case ID `workload_case_e9e319e1d985c06e`，10×10 case ID `workload_case_b8a0150a3e90985f`；与 R1 的 ID 不同，必须重新生成证据。

把 3×3/10×10 每段 `_segment_spec` 真正送入生产 `build_ir0→logical_expand`，验证三段图展开均成功，不再只测编译输入。3×3 和 10×10 两条针对测试 **2/2 PASS，8.986s**；全部 100 source case 的固定回归 **4/4 PASS，64.951s**。生产 full compile、native finalizer 和真实 NpuSim 对修复后的 profile 仍待执行；M1/M2/M3 均不因此标完成。
