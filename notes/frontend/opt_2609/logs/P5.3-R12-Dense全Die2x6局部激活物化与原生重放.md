# P5.3-R12：Dense 全 Die 2×6 局部激活物化与原生重放

日期：2026-09-19。本轮承接 R11 已确认的 64 KiB SRAM 初始种子下界：旧投影把每个 fused GEMM A tile 都当成独立 `BORROWED` ProgramIO 输入，53 个输入种子与 Embedding 表合计至少 69,124B，导致正式 `--scaled-all-dies --mesh-size 2x6` 编译失败。本轮目标是保留真实源张量和 rank-local tile 语义，把这些 A tile 改为任务内本地物化，并在 12 个活跃 Die 上完成三段 Dense 推理原生运行。

## 开发内容

1. 行并行 GEMM 的 A 逻辑切片改为当前 TP rank 的 K 分片：偏移为 `(chunk_m_offset, rank_k_offset)`，形状为 `(chunk_m, rank_k)`；`FusionPlan.validate_against` 同步执行精确校验，避免把完整 K 输入错误绑定到每个 rank。
2. `NaiveProjectToIR2` 在 tiled COMP 的 LHS operand 是局部临时值时，派生一个确定性 `LOCAL_COPY`：从 IR-1 源激活的同一逻辑切片读取，写入 COMP 的局部 A operand，精确携带 dtype、字节数、同步事件和内部/状态/跨覆盖依赖。COMP 显式依赖该复制任务。
3. IR2 DAG 对派生任务执行 fail-closed 反向校验：任务 ID、来源 COMP、Die/rank、切片、字节数、读写值、同步和依赖必须完全一致；派生任务不冒充计划 action，但参与规范排序和图入口依赖。DAG 与 projection schema 分别提升到 `v1alpha15` 和 `v1alpha14`。
4. 更新 action、IR2、投影和 SRAM 测试 fixture，使其覆盖 rank-local K 切片、派生复制数量、复制→COMP 依赖和跨覆盖入口迁移。

## 2×6 真实编译与原生运行

生产编译使用 2×6 mesh、`scaled_all_dies=true`、12 个活跃 Die、三段 Dense sequence，编译耗时 528.212s，前端峰值 RSS 1,347,996 KiB；三个 segment 的 compiled core die 集合均为 0..11，说明不再退回子网映射。64 KiB wire-address SRAM 预检、三份约 25 MiB linked manifest、NPUP、finalizer 与 ProgramIO sidecar 均成功生成。

首次 runner 调用遗漏 `--dramsys-root`，原生阶段在加载 DRAM 配置时以 `Unsupported DRAM type` 退出。补齐同一作业目录中的 `DRAMSys` 后，使用完全相同的三组 NPUP、linked manifest、ProgramIO 和 hardware 配置直接重放 NpuSim，退出码为 0：

- segment 标志为 `(0, final=0)`、`(1, final=0)`、`(2, final=1)`；one-shot drain 为 `segments=3 one_shot=1`；
- KV 边界依次为 18,432B、36,864B、55,296B，三个 digest 均 `pass=1`；
- 唯一 `SIM_RESULT` 为 `makespan_cycles=374660`，模拟结束时间 749,320ns，真实运行 562.955s；
- 12 个活跃 core 的 `PROGRAM_MEMORY` 均为 issued=completed=65，LSU/DTE residual=0；
- Host lane 完成 36、确认 72、mismatch=0，每个 Die 恰好完成 3 段；P2P、collective、router、D2D 均排空且 data/control credit 平衡。

[紧凑收据](P5.3-R12-Dense全Die2x6局部激活物化原生重放收据.json) SHA256 为 `23b5a72d241291c2780123c7b6115fa9143fce8fad5dadddb202236b61f5db94`，记录编译时源码、工具、三段产物和原生 stdout 哈希。编译后只有 `schema/ir2.py` 因 schema 版本提升和缺失派生任务的 `SchemaError` 加固发生变化，lowering 与已重放原生产物未变化；因此本次结果作为开发期原生证明，正式矩阵记账仍需在最终源码上由 runner 完成 Fresh 复跑。

## 空间控制与后续

本轮仅复用 `/workspace/build-debug-final`，没有创建新 build tree。编译与运行全部放入 `scripts/frontend_tmp.py` 管理的 `/tmp/waferai-frontend-m3-dense-tile`，配额 4 GiB、失败保留 2 小时；收据写入仓库后通过 `release` 把该根从 137,221,833B 降到 23B。额外构建审计确认无进程使用且已被当前 debug 构建替代后，删除 Git 忽略的旧 `build-release-final`（10 GiB）和 `build-debug-dense-infer-pager`（2.4 GiB），保留刚完成本次验证的 `build-debug-final`（3.9 GiB）。后续 2×7 及双 Fresh 运行继续使用同一机制，runner 命令必须显式传入 `/workspace/DRAMSys`，每次先写紧凑收据再 release 原始 JSON、VCD 和 linked manifest。

下一步是在最终源码上完成 2×6、2×7 双 Fresh 自动 runner 验证；随后处理单张 Embedding 表本身超过 64 KiB 的更大全 Die 形状，加入 HBM→SRAM 行 tile、局部索引映射与原生 lookup 合同。
