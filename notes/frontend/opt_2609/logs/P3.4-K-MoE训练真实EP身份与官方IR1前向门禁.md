# P3.4-K：MoE 真实 EP 身份、官方 IR1 前向与具名 FP32 梯度源

## 目标与本阶段准确范围

把此前 Stage I 正式 `IR1.validate` 对 `MOE_EXPERT_FORWARD` 抛 `KeyError`、以及把 TP shard0 当物理 EP die0 导致八份 die1 专家参数错绑的两个实际阻断，改为严格接受真实 TP1×EP2 两层 MoE **完整前向源图**。同时接入公共 GEMM 参数梯度 0x25 的独立、具名 FP16 activation/upstream → FP32 dW 源形状和真实 forward/state 声明门禁。MoE backward、Router WGRAD、全部共享参数梯度、梯度同步、SGD、两步 StateABI 版本链及最终单时间线 NpuSim **仍未完成**。

## 源码与物理合同

- `PersistentStateIdentity.ep_owner_rank` 是有显式身份 ID 的 opt-in 专家 EP owner。原 `shard_index=0` 保持真实 TP shard，`generation=0` 保持真实版本。字段缺省时稳定身份 key 和既有 Dense ID 不变；该字段只能赋予 TRAINABLE_PARAMETER。
- 16 份专家/router state owner 来自冻结的 E2E v0 `StateVersion`、其 `TensorValue.logical_rank` 及实际生产 `StateABI` Die0/Die1；共享 11 份状态没有 EP owner。Stage G source wrapper 与 Stage I physical owner proof 都反查真实 E2E 参数与投影切片。
- 原始16MiB HBM/64KiB SRAM case 在 Stage H 保持容量拒绝；合法 profile 是单独公开的新32MiB/die、128KiB/core request ID，四个真实TRAIN leaf 仅作为前向专家物理布局参考，未组装成 full training 时间线。
- `PhysicalNode.validate` 在 IR1 对完整五类 MOE_* 和原生0x23/0x24/0x25 使用与 `LogicalNode.validate` 相同的 workload/kind、phase、输入输出数、impl_ref 与 FP32 参数输出闭包。`IR1.validate` 只有对于带真实 opt-in owner 的 TP1×EP2 EP group，才用 `(TP shard0, EP owner)` 对应 group logical_coord `(0,owner)` 及 HBM home Die；旧无 EP owner 的 source 仍按原 TP shard 验证。
- `GEMM_WEIGHT_WGRAD` 需要真实 source forward OpKind.GEMM（或 MoE expert forward）与该 op 的 READ persistent StateDecl，FP16 权重 `(m,n)`、物理输入 `X[k,m]`、`dY[k,n]` 和 owned FP32 `dW[m,n]`。Scoped Dense CE/head source 可对现有只读 Parameter 求梯度，然而只有 TRAINABLE_PARAMETER 能进入完整训练优化器版本门禁；不能因片段有 FP32 dW 冒称可执行模型更新。
