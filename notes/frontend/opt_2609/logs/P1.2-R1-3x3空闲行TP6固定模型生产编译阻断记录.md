# P1.2/P1.3-R1：3×3 空闲行 TP6 固定模型生产编译阻断

日期：2026-09-15。对应计划中固定模型可占物理矩形子集、空闲计算 Die 仍提供路由的能力。本条记录为真实失败边界，不能计入 Dense 推理成功形状，更不能计入 M1/M3。

## 输入与开发检查

沿用已在 2×3 和 3×2 真实 NpuSim 双 fresh 验过的 FP16、V128/H48/I96/L2/NH6/KVH6/DH8 两层 Dense 模型、TP6、六请求 Prefill6→Decode1→Decode1，HBM 每物理 Die 1 GiB。新 3×3 物理网络共有九个 Die，显式 active_die_ids=(0,1,2,6,7,8)：中间一行 3、4、5 为计算空闲的物理路由节点。请求 case ID 是 workload_case_6f58db3b468e72e8，与 2×3 已验证 case 不同。同模型 production materialize_workload_preflight 在内存中真实生成九 Die mesh、六活跃 Die、96 个逻辑 op；扩展后的同源固定模型单测 4/4 PASS，其中一项只验证物化形状和地址容量，不声称后端路由通过。

## 真实拒绝与下一步开发

新目录 /tmp/p3-r8-tp6-3x3-idle-row-fresh0 的真实运行器在 production_compile 阶段 0.024 秒拒绝，记录 compile_failure.json：dense_compile_sequence_unsupported，具体原因是 request.tp_must_cover_mesh、request.full_row_major_mesh_required、manifest.full_row_major_mesh_required；runtime_status=not_measured。该目录没有 linked manifest、NPUP、ProgramIO 或 SIM_RESULT，不能把单纯物化成功冒充物理运行。

检查下一层 RectMesh 生产编译器发现另一个独立门槛：_validate_rect_mesh_compile_inputs 要求实例 TP 恰为整个 mesh.rank_count，EXPLICIT group 也只能精确绑定 tuple(range(mesh.rank_count))。只去掉 Dense sequence 前置检查仍无法编译。legacy_dense_backend 的统一兼容门禁同样依赖全行列 Die。后续 P1.2/P1.3 实施需要有边界地同时拓宽 sequence 生产入口、实际 EXPLICIT rank→die group 和 RectMesh 编译合同，并保留现有全活跃 TP=rank baseline 产物不变；以两轮从空目录编译→真实 finalizer/原生 ProgramIO→NpuSim 核对跨中间空闲行路由、实际 D2D 配对、每段 KV 版本及最后 one-shot 才能标该 3×3 映射 verified。

此阻断不能通过把 mesh 暗改成 2×3、让空闲 Die 执行幽灵计算、从 2×3 用时相加或放宽模拟内存解决。1×6、6×1 全六 Die 长条矩形的同模型测试使用已有 TP 等于物理 Die 数的合法生产链，和这里的 TP6/九物理 Die 显式映射是两种不同能力。
