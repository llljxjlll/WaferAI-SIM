# P1 物理拓扑与逻辑并行解耦开发记录

日期：2026-09-14
状态：基础 schema、确定性 route/collective plan 与 hardware core binding 完成；真实 simulator canary 留待 workload runtime 接入。

## 1. 本次目标

在不改变既有 `flexible_mesh_groups.py` 行为的前提下，建立可独立接入新 workload 入口的并行放置合同：

1. 将完整物理矩形 mesh 与参与计算的逻辑 rank 分开表示。
2. 支持 Dense `TP × DP` 与 MoE `TP × EP × DP`，首版保持 `PP=1`。
3. 允许显式选择 active Die，未选 Die 保持 idle-compute、routing-active。
4. 显式记录逻辑 rank 到 `die_id/local_core` 的映射。
5. 生成并校验 canonical group 与参数 ownership domain，避免不同 expert 的梯度错误同步。

## 2. 开发内容

新增 `schema/parallel_placement.py`，包含以下版本化不可变对象：

| 对象 | 作用 |
|---|---|
| `LogicalRankCoordinate` | 记录 `(dp, ep, tp, pp)` 逻辑坐标 |
| `ParallelRankPlacement` | 记录 logical rank 到物理 Die 和 local core 的映射 |
| `ParallelGroup` | 记录 MODEL、TP、DP、EP、共享参数同步和 expert 梯度同步组 |
| `ParameterOwnershipDomain` | 记录一个共享参数或 expert 参数 TP shard 的 primary/replica ranks 及同步组 |
| `ParallelPlacement` | 汇总物理 mesh、并行度、rank placement、groups 和 ownership |

新增两个构建入口：

- `build_dense_parallel_placement()`：生成合法 Dense TP/DP placement。
- `build_moe_parallel_placement()`：生成合法 MoE TP/EP/DP placement，expert 数必须是 EP 的正整数倍，支持每个 EP partition 拥有多个 experts。

关键语义如下：

- `RectMeshSpec` 继续描述完整无洞物理 mesh，`routing_die_ids` 包含所有物理 Die。
- `active_die_ids` 只描述承载 workload rank 的 Die；`idle_die_ids` 是其物理补集。
- 首版一 Die 最多放一个 workload rank；active Die 可以非连续，并保持用户给定的 rank→Die 次序。
- Dense shared 参数按 TP shard 建立 owner，副本仅跨 DP。
- MoE shared 参数按 TP shard 建立 owner，副本跨 DP/EP；expert 参数按 `expert_id + TP shard` 分开建 owner，副本只跨相同 EP partition 的 DP ranks。
- 所有 group 和 owner 都使用稳定 artifact ID；反序列化后重新执行完整闭合校验。
- schema 已加入 `wafer_frontend.schema` 公共导出。

## 3. 校验与失败诊断

当前 schema 会拒绝：

- TP/DP/EP/PP 非正整数、`PP != 1`。
- logical rank 数超过物理 Die 数。
- active Die 数量错误、重复、越界，或 local core 为负。
- logical rank 缺失、重复，或逻辑坐标没有完整覆盖并行度乘积。
- Dense 使用 EP，MoE expert 数为零或不能被 EP 整除。
- group 缺失、重复、成员引用未映射 rank，或不符合 canonical logical mapping。
- owner 重复、TP shard/expert 越界、同步组缺失，或 replica ranks 与同步组不一致。

## 6. 第二切片：确定性 route/collective lowering plan

新增 `schema/parallel_transport.py` 和 `passes/parallel_transport.py`。计划层复用现有生产类型：

- 使用 IR1 `PairRoute` 与 `RouteHop` 表示 X-first 物理路径、端口、链路和资源。
- 使用 manifest `CoreRuntimeBinding` 和 `LogicalCoreRef` 表示 frontend core 与 runtime core 的绑定。
- 新增最小的 `ParallelCommunicationRequest`、`ParallelTransfer` 和 `ParallelTransferEndpoint`，用于闭合 collective 请求及成对 SEND/RECV。

`build_parallel_transport_plan()` 直接消费 `ParallelPlacement + PhysicalFabric`，提供以下确定性算法：

| 通信种类 | 计划层算法 |
|---|---|
| P2P | 一个有向 transfer |
| AllGather | `N-1` 步 ring，每步每 rank 一个 transfer |
| ReduceScatter | `N-1` 步 ring，每步每 rank 一个 transfer |
| AllReduce | ReduceScatter ring 后接 AllGather ring |
| AllToAll | 所有有序不同 rank pair 的 direct exchange |

`transfer_bytes` 明确定义为一个生成 transfer 的 payload。该计划只负责 transport；reduce/concat 的 compute lowering 仍由后续 workload lowering 负责。单成员 collective 合法退化为零 route、零 transfer、零 endpoint，同时保留该 rank 的 core binding。

## 7. 第二切片：路由与 endpoint 闭合

路由使用 placement 中的 logical-rank→Die 映射，并依据完整物理 mesh 生成 X-first 路径。中间节点从完整 `PhysicalFabric` 解析，因此 idle-compute Die 可以作为 routing-active transit Die。

每个 transfer 必须闭合为：

```text
request
  -> transfer(source rank, destination rank, bytes, route)
  -> SEND(source core, peer, same bytes)
  -> RECV(destination core, peer, same bytes)
```

校验会拒绝：

- P2P rank 越界、相同端点，collective group 缺失。
- route 端点、X-first die path、hop link/port/resource 与 fabric 不一致。
- transfer 缺 route、引用未知 request，或不符合声明的 deterministic algorithm。
- SEND/RECV 缺失、角色错误、rank/peer/bytes 不匹配或存在多余 endpoint。
- plan 被用于不同 placement/fabric digest。

## 8. 第二切片：runtime core binding

core binding 不使用 `die_id * 固定 stride + local_core` 推算。builder 在每个实际 `DieSpec.cores` 中按 `local_core_id` 查找 `CoreSpec`，复制其：

- `core.id` 到 `core_spec_ref`
- `core.runtime_core_id` 到 `runtime_core_id`
- `core.sram_profile_ref` 到 `sram_profile_ref`

计划随后再次与 `PhysicalFabric` 做精确反向校验。local core 不存在、runtime core 重复、uint16 越界等由 fabric/schema 在 plan 创建前拒绝。

## 10. 第三切片：transport 绑定真实 workload 通信点

`ParallelCommunicationRequest` 新增 case ID、request digest、P3 logical operation ref、workload phase/step/layer、tensor value refs、精确 bytes 与显式 no-op 标记。`ParallelTransfer` 继承 parent request 的 workload/value 绑定，同时把 collective 内部的 `algorithm_phase` / `algorithm_step` 与 workload phase/step 分开，避免 ring step 被误认为训练或 Decode step。

materialization 从 P3 graph 的 QKV、GRADIENT_SYNC、DISPATCH 和 COMBINE operation 生成 request：每层 TP、每个训练 step 的 gradient sync、MoE 每个 dispatch/combine payload 都保留独立引用。零 token expert 生成零 bytes no-op request，不生成虚假的 route、transfer 或 endpoint。

独立 oracle 重新推导 operation/group/value coverage，核对 case/digest、phase/step/layer、owner group、payload bytes。transport plan validator继续检查 transfer 与 request 一致，并严格配对 SEND/RECV 的 rank、peer 和 bytes。

新增测试覆盖 workload 与 algorithm 两套 step 字段、显式零 payload no-op，以及 transfer 对 parent request 的完整绑定。联合聚焦回归 40/40 通过。真实 runtime backend 未修改，simulator canary 尚未接入。
