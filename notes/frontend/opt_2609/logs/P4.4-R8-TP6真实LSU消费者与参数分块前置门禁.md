# P4.4-R8 TP6 真实 LSU 消费者与参数分块前置门禁

日期：2026-09-16。`dense_inference_rect_chunk_plan.py` 新增只读源级预检：从经过 `LinkedProgramManifest.validate` 的生产片段提取每个物理 Die 的真实 parameter StateABI、`state_operand_bindings` 与对应 `LSU_LOAD` 的 literal 字节数；调用方必须明确给出每 Die 容量和非空 KV/activation 保留区。候选 chunk 以 64B 对齐并精确覆盖源字节范围，但返回 `native_execution_admitted=false`，因为尚未实现分块外存搬运、record 重写、consumer 分块计算或原生完成时序。

对实际 TP6 `2x3` source `/tmp/m1-dense-fixed-2x3-fresh0/segment_0.linked.json` 使用正式 typed 反序列化执行预检：90 个 parameter StateABI，单个最大 12,288B；StateABI `state_abi_3e8112b6698925fe` 被原生完整 `LSU_LOAD size_bytes=12288` 消费。在同一个 12,288B/Die HBM 约束下，**仅为每 Die 任意状态保留 64B** 就使最大参数窗口不足 12,288B，预检准确报 `requires_tiled_consumer`。现实负载还需要非零 KV/activation，因此这个最宽松反例已足够证明只把 DMA 拆成多笔、保持原 LSU/计算 record 不变，无法满足 2×3 的真实原生 offload 目标。这里检查的是生产 linked 源，不把旧硬件配置的物理执行记录当成新的 native 成功。

四项有价值的正反单测验证 12,288B 参数在 8KiB 窗口的两个不重叠源区间候选、完整12KiB原生 LSU 必须拒绝、缺消费者/重叠 HBM 预留区与重复 StateABI 必须拒绝。下一步需实现并证明 tile 化算子/LSU byte-range 的源到原生对应关系，扩六 Die HBM/external backend 与真实 KV/activation 容量计划，再运行完整矩形双 Fresh；此预检只定义正确的拒绝边界，M2 2×3/3×2 尚未通过。
