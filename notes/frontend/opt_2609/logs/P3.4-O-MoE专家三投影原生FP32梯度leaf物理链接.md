# P3.4-O：两层 MoE 专家三投影具名 FP32 WGRAD 物理 leaf

## 开发目标与真实修复

StageM 的两层/两专家/two-step 源绑定检查已发现旧 TRAIN leaf 对 gate/up 的 WGRAD 把 (k,H) 的 backward_by_rank 当成 (k,I) 的 SwiGLU backward 上游，又用 FP16 MATMUL→LOCAL_REDUCE cast 代替具名 FP32 WGRAD。现在仅在 full_model_dataflow opt-in TRAIN 下对每个非空专家实际发出三条公共 GEMM_WEIGHT_WGRAD_TIMING 0x25；旧默认入口不变。gate/up 共同读取物理 forward activation (k,H)，分别读取同一个 SWIGLU_BACKWARD_TIMING 输出 buffer 的 FP16 (k,I) 前半/后半；down 读取物理 SWIGLU forward 生成的 (k,I) expert_activated 和真实 backward (k,H)。三个 owned FP32 gradient 切片分别是 0/128/256 起始，各128字节，完整专家 FP32 dW 共384字节；gate/up/down 的 (m,n,k) = (4,8,2)/(4,8,2)/(8,4,2)，每专家三投影共384 logical FLOPs，源 P2 实际 expert FP16 参数仍192字节，不靠缩小模型或零work伪动作。

首次真实 Python LinkedProgramManifest.validate 四段通过，但两旧 finalizer 因缺公共0x25 ABI 拒 opcode37；改用 R6 真实 scoped canary 冻结的正式 C++ finalizer后，四段正确拒无用的旧 expert_wgrad_stage (FP16 MATMUL→cast staging) ProgramSymbolDefinition.logical_cores 与 relocation scope 不相等。物理原因是 opt-in 原生0x25从未引用这个stage却还分配实体。仅删除该孤儿 BufferABI/符号和旧不可达 FP16 staging 下放分支、将其后scratch紧排，不改变专家数据字节、FLOPs、三个FP32输出或其它训练组件。沿 source typed EXPERT_DGRAD→SWIGLU_BACKWARD→原生0x25记录及符号/relocation/AddressOperandBinding/BufferABI精确slice重签，C++最终器现四段真实EXIT0。

## 关联生产阶段 cut 测试修正

删除已经不被任何native0x25 record引用的旧FP16 `expert_wgrad_stage` BufferABI 时，每core的前向阶段少一条SRAM_ALLOC动作，故既有PhysicalTrainingPhaseCut首条BACKWARD_GRADIENT SEND/RECV的index由固定`[26,32]`变成实际`[25,31]`。这个位置来源于P2 flow marker和真实record stream，不是模型梯度来源或时间线变更；只改硬编码数值会在下次合法scratch生命周期变化时再次失效。已将 `test_full_training_timeline_linker.py` 核查改为每核cut index等于该核forward records实际长度、前后片段都非空、所有原record严格拼接守恒；`python3 -m unittest -q llm.test.frontend.unit.test_full_training_timeline_linker` **12/12 PASS，13.652秒**。官方cut函数继续要求原P2 BACKWARD_GRADIENT rank0→rank1 SEND/RECV exact marker、禁止过早SRAM_FREE和过迟SRAM_ALLOC，不因测试改动放宽。
