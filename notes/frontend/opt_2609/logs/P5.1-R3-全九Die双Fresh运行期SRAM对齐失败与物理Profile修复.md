# P5.1-R3：全九 Die 双 Fresh 运行期 SRAM 对齐失败与物理 profile 修复

日期：2026-09-15。延续 [R2 偶数 ROPE 源修正](P5.1-R2-全九Die真实编译ROPE拒绝与模型修正.md)。本记录保留已经到达真实 NpuSim 的两轮失败和针对原生字寻址的模型/硬件修正；**两轮均没有完成 Prefill，也没有一个成功运行 case。**

## 同一失效模式的两次独立执行

从干净的 `/tmp/m1-tp9-source-freeze` 固定提交 `4ffadee6d80c569e0c971247cce14a2781f29f12` 分别在两个空目录 `/tmp/m1-dense-scaled-all9-3x3-even-rope-fresh0`、`...fresh1` 完整物化并生产编译修正后的两层 FP16 Dense TP9/H18/I36/NH9/KVH9/DH2 模型。case ID `workload_case_e9e319e1d985c06e`，九个 Die 在全部三段都有 core stream、空闲 Die 为零；生产编译耗时 298.582/347.368 s、前端峰值 734,976/734,456 KiB。每轮三份 linked manifest 约 14 MiB/段，finalizer 生成三份 657–660 KiB NPUP，typed ProgramIO 和原生 resolver 三段都成功，两个目录的三 NPUP SHA 和三 sidecar SHA 逐个相同。源码、native finalizer、resolver、NpuSim、SIM config 在隔离树与固定文件上绑定；没有复用第一轮构建产物作为第二轮输入。

两轮各运行一个完整物理 3×3 NpuSim 进程，均退出码 1，结尾同样是 `SystemC E549`：`SRAM fixed allocation address is not aligned: region=sram label=frontend_label_program_symbol_56664a689e0f5e0b offset=36 base=0 requested_alignment=32 effective_alignment=64`，位置为 core0/36,085 ns。对应 segment0 `LinkedProgramManifest.fragments[368]` 的 `SRAM_ALLOC_AT` literal 是 offset36/size36/alignment2；BufferABI 值 `temp.fused_op_skeleton_41483555e2c321e9.chunk.0.rank.0.recv.from.1`，即 36B FP16 `LOCAL_REDUCE` 接收片段。front-end 的 `naive_intra_die` 为小于硬件行尺寸的 reduce staging 保留 2B 紧密 stride，而 native `Sram_lifecycle` 把 record2B 与32B legacy字宽求共同对齐，再与 hardware64B 取有效64B，并以64B粒度保留容量。36B 内部片段无法作为独立 word-aligned fixed allocation；这是物理合同不一致。不能把两个失败当作双跑通过，也不能直接降低 native 字宽绕过。

## 针对主 shape-scaled profile 的源修正

当前版本优先让 P5 主 Dense 推理 profile 在 1..10 全形状上形成可执行的物理 word-aligned 源：`TP=rows×columns`，`NH=KVH=TP`、`DH=rotary_dim=16`、`H=I=16×TP`，每 Die 一 request 的 Prefill1→Decode1→Decode1，TP 包含每个物理 Die。整行隐藏向量的 FP16 片段是 `32×TP` B，奇数 TP 的 reduce staging 不再是36B subword stride。该 shape-scaled source 与 R2 case ID 必然不同：新 3×3 是 `workload_case_08e8a2359dead3c4`，新 10×10 是 `workload_case_cf726a3f4b6e5faf`。生产 compile Fabric 和生成的 native hardware 均明确选择 32B SRAM allocation alignment；对正常固定模型 runner 保持原 profile。源码下三段 3×3/10×10 `build_ir0→logical_expand` 定点测试已 **2/2 PASS，9.184s**，全 100 source case 正在重跑。生产真正 SRAM offset、NPUP 和 NpuSim 是否对新 profile 通过，仍必须按新 ID 和新 SHA 从空目录实测，不能由维度算式推定。

runner 的 NpuSim 失败路径现在会把完整原始 stdout 写在 `npusim.failure.stdout.txt`，并单独生成带 phase=`native_npusim`、source/tool SHA、case ID、NPUP SHA、wall/RSS 的 `runtime_failure.json`；对外异常只给末尾关键错误，避免失败时丢失几万行原始诊断。旧失败产物的相同工具人工 replay 可额外保存 `npusim.failure.replay.stdout.txt`，它是诊断复现，不是原来两轮的第三次 fresh 成功运行。

全 100 唯一矩形源 case 加原固定模型回归随后 **5/5 PASS，62.146s**。旧失败产物用同一 native 工具人工 replay 亦在36,085 ns/同一 label 重现 E549，完整原始 stdout 留在 `/tmp/m1-dense-scaled-all9-3x3-even-rope-fresh0/npusim.failure.replay.stdout.txt`，SHA-256 `02d948ce2b70dfea7bf0dd86056a6e518ad4a5d6783881766963145f2a0af1ba`；这是诊断重现，不是新的成功 case。

## 验收边界

此修正仅是发布用 **合法 shape-scaled 模型 profile** 的物理对齐选择，尚未提供任意小于字宽 reduce staging 的通用打包根分配；这样的模型仍应在能力门禁处显式拒绝或另行开发真实 packed-root BufferABI/生命周期。训练、MoE、低 HBM/offload、全 100 runtime 和超 10×10 都未由本记录完成。M1/M2/M3 completion 保持 false。下一步把全 100 source test 收据补齐，冻结新提交，再用两空目录重跑全九 Die 的 production compile→native full sequence；先逐段检查每个 `SRAM_ALLOC_AT` 地址是否满足实际 hardware 对齐，再等待真实 KV/one-shot/SIM_RESULT 和双跑比对。
