# P3.4-I：真实两层 MoE TRAIN 前向 IR1 候选和两个独立生产门禁

## 目标与代码

沿 P3.4-G 的32节点完整共享Dense＋逐层MoE前向源图，使用 P3.4-H **同一生产** `workload_case_f698249222425f2d`（两层、TP1×EP2、V16/H4/I8、128KiB SRAM与各Die32MiB HBM）已源签 physical case、EP(1,2) D2D 双向 PhysicalGroup、27State官方 `PersistentStateManifest`，构建真正官方schema类型 `IR1.create(producer_pass="moe_ep_train_forward_placement_candidate")` 的一个完整物理**候选**：20共享Dense前向节点与12MoE节点各有物理 `PhysicalNode`，沿同一 group 精确保留 source logical node id/kind/impl/workload/IO、原32节点完整 DATA/control graph和27份 trainable state access。不是用时间之和替代 timeline，也不复用额外旧Dense MLP。

NEW `MoeEpPlacedIr1SourceCandidate` 额外保存16份明确 provenance，每一份将真实原E2E `StateVersion(version0)`、原 `TensorValue.logical_rank`、**TP shard=0**、真实EP rank0/1与 physical group rank→Die、原 MoE expert aggregate StateABI state_ref＋三64B投影精确offset、最终27份官方 HBM binding ID/地址/Die 一对一校对。八份专家/路由EP1状态确有物理 die1 home，却没有把 `PersistentStateIdentity.generation` 或 `shard_index` 冒作EP rank；证据失配、错绑路由、删任何物理节点、少一投影会由独立 source oracle 立即拒绝。

## 实测官方生产门禁

调用这个**真实官方 IR1**候选的 `IR1.validate`，原始异常为 `KeyError(<OpKind.MOE_EXPERT_FORWARD: 'moe_expert_forward'>)`，发生于 `schema/ir1.py` 的 `PhysicalNode.validate` 对新MoE OpKind缺 `NodeWorkload` 映射（新增0x23/24/25独立FP32 WGRAD物理opcode将来也要独立补严格映射）。这是当前生产校验器功能缺口，候选尚不合法；不能仅见 `IR1.create` 返回 object 就称 physical full-model ready。

第二道独立门禁已经通过原官方schema代码确认：`IR1.validate` 对所有 `PersistentStateIdentity.shard_index` 取 group physical rank，要求每个HbmBinding Die等于该rank对应Die。现在两轴真 `TP1×EP2`，八份EP1专家/路由原 source TP shard是0而E2E owner/StateABI physical Die是1；旧规则错误地选择group rank0→die0，所以即便补物理MoE OpKind类型也会拒绝准确的EP1状态。要版本化 public `PersistentStateIdentity.ep_owner` 或 IR1 物理 provenance字段与 strict typed E2E view/生产StateABI closure，明确区分TP shard与EP rank，然后在IR1中仍保留完整旧TP/DP默认合同；不能把shard0悄悄写1或者取消 official validate。
