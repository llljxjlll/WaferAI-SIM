## 2. P4.1 外部层 schema

新增 schema/external_memory.py。

### 2.1 存储与链路合同

ExternalMemoryFabric 复用 P2 的 MemoryTierCapacity 描述容量和地址范围，并显式区分：

- external capacity：外部 backing 的有限地址空间。
- HBM capacity：传输目标或来源 die 的有限地址空间。
- ExternalMemoryLink：一个 external backing 的传输 controller/link。
- ExternalMemoryConnection：link 到具体 die HBM 的连接和 route。

初版 link 只允许 HALF_DUPLEX_SHARED，两个传输方向使用同一个服务时间线。每条 link 必须声明：

- ingress die。
- bytes_per_cycle。
- latency_cycles。
- queue_depth。
- max_outstanding。

max_outstanding 不得超过 queue_depth 加一个正在服务的请求。容量、带宽、队列和 outstanding 必须为正数；latency 可以为零。

### 2.2 直连与非直连 die

每条 link 必须存在 ingress die 的直接连接。直接连接的 route 必须恰好为 ingress die，额外 route latency 为零且没有 route bandwidth。

访问非直连 die 时必须给出：

- 从 ingress die 开始、在 target die 结束的无重复 route_die_ids。
- 非零的 route_latency_cycles。
- 非零的 route_bytes_per_cycle。

因此非直连 die 不能省略路径，也不能被计为零成本。当前 route 参数表示该路径的总附加服务成本。

Fabric 校验还包括：

- external/HBM tier 类型正确。
- 地址范围按 `(tier, location_ref)` 所属地址域检查；同一 owner 不重叠，不同 die 的 HBM 可以各自从本地地址 0 开始。
- 每个 external backing 恰好对应一条 link。
- connection 的 link、HBM 和 target 引用闭合；HBM owner 必须使用规范 `die:<id>`，且该 id 与 connection target 相等。
- 每个 HBM capacity 至少有一个 external connection。
- 同一 link/target connection 不重复。
- schema 严格 JSON 往返和稳定 artifact ID。

## 3. P4.2 确定性传输服务

新增 passes/external_memory.py。

### 3.1 Payload 存储

SparseMemoryImage 是容量受限的稀疏字节存储：

- 未写入地址读为零。
- 非零和零字节都按真实 payload 语义写入。
- 每次 read/write 都检查配置的半开地址范围。
- 稀疏宿主表示不改变被模拟的容量；越界仍返回 external_memory_address_out_of_range。

execute_external_transfers() 要求 external/HBM image 与 fabric capacities 精确闭合，不接受缺失、额外或绑定错误的 image。

### 3.2 时序公式

每条 link 独立维护可用时间。相同 issue cycle 的请求按稳定 request ID 排序。

直接连接：

    external_service_cycles =
      latency_cycles + ceil(payload_bytes / bytes_per_cycle)

非直连连接：

    route_service_cycles =
      route_latency_cycles + ceil(payload_bytes / route_bytes_per_cycle)

    total_service_cycles =
      external_service_cycles + route_service_cycles

共享 link 上：

    start_cycle = max(issue_cycle, previous_completion_cycle)
    completion_cycle = start_cycle + total_service_cycles
    queue_stall_cycles = start_cycle - issue_cycle

external_to_hbm 与 hbm_to_external 在同一 link 上串行，不能同时获得两份带宽。不同 external links 有各自时间线，可以并行。

请求进入服务前检查 issue cycle 上的 outstanding 和等待队列占用。超过任一上限时返回 external_queue_exhausted，不静默创建无限队列。

### 3.3 完成与统计

每个成功请求产生唯一 ExternalTransferCompletion，包含：

- request/link/direction。
- start/completion cycle。
- external 与 route service cycles。
- queue stall。
- payload bytes。
- 实际搬运 payload 的 SHA-256 digest。

ExternalTransferReport 要求 completion 精确覆盖 request，重新计算时序、地址、queue/outstanding 上限和统计。统计包含：

- submitted/completed/pending requests。
- external read/write bytes。
- HBM read/write bytes。
- shared-link busy cycles。
- queue stall cycles。
- 最大 queue occupancy。
- 最大 outstanding。
- makespan。

## 7. P4.3 HBM residency/offload planner

本次后续切片新增 schema/offload.py 与 passes/offload.py，在 P2 allocator 和 P4 external transfer service 上实现确定性的 offload_blocking 组件 API。

### 7.1 输入与输出合同

输入由以下对象组成：

- OffloadChunk：逻辑 state generation 0、对象类型、chunk 大小/对齐、external backing 地址和目标 connection。
- OffloadTraceEvent：连续 ordinal 的 PIN、UNPIN、READ、WRITE 事件及显式依赖。
- OffloadResidencyRequirement：普通事件使用 AUTO_BRING_IN；需要验证预取/依赖的 consumer 可声明 MUST_ALREADY_RESIDENT。
- ExternalMemoryFabric：复用 P4.1 的 external/HBM 容量、连接和链路参数。

输出 BlockingOffloadPlan 包含：

- 完整 state generation 列表。
- P2 MemoryPlan 生成的每段 HBM lifetime、allocation、地址和 peak。
- 显式 external_to_hbm / hbm_to_external transfer request sequence。
- 严格串联的 bring-in、consume、pin/unpin、dirty writeback 和 clean discard operation。
- bring-in/writeback/discard、读写消费、bytes、blocking cycles、HBM peak、pin 及最终 drain 统计。

BlockingOffloadExecution 使用 P4.2 SparseMemoryImage 和 execute_external_transfers 执行计划内的真实字节搬运，并要求 transfer report 与计划的 fabric/request 精确相等。

Plan 和 Execution 均保持 simulator_runtime_integrated=false。本切片是 Python 组件级 blocking offload，不是 C++ NpuSim 完整负载 runtime。

### 7.2 Next-use、eviction 与状态版本

每个 HBM endpoint 独立计算 resident bytes。Bring-in 前容量不足时，只从 pin_count 为零的 resident chunks 中选择 victim：

1. 优先选择下一次使用最远的 chunk。
2. 没有未来使用视为最远。
3. 下一次使用相同则按稳定 chunk ID 选择。

Victim 为 clean 时生成 CLEAN_DISCARD，不产生虚构 transfer；victim 为 dirty 时生成 HBM_TO_EXTERNAL writeback，并保持 HBM allocation 至 writeback completion。新 bring-in 只能在该 completion 之后复用地址。

Bring-in 占用 HBM 地址后先记录 TRANSFERRING residency，完成时切换为 CLEAN。WRITE consumer 为对应逻辑 state 创建 generation+1，predecessor 指向同 state 的前一代，并在 WRITE 完成点切换为该 generation 的 DIRTY residency。Dirty writeback 完成前保留 HBM lifetime，完成后状态变 clean 并退出 resident window；最终 planner 按稳定 chunk ID 排空，保证 final resident、dirty 和 pin 均为零。

为支持这一合同，P2 MemoryPlan 允许同一物理 allocation 上存在多个时间连续的 residency segments。Segments 必须无缝覆盖 allocation lifetime、属于同一逻辑 state，且 version 只能保持不变或沿 predecessor 逐代推进。P4 validator 会在 operation 的实际 start/ready cycle 查找对应 residency，拒绝只有 operation generation、没有物理 residency 的伪造计划。

PIN 会自动 bring-in 后增加引用计数；UNPIN 减少引用计数。Pinned chunk 不参与 eviction。末尾引用计数非零返回 offload_pin_leak，容量全部被 pinned chunks 占用返回 offload_pinned_capacity。

Consumer operation 精确依赖前一 blocking operation。自动 bring-in 后的 READ/WRITE cycle 等于 transfer ready cycle。MUST_ALREADY_RESIDENT 在没有既有 residency 时返回 offload_read_before_resident。

### 7.3 Resident-only 对照与容量

plan_resident_only_memory() 将同一组 chunks 作为整个 lifetime 同时驻留，直接调用 P2 plan_hierarchical_memory。相同模型状态在低容量 HBM 上由 resident-only 返回 memory_capacity_exceeded，而 offload_blocking 可以通过分段 residency 运行。

单个 chunk 对齐后仍大于目标 HBM capacity 时返回 offload_minimum_window_insufficient。所有成功计划再次执行 P2 MemoryPlan.validate，并要求记录的 HBM peak 不超过配置容量。

## 8. 集成审阅问题 7/8 修复

### 8.1 Typed address-space owner

集成审阅发现 ExternalMemoryFabric 原先把所有 HBM capacity 放在同一个全局数值地址域内检查 overlap。这会错误拒绝 `die:0` 和 `die:1` 都从本地地址 0 开始的合法配置，同时 connection 没有验证目标 die 是否真正拥有所引用的 HBM。

修复后：

- capacity overlap 按 `(MemoryTier, location_ref)` 分域检查；同一 typed owner 的相交区间仍 fail closed。
- 每个 HBM `location_ref` 必须使用规范 `die:<uint64>` 形式。
- 每个 ExternalMemoryConnection 的 `target_die_id` 必须等于 HBM owner die。
- transfer service 继续通过 connection 的 `hbm_capacity_ref` 选择目标 SparseMemoryImage；两个 die 即使使用相同本地地址，也不会混写。

该语义变更使用 `wafer_frontend.external_memory_fabric/v1alpha2`，不会把旧解释静默伪装为同一 schema。

### 8.2 Workload/source binding

BlockingOffloadPlan 原先只携带独立 chunks/events 和派生 memory plan，无法证明这些状态来自当前 request、logical graph 及其源 memory plan。修复将计划 schema 升为 `wafer_frontend.blocking_offload_plan/v1alpha2`，并新增：

- `request_digest` 与 `logical_graph_digest`。
- 嵌入的 `source_memory_plan` 及 `source_memory_plan_digest`。
- `OffloadStateMapping`，逐 chunk 一一绑定 source state version 与 source allocation。

计划自校验要求 source digest 与嵌入 artifact 的 canonical digest 相等；mapping 必须精确覆盖所有 chunks，且 source version、allocation、object kind、external tier、size、alignment、address 和 capacity 均一致。派生 generation 只能属于已映射 logical state，validator 还会重建每个 chunk 的权威 version chain，并要求 state_versions 精确等于 generation-0 输入加实际 WRITE 结果。

`validate_blocking_offload_plan()` 和 `execute_offload_blocking()` 现在要求调用方传入当前 request、logical graph、source memory plan 三个 expected digest；任一不一致返回 `offload_workload_binding_mismatch`。因此从另一个 case 拼入一份自洽计划也不能在当前 workload context 中执行。

这是显式 schema/API 迁移：v1alpha1 offload plan 不会被 v1alpha2 decoder 当作兼容对象读取。当前仓库内调用点及 focused tests 已迁移；新 schema 的公共 `__init__.py` 导出由主线集成统一处理。

## 9. P4.2 C++ external-memory component runtime

### 9.1 交付范围

新增以下独立 C++17 组件：

- `llm/include/memory/external_memory_service.h`
- `llm/src/memory/external_memory_service.cpp`
- `llm/unittest/external_memory_service_selftest.cpp`

根 CMake 新增 `npusim_external_memory_service` static library、`npusim_external_memory_service_selftest` 可执行文件及 `external_memory_service_selftest` CTest。

组件配置与 Python ExternalMemoryFabric v1alpha2 的核心语义对齐：

- external capacity 使用显式 owner，HBM capacity 使用显式 owner die；地址 overlap 只在相同 typed owner 内拒绝。
- connection 必须引用已声明 link/HBM，`target_die_id` 必须等于 HBM owner die。
- 直连 route 必须为 ingress die 的零成本单点路径；非直连 route 必须从 ingress 开始、在 target 结束，并声明非零 latency/bandwidth。
- 每个 external capacity 恰有一个 service link；每个 link 有 ingress-die direct connection；每个 HBM capacity 均有 connection。

`SparseMemoryBacking` 是有限地址范围内的稀疏字节 backing：未写入字节读零，写零会删除稀疏项，所有读写均检查正长度、uint64 overflow 和 capacity bounds。每个 HBM capacity 持有独立 backing，因此不同 die 可同时使用 local address 0。

`ExternalMemoryService::Execute()` 接受 external↔HBM 请求，按 `(issue_cycle, id)` 确定排序，并按 connection 引用选择 external/HBM backing。每个 link 使用共享 half-duplex timeline，两个方向不能并行。时序与 Python 服务一致：

    external_cycles = latency + ceil(payload_bytes / bytes_per_cycle)
    route_cycles = remote ? route_latency + ceil(payload_bytes / route_bytes_per_cycle) : 0
    completion_cycle = max(issue_cycle, link_free_cycle) + external_cycles + route_cycles

提交时严格检查 queue depth 和 max outstanding。成功报告包含逐请求 start/completion、external/route service、queue stall、payload bytes，以及方向性 external/HBM bytes、link busy cycles、总 stall、最大 queue/outstanding、makespan 和 pending 数。

### 9.3 Component runtime 与 workload runtime 边界

该 C++ 服务已实际执行有限 external/HBM backing 间的非零 payload 搬运，并形成可运行的 component runtime。第 9 节记录的是初始独立 batch service；第 10 节在此基础上增加了直接访问现有 HBMBackend 的 SystemC runtime bridge。完整 workload runtime 仍未绑定：

- N6/npup external-memory opcode、record 或 action DAG。
- finalizer、ProgramIO、workload lowering 和统一 runner。
- compute/LSU/DTE action DAG 和完整 workload 共用时间线。
- P4.3 planner 输出到 C++ request 的序列化桥接。

因此不能把本节的 C++ selftest 记为 Dense/MoE 训练或推理的 offload workload runtime，也不能将 `offload_runtime_verified` 置为 true。完整 workload runtime 仍属于后续 P4.4–P4.9 集成。

## 10. P4.2 C++ HBM runtime bridge

### 10.1 版本化 typed DMA 与真实 HBM backing

新增：

- `llm/include/memory/external_memory_runtime.h`
- `llm/src/memory/external_memory_runtime.cpp`
- `llm/unittest/external_memory_runtime_selftest.cpp`

并在 CMake 中加入 `npusim_external_memory_runtime` static library、integration selftest 和 `external_memory_runtime_bridge_selftest` CTest。

`TransferRequest` 新增显式 schema version `npusim.external_dma_request/v1alpha1`。`ExternalMemoryRuntimeBridge` 在 admission 时校验 schema、唯一 request ID、方向、当前 cycle、connection、external/HBM 地址范围、queue depth 和 max outstanding；所有检查通过后才登记请求、更新 submitted 统计并进入 link worker。失败请求不会修改 external backing、HBM backend 或已提交统计。

桥接器只维护 external sparse backing。HBM 一侧不再建立副本，而是按 `hbm_capacity_ref` 找到调用方提供的 `HBMBackend*` 并提交标准 `HBMBackendTransaction`：

- external→HBM 在 admission 时快照 external payload，完成 external/route service 后向真实 backend 提交 write。
- HBM→external 先从真实 backend read；只有 backend 成功完成后才把 payload 写入 external backing。
- backend 返回的 completion delay、service time、status 和 error 均进入 runtime completion；backend 失败不会对反向 DMA 的 external 目标进行部分写入。

现有 `HBMRuntime` 拥有的 backend 可直接作为 binding 传入；integration selftest 使用 `BehavioralHBMBackend` 验证与现有 backing 的实际互操作。当前 ExternalMemoryFabric 只有 HBM owner die，没有 stack/channel 标识，因此 bridge 要求上层显式提供完整且非空的 `capacity_ref -> HBMBackend*` 映射，不能从 `HBMRuntime` 拓扑自动猜测 endpoint。

### 10.2 SystemC completion 与共享链路

每个 external link 由一个 SystemC thread 串行处理，请求两个方向共享同一 half-duplex 队列和 service timeline。远端 route 成本继续使用 fabric 中显式声明的 route latency/bandwidth。

runtime 提供：

- `Poll(request_ref)`：非阻塞读取单请求 completion。
- `Wait(request_ref)`：SystemC process 内等待对应请求完成。
- `CompletionEvent()`：供调度器轮询任意 completion。
- `Outstanding()` 和 `Stats()`：报告完成数、失败数、方向性 external/HBM bytes、external/HBM service time、queue stall 和最大 outstanding。

completion 包含 request ID、status/error、submit/start/complete time、external/HBM service time 和 payload bytes。写入真实 backend 后才发布 external→HBM completion；读取真实 backend 并提交 external 写入后才发布 HBM→external completion。

### 10.3 Integration selftest

selftest 覆盖：

1. external 中的非零 payload 经 DMA 写入 `BehavioralHBMBackend`，completion 前 Poll 未就绪，Wait 后直接 backend read 得到相同 payload。
2. 先直接写脏数据到同一个 HBM backend，再执行 HBM→external DMA，external probe 得到 dirty payload。
3. capacity 越界、缺 connection 和错误 schema 均在 admission 阶段失败，submitted 计数不变。
4. max outstanding/queue depth 耗尽拒绝第三个请求；已接受请求按 half-duplex 次序完成。
5. backend 读失败时 external 目标保持原值，失败状态进入 completion/stats。

### 11.4 能力边界与剩余集成

新增公共 `ADAMW_UPDATE` opcode（`0x21`）和独立内部 PrimId（68），没有复用或重命名
`SGD_UPDATE`。固定 record payload 显式携带 FP16 weight/output、FP32 gradient，以及

负 weight decay 和所有非有限超参数。published work model 对每个元素计 18 个 vector ops、

FP32 gradient/master/m/v、FP32 step counter，以及更新后的 FP16 weight、FP32 master/m/v/
step counter。

`Adamw_update_prim` 经 factory、严格 wire 和 record lowering 进入真实 WorkerCore timing
执行路径，并输出包含 step、beta/epsilon/weight-decay bits 和 SRAM read/write bytes 的
