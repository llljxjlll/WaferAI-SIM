# P3.4-F：MoE 训练非零索引与原生 FP32 参数梯度源类型

## 范围与原始观察

目标是为两层、1×2 Die/EP2、两步 SGD 的 MoE 训练建立不能由假索引或 FP16 dX 代替的物理 WGRAD 输入。现有完整 Dense 两层训练的 Embedding 源 `T0.token_ids` 为 BORROWED INT32；原 bounded CE ProgramIO 默认填入 4 个零索引。这样的输入只能覆盖全零基础形态，不能证明非零、重复索引的全量词表 scatter。现有 internal Norm 反向只写 FP16 dX，也不能满足 FP32 gamma 权重梯度。完整 MoE 训练仍没有替换原 Dense MLP 的正式 IR0、物理全反向、两步单时间线以及最终 NpuSim 证据。

## 开发

- 新的版本化 `MoeTrainTokenInputCase` 精确签原 `WorkloadRunRequest.case_id`、request digest、两层两步四条 frozen route trace ID/digest、实际 MoE logical graph digest、TRAIN seq=4 和模型**原完整 V=16**；显式的两步合法索引分别为 `(3,3,5,7)`，没有缩小词表或梯度 extent。旧 `WorkloadRunRequest` 本身无 token payload，新的 artifact 是可审查的独立 workload input，不冒充旧请求默认值。
- `build_source_bound_moe_train_token_program_io` 只修改真实 bounded Dense CE ProgramIO 中 `T0.token_ids` 唯一 BORROWED INT32 ABI 的 16B blob，其他 58 条 initialization 与 output probes 保持生产原合同，结果再次 `ProgramIoContract.validate_against(real linked manifest)`。`derive_forward_embedding_index_trace` 只能从修改后的原始 blob 解码；另一独立检查对源 input bytes/digest/step 与实际 ProgramIO decoded trace 作逐字节对照。新 blob SHA256 为 `0d69652bd563f9877f6225aee86278c9441be929f3827ec473c601e5caf9328d`，原零索引 blob SHA256 为 `374708fff7719dd5979ec875d56cd2286f6d3cf7ec317a3b25632aab28ec37bb`。索引 3 出现两次，固定记录 index_trace 后缀 12 槽全零。
- 正式 `OpKind.EMBEDDING_TABLE_WGRAD` / `NORM_GAMMA_WGRAD` 分别绑定单独公共 fixed external0x23/0x24 的 exact impl_ref、operand count、pure WGRAD phase 和 FP32 output；其 workload 严格要求 `logical_rows = rank_rows × tp_degree`。Embedding 输入 INT32 indices、FP16 full V16×H4 table、FP16 dHidden、FP32 **V16×H4=256B** table gradient，Norm gamma 4×4 两个 FP16 输入、FP32 H4=16B output。`LogicalNode.validate` 与 `IR0.validate` 验各输入/梯度 dtype、形状、来源梯度 producer，`DenseIR0Validator` 验物理 rank/local TP extent；dIndex 和 FP16 dX 不能顶替 WGRAD。
