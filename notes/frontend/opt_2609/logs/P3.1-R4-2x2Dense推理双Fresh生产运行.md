# P3.1-R4：2×2 Dense 推理双 fresh 生产运行

> **后续校正（2026-09-15）**：本记录的Dense sequence真实运行使用native `x=4` 且缺`y`（原生4×4核/Die），而编译Fabric为2×2核/Die；global core ID被解释为错误物理Die。原exit0/KV/周期是该错误硬件下的历史观测，不能计入目标矩形物理Die或跨Die路由验收。详见[P1.1-R1 核几何审计](P1.1-R1-前端原生核几何失配与矩形物理路由修正.md)；正确几何的全新双跑另计。

## 目标和方法

冻结 fixture 为 FP16、V128/H32/I64/L2/NH4/KVH4/DH8、四个 request 各 Prefill4 后 Decode2，resident HBM 且 `timing=true,functional=false`；每段四个 core stream 对应四个 active Die。

对固定 2×2/TP4、四个 row-major Die 全参与、两层 Dense 模型，运行 Prefill→Decode→Decode。两个独立 Python 子进程分别从 `_two_by_two_case()` 物化和 `compile_dense_e2e_sequence_runtime_profiles()` 开始，分别写入新 `/tmp` 目录，随后各自执行三次真实 finalizer、构建并验证三份 typed ProgramIO、在各自一个 fresh NpuSim/SystemC 实例内运行三段。NpuSim 在每段装载时对 sidecar、linked manifest 和 NPUP 调用 C++ `frontend::program_io::ParseAndResolve`，并验证 KV state continuity；这是实际解析，而非只生成 JSON。

旧 2×2 记录里此前已有单次生产编译/运行。本补测的两个执行都重新物化、编译、最终化、解析和模拟，不复用第一次的 manifest、NPUP、ProgramIO 或实例。输出仅在 `/tmp`；源码、既有 runner、TP16 进口前端以及 `build-debug-final` 保持只读。它只为这一固定 Dense 推理维度补双 fresh 证据，不代表 M1 四家族、八形状矩阵或训练闭环完成。
