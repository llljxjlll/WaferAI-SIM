# 前端 Naive Dense 静态前向 MVP 开发方案

> 依据：`notes/frontend/前端建模方案.md`
>
> 当前目标：只实现 **naive 策略的静态 Dense 前向负载端到端跑通**，并冻结后续
> Swizzling、片上优化和其他策略需要的替换接口。
>
> 本文是开发执行方案，不扩大 `前端建模方案.md` 的能力声明。

---

## 1. 首版目标与完成定义

本方案 N0–N7 的交付名称固定为 **Naive Dense 静态前向 MVP**。它只覆盖
analytic Llama-like、静态 `ProfileKey`、单 instance、TP/SP、Dense 前向和
deterministic naive inter/intra policy；它不是《前端建模方案》的完整 S1，也不代表
`req.md` 中训练、动态 KV transfer、MoE 或两个 optimized 技术点已经完成。

### 1.1 目标链路

首版必须通过一条命令完成以下完整链路：

```text
experiment YAML
  → IR-0
  → LogicalExpand
  → Placement / IR-1
  → NaiveFusionPartition
  → NaiveInterDiePolicy / per-rank FusionAction DAG
  → ProjectToIR2
  → NaiveIntraDiePolicy / IntraDieSchedule
  → GlobalActionDAG
  → coarse / standalone collective / ISA region lowering
  → ManifestLinker → ProgramArtifactFinalizer
  → program.npup
  → npusim --program
  → trace + metrics + validation report
```

这里的“端到端”同时要求：

- 前端能从模型与并行配置生成完整负载，不能只运行手写的单个 collective fixture。
- 普通算子、独立 collective 和目标 GEMM+ReduceScatter region 进入同一个 artifact。
- 整次运行只使用 `config_helper_program`/strict transport，不能把 JSON 与 ISA 两次运行的时间相加。
- IR-2 必须由完整的 per-rank Action DAG 投影产生，不能先生成 IR-2 再补 collective 顺序。
- 输出必须可以回溯到输入配置、每级 IR、policy 名称和 simulator artifact。

### 1.2 首版负载范围

首版选择能够验证完整架构、同时尽量减少变量的 S1 子集：

| 项目 | 首版支持 |
|---|---|
| 模型 | analytic Llama-like Dense 前向 |
| 场景 | 静态 prefill/decode ProfileKey；先跑 prefill smoke，再补静态 decode |
| 并行 | 单 instance，TP；需要 ReduceScatter 时开启 SP |
| 目标 region | 行并行 partial GEMM → ReduceScatter completion |
| 后处理 | bias/residual/activation 保持在 reduction 后；首个 smoke 可放在 region 外 |
| placement | 用户指定或 deterministic compact placement |
| inter-die policy | 固定 naive |
| intra-die policy | 固定 naive |
| 执行 | 静态 profile、统一 Program artifact、单 helper |
| 精度 | timing 与 functional oracle 分开验收 |

### 1.3 首版不做

以下能力只保留接口，不进入当前实现和完成标准：

- `swizzle_topo`、ring/tree 搜索、chunk owner 重排和 plan 搜索；
- optimized core placement、NoC route、SPM banking、双缓冲和通信阴影调度；
- 在线 PDS、`RegionCall`、动态 variant dispatch；
- surrogate、候选搜索和大规模多保真评估；
- PD 分离、持久 KV handoff、`tp_P != tp_D`；
- Dense 完整反向、optimizer、ZeRO、PP 物理流水；
- MoE gating、AllToAll 和 MoE PD；
- HLO/FX 作为主输入；
- 任意 FusionGroup 自动发现和任意 epilogue 跨 reduction 重排。

如果用户在首版配置中选择上述能力，前端必须明确报
`UnsupportedFeatureError`，不得静默回退到 naive 后继续运行。

## 2. 开发原则

1. **先正确、后优化。** naive 仍须执行正确的数学依赖和完整通信，不能用时间常数替代。
2. **固定 pass 顺序。** `Placement → FusionPartition → FusionPlan → ProjectToIR2 → IntraDiePolicy`
   是硬约束。
3. **接口与实现分离。** 首版只注册 naive implementation，但所有 pass 通过接口调用。
4. **一个执行后端。** 三类 lowering 最终形成一个 `ProgramArtifact`，由
   `config_helper_program` 执行。
5. **不重复定义二进制 ABI。** Python 前端不自行编码 `.npup`；C++ bridge 复用
   `ValidateProgramArtifact/EncodeProgramArtifact`。
6. **每阶段都有可序列化产物。** 失败时能定位到具体 pass，而不是只看到 simulator 超时。
7. **无静默降级。** 非法 FusionGroup、SRAM 超限、缺失 endpoint、能力不支持都必须在运行前失败。

## 4. 必须先冻结的接口

首版实现以下接口，并只注册 naive 版本：

```python
class FusionPartition:
    def run(self, ir1, semantic_candidates) -> list[FusedOpSkeleton]: ...

class InterDiePolicy:
    def plan(self, ir1, fused_op, profile) -> FusionPlan: ...

class ProjectToIR2:
    def run(self, ir1, plans) -> list[IntraDieDAG]: ...

class IntraDiePolicy:
    def schedule(self, dag, hardware) -> IntraDieSchedule: ...

class CoarseLowering:
    def lower(self, scheduled_op) -> CommandFragment: ...

class StandaloneCollectiveLowering:
    def lower(self, scheduled_actions) -> CommandFragment: ...

class IsaRegionLowering:
    def lower(self, plan, schedule) -> RegionManifest: ...

class ManifestLinker:
    def link(self, global_dag, fragments) -> LinkedProgramManifest: ...
```

为避免后续阶段隐式补计划，首版同时冻结：

```python
class StandaloneCollectivePlan:
    id: str
    op_id: str
    algorithm: str
    group_ref: str
    profile_key: ProfileKey
    rank_programs: dict[int, tuple[FusionAction, ...]]

class GlobalActionDAGBuilder:
    def build(self, ir1, dags, schedules) -> GlobalActionDAG: ...
```

其中 standalone 与 fused plan 共用 action 语义，但使用不同的 plan 类型和来源 ID。
IR-1 必须显式携带不可变的 value table（含 layout/sharding/producer/consumer），任何下游
pass 都不得通过进程全局对象回读 IR-0。`IntraDieDAG` 只保存语义 task/value/flow/deps；
`IntraDieSchedule` 只保存 core、NoC、port、buffer、发射顺序和逻辑 event/token；最终物理
tag/token/group/event ID 只由 artifact finalization 分配。

链接明确分成两步：Python `ManifestLinker` 产生版本化、可重定位的
`LinkedProgramManifest`；C++ `ProgramArtifactFinalizer` 只做 relocation、最终 ID 分配、
`ProgramArtifact` 构造/验证/编码。两步均不得重新选择 policy、peer、chunk、route 或 schedule。

接口约束：

- 输入对象不可原地修改；pass 产生新对象或显式 result。
- 每个 result 携带 `schema_version`、`producer_pass` 和稳定 ID。
- FusionPlan 派生的 IR-2 节点必须携带
  `origin_ref=(plan_id, rank, action_id)`。
- optimized policy 未实现时不注册；不能用同名空壳调用 naive。
- lowering 只翻译已经决定的 action，不得重新规划。
- `ManifestLinker` 只合并 fragment、逻辑符号和 relocation，不分配物理 ID；
  `ProgramArtifactFinalizer` 只绑定物理身份和 ABI。二者都不改变 policy/schedule。

## 5. 阶段总览

| 阶段 | 核心内容 | 依赖 | 阶段产物 |
|---|---|---|---|
| N0 | 现有后端能力闸门 | 无 | capability report + 手写 2-die program |
| N1 | 工程骨架、Schema、PassManager、接口 | 无（与 N0 并行） | IR round-trip 与 pass-order 单测 |
| N2 | Dense IR-0 与 LogicalExpand | N1 | `ir0.json`、expanded logical view |
| N3 | 固定 placement 与 IR-1 | N2 | 无 FusionPlan/IR-2 的 `ir1.json` |
| N4 | naive FusionPartition 与 inter-die Action DAG | N3 | `fusion_plan.naive.json` |
| N5 | IR-2 投影与 naive intra schedule | N4 | per-die DAG/schedule + GlobalActionDAG |
| N6 | 三类 lowering、linker 与单 artifact 执行 | N5、N0 gate | `program.npup` + 单层联合 trace |
| N7 | 完整 naive Dense 负载、CLI、CI 与基线冻结 | N6 | 一键 E2E、报告、golden baseline |

N0 的代码修复可与 N1/N2 的纯前端工作并行，但 N6 不得在 N0 capability gate 未通过时开始集成。

## 6. 各阶段开发方案

### N0 — 现有后端能力闸门

#### 开发内容

1. 盘点并运行现有 Program 路径：
   - `program_format` 编解码与 CRC；
   - `config_helper_program` 的强异常安全、ACK/DONE；
   - cross-die P2P endpoint；
   - raw-byte P2P、FP16/FP32/RNE 的 standalone `LOCAL_REDUCE`，以及现有
     collective 内部 `REDUCE_COMPUTE`；
   - GEMM compute record；
   - SRAM alloc/bind、DTE issue/wait；
   - collective program image 和 endpoint session 上限。
2. 复用现有 fixture 生成一个手写的 2 die × 1 core、双 owner TP=2 RS 程序：
   - 两端各执行 partial GEMM；
   - chunk 0：rank 1 发给 owner rank 0；
   - chunk 1：rank 0 发给 owner rank 1；
   - 两端各将 local partial 与 remote partial 按 rank 序 FP32 accumulate、RNE 为 FP16 输出；
   - 完成 ACK/DONE。
3. 分开运行 timing oracle 与 functional oracle。
4. 形成 capability report：`supported / repair / blocked`，记录对应测试和代码位置。
5. 若能力缺失，只修复阻塞 naive E2E 的最小集合；不扩展 optimized collective。

#### 开发目标

确认 `ProgramArtifact → config_helper_program → simulator` 已能承载首版的
GEMM、跨 die P2P、本地 reduction 和控制包络。

#### 要达到的效果

- 手写 2-die artifact 无死锁完成。
- SEND/RECV bytes、dtype、FSM/tag 成对。
- reduction 数值与 CPU oracle 一致或满足已声明 tolerance。
- 重复运行 trace digest 稳定。
- 任何一项失败都形成 N6 的前置阻塞项，而不是由前端绕开。

#### 退出条件

`U3-T`、`U3-F` 对应能力通过；能够明确列出将被前端复用的 API。

---

### N1 — 工程骨架、Schema 与 PassManager

#### 开发内容

1. 建立 Python package、CLI 骨架和测试目录。
2. 实现 IR-0、IR-1、FusionPlan/FusionAction、IntraDieDAG、
   IntraDieSchedule、GlobalActionDAG、LinkedProgramManifest 的 dataclass/schema。
3. 实现 canonical JSON：
   - 稳定字段顺序；
   - 明确 `schema_version`；
   - enum 严格解析；
   - 64-bit bytes/address；
   - 未知字段和缺失必填字段报错。
4. 实现 PassManager 状态机，编码唯一合法顺序。
5. 实现 policy/lowering registry，只注册 `naive`。
6. 实现统一错误类型和诊断路径，例如
   `ir1.instances[P0].fused_ops[1].plan...`。

#### 开发目标

先固定模块边界、序列化契约和 pass 顺序，使后续开发不会绕过 FusionPlan 或修改上游对象。

#### 要达到的效果

- 所有 Schema 可 round-trip，序列化字节稳定。
- 在没有 FusionPlan 时调用 `ProjectToIR2` 必须失败。
- 选择 `swizzle_topo` 或 `optimized` 必须明确报 unsupported。
- 同一输入两次编译得到相同 ID 和 JSON digest。

#### 退出条件

Schema/serde/pass-order/unsupported-policy 单测全部通过，CLI 可执行
`validate-spec` 和 `dump-empty-pipeline`。

---

### N2 — Dense IR-0 与 LogicalExpand

#### 开发内容

1. 实现 analytic Llama-like Dense 前向模板：
   - QKV projection；
   - attention coarse op；
   - O projection；
   - Gate+Up；
   - Down；
   - norm/residual/activation 等必要节点。
2. 实现 `TensorValue` producer/consumer、logical layout、sharding 与 alias 信息。
3. 实现闭式 `ShardingDerivation` 和 `CollectiveInsertion`。
4. 支持静态多维 `ProfileKey`；首版 YAML 必须显式给出
   `prefill_tokens/decode_tokens/num_seqs/context_sum/context_max/kv_pages`
   （`expert_load` 可为空），不从单一 `t_bucket/M` 猜测其余维度；不实现在线 arrival/scheduler。
5. 实现 `LogicalExpand`：
   - layer 展开；
   - 静态 profile 展开；
   - 保留稳定的 layer/op/value ID。
6. 实现 `FusionSemanticValidator` 的首版必要规则：
   - 凸子图和 boundary value；
   - 同 stage/phase/group；
   - partial GEMM reduction axis 与 RS 匹配；
   - bias/activation 不得位于 reduction 前；
   - 外部 consumer、effect/alias 安全。
7. 生成候选池，但此阶段不选择 FusionPartition。

#### 开发目标

从模型配置得到数学上正确、可验证、与 placement 无关的完整 Dense 前向逻辑图。

#### 要达到的效果

- 参数量、每层 GEMM FLOPs 和 collective bytes 对解析式。
- 行并行 GEMM 的输出明确标为 partial，必须经 reduction completion 才能被后处理消费。
- IR-0 中没有 die/core/port 信息。
- 同一 ProfileKey 生成确定的图；不同 ProfileKey 不共享错误 shape。

#### 退出条件

完成 `前端建模方案` 验证阶梯中适用于 Dense 前向的部分：covered linear parameter、
每个 GEMM 的 `2MKN`、AllGather/ReduceScatter bytes；不以训练 `6ND` 作为本 MVP 验收。非法
`GEMM → bias/activation → RS` fixture 被拒绝。

---

### N3 — 固定 Placement 与 IR-1

#### 开发内容

1. 实现 `PhysicalFabric` 和 `GroupRegistry` 的解析与验证。
2. 实现 deterministic compact placement：
   - 支持显式 die list；
   - 自动模式使用固定、可复现的 row-major 规则；
   - 校验 group size、die 重复和越界。
3. 生成 IR-1：
   - rank → die；
   - pair route；
   - hop/transit die；
   - port/link/link_group 资源关联；
   - resource capacity；
   - canonical traffic profile。
4. 普通 op、value、candidate FusionGroup 保留稳定逻辑 ID。
5. 添加阶段不变量：N3 输出中不得出现 FusionPlan 或 IR-2 node。

#### 开发目标

将逻辑 workload 绑定到确定的 die mesh，为 naive collective plan 提供唯一的 peer 和 route 依据。

#### 要达到的效果

- `ir1.json` 可以独立检查每个 rank 的 die、第一跳、最后一跳和 transit path。
- TP=2/TP=4 的 mapping 与手算一致。
- 不相交 group 不会错误共享静态带宽负载。
- 修改 placement 后只从 N3 起重算。

#### 退出条件

2×1、2×2 fabric 的 route/resource-incidence golden 测试通过，IR-1 中仍无 action 顺序。

---

### N4 — Naive FusionPartition 与 Inter-die Action DAG

#### 开发内容

1. 实现 `NaiveFusionPartition`：
   - 只选择已通过语义校验的
     `[row_parallel_partial_gemm, ReduceScatter]`；
   - 首版不把 bias/residual/activation 纳入 region；
   - 其他算子保持普通或 standalone collective。
2. 实现 `NaiveInterDiePolicy`，使用确定性 baseline：
   - RS 输出按 canonical logical shard 切 chunk；
   - `chunk_owner = canonical rank`；
   - `output_permutation/inverse_permutation = identity`；
   - source rank 按升序向 owner 发送 partial；
   - owner 按固定 rank 顺序 reduce；
   - phase 间使用显式 WAIT/BARRIER；
   - route 只从 IR-1 推导，不支持 source routing。
3. 生成每个 rank 的完整 `FusionAction`：
   `COMP/SEND/RECV/REDUCE/WAIT/BARRIER`。
4. 生成确定的 logical channel/event，具体 tag/token 留给 linker。
5. 实现 Action DAG 验证：
   - SEND/RECV 一一配对；
   - bytes/dtype/slice/peer 一致；
   - deps 无环；
   - 每个输出 chunk 恰好完成一次 reduction；
   - 后继只能依赖 reduction completion。
6. 保留 `InterDiePolicy` 接口；不实现 ring/tree/swizzle 搜索。

#### 开发目标

在不做任何优化搜索的情况下，把 GEMM+RS 的数学依赖完整展开为可执行、可投影的 per-rank Action DAG。

#### 要达到的效果

- TP=2 时能清楚看到两个 owner chunk 的固定收发与 reduction。
- TP=4 时每个 chunk 的贡献次数、消息数和总 bytes 正确。
- naive plan 不改变输出 shard layout。
- plan 不依赖旧 JSON `PlanTier0Collective` 重新生成 peer/barrier。

#### 退出条件

`fusion_plan.naive.json` 通过 pairing、DAG、bytes、layout 和 numerical-order 静态检查。

---

### N5 — ProjectToIR2 与 Naive Intra-die Schedule

#### 开发内容

1. 实现 `ProjectToIR2`：
   - ordinary op → ordinary semantic node；
   - standalone collective plan → standalone action node；
   - FusionAction → per-die COMP/SEND/RECV/REDUCE/WAIT；
   - 多跳 flow → transit die 上的 TRANSIT；
   - 所有节点写入 `NodeOrigin`。
2. 实现 `NaiveIntraDiePolicy`：
   - core 使用固定 round-robin 或配置指定；
   - endpoint 选择与 C2C port 一致；
   - NoC 使用确定性最短路；
   - SPM 使用顺序 allocation，不做复用和 bank 优化；
   - schedule 使用 DAG 拓扑序；
   - fused region 保留 GEMM 完成 → RS 完成的 barrier，不尝试 overlap。
3. 实现 buffer/lifetime/capacity 检查，超限直接失败。
4. 构建 `GlobalActionDAG`，验证跨 die deps 和 entry/exit event。
5. 输出语义 DAG 与 schedule 两个文件，避免调度决策写回语义图。

#### 开发目标

把已经确定的跨 die plan 转成每个 Die 上可执行的 naive schedule，同时保持后续替换 intra policy 的边界。

#### 要达到的效果

- 任一融合节点都可回溯到 `(plan_id, rank, action_id)`。
- 缺 core/port/route/buffer binding 的 DAG 不能进入 lowering。
- transit die 能看到对应 flow 的 ingress/egress 占用。
- 同一 IntraDieDAG 可在未来交给 optimized policy，而无需重建 FusionPlan。

#### 退出条件

`U0-P`、`U0-M`、SRAM capacity 和 2×2 TRANSIT 静态检查通过。

---

### N6 — 三类 Lowering、ManifestLinker、Finalizer 与统一执行

#### 开发内容

1. 实现 `CoarseLowering`：
   - 普通 GEMM/attention/elementwise 映射为现有稳定 compute/cost record；
   - 保留输入输出 buffer 和依赖。
2. 实现 `StandaloneCollectiveLowering`：
   - 只翻译 N4/N5 已决定的 standalone action；
   - 首版优先支持负载实际需要的 AllGather；
   - 不调用 legacy planner 重选算法。
3. 实现 `IsaRegionLowering`：
   - 按 FusionAction 顺序生成 GEMM、raw-byte P2P endpoint、standalone
     `LOCAL_REDUCE`、WAIT/BARRIER；独立同 Die collective 才可使用其既有
     `REDUCE_COMPUTE`；
   - 使用 N5 的 core/route/buffer/schedule；
   - 不进行 Swizzling 或 double buffering。
4. 实现最小 Python `ManifestLinker`：
   - 合并三个 fragment；
   - 生成地址/symbol/relocation 声明；
   - 合并 SRAM region 和 lifetime 声明；
   - 保留逻辑 channel/token/event symbol；
   - core group；
   - start/terminal/ACK/DONE envelope 声明；
   - SEND/RECV、permutation 和 consumer layout 终检。
5. C++ `ProgramArtifactFinalizer` 分配最终 tag/token/group/event ID，构造
   `ProgramArtifact`，调用现有 validator 和 encoder。
6. 用单一 `npusim --program program.npup` 运行。
7. 保存 compile manifest、artifact digest、trace 和 validation report。

#### 开发目标

让一个包含普通计算、独立 collective、naive GEMM+RS region 的静态 workload 在同一 strict timeline 上完成。

#### 要达到的效果

- 不启动第二个 helper，不拼接两次模拟时间。
- 单层 TP=2 负载无死锁完成。
- 所有 active core 收到唯一、正确的 control envelope。
- timing trace 能看到 ordinary/standalone/fused action 的真实先后关系。
- functional oracle 验证每个 RS 输出 shard。
- artifact 加载失败时不污染 simulator 全局状态。

#### 退出条件

`U1/U2/U3-T/U3-F` 通过，生成可重复执行的 `program.npup`。

### N7 — 完整 Naive 负载、CLI、CI 与基线冻结

#### 开发内容

1. 完成单命令 runner，例如：

   ```bash
   python -m llm.frontend.wafer_frontend.cli run \
     --spec notes/frontend/examples/naive_dense_tp2.yaml \
     --out build/frontend-naive-tp2 \
     --npusim build/npusim
   ```

2. 固定三层验收案例：

   | Case | 用途 | 配置 |
   |---|---|---|
   | E0 | 最小通信/数值 smoke | 2 die × 1 core，单 partial GEMM+RS |
   | E1 | 混合 lowering 集成 | 2 die，1 个 Dense block，静态 prefill ProfileKey |
   | E2 | 多 die/TRANSIT/多层 | 2×2 die，TP=4，2 个小型 Dense block |

3. 如运行成本可接受，再增加非阻塞 nightly：
   - 更多 layer；
   - 静态 decode ProfileKey；
   - 不同 compact placement。
4. 生成统一报告：
   - 配置与各级 IR digest；
   - policy 固定为 naive；
   - op/action/flow 数量；
   - analytic 与 observed bytes；
   - makespan；
   - ACK/DONE；
   - peak SRAM；
   - functional/timing validation 状态。
5. 将 E0/E1 纳入 CI，E2 依据耗时进入 CI 或 nightly。
6. 冻结 naive golden：
   - JSON digest；
   - program artifact digest；
   - 关键 trace invariant；
   - 不冻结容易受微小成本模型变化影响的完整周期序列。
7. 写明后续 optimized policy 的接入步骤和禁止修改的 ABI。

#### 开发目标

把首版从“若干模块可用”提升为可重复的一键端到端流程，并形成未来优化版本的可信 baseline。

#### 要达到的效果

- 新环境中按文档命令可从 YAML 生成并执行负载。
- E0/E1 连续多次运行结果确定，无死锁、无泄漏。
- E2 的 TRANSIT、端口和 D2D bytes 守恒。
- 接入未来 optimized policy 只需新增 policy implementation 并注册，不修改 IR Schema、ProjectToIR2、lowering 或 linker。
- 当前结果只声明“naive E2E 已跑通”，不声明 Swizzling 或 intra 优化收益。

#### 退出条件

下文 §8 的完成清单全部满足，naive baseline 和接口说明经过评审。

## 7. 阶段依赖与失败处理

```text
N0 backend capability ───────────────────────────────┐
                                                     ▼
N1 contracts → N2 logical → N3 placement → N4 plan → N5 schedule → N6 link/run → N7 E2E
```

硬性停止条件：

- N0 的 FP reduction 或 cross-die endpoint functional test 失败：禁止进入 N6 集成。
- N2 的 FLOPs/bytes 不对：禁止通过调整 simulator cost 掩盖。
- N3 尚未 placement：禁止运行 FusionPartition cost/InterDiePolicy。
- N4 没有完整 `rank_programs`：禁止 ProjectToIR2。
- N5 没有 route/bank/buffer/schedule：禁止性能模拟。
- N6 中出现两个 helper 或两条独立 timeline：不算端到端通过。
- optimized 配置被偷偷映射为 naive：测试必须失败。
- SRAM、endpoint session 或消息大小超限：显式报错；首版不自动搜索替代方案。

## 9. 后续优化接口的预留方式

naive E2E 完成后，后续开发只能通过以下替换点加入技术点：

| 后续能力 | 替换接口 | 不应修改 |
|---|---|---|
| Fusion region 搜索 | `FusionPartition` | IR-0/IR-1 Schema、lowering ABI |
| 跨 die Swizzling | `InterDiePolicy` | ProjectToIR2、ISA opcode 语义 |
| 片上优化 | `IntraDiePolicy` | FusionPlan 的 peer/chunk/deps |
| 新普通算子成本 | `CoarseLowering` | ManifestLinker/finalizer/control envelope |
| 新 collective 算法 | plan implementation | strict SEND/RECV/REDUCE contract |
| 动态执行 | `RegionCall`（后续） | 静态 ProgramArtifact 路径 |
| 大规模搜索 | conditional surrogate（后续） | 精确 E0/E1/E2 baseline |

未来的 naive/optimized 对比必须满足：

- 同一模型、ProfileKey、placement 和普通算子 cost；
- 同一 ISA region lowering；
- 仅 policy 产生的 partition/Action DAG/schedule 不同；
- 两边均经过同一 linker 和 simulator；
- 不允许 naive 走 JSON、optimized 走 ISA。

这保证首版 naive 工作不会被丢弃，而是成为两个优化技术点的可验证基线。
