# S1–S3 后续开发方案：完整训练与推理负载的 Naive 执行评估

## 1. 目标、范围与完成口径

本方案承接《前端建模方案.md》，目标是把其中 S1、S2、S3 描述的训练与推理负载
逐步变成可在 WaferAI-SIM 中执行、可重算、可回归的统一 ProgramArtifact。

本轮开发采用 naive-first：

- 必须端到端跑通 S1 Dense 前向、S2 Dense 完整 train step、S3 MoE train/infer；
- 必须正确建模 shape、依赖、FLOPs、通信、内存生命周期、路由、调度和 simulator timeline；
- 不要求计算 primitive 产出最终训练权重或推理 token；
- collective 的非零 reduction、数据搬运、地址和生命周期仍须保留 functional oracle；
- inter-die 与 intra-die 两个优化技术点只冻结可替换接口、provenance 和对比协议；
- 本轮不实现 optimized、swizzle 或 bank-aware policy，不伪造优化结果。

因此必须区分两个完成状态：

1. S1-N / S2-N / S3-N：该阶段的 naive workload 已完整端到端执行，可用于性能评估。
2. S1-R：原文要求的 naive/optimized 研究验收，包括真实 2×2 消融矩阵。

本方案的当前开发承诺是完成 S1-N、S2-N、S3-N 和 optimization-ready。由于用户明确要求
暂不实现 optimized policy，原文意义上的 S1-R 不能随 S1-N 一起标记完成。S1-N 完成后应
立即允许 O1/O2 与 S2/S3 并行开发；只有真实 optimized 实现进入 registry、通过同一后端
门禁并产出四格消融结果后，才允许关闭 S1-R。

在线请求调度与动态 RegionCall 记为独立的 S1-Ext。它有研究价值，但不是原 S1 的验收项，
也不阻塞 S1-N 或 O1/O2。

本方案不依赖飞书中无法随仓库展示的内容。所有声明、公式、case、golden 和退出条件必须
在本文件、schema、测试或 checked-in report 中可见并可执行。

沿用原方案的始终不覆盖项：KV 抢占/驱逐、投机解码、前缀缓存复用、自动搜索 PP bubble
调度、通用 sharding propagation 不动点。它们可以在未来单独立项，但不影响本方案的
S1-N/S2-N/S3-N 完成判定。

## 2. 当前基线与 S1 声明差距

### 2.1 已有基线

当前 N0–N7 已完成：

- Dense 静态 prefill 的 IR0 → IR1 → IR2 → GlobalAction → lowering → linking；
- TP/SP、mesh placement、route、TRANSIT、SRAM root/view、ProgramIo；
- naive GEMM+ReduceScatter 与 standalone AllGather；
- E1 TP2/L1/2×1 和 E2 TP4/L2/2×2 timing 端到端；
- analytic/observed D2D bytes、ACK/DONE、drain 和 makespan 报告。

这些结果是后续阶段的不可回退基线，但不等于《前端建模方案.md》的 S1 已完成。

### 2.2 S1 覆盖声明：当前实到 3.5 / 6

| S1 原声明 | 当前事实 | 计分 |
|---|---|---:|
| TP/SP 并行 | 已有 TP1、TP2、TP4 与 SP 闭环 | 1 |
| PD 融合与分离 | schema 强制只有一个 instance，无法形成真实 P/D 两套 placement | 0 |
| die mesh 嵌入与等效带宽 | N3 route/resource/capacity 与 TP4 TRANSIT 已闭合 | 1 |
| 跨 die KV 传输 | 没有逐层持久 K/V buffer、handoff、admission 和 reshard | 0 |
| GEMM+collective naive/optimized 对比 | 只有 naive Action DAG，优化侧不存在 | 0.5 |
| 单 die 计算通信图 | IR2 DAG/Schedule/GlobalAction 已闭合 | 1 |

合计 3.5 / 6。这里的计分规则固定为：`0` 表示该条目的两侧能力都不存在或主能力不存在；
`0.5` 只表示对比条目已有可执行 baseline、但缺少 optimized 对照；`1` 表示该条目要求的
全部能力和端到端验收均已完成。`0.5` 不是按单测数量折算，也不能用于宣称技术点已验证。

### 2.3 S1 顶层验收：当前只计 1 / 3

| S1 原验收 | 当前状态 |
|---|---|
| 参数量、FLOPs、per-layer 通信量的完整解析式门禁 | 有局部 sample oracle，但没有覆盖 prefill/decode/PD/train-forward 的完整 case matrix，暂不计通过 |
| 端到端跑通 | 静态 prefill naive E1/E2 已通过，计通过 |
| inter × intra 2×2 消融可复现 | 不可能；没有任何 optimized policy |

后续不得用“E1/E2 已跑通”替代另外两项验收。

### 2.4 为什么当前不可能做 2×2 消融

policies/registry.py 虽声明了八种 registry kind，但与两个研究技术点直接对应的有效候选只有：

    INTER_DIE: naive
    INTRA_DIE: naive

schema 中存在 swizzle_topo / optimized 枚举，不代表实现存在。阶段 0 收口后：

- production registry 只激活 inter-die naive、standalone direct_all_gather 和 intra-die naive；
- inter-die swizzle_topo 与 intra-die optimized 仅为 declared-but-unavailable，选择后在任何
  pass 执行前抛出 StageNotImplemented，绝不 fallback；
- compile_naive 和 runner 已只通过 registry 创建 policy，并把 selection、implementation
  schema、config digest 和 capability IDs 写入 context、receipt 与 report；
- 全库仍没有可执行的 swizzle 或 optimized implementation。

所以当前仍只有 baseline，不能验证两个技术点，也不能生成四个可比较的 artifact；变化只是
该事实现在由机器可读 provenance 和 fail-closed registry 证明，而不是依赖人工 grep。

### 2.5 当前 schema 的硬门禁

schema/experiment.py 和 schema/logical.py 当前明确限制：

- workload.mode 必须是 infer；
- role=train 被拒绝；
- parallel.instances 必须恰好一个；
- replicas、dp、pp、ep 必须等于 1；
- IR0Template.job 必须是 INFER；
- Dense logical mesh 必须只有 TP 轴；
- dynamic region dispatch 被拒绝。

checked-in examples 只有 naive_dense_tp2.yaml 与 naive_dense_tp4.yaml，二者都满足
decode_tokens = 0。虽然 unit 中有 decode 形状测试，但 decode 没有经过 placement、schedule、
lowering、ProgramIo 和 simulator，因此不能声明 decode 端到端支持。

## 3. 开发原则

### 3.1 负载评估而非模型结果

本方案评价的是执行情况，不要求输出真实 token 或训练后的参数。每个算子至少必须具备：

- typed workload 与精确 input/output shape；
- FLOPs、读取/写入字节、状态量和 collective bytes 的解析式；
- producer/consumer、phase、stage、effect 和 lifetime；
- 对应 backend timing/cost contract；
- 可被 schedule、lowering、linker 和 simulator 接受的 record。

不能用空算子或常数延迟代替缺失工作量，也不能把 unsupported 标记改名为 pass。

### 3.2 单一执行时间线

每个静态 profile 或完整 train step 必须链接成一个 ProgramArtifact，并在一次 simulator
运行中完成。禁止把前向、反向、collective、不同 PP stage 或 P/D 两侧分开模拟后相加。

### 3.3 Naive 也必须精确

naive 指策略简单，不代表 contract 宽松。所有 naive policy 必须：

- deterministic、content-addressed、无隐式 fallback；
- 完整保留 route、rank、chunk、stage、phase、bucket 和 token lineage；
- 返回前通过 cross-validator；
- 使用真实资源容量，不用无限 SRAM 或虚假 bandwidth 让 case 通过。

### 3.4 优化接口不得是装饰

registry 必须成为 production compiler 的唯一 policy 选择入口。枚举、声明但无 factory 的条目
必须显式 StageNotImplemented，不得回退 naive。receipt 与 report 必须记录：

- registry kind、implementation name 和 implementation schema version；
- policy config canonical digest；
- factory/build identity；
- 输入/输出 artifact digest。

### 3.5 每阶段都有独立退出门禁

阶段未满足其 analytic、schema、integration 和 runtime 四类门禁时，不进入下阶段，也不更新
coverage 声明。breaking schema 必须升版并一次迁移 producer、serde、validator 和 golden。

### 3.6 Digest 重新冻结政策

digest 只在明确的 schema、policy 和 backend 版本周期内稳定，不承诺跨 breaking ABI 保持
字节不变。任何 golden digest 变更都必须在同一变更中附带：

- 变更原因，以及对应的 schema/policy/backend 版本变化；
- 旧 digest、新 digest 和受影响的 case 清单；
- action/record/flow/bytes/memory/makespan 等语义差异说明；
- 自动重生成命令或工具输出；
- review 记录，明确该变化是预期重冻结而不是回归掩盖。

禁止因为测试变红直接更新 golden，禁止手工改写 digest，禁止在没有语义差异解释时批量
重新冻结。若只有 digest 变化而结构、版本和预期语义都未变化，应按非确定性或 provenance
缺陷处理。阶段 0 仅允许因新增 policy provenance 重新冻结；阶段 1b 的地址 ABI、allocator
或 lifecycle breaking 变化必须建立新的 baseline epoch，不得声称 E1/E2 artifact bytes 不变。

## 4. 目标架构增量

### 4.1 顶层输入

ExperimentSpec vNext 需要把 WorkloadSpec 改成严格 tagged union：

- InferWorkload：static profile、shape distribution、request trace、generator；
- TrainWorkload：data spec、step spec、explicit microbatch sequence；
- 多个 ParallelInstance：prefill、decode、both、train；
- 多轴 parallel：tp、sp、dp、pp、ep、replicas；
- TrainStructure：global/micro batch、grad accumulation、PP schedule、recompute、
  gradient bucket、ZeRO/FSDP、optimizer；
- MoESpec：expert count、top-k、capacity、drop policy、load distribution。

旧 v1alpha2 继续 fail closed；不原地放宽。

### 4.2 IR 与 workload

需要新增或启用：

- 完整 Dense forward：embedding、RoPE、attention、MLP、residual、LM head、sampling/CE forward；
- inference request/profile：ragged request shape、query-key pairs、KV page/span；
- persistent KV value 和跨 instance cross edge；
- FWD、DGRAD、WGRAD、RECOMPUTE、OPTIMIZER phase；
- attention/norm/activation/embedding/CE backward workload；
- gradient bucket、optimizer state、parameter/gradient ownership；
- MoE gate、dispatch、expert GEMM、combine 与 AllToAll。

每个新增 workload 都要有 graph validator 和解析式 oracle，不能只增加 enum。

### 4.3 物理内存与 backend

完整推理/训练不能继续依赖 64 KiB、无复用的全程序 SRAM。该能力分成最小状态底座与可扩展
内存两部分：

- 阶段 1a 提供 HBM-backed persistent KV/optimizer identity、显式 DMA 和最小
  STEP/PERSISTENT lifecycle；
- 阶段 1b 再提供 TASK/LAYER/MICROBATCH/STEP/PERSISTENT 完整生命周期、root/view、alias、
  lifetime reuse、spill，以及 region-relative/扩宽地址 ABI；
- parameter、activation、gradient、optimizer state 和 KV 都必须有明确 backing；
- persistent KV 与 optimizer state 跨 action/iteration 保留；
- 新 backward/optimizer/MoE record 的 typed coarse timing lowering；
- AllReduce、ReduceScatter、AllGather、AllToAll 的 naive exact lowering。

扩宽地址或新增 opcode 属 breaking backend ABI，必须保留 codec/selftest/finalizer/ProgramIo
四层门禁。

### 4.4 Runner 与报告

现有 E1/E2 hard-coded case identity 要升级为 versioned CaseManifest。报告至少新增：

- workload mode、profile/request/step identity；
- phase/stage/microbatch/op/collective counts；
- forward/backward/optimizer FLOPs；
- activation/gradient/KV/weight/optimizer bytes；
- NoC/D2D/HBM observed 与 analytic bytes；
- peak SRAM/HBM、reuse、spill；
- makespan、PP bubble、MFU-like workload utilization；
- infer 的 TTFT/TPOT/queue，train 的 step time/samples-per-second；
- policy implementation identity 和 capability status。

## 5. 分阶段开发

阶段编号表示主题，不表示所有阶段必须串行。固定依赖为：

    基础：阶段 0 → 1a
    S1-N：阶段 1a → 2 → 3 → 4 → 6
    S1-Ext：阶段 4 → 5（独立扩展，不阻塞 S1-N）
    优化研究：阶段 6 → O1、O2（与 S2/S3 并行）
    S2-N：阶段 6 → 1b → 7 → 8 → 9 → 10 → 11
    S3-N：阶段 11 → 12 → 13 → 14

阶段 0/1a 是 S1–S3 共用底座；阶段 1b 是大模型和 S2 前的扩展门禁。不得为训练或 MoE
复制第二套 schema、allocator、linker 或 runner。每个后续阶段必须继续运行所有已完成阶段
的 regression。

工作量使用相对规模：S 表示局部 schema/producer/test 变更；M 表示跨 2–3 层并新增端到端
case；L 表示跨 schema、编译链、backend/runtime 的 breaking 或多子系统开发。该标记用于
排期与并行拆分，不是工期承诺。

### 阶段 0（M）：声明校正、Capability Manifest 与 Policy Wiring

**开发内容**

- 新增 versioned CapabilityManifest，把 S1/S2/S3 每项能力标为 unsupported、
  schema-only、unit-only、e2e-timing 或 e2e-functional；
- 将本文件的覆盖表和验收表变成 checked-in machine-readable case matrix；
- 让 compile_naive/runner 从 PolicyRegistry 创建 inter/intra policy；
- 激活 naive factories；为 swizzle_topo 和 optimized 只声明接口与 available stage；
- policy selection、config digest 和 implementation ID 进入 context、receipt、report。

**开发目标**

建立唯一、不可冒认的能力真相，消除“枚举存在即实现”和“unit 覆盖即 E2E 覆盖”。

**要达到的效果**

- 选择 naive 可复现当前 E1/E2；
- 选择未实现 optimized 明确失败且绝不 fallback；
- fake Protocol implementation 可在测试中替换 naive 并保持完整 provenance；
- 当前状态明确显示 S1=3.5/6、验收=1/3。

**退出门禁**

registry、compiler、receipt、report tamper focused 全绿；本阶段若只因新增 policy provenance
改变 E1/E2 digest，必须按 §3.6 提交差异和 review 后重新冻结，其他结构与执行语义不得改变。
后续 breaking 阶段不继承“artifact bytes 不变”的承诺。

**实现状态（2026-08-16）**

阶段 0 已完成。checked-in 真相位于
`notes/frontend/baselines/stage0-policy-provenance-v1/`：包含 E1/E2 完整持久运行目录、
CaseMatrix、CapabilityManifest 与 baseline review。E1/E2 ProgramArtifact SHA、record、
relocation、通信量和 makespan 均与原 golden 相同；仅 pipeline/context/report 因 policy
provenance 升版。当前声明由测试重算为 S1=3.5/6、验收=1/3，S2/S3 全部 unsupported。

### 阶段 1a（M）：最小持久状态与数据搬运底座

**开发内容**

- 引入 HBM-backed parameter/KV/state BufferBinding 和显式 DMA load/store；
- 为逐层 KV、request/instance 和未来 optimizer state 建立稳定、不可冒认的状态身份；
- 增加最小 STEP/PERSISTENT lifecycle，不在本阶段实现通用 reuse、spill 或 alias；
- ProgramIo 支持 persistent input image、KV state seed/probe 和跨 action 保留；
- 地址继续受当前 ABI 与容量门禁约束，超过范围的小模型明确 fail closed。

**开发目标**

以最小改动解除“无持久状态”限制，优先支撑小型 decode、PD 和 KV handoff 的精确 E2E。

**要达到的效果**

- KV 在整个 request 及 P→D handoff 期间保持同一逻辑身份；
- parameter/KV 的 HBM↔SRAM 搬运进入 action、bytes 和 timeline；
- optimizer state identity 可被 S2 复用，但本阶段不宣称 optimizer 已执行；
- S1 case 不依赖 breaking 地址扩宽或通用 allocator 重写。

**退出门禁**

小型单核 HBM→SRAM→compute、逐层 KV 持久化、P→D handoff 和非法 state identity 的
schema/C++/runtime 测试全部通过；当前地址范围外的 case 必须稳定拒绝。

### 阶段 1b（L）：地址 ABI、复用与 Spill 扩展

**开发内容**

- 将 compute/data address 扩宽或改为可验证的 region-relative ABI；
- 补齐 TASK/LAYER/MICROBATCH/STEP/PERSISTENT lifecycle；
- 增加 root/view、alias、lifetime reuse、spill、prefetch 和 writeback contract；
- allocator 从“全程序单调占用”升级为按真实 lifetime 复用，并精确报告 peak；
- 一次迁移 codec、schema、lowering、finalizer、ProgramIo 和既有 case。

**开发目标**

解除 64 KiB 与无复用限制，为大模型、完整训练和 MoE 提供可扩展内存底座。

**要达到的效果**

- 多层权重不要求同时驻留 SRAM；
- activation 可在 microbatch/layer 边界释放、复用或 spill；
- 大于 64 KiB 的合法负载不因 wire address 假限制失败；
- allocator 改变能反映在 HBM traffic、peak memory 和 makespan 中。

**退出门禁**

地址边界、跨层 reuse、spill/writeback、容量不足和非法 alias 的四层门禁全部通过；按
§3.6 建立新的 baseline epoch，并审阅所有受影响 case 的结构和 digest 差异。

### 阶段 2（M）：S1 Dense 前向算子闭包

**开发内容**

- 补齐 embedding、RoPE、LM head、sampling/CE forward 的 typed workload 和 cost；
- 统一 prefill、decode、train-forward 的 layer template；
- 为 Attention 明确 causal/mode/context/KV read bytes；
- 为 RMSNorm/SwiGLU 等补齐当前 timing ABI 缺失的参数和 shape 语义；
- 建立公开模型参数量、forward FLOPs、每层 TP/SP 通信量 oracle。

**开发目标**

让“完整 Dense 前向”包含模型首尾和全部非 GEMM 算子，而不是只模拟 transformer block 主干。

**要达到的效果**

- LLaMA 类 Dense 模型可从 embedding 运行到 logits/sampling 或 CE forward；
- 推理与训练前向共用相同 FWD 图；
- 每个 op 的时间来自 backend cost model，shape/bytes 可由前端重算。

**退出门禁**

参数量误差 <0.1%；forward FLOPs 与解析式一致；TP1/TP2/TP4 per-layer communication
逐项一致；HLO/FX 抽样只作为覆盖验证，不作为主 producer。

### 阶段 3（L）：S1 静态 Prefill、Decode 与 Ragged Profile

**开发内容**

- 增加 checked-in decode_tokens > 0 的 E2E case；
- ProfileKey 增加可判定的 request-shape 或 exact attention-pair 描述；
- 支持纯 prefill、纯 decode、mixed batch 和多 sequence ragged profile；
- 建模 KV read/write、page/span 和 context_sum，不把相同 M 当作相同 Attention；
- 实现多 profile domination selection、fallback 与每 profile artifact。

**开发目标**

把 decode 从 logical unit test 提升为真实 placement→artifact→simulator 路径。

**要达到的效果**

- 同 M 的 prefill/decode 产生相同线性 FLOPs，但具有不同的 attention/KV bytes；
- checked-in D1 case 含 decode_tokens > 0；
- mixed/ragged case 的 query-key pairs 与 KV HBM traffic 可解释；
- profile 无覆盖时显式失败或走已声明 fallback。

**退出门禁**

PREFILL、DECODE、MIXED 三个静态 case 均完成两次稳定运行；analytic/observed KV、HBM、
D2D bytes 闭合。

### 阶段 4（L）：S1 PD 融合/分离与逐层 KV Handoff

**开发内容**

- 放开多 instance，支持 prefill/decode/both 与独立 placement；
- 每层生成 K/V cross edge，不使用单个请求 ID 代替 payload；
- 支持 tp_P == tp_D 的直连和 tp_P != tp_D 的 KV reshard；
- 建模 decode replica 选择、persistent KV ownership、handoff completion 与 decode-start 依赖；
- PD fused 保持无 handoff，PD separated 生成真实 route/TRANSIT/buffer/runtime。

**开发目标**

补齐 S1 六项覆盖中缺失的 PD 和跨 die KV 传输。

**要达到的效果**

- 同一请求的每层 K/V 在 P→D 间有可追踪 flow；
- fused/separated 使用相同 model/profile/cost model，只改变 instance 与 cross edge；
- tp_P/tp_D 独立改变流量矩阵；
- 静态请求关键路径可分解出 KV handoff 与 decode-start 等待。

**退出门禁**

PD-F、PD-S-equal-TP、PD-S-reshard 三个 naive case 通过；logical unique bytes、replicated
bytes、per-link observed bytes 与解析式一致。

### 阶段 5（L）：S1-Ext 在线推理调度与 Region Variant

**开发目标**

## 7. 优化接口的冻结方式

本轮只留接口，不实现算法。必须做到：

1. InterDiePolicy：输入 exact IR1、FusionCandidate、route/resource profile，输出完整
   per-rank Action DAG；不得修改 graph 语义。
2. IntraDiePolicy：输入 exact semantic DAG 与 fabric，输出 core/NoC/buffer/order schedule；
   不得修改 action、flow 或 bytes。
3. 两类 policy 都提供 name、schema version、capability set、config 和 stable digest。
4. compiler 与 runner 只通过 registry 创建 policy。
5. naive 是已激活实现；swizzle_topo/optimized 是 declared-but-unavailable。
6. 未来 optimized 输出必须通过与 naive 相同的 validators、lowering、finalizer、ProgramIo 和 runner。
7. 2×2 matrix 的四个格子必须保持同一 spec、placement、profile、cost model 和 backend，只允许
   inter/intra policy identity 与其合法 schedule 改变。

阶段 6 通过后即可启动以下两个研究阶段，不依赖阶段 5、阶段 1b 或阶段 7–14。O1/O2
不属于当前 naive-first 实现承诺，本轮只冻结下述接口和门禁。

### O1（L）：Inter-die Swizzle

**开发内容**

- 在 RegistryKind.INTER_DIE 下注册真实 swizzle factory，不复用或包装 naive 输出冒充；
- 实现物理环序、chunk/owner/phase 编排和共享出口感知；
- 保持 model、placement、logical collective bytes 和 backend cost model 不变；
- 将 permutation、phase、route/resource decision 和 policy digest 写入 provenance；
- 用同一 S1 baseline 生成 naive×naive 与 swizzle×naive 两组 artifact。

**开发目标**

独立验证 inter-die 编排能否在相同语义工作量下改变链路冲突和完成时间。

**要达到的效果**

- logical FLOPs、collective payload 和数值 oracle 与 naive 完全一致；
- route、shared-resource work、phase overlap 和 makespan 的变化可解释；
- swizzle artifact 可重复，任一非法 permutation 或能力不匹配均 fail closed；
- 不依赖 S2/S3 扩展的算子或 case。

**退出门禁**

swizzle×naive 单变量对照通过同一 validator/finalizer/runtime 门禁，analytic 与 observed
per-link bytes 闭合；registry 中存在可执行 factory，报告不得再标记该格 unsupported。

### O2（L）：Intra-die Optimized Dataflow

**开发内容**

- 在 RegistryKind.INTRA_DIE 下注册真实 optimized factory；
- 实现关键路径优先、bank balance、lifetime reuse 和 communication shadow；
- 只改变 core/buffer/order 的合法 schedule，不修改 action、flow、bytes 或模型语义；
- 将排序目标、bank/lifetime decision、config 和 policy digest 写入 provenance；
- 用同一 S1 baseline 生成 naive×naive 与 naive×optimized 两组 artifact。

**开发目标**

独立验证 intra-die dataflow 能否减少空闲、bank 冲突和不可隐藏通信。

**要达到的效果**

- GlobalAction DAG、route 和 logical bytes 与 naive 完全一致；
- core order、bank pressure、reuse、communication shadow 和 makespan 差异可解释；
- optimized artifact 可重复，容量、依赖或生命周期不合法时明确拒绝；
- 不依赖 S2/S3 或 S1-Ext。

**退出门禁**

naive×optimized 单变量对照通过同一 validator/finalizer/runtime 门禁，memory/bank/timeline
报告闭合；registry 中存在可执行 factory，报告不得再标记该格 unsupported。

O1/O2 与 S2-N、S3-N 并行推进；S2/S3 扩大覆盖面，但不是两个技术点主结果的前置条件。
进入实现后必须使用阶段 6 冻结的同一 S1 baseline 形成四格消融。两个单变量门禁及完整
2×2 matrix 通过后可独立声明 S1-R complete，无需等待 S2-N、S3-N 或 S1-Ext。

## 8. CI、Nightly 与性能策略

### 默认 CI

- 所有 schema/serde/stable-ID/tamper unit；
- 每阶段最小 analytic oracle；
- S1 F-P2、F-D1；
- S2 T0/T1；
- S3 M0；
- finalizer、ProgramIo、non-zero reduction oracle。

### Nightly

- S1 PD reshard；S1-Ext 完成后再加入 online trace；
- S2 PP2、ZeRO、AdamW；
- S3 skew、train、PD；
- 多层与更大 mesh；
- deterministic repeat 和容量边界。

### 大模型评估

先用小模型精确 E2E 锁正确性，再扩大 shape。若完整 artifact 的编译或仿真成本过高：

- 可以使用由精确联合仿真标定的 conditional surrogate 做搜索剪枝；
- 最终候选仍必须回到统一 simulator；
- surrogate 输出必须带 calibration domain 和不确定度；
- 禁止把单 die LUT 或解析下界当成完整 wafer 结果。

## 9. 风险与 Fail-closed 规则

| 风险 | 规则 |
|---|---|
| schema enum 先于实现 | enum/registry declaration 不计 coverage；必须有 producer+validator+E2E |
| training 用 forward×3 代替 | 禁止；必须显式 backward op 和 phase DAG |
| decode 忽略 KV | 禁止；decode case 必须有 persistent KV bytes/state |
| PD 只传 request ID | 禁止；必须逐层 K/V tensor flow |
| gradient 每权重一次 AR | 禁止；必须按 bucket/cadence |
| MoE 使用 rand gating | 禁止作为验收；必须 deterministic assignment |
| 大模型借无限 SRAM 通过 | 禁止；必须 HBM/residency/reuse 或明确容量失败 |
| optimized 不存在却生成矩阵 | 禁止；declared-but-unavailable 必须失败 |
| 多段模拟时间相加 | 禁止；每个 case 一个 ProgramArtifact、一次 timeline |
| timing-only 被称数值正确 | 禁止；报告必须区分 timing、transport functional 与 model functional |

## 10. 分阶段完成定义

### 10.1 所有完成状态的共通门禁

任一状态只有同时满足以下条件才可声明完成：

- 对应 case 在真实容量、真实 route、统一 ProgramArtifact 下执行；
- 解析式与 observed bytes/memory/timeline 已交叉验证；
- policy registry 是 production 入口，未实现选择显式拒绝；
- capability manifest、测试、报告和文档一致；
- digest 固定在明确 baseline epoch 内，任何重新冻结符合 §3.6。

### 10.2 S1-N Complete

    S1-N naive workload execution evaluation complete
    S1 research coverage = 5.5/6
    S1 top-level acceptance = 2/3
    optimization interfaces frozen

该声明包含 prefill、decode、ragged、PD/KV、train-forward、mesh 和单 die graph 的 naive E2E，
