> 文档状态：设计定稿（未实现）
>
> 需求来源：`notes/frontend/req.md`
>
> 目标：把训练/推理负载端到端映射到 WaferAI-SIM，并在其中插入 GEMM+collective 融合算子，

## 0. 决策速览

| 问题 | 结论 |
|---|---|
| IR 层数 | **3 个**：IR-0 逻辑图、IR-1 物理图、IR-2 单 Die 图 |
| IR 边界的依据 | 沿用户的搜索顺序切分，每个边界锁定一组已决定的参数，支持上游缓存复用 |
| 固定 pass 顺序 | `LogicalExpand → Placement → FusionPartition → InterDiePolicy/collective plan → per-rank Action DAG → ProjectToIR2 → IntraDiePolicy → lowering/link/simulation`（§2.2.1） |
| mesh 归属如何表达 | 算子只引用**具名 mesh**，不内联 die 列表；同一 die 可属于不同 mesh，各自独立生成 route/resource 容量签名；等效带宽还必须指定 traffic template 或具体 plan |
| SPMD 如何自动推导 | **多轴 `DeviceMesh` + 每张量 `Sharding{dim_map, partial}`**（GSPMD/DTensor 标准形式）。collective 的类型与通信量由 **sharding 差量推导**，非声明。`partial` 是让规则可推导而非硬编码的关键机制（§3.1 ⓪） |
| SPMD 的范围约束 | 采用 GSPMD 的**表示**，**不实现通用传播不动点**——推导仍走 §3.3 闭式规则；`Sharding` 用于承载与校验，不驱动通用求解器。alias 同理只保留 `alias_set` 字段 |
| IR-2 为何分两层 | `IntraDieDAG`（语义）/ `IntraDieSchedule`（决策）分离，使 `IntraDiePolicy: DAG → Schedule` 签名良定义，消融可在**同一语义**下比较两种调度；`BufferBinding` 的 `bank`/`lifetime` 是片上编排的核心决策变量 |
| `eq_bandwidth` 怎么算 | **两级模型**：mapping 先生成资源关联矩阵与 canonical traffic template 下的静态带宽；每个 Swizzling 再按 phase、bytes、共享资源和并发场景计算 plan-specific 带宽与 makespan。`bounded_saf` 还需计入逐跳整流序列化（§4.2.1） |
| 晶圆级特有的瓶颈 | **出口端口**可能先于链路饱和——默认每 die 每方向仅一个 C2C 端口，且多端口共享同一 packet/cycle 切口。值得作为独立实验维度 |
| 融合算子如何表达 | **表达成「调度」，不是新 opcode**；naive 与优化版是同一组 record/prim 的不同交错 |
| 融合的建模方式 | **算子上的候选分组（`FusionGroup`），不是一种算子类型**。候选通过语义校验后物化为 `FusedOp/FusionPlan`，再通过资源校验才能 lowering 为可执行 region |
| 三种表示都支持 | 分开写（无组）／GEMM+通信成组／自定义候选组合——共用一套 `FusionGroup` 表示；“可表示”不等于“可合法重排” |
| 融合合法性 | **两阶段校验**：IR-0 检查凸性、数据依赖、tile/reduction/layout、外部 consumer、副作用与数值契约；IR-1/IR-2 再检查 owner permutation、SRAM/buffer 与可执行性 |
| 跨 die collective 后端 | **规划与执行解耦**：JSON/IR policy 决定算法、rank/chunk/phase/peer，并按确定性路由规则推导 `expected_route`；融合区由 ISA lowering 将其展开成跨 die P2P endpoint + 本地 reduce。现有 FP16 reduction 是硬缺口（§8.1） |
| JSON 与 ISA 现状 | 两套 loader/transport **当前互斥**；`coreconfigs` 不是共同的可执行表示，不能直接拼接。需先统一成 owned `CoreCommandStream`（§8.3） |
| 两个技术点的后端归属 | **异构算子 lowering、单一执行后端**：普通计算用 JSON coarse model；非融合 collective 用 standalone strict lowering；GEMM+collective 融合区用 ISA 细粒度 lowering；三者经 `ProgramLinker` 汇成一个 strict 命令流 |
| JSON/ISA 边界契约 | `RegionManifest + BufferBinding + entry/exit event`，显式绑定 tensor slice、地址、layout、生命周期与 logical channel/event；具体 tag/token 由 linker 分配，不再使用单个 `Program_graft` + 字符串 label 的三明治边界 |
| 统一执行的前置条件 | FP16 local reduce、跨 die P2P action、strict coarse/standalone adapter、统一 prim 所有权、Program linker、functional oracle 与 mixed-stream 正确性测试（§8.7） |
| 消融如何避免后端混淆 | 目标融合区的 naive/optimized **都走同一 ISA region lowering**，只改变 Action DAG；非目标计算/collective 分别固定走同一 coarse/standalone lowering |
| 「全开」如何评估 | 静态桶优先链接成一份完整 artifact 做一次精确仿真；规模过大时才使用带边界条件的多保真模型，并用小规模多 die 联合仿真校准交互误差（§8.8） |
| surrogate 是什么 | **由 inter×intra 联合精确仿真标定的条件代理模型**，用于大规模剪枝/多保真闭环；输入含 plan、物理映射、并发与内存状态，输出带不确定度的 makespan/边界资源轨迹。不是单 Die 标量 LUT，也不是真值（§8.8） |
| PD 融合/分离如何表达 | IR-0 中 **`Instance` 的数量与 role**；`cross_edges` 空 = 融合，非空 = 分离 |
| 训练如何表达 | `IR0.job=TRAIN` + `TrainStructure`；算子带 `phase`(FWD/DGRAD/WGRAD/RECOMPUTE) 与 `stage`；collective 带 `role`(ACTIVATION/GRADIENT/WEIGHT_GATHER) |
| **范围按三阶段声明** | **S1 Dense 前向** / **S2 Dense 完整 train step** / **S3 MoE train-infer**，各有验收标准（§1）。未达标不得声称支持。**S1 已足以支撑两个技术点的主结果**——融合目标全在 dense 线性层内 |
| 「端到端训练」的实际边界 | 当前仅覆盖**线性层**反向；attention/norm/activation/embedding/CE loss 反向、PP 物理映射与跨 stage P2P、gradient bucket、ZeRO stage、optimizer、selective recompute 区域**均属 S2，尚未覆盖** |
| MoE 的实际边界 | 当前只能称**「合成 MoE 通信代理」**——gating 是 `rand()`、A2A 未接入 MoE 路径、无 MoE PD 版本（§10 缺口 5/6）。`req.md` 要求的 MoE 训推属 S3 |
| 梯度归约由什么决定 | **由 sharding 差量推导，非「M 被切就要 reduce」**。DP 轴恒 `partial`；SP 轴取决于该 GEMM 前后是否已 AllGather，须 layout propagation 判定。且 DDP 按 **bucket** 而非按权重发起 collective |
| `COLL.role` 为何必需 | 三类 collective 的**时间裕度差几个量级**——`ACTIVATION` 卡关键路径（融合价值最高），`GRADIENT`/`WEIGHT_GATHER` 裕度大（靠调度即可）。policy 必须读取，否则优化预算会浪费 |
| microbatch / recompute / profile | **均不在 IR-0 展开**，以 spec 形式携带，统一在 IR-0→IR-1 展开（§4.1.1）。改 `grad_accum`、`pp_schedule` 或 ProfileKey 集合时按缓存边界重算 |
| 顶层配置的唯一真相 | **`parallel.instances`**（方案 B）；不设独立的 `pd` 字段，避免自相矛盾 |
| 推理动态性的边界 | IR 表征动态性的**值域与分布**（形状动态性，分桶）；**时序动态性**不进 IR，交给调度器/trace |
| 运行形状用什么表示 | **多维 `ProfileKey`**（`prefill_tokens/decode_tokens/num_seqs/context_sum/context_max/kv_pages/expert_load`），**不是标量 M**。相同 M 可来自 prefill/decode/混合，attention 与 KV 代价差数量级（§7.3.1） |
| profile 如何选择 | **支配覆盖**——profile 须在**每个维度**上 ≥ 实际形状，取满足者中最小的；无覆盖走显式 fallback。**不是「最近桶」**，任一维向下 padding 都会低估资源（§7.3.2） |
| 加速比如何聚合 | `Σ w_b·T_base,b / Σ w_b·T_opt,b`，**不是 `Σ w_b·speedup_b`**——比值的加权平均 ≠ 平均的比值（§7.3.3） |
| weights 是常量吗 | **不是**。优化改变迭代耗时 → 排队变化 → profile 分布改变。在线场景须**逐候选配置重跑 `scheduler_model` 闭环**，直接比 makespan/延迟分位数，不加权（§7.3.4） |
| PDS 的真实缺口（更正） | `batch_size=1` **仅作用于 prefill 准入**；decode 以 `HW_CORE_CREDIT` 为上限，**`T` 不恒为 1**。真正缺陷是 `generate_prims` 把 ragged batch 压成 `B=1, T=Σtokens`，丢失每请求 context（缺口 6） |
| `tp_P != tp_D` 的现状 | **结构上不支持**——`config_helper_pds` 由 `json_template_p.size()` 推出**唯一** `tp_size` 并用于两类核。IR 层已可表达一般 reshard，仿真器支持属缺口 4；修复前 PD 实验只能跑 `tp_P == tp_D` |
| 负载输入层级 | 三层，**训练与推理对称**：统计描述 → 工作单元序列 → 送进 IR-0 的形状；用户可从任意一层进入 |
| 训练 vs 推理的第三层 | 推理是**形状分布**（profile+权重，随机需加权）；训练是**可展开为 microbatch DAG 的 spec**（`TrainStructure`，确定性）。**两者都以 spec 形式进 IR-0，展开在 IR-1**（§4.1.1） |
| 中间展开器 | 推理是**请求调度器**（离线模型 / 仿真器 `config_helper_pds`）；训练是**梯度累积 + PP schedule 展开** |
| 动态性进不进 IR 的判据 | 不是「时序 vs 形状」，而是**「确定可展开 vs 随机需模拟」**——训练的 PP 时序进 IR，推理的到达/排队不进 |
| 外部框架接入 | **框架能给 IR-0，给不了 IR-1**（无框架掌握 die mesh）；且一次只给一个配置，非扫描空间。`analytic` 为主路径，`hlo` 作覆盖度验证 |
| FusionPlan 的粒度 | **按多维 `ProfileKey` 编译**，以逐维支配覆盖选择 profile；无覆盖显式 fallback，不使用标量 M 的最近桶（§7.3） |
| 第一阶段的动态性来源 | 模式 A（静态桶编译 + 统一命令流）为主；模式 B 当前缺 strict `RegionCall`、独立 `tp_P/tp_D` 与持久 KV handoff，先作 trace 产生器（§7.2.1/§8.5） |
| 训练的覆盖范围 | 仅前向可直接跑；反向在 IR-0 层展开为 dgrad/wgrad（复用 `Matmul_f`），梯度 collective 需补 |

## 1. 范围与准确性边界

范围按**三个可验收阶段**递进声明。每阶段有明确的验收标准；
未达标的能力不得在论文或文档中声称支持。

### S1 — Dense 前向（推理 prefill/decode + 训练前向）

**覆盖**：TP/SP 并行、PD 融合与分离、die 粒度 mesh 嵌入与等效带宽推导、
跨 die KV 传输、GEMM+collective 融合的 naive/优化对比、单 die 计算通信图。

**验收**：验证阶梯 1–3 通过（参数量、FLOPs、per-layer 通信量对 Megatron 解析式）；
端到端跑通；2×2 消融矩阵可复现。

> **S1 已足以支撑两个技术点的主结果**——融合目标 GEMM+RS/AG 全部位于 dense 线性层内。
> S2/S3 增加的是覆盖面，不是核心结论。

### S2 — Dense 完整 train step

**在 S1 基础上补**（当前**全部缺失**）：

| 缺口 | 说明 |
|---|---|
| 非线性层反向 | attention（flash 反向是独立 kernel，非 3 个 GEMM）、norm、activation、embedding（scatter-add）、vocab-parallel CE loss |
| PP stage → 物理区域映射 | 现有 `Op.stage` 未绑定 die 子区域 |
| 跨 stage activation/gradient P2P | IR-0 的 `cross_edges` 目前仅 INFER |
| gradient bucket / cadence | DDP 按 bucket 而非按权重发起 collective；bucket 大小是真实调参项 |
| ZeRO / FSDP stage | ZeRO-1/2/3 通信模式差异极大，当前无 `zero_stage` 参数 |
| optimizer / update | 状态与通信 |
| selective recompute 的 checkpoint region | 现有 `recompute` 枚举未指明**哪些**区域 |

**验收**：反向 FLOPs 对 `6ND`；梯度通信量对所声明 ZeRO stage 的解析式；
PP bubble 比例对 1F1B 解析式；一个完整 step 的 timeline 可逐段解释。

### S3 — MoE train / infer

**现状：只能称「合成 MoE 通信代理」，不能称完整支持。**
`req.md` 第 28 行要求 MoE 训推，但仿真器侧 gating 是 `rand()`（§10 缺口 5）、
AllToAll 未接入 MoE 路径、无 MoE 的 PD 版本（§10 缺口 6）。

**验收**：专家负载分布可控（非 `rand()`）；A2A 通信量对 top-k 解析式；MoE PD 可跑。

### 始终不覆盖

KV 抢占与驱逐、投机解码、前缀缓存复用、PP bubble 调度策略搜索、
通用 sharding propagation 不动点（见 §3.1 ⓪ 的范围约束）。

**精度声明**：本前端产出的是**形状、通信量、依赖关系与调度**，不产出 cycle 数。
所有时间由仿真器的既有成本模型给出。前端不得像 `Gemm_rs_swizzle` 那样手工注入
`compute_cycles`——那会绕开 exu/sfu/vec 成本契约，使结果不可比。

## 2. 三个 IR

### 2.1 总览

| | **IR-0 逻辑图** | **IR-1 物理图** | **IR-2 单 Die 图** |
|---|---|---|---|
| 视角 | 纯逻辑，无物理 | die 粒度 | 单个 die 内 |
| 组的表达 | `tp0 = 4 个逻辑 rank` | `tp0 = die[0,1,4,5]` + embedding | 已消解为方向 |
| 通信的表达 | `RS, 16.78MB, group=tp0` | 同左 + 跳数/等效带宽/过境/竞争 | `SEND(dir=E, 2.1MB)` |
| 计算的表达 | `GEMM(2048,3584,4096)` | 同左（未再切分） | `COMP(chunk_c)` |
| 物理坐标 | 无 | die 坐标 | 核坐标 / 端口方向 |
| 产生者 | 解析式推导 / HLO dump / vLLM trace | expanded logical view + placement | IR-1 + 完整 standalone/FusionPlan Action DAG；随后才做 intra-die mapping、lowering 与统一 link |

三者都必须可序列化为 JSON——消融实验依赖 diff。

### 2.2 IR 边界 = 搜索顺序

这是三个 IR 如此切分的**唯一理由**：每个边界对应一个可配置参数，改动只需从该边界起重算。

| 搜索维度 | 作用位置 | 改变什么 |
|---|---|---|
| PD 融合/分离（推理） | IR-0 的生成 | instance 数量与 role、`cross_edges` |
| 并行切分 | IR-0 的生成 | GEMM 的 mnk、collective 的种类与量 |
| 确定性逻辑展开 | IR-0 内部 pass | microbatch/stage/profile 节点与 collective 语义；这是瞬时 expanded view，不新增公共 IR |
| 位置 mapping | expanded logical view → IR-1 | die placement、Group.embedding、pair route 与资源容量签名 |
| 融合划分 | 已 placement 的 IR-1 | 从已通过语义预检的候选中选择 FusionPartition，物化 FusedOp skeleton |
| 跨 die 编排 | IR-1 内标注 | collective algorithm、chunk/owner/phase/peer、expected_route 与 per-rank FusionAction DAG |
| IR-2 投影 | IR-1 + 完整 FusionPlan | 按 rank/action 确定性生成每 die 的 COMP/SEND/RECV/REDUCE/WAIT/TRANSIT |
| 片上编排 | projected IR-2 | core placement、NoC route、SPM banking、buffer lifetime 与 schedule |
| 执行 lowering/link | scheduled IR-2 → CoreCommandStream | 普通/standalone/fused 三类 fragment 与统一链接 |

### 2.2.1 唯一合法的 pass 顺序

公共 IR 仍只有三级；`LogicalExpand` 和 `ProjectToIR2` 是确定性变换，不新增第四种 IR。
编译顺序固定为：

```text
IR-0
  → LogicalExpand
  → Placement                                      # 产生带 embedding 的 IR-1
  → FusionPartition                                # 选择候选 region
  → InterDiePolicy / CollectivePlan
  → FusionPlan.rank_programs                       # 完整 per-rank Action DAG
  → ProjectToIR2                                   # 物化 flow/peer/chunk/deps/TRANSIT
  → IntraDiePolicy                                 # core placement / NoC route / banking / schedule
  → GlobalActionDAGBuilder
  → three lowerings → ProgramLinker → simulation
```

IR-0 中用户声明的 `FusionGroup` 只是经过语义预检的候选；真正的
`FusionPartition` 选择在 placement 后进行，因此可以读取 embedding/cost。Partition 与
InterDiePolicy 都只给 IR-1 填字段；**只有** `ProjectToIR2` 创建 IR-2。

以下是不允许放宽的 pass invariant：

1. `ProjectToIR2` 不得在 `FusionPlan.rank_programs` 完整前运行；图二中的 SEND/RECV
   顺序、chunk dependency、peer、bytes 和 TRANSIT 都必须来自具体 FusionAction。
2. 每个由 FusionPlan 派生的 IR-2 节点必须反向引用 `(plan_id, rank, action_id)`；普通节点引用
   `op_id`，独立 collective 节点引用 `(collective_plan_id, action_id)`。投影不得自行重选
   collective algorithm、peer 或 barrier。
3. `IntraDiePolicy` 的输入是已投影、尚未片上映射的 `IntraDieDAG`；输出才是带
   core/NoC/bank/buffer/schedule 的 `IntraDieSchedule`。
4. schedule simulation 只能消费已经完成物理映射和资源绑定的 schedule。抽象 DAG 可以做
   shape/bytes 下界剪枝，但不能产生被当作真实性能的模拟结果。

图三（`ref/intra-die优化框架.png`）的反馈环因此定义为：

```text
候选 partition / tiling
  → placement / route / banking
  → resource-constrained schedule simulation
  → latency / contention / SRAM feedback
  → 下一轮候选 partition / tiling
```

这里的 placement 包括片上 core placement；若搜索也改变 die placement，则必须回到 IR-1
重新计算 embedding、route 和 FusionPlan，不能复用旧 IR-2。禁止“先模拟抽象 DAG，再补
placement/route/banking”，因为那时端口、NoC、bank conflict 和 SRAM live range 均未定义。
序列化自检：固定同一 `FusionPartition` 时，`ir1.naive.json` 与 `ir1.swizzle.json` 的 diff
必须只出现在 `FusedOp.plan`；若同时比较 partition，额外只允许 FusedOp membership 改变。

### 2.2.1 序列化约定

本文档的 schema 用伪代码书写，其中两类写法**不是合法 JSON**，落地时按下列约定转换：

| 伪代码写法 | 含义 | JSON 落地形式 |
|---|---|---|
| `{(a, b) -> v}` | 元组作 key（如 `hop_distance`、`pair_routes`） | **记录数组**：`[{"a":…, "b":…, "v":…}, …]`。不用 `"a,b"` 拼接字符串——无法反解且易与合法 id 冲突 |
| `[0..7]` | 区间简写 | 显式枚举 `[0,1,2,3,4,5,6,7]`。die id 集合可能不连续，区间语法不具普遍性 |
| `int = 1` | 带默认值 | 字段可缺省；loader 补默认 |

三个 IR 都必须能**无损往返**（load → dump → load 得到同一对象），
这是消融实验依赖 diff 的前提（§2.2）。

### 2.3 什么不是 IR

三样容易被误认为 IR 的东西：

- **PhysicalFabric**（die 网格、D2D 带宽、NoC）——是**环境**不是程序，是 IR-0→IR-1 变换的输入参数。
- **FusionPlan / placement**——是**决策**，序列化后是 IR-1 的字段，不是独立表示。
- **JSON workload config 与 `.npup`**——是三类 lowering 的输入/片段格式，不是多个可在运行时直接拼接的最终后端。
- **`CoreCommandStream` / linked artifact**——是 lowering/link 阶段的最终执行表示，schema 属于统一后端契约（§8.3）。

#### ⓪ 多轴 mesh 与 sharding：SPMD 自动推导的载体

> **早期草稿的缺陷**：`LogicalGroup{id, size, kind}` + `Op.group_ref: str` 是**算子中心**的表示，
> 张量没有切分状态。后果是 §3.3 的四条切分规则**在 IR 里无处存放**——
> 「列并行 → 输出沿 N 分片」是关于**张量**的陈述。于是需求第 3 点「SPMD 切分自动推导」
> 实际退化成 §3.2 的查表：能跑标准 transformer，遇到 MLA/MoE 变体即失效。

两个修正：

**多轴。** 真实场景中一个张量同时被多个轴切——权重 `[K,N]` 的 K 沿 tp 切、整体沿 dp 复制；
激活 `[B,S,H]` 的 B 沿 dp、S 沿 sp、H 沿 tp。单个 `group_ref: str` 表达不了，
故改用 `DeviceMesh{axes}` + 每张量的 `Sharding{dim_map}`（GSPMD/DTensor 的标准形式）。

**`partial` 状态。** 这是让四条规则从「硬编码」变成「可推导」的关键机制
（jax 称 `Partial`，DTensor 称 `_Partial`）。行并行 GEMM 的输出即 `partial=[tp]`，
下游需要什么状态就决定了插什么 collective：

| sharding 差量 | 推导出的 collective |
|---|---|
| `partial(a)` → replicated | AllReduce over a |
| `partial(a)` → sharded(a) | **ReduceScatter** |
| sharded(a) → replicated | AllGather |
| sharded(a, dim i) → sharded(a, dim j) | AllToAll |
| 轴集合不同 | 上述的复合 |

由此获得四项此前无法可靠完成的能力：

| 能力 | 机制 |
|---|---|
| collective 类型与通信量 | 由 sharding 差量推导，非声明（`COLL.derived`） |
| RS 后的输出 layout | 就是 output tensor 的 `Sharding`，明确可查 |
| `tp_P != tp_D` 的一般 reshard | 「同一张量的两个 Sharding」的通用求解，不再手推特例（§4.3） |
| FusionGroup 可分块性 | GEMM 输出的分块维必须与 collective 的 shard 维一致——两者都是 `dim_map`，直接比对 |

**范围约束**：采用 GSPMD 的**表示**，但**不实现通用传播不动点**。
推导仍走 §3.3 的闭式规则（transformer 结构固定）；`Sharding` 的作用是
**承载并校验**结果，而非驱动一个通用求解器。这样既拿到正确性与可扩展性，
又不必重建整个 GSPMD。同理 alias 不做通用分析，只保留 `alias_set` 字段。

四点说明：

**① `kind` 必须保留 `ELEMENTWISE`/`NORM`/`ATTENTION`**——不能把图压成只有 GEMM，
否则 intra-die 优化器没有可以塞进通信阴影里的算子（需求第 7 点）。

**①′ 融合是“候选分组”，不是“算子类型”。**
早期草稿用 `Op.kind = FUSED` 表达融合，只能承载固定的 `(一个 GEMM, 一个 collective)` 二元组。
`FusionGroup` 可以表示更多相邻算子，但成员数与种类不设限只是 **IR 表达能力**，
不代表这些算子可以任意交换数学顺序：

| 表示 | 写法 |
|---|---|
| GEMM 与通信**分开** | 两个 `Op`，不出现在任何 `FusionGroup.members` 中（或所属组 `impl:"none"`） |
| GEMM + 通信**融合** | `FusionGroup{members:[partial_gemm, rs]}` |
| 带后处理的合法候选 | `FusionGroup{members:[partial_gemm, rs, bias, activation]}`，依赖顺序仍由 value DAG 锁定 |

对行并行 GEMM，rank 上的 GEMM 结果只是沿 K 维的 **partial sum**。原示例
`GEMM → bias → activation → ReduceScatter` 在通常语义下不成立：bias/residual 若在 reduction
前加入会被每个 rank 重复累加，非线性 activation 也不与求和交换。正确的逐 chunk 依赖是：

```text
partial GEMM(chunk i)
    → ReduceScatter / reduction completion(chunk i)
    → bias / residual / activation(chunk i)
```

优化来自流水重叠而不是改变数学依赖：chunk `i` 的 reduction 后处理可以与 chunk `i+1`
的 GEMM/通信并行。只有当某个算子被证明对目标 reduction 是同态、且 bias/常量只计入一次时，
validator 才能允许它跨过 reduction；不能靠算子名称白名单默认放行。

**合法性约束采用两阶段校验：**

IR-0 的 `FusionSemanticValidator` 在 placement 前验证数学等价性：

1. **凸子图与显式数据边界**——成员连通且无“出组再回组”路径；`boundary_inputs/outputs`
   必须由 `TensorValue.producer/consumers` 推导，不能只凭 `deps` 猜测。
2. **作用域一致**——不跨 stage、phase、microbatch；组内 collective 使用同一 `group_ref`。
   TP ReduceScatter 与 EP AllToAll 不得混为一个 collective domain。
3. **tile domain 可组合**——成员的 chunk/tile 必须存在形状一致或可证明的 broadcast/bijective
   映射；tile 边界、dtype、padding 与 tail tile 都必须闭合。
4. **reduction axis 与代数顺序正确**——GEMM 的 partial axis、collective 的
   `reduction_axes/reduce_op` 及 epilogue 依赖必须匹配；未完成 reduction 的 partial value
   不得流入 bias、residual、norm 或非线性算子。
5. **layout 契约闭合**——每条内部 value edge 的 producer layout 与 consumer layout 兼容；
   任何必要的 reshard/transpose 都必须是显式 action，不能被“融合”隐去。
6. **外部 multi-consumer 安全**——组内中间值若仍有组外 consumer，必须导出为 boundary value，
   保留其版本与完成 event；若计划会提前覆写、改变 layout 或延后到破坏外部依赖，则拒绝融合。
7. **副作用与 alias 安全**——RNG、状态更新、in-place 写和共享 alias 必须由 effect token/alias
   依赖排序；无法证明可重排时拒绝。
8. **数值归约契约**——ring/tree/chunk 改变浮点结合顺序时，必须满足
   `numerical_policy = bitwise | tolerance`；bitwise 模式只接受保持规定归约顺序的 plan，
   tolerance 模式也必须通过指定 accumulation dtype、舍入方式和 functional oracle。

IR-1/IR-2 的 `FusionPlanValidator` 在 mapping、chunk 和 buffer 方案确定后验证可执行性：

9. **owner/layout permutation 完整**——改变 ReduceScatter 的 `chunk_owner` 时必须生成双射
   `output_permutation` 与 `inverse_permutation`。region 出口要么显式恢复 canonical
   layout，要么为每个后继绑定新的 physical layout；两者都没有则拒绝。
10. **SRAM 与生命周期可行**——按 die/core 统计 input、partial sum、双缓冲、SEND/RECV、
    reduce scratch、epilogue output 的并发 live range，并校验容量、bank、alignment 和
    in-flight chunk 上限；超限候选只能减小 tile/chunk 或被剪枝，不能只按总 tensor bytes 判断。

`origin="declared"` 只表示候选来源，不绕过验证。Stage 5 自动发现与用户声明的组必须经过
同一 validator；失败时返回具体 value/action/resource 诊断，而不是静默退化成不同数学图。

**② `COLL.role` 不是装饰字段。** 梯度 ReduceScatter 与激活 ReduceScatter 结构相同，
但**时间裕度差几个量级**：

| role | 出现位置 | 时间裕度 | 对融合的意义 |
|---|---|---|---|
| `ACTIVATION` | TP 行/列并行的前后 | **无**，卡在关键路径上 | 融合价值最高，唯一必须靠算子内重叠解决的 |
| `GRADIENT` | wgrad 之后（DP/ZeRO） | 大，可拖到 step 末尾 | 靠调度即可，融合收益有限 |
| `WEIGHT_GATHER` | GEMM 之前（FSDP/ZeRO-3） | 大，可提前数层预取 | 同上 |

`InterDiePolicy` 必须读取此字段——否则会把优化预算浪费在裕度充足的通信上。

**③ microbatch 维度不在 IR-0 展开。** `Instance.ops` 是**单 microbatch 的算子模板**，
microbatch 数量与交错方式由 `TrainStructure` 声明，**展开推迟到 IR-1**。

理由：`grad_accum=8 × 32 层 × 5 算子 × 3 phase ≈ 3840` 节点，展开进 IR-0 纯属浪费；
且这与 `m_spec` 的处理**完全一致**——IR 携带 spec，展开在下游。
§6.1 所述「训练的层级 A 是 microbatch DAG」指的是**可推导的** DAG，而非 IR-0 中显式存储。

1F1B 带来的跨 microbatch 重叠机会（microbatch `i` 的 backward 与 `i+1` 的 forward）
在展开后自然成为 DAG 中的并行分支。

### 3.2 单层算子模板（结构知识的唯一来源）

记 `M` = token 数，`p` = tp 度。Llama 式一层：

| # | 算子 | M | K | N | tp 切法 | 相邻 collective |
|---|---|---|---|---|---|---|
| 1 | QKV proj | M | H | (NH+2·KVH)·DH | 列并行 N/p | 前：AllGather（仅 SP） |
| 2 | attention | 按 head 批量 | — | — | heads/p | 无 |
| 3 | O proj | M | NH·DH | H | 行并行 K/p | 后：**AllReduce** 或 **ReduceScatter**(SP) |
| 4 | Gate+Up | M | H | 2I | 列并行 N/p | 前：AllGather（仅 SP） |
| 5 | Down | M | I | H | 行并行 K/p | 后：**AllReduce** 或 **ReduceScatter**(SP) |

MoE 替换 4/5：`AllToAll(dispatch) → Gate+Up → Down → AllToAll(combine)`，专家维按 `ep` 切。

第 3、5 行的「GEMM + ReduceScatter」是融合目标，每层出现两次。

### 3.3 切分规则（GSPMD propagation 的闭式解）

transformer 结构固定，不需要通用传播算法，规则只有四条：

| 切法 | 数学后果 | 必需通信 |
|---|---|---|
| 列并行（切 N） | 输出天然沿 N 分片 | 无；下游若要完整 → AllGather |
| 行并行（切 K） | 每 rank 只有部分和 | AllReduce；输出若沿 M 分片 → **ReduceScatter** |
| SP（norm/residual 沿 M 切） | 列并行前缺 token | 前 AllGather + 后 ReduceScatter，替代一次 AllReduce |
| EP（专家维切） | token 需路由 | AllToAll ×2 |

### 3.4 训练的反向展开

每个前向 GEMM `Y = X·W` 展开成三个：

```
fwd:   Y [M,N] = X[M,K] · W[K,N]
dgrad: dX[M,K] = dY[M,N] · Wᵀ[N,K]      切分与 fwd 转置，collective 对偶
wgrad: dW[K,N] = Xᵀ[K,M] · dY[M,N]      M 是归约维
```

> **早期草稿的两处错误**（已更正）：
>
> ① 曾写「M 被 dp/sp 切分 → **每个权重**多一次梯度 AllReduce」。两处不成立：
> **(a)** DDP 按 **bucket** 而非按权重发起 collective，bucket 大小是真实调参项；
> **(b)** 「M 被切就要 reduce」是捷径推断，不能只看 M 是否分片。
>
> ② 曾写「dgrad/wgrad 本身就是 GEMM，**仿真器无需新原语**」。
> 该结论**仅对线性层成立**，见下方 S2 缺口。

**正解：由 sharding 差量推导，不用 prose 捷径。**
`dW = Xᵀ·dY` 沿 M 归约，故 **M 的 sharding 含哪些轴，`dW` 就在哪些轴上 `partial`**：

- **DP 轴**：恒成立（不同 rank 见不同样本）→ `dW.partial ∋ dp`
- **SP 轴**：取决于该 GEMM 前后是否已 AllGather，**必须由 layout propagation 推导**，
  不能假定「SP 切了 M 就要归约」

得到 `partial` 后，插 AllReduce 还是 ReduceScatter 由**目标 sharding**（即 ZeRO stage）决定，
查 §3.1 ⓪ 的差量表。这正是引入 `Sharding{partial}` 所要解决的问题。

**覆盖边界**：`dgrad`/`wgrad` 确实是 GEMM，可直接用现有 `Matmul_f`。
但**非线性层的反向不是**——attention（flash 反向为独立 kernel）、norm、activation、
embedding（scatter-add）、vocab-parallel CE loss 均需各自的反向表示。
这些属于 §1 的 **S2 阶段**，当前未覆盖。

落到 schema 上：

| 展开产物 | `Op.phase` | 相邻 collective 的 `COLL.role` |
|---|---|---|
| 前向 GEMM | `FWD` | `ACTIVATION` |
| dgrad | `DGRAD` | `ACTIVATION`（与 fwd 对偶） |
| wgrad | `WGRAD` | **`GRADIENT`**（DP 组，裕度大） |
| 重算的前向（`recompute != none`） | `RECOMPUTE` | 通常无 |

`recompute` 的语义：`TrainStructure.recompute` 为 `selective`/`full` 时，
展开器在反向路径上插入 `phase=RECOMPUTE` 的前向算子副本，
并相应删去被重算张量的活跃期依赖。此展开与 microbatch 展开一样发生在 IR-1。

### 3.5 外部框架接入（`model.source`）

IR-0 是**框架中立**的——它的字段里没有一个与 PyTorch/JAX 有关。因此可以有多个生产者：

| `source` | 来源 | 到 IR-0 的差距 | 定位 |
|---|---|---|---|
| `analytic` | `arch` + `parallel` 解析推导（§3.2/§3.3） | — | **主路径**，覆盖全部扫描配置 |
| `hlo` | PyTorch/XLA SPMD 或 JAX 的 partitioned HLO dump | 最小：collective 是显式算子，带 `replica_groups` 与分片形状；且给出全部非 GEMM 算子 | 覆盖度验证，论文里做一次 |
| `fx` | `torch.export` / `torch.compile` 的 fx graph | 形状可得，但 collective 需从 `torch.distributed` 调用侧反推 | 备选，Megatron/DTensor 场景 |

**根本边界：框架能给 IR-0，给不了 IR-1。**
HLO 的 `replica_groups` 只说明哪些 rank 参与，不说明这些 rank 在哪块 die 上。
`Group.embedding`（跳数/等效带宽/过境/共享链路）是晶圆级特有的层次，
没有任何框架掌握这一信息。框架集成能替代的仅是整条链路最上面的一段。

**第二重限制**：框架跑一次只产出一个配置，而实验需要扫 `tp × placement × policy` 的笛卡尔积。
因此框架给的是**一个验证点，不是一个扫描空间**——这是 `analytic` 必须作为主路径的根本原因。

不适合接入的：TensorRT-LLM（engine 不透明、plugin 黑盒）、
MindSpore/Paddle（需各自单独适配，收益重复）。

### 3.6 验证阶梯

解析推导最大的风险是「推错了自己不知道」。四级交叉验证，从便宜到贵：

1. **参数量自洽**：`Σ K·N` 对上模型公开参数量，误差 < 0.1%
2. **FLOPs 自洽**：训练 `Σ 2·M·K·N × 3` 对上 `6 × params × tokens`
3. **通信量对照**：per-layer AllReduce 字节数对上 Megatron-LM 的解析式
4. **抽样比对 HLO**：挑 1~2 个配置跑 PyTorch/XLA dump，逐算子核对

### 4.1.1 IR-0 → IR-1 的两处展开

除 placement 外，IR-0→IR-1 还负责把 IR-0 中以 **spec 形式**携带的维度展开成具体节点：

| 展开 | 依据 | 产物 |
|---|---|---|
| **microbatch × PP schedule** | `TrainStructure.{micro_batch_count, pp_schedule, interleave_chunks}` | 每个 `(microbatch, stage, phase)` 组合一个算子实例；1F1B 的跨 microbatch 重叠成为 DAG 中的并行分支 |
| **recompute** | `TrainStructure.recompute` | 反向路径上插入 `phase=RECOMPUTE` 的前向副本 |
| **profile 分桶**（推理） | `m_spec.profiles` | **一份 IR-1**，其 `FusedOp.plan` 为 `{profile_id -> FusionPlan}`；每个 profile 各自展开到 IR-2 与 artifact |

三者都遵循同一原则：**IR-0 携带 spec，IR-1 负责展开**。
这使得改动 `grad_accum` 或 `pp_schedule` 时 IR-0 可完全复用（见 §6.3 的缓存表）。

### 4.2 embedding 的静态容量签名

`Group.embedding` 只保存由 `members + logical_shape + placement + fabric` 唯一决定的静态事实。
它可以回答“这组 rank 的逻辑流会经过哪些物理资源、在约定 traffic template 下的容量上界是多少”，
但不保存某个 Swizzling 在某个并发场景中的实际带宽；后者属于 `PlanEvaluation`。

静态资源至少包括：每一跳的出口 port、有向 D2D link、共享 `link_group` cut；
若评估端到端通信，还应加入源/目的 die 的 NoC、HBM 与 RX buffer 资源。

- **`pair_routes/resource_incidence`**：任意 rank pair 的确定性路径，以及路径占用的全部资源。
- **`resource_capacity`**：逐资源容量，不能假定所有 link/port 都等速。
- **`canonical_profiles`**：在具名 traffic template 下计算出的可缓存容量特征，例如
  `mesh_neighbors`、`direct_a2a`、`ring_cw`、`ring_ccw`；template 是该数值定义的一部分。
- **`hop_distance/transit_dies`**：用于延迟、SAF 路径下界和 IR-2 `TRANSIT` 物化。

> `static_eq_bandwidth(mapping)` 没有完整定义；正确接口是
> `canonical_eq_bandwidth(mapping, traffic_template, d2d_mode)`。

### 4.2.1 两级 `eq_bandwidth` 计算

#### 仿真器 D2D 模型（已核对）

| 事实 | 设计含义 |
|---|---|
| die 级路由是确定性的 | 给定 mapping 与 peer 后可精确枚举 `expected_route` |
| `port_rate` 与 `link_rate` 分离 | port 和 link 都必须成为独立资源 |
| 同一有向 die pair、同 `link_group` 共享 cut | 多端口不能简单相加带宽 |
| `behavioral` 不建模跨 flow 争用 | 只能使用解析容量/延迟近似 |
| `bounded_saf` 是 whole-flow store-and-forward | 每一跳完整收流后才能转发，有限消息存在逐跳整流序列化 |

#### 第一级：mapping 的 canonical 静态带宽

设 template 中的逻辑流集合为 `F`，物理资源集合为 `R`：

```text
A[r,f] = flow f 是否使用 resource r
C[r]   = resource r 的容量
w[f]   = flow f 的归一化字节权重

W[r] = Σ_f A[r,f] · w[f]

lane_eq_bandwidth(mapping, template)
    = min_{r: W[r] > 0} C[r] / W[r]
```

`lane_eq_bandwidth` 表示所有 template flow 按相同比例推进时，一个归一化逻辑 lane 的速率。
若所有资源容量均为 `D2D_BW`、瓶颈资源上有 `k` 个等权流，则结果是 `D2D_BW/k`。

这正是需求图中可作为 Swizzling 匹配特征的静态量。例如 TP 的 canonical logical-edge template
若每条边映射到互不冲突的单跳资源，则 `BW_TP=D2D_BW`；EP template 若有两条逻辑流共享同一
出口或中间链路，则 `BW_EP=D2D_BW/2`。距离本身不会在流体容量公式中自动除带宽，
但更长路径更容易产生资源重叠，并在 `bounded_saf` 下增加有限消息的逐跳序列化。

`canonical_profiles` 只统计该 group/template 使用的资源。另一个 group 在完全不相交链路上的
热点不能降低这里的静态带宽；组间竞争属于第二级场景评估。

#### 第二级：Swizzling 的 plan-specific 带宽

候选 `FusionPlan P` 决定 chunk、peer、phase、bytes、依赖和 compute release time。
对 phase/时间窗口 `q` 物化实际 action 后计算：

```text
F_target(P,q) = 该窗口内目标 plan 的流
R_target(P,q) = 这些流实际使用的资源并集

W_target[r,q] = Σ_{f∈F_target, r∈route(f)} bytes[f,q]
C_available[r,q] = C[r] - overlapping_background_rate[r,q]

T_capacity(P,q)
    = max_{r∈R_target(P,q)} W_target[r,q] / C_available[r,q]
```

若任一目标资源的 `C_available[r,q] <= 0`，该窗口不可调度，候选直接判为 infeasible。

背景流只有同时满足“执行时间重叠”且“使用 `R_target` 中同一资源”时才扣减容量。
不能把所有 group 的全局最大热点套到目标 plan 上。

若需要带宽指标，必须同时报告其归一化口径：

```text
lane_eq_bandwidth(P,q) = 归一化 lane bytes / T_capacity(P,q)
aggregate_goodput(P,q) = useful_logical_bytes(P,q) / communication_span(P,q)
```

`aggregate_goodput` 可以高于单条 `D2D_BW`，因为多条物理链路可以并行；
`lane_eq_bandwidth` 用于与单链路带宽比较。两者不得混名为一个 `eq_bandwidth`。

#### SAF 与最终选择目标

容量公式是快速筛选的流体下界。孤立流在 packet-pipelined/behavioral 近似下可写为：

```text
T_flow ≈ Σ latency[e] + bytes / min_e C[e]
```

但当前 `bounded_saf` 采用 whole-flow store-and-forward，更接近：

```text
T_flow_saf ≈ Σ_{e∈route} (latency[e] + bytes / C[e])
T_proxy(P,q) = max(T_capacity(P,q), max_f T_flow_saf(f))
```

多流仲裁、RX backpressure、buffer 和 COMP/SEND/RECV/REDUCE/WAIT 依赖仍需资源约束调度或
统一命令流仿真。Swizzling 的正式选择目标是融合 region/layer 的 `region_makespan`：

```text
best_plan = argmin_P PlanEvaluation(P, scenario).region_makespan
```

带宽只用于候选生成、剪枝和解释瓶颈，不能替代端到端 makespan。

#### 旧公式为何作废

旧实现使用全局 `max(flow_count)`，存在以下问题：

1. 不相交 group 的热点也会错误降低目标 group 带宽；
2. 只数流数量，不区分 bytes、chunk 大小、release time 和持续时间；
3. 端口只统计原始 source，遗漏每个 TRANSIT die 的转发出口；
4. 未显式建模异构容量、共享 `link_group`、RX/NoC/HBM 与仲裁；
5. `eq_bandwidth` 依赖具体 plan，却被放进 plan 之前的静态 embedding，形成依赖环；
6. “跳数只增延迟”的结论未按 behavioral/pipelined 与 whole-flow SAF 区分。

因此前端应缓存静态 `resource_incidence/canonical_profiles`，按候选生成 `PlanEvaluation`；
规模较大时先用上述 proxy 排序，再对前若干候选运行统一命令流精确仿真。

### 4.3 PD 分离的表示

**IR-0 层**：

```python
instances: [
  Instance{id:"P0", role:PREFILL, parallel:{tp:8,sp:true},
           m_spec:{kind:"static", value:2048}},
  Instance{id:"D0", role:DECODE,  parallel:{tp:4,sp:true},
           m_spec:{kind:"profiles", profiles:[ProfileKey...], weights:[...]}},
]
cross_edges: [
  KvHandoff{src:"P0", dst:"D0", layer:l, async:true,
            logical_bytes_per_token: 2*KVH*DH*dtype_bytes,
            granularity:"per_layer",
            shard_dim:"kv_head",
            flow_matrix: derive_head_slice_assignment(tp_P, tp_D, KVH)}
                                                    for l in 0..L-1
]
```

三个 PD 特有的要点：

1. **`cross_edges` 逐层 L 条，不是 1 条。** 逐层 KV 传输的重叠机会必须在 IR 里体现，
   建成一条大边则下游无论如何优化都藏不住。
2. **`m_spec` 显式区分静态/动态。** P 侧形状编译期已知；D 侧由调度器给，只能给 profile 分布。

   > **仿真器现状澄清**（修正早期草稿的误判）：`batch_size = 1`
   > （`config_helper_pds.cpp:42`）**只作用于 prefill 准入分支**（`if (done < batch_size)`）；
   > decode 分支完全以 `HW_CORE_CREDIT` 为上限，`batch_size` 在其中不出现。
   > 因此 **decode 的 `T` 不恒为 1**，可累积到 credit 上限。
   >
   > 真正的问题是 `generate_prims` 把 ragged batch 压平：
   > `B` 硬编码为 1、`T = Σ tokens`，**每请求的 context 长度在 GEMM 形状中丢失**。
   > 这正是 §7.3.1 所述「标量 M 不足以定价 attention」在仿真器侧的对应缺陷（§10 缺口 6）。
3. **`reshard` —— 最易遗漏的一环。** `tp_P ≠ tp_D` 时 KV 传输不是一对一 P2P，而是两个不同大小的
   group 之间的重分片。`tp_P > tp_D` 是 gather，反之是 scatter：

   ```
   tp_P=8, tp_D=4, KVH=8:  P rank i 持有 head i；D rank j 需要 head 2j, 2j+1
   reshard = [(0,0),(1,0),(2,1),(3,1),(4,2),(5,2),(6,3),(7,3)]
   ```

   实践后果：**`tp_P` 与 `tp_D` 的选择直接决定 KV 传输的流量模式**，是一个独立的可扫维度。

   > **仿真器现状**：`config_helper_pds` 由 `tp_size = json_template_p.size()` 推出**唯一**的
   > `tp_size`，并用同一个值为 prefill 与 decode 核分组（`config_helper_pds.cpp:52,57,60`）。
   > 因此**当前结构上强制 `tp_P == tp_D`**，本节的一般 reshard 是 IR 层能力，
   > 其仿真器支持属 §10 缺口 4。在该缺口修复前，PD 实验只能跑 `tp_P == tp_D`。

**IR-1 层**：placement 把每个 instance 绑到一块 die 区域，KV 边落成具体路由。
以 4×4 die、1 个 P + 2 个 D 为例：

```python
PhysInstance{id:"P0", die_region:[0,1,2,3,4,5,6,7]}   # 上半 4×2
PhysInstance{id:"D0", die_region:[8,9,12,13]}      # 左下 2×2
PhysInstance{id:"D1", die_region:[10,11,14,15]}    # 右下 2×2

cross_routes: [
  KvRoute{layer:l, src_die:0, dst_die:8, path:[0→4→8],   hops:2},
  KvRoute{layer:l, src_die:1, dst_die:8, path:[1→0→4→8], hops:3},
  ...                                               # 8 条 × L 层
]
```

`die_region` 同时补上了仿真器侧的一个缺口：instance 的 mesh footprint 目前分散在
`pds` 的 `prefill_cores`/`decode_cores` 与 `mapping.spec` 两处，无统一声明。
JSON planner/config generator 从 `die_region` 同时导出两者，保证一致。

**PD 融合**在 IR-0 中就是**一个 instance**（`role: BOTH`）且 `cross_edges` 为空——
没有 KV 搬运正是融合模式的本质优势。

### 4.3.1 KV handoff 的静态等效带宽

KV handoff 是一个已知 mapping、已知张量分片的 P2P reshard；其静态带宽也必须先生成
**流量矩阵**，不能只用“P 区域到 D 区域的 mesh 带宽”或 `D2D_BW / hop`。

先考虑没有 KV-head 复制的常见情况。设一次 handoff 搬运 `T` 个 token，KV head 数为
`KVH`，每个 head 维度为 `DH`，元素字节数为 `dtype_bytes`。令 `PHeads(i)` 为 prefill
rank `i` 持有的 head slice，`DHeads(j)` 为 decode rank `j` 需要的 head slice，则：

```text
h[i,j] = |PHeads(i) ∩ DHeads(j)|
b[i,j] = 2 · T · DH · dtype_bytes · h[i,j]   # K 和 V
```

只为 `h[i,j] > 0` 的 rank pair 建 flow，再由 placement/routing 得到每条 flow 的物理路径。
当 head 不是整除分片、按更细 tensor slice 切分或存在复制时，把 `h[i,j]` 换成显式的
`assigned_slices[i,j]`；同一目标副本只选择一个源副本，不能把所有集合交集都重复发送。

IR-1 应为每一层生成并缓存：

```python
KvTransferProfile {
  src_instance, dst_instance, layer, token_bucket, d2d_mode,
  flows: [{
    src_rank, dst_rank, head_slices, bytes,
    release_event, expected_route
  }],
  resource_work: {resource_id -> bytes},
  bottleneck_resource,
  lane_eq_bandwidth,
  logical_goodput,
  transfer_span,
  saf_path_bound
}
```

对 flow `(i,j)` 和资源 `r`，令 `A[r,i,j]` 表示其路径是否占用该资源。静态、无背景流时：

```text
W[r] = Σ_(i,j) A[r,i,j] · b[i,j]
T_capacity = max_{r:W[r]>0} W[r] / C[r]

T_path_saf = max_(i,j) Σ_{e∈route(i,j)}
                         (latency[e] + b[i,j] / C[e])

T_static_proxy = max(T_capacity, T_path_saf)        # bounded_saf
```

资源集合与 §4.2 相同，至少含 transit die 的出口 port、有向 link 和共享 `link_group`；
若要评估端到端 handoff，还要加入源/目的 NoC、HBM、RX buffer。`behavioral` 模式没有真实
跨 flow 仲裁，因此这个解析值只能作为容量估计；`bounded_saf` 还必须保留逐跳整流项。

用于与单链路比较的 per-head lane 指标为：

```text
u = 2 · T · DH · dtype_bytes
w[i,j] = b[i,j] / u = h[i,j]
lane_eq_bandwidth
    = min_{r:ΣA[r,i,j]w[i,j]>0}
        C[r] / Σ_(i,j) A[r,i,j] · w[i,j]
```

用于回答“整份 KV 多久搬完”的指标则是：

```text
B_logical_unique = 2 · T · KVH · DH · dtype_bytes
logical_goodput = B_logical_unique / transfer_span
```

`logical_goodput` 可能高于一条 D2D link 的带宽，因为多个 flow 可以走不相交链路并行；
若 decode layout 有必要的复制，另报
`delivered_goodput = Σ b[i,j] / transfer_span`，不得与去重后的 logical goodput 混用。
最终 `transfer_span` 应由带 release event 的资源约束调度或统一命令流仿真得到，而不是直接
取 proxy；逐层异步 handoff 还要用各层 GEMM 完成事件作为 release time，才能计算与后续计算/
其他层传输的重叠。

缓存键至少包含
`(P placement, D placement, tp_P, tp_D, KVH, dtype, token_bucket, reshard layout, d2d_mode)`。
一次请求通常只路由到一个 decode replica，不应把所有 D instance 同时计入背景流。
PD 融合时没有 handoff，`transfer_span=0`、带宽指标记为 **N/A**，不能写成无穷大。

## 5. IR-2：单 Die 图

IR-2 分为**两层**：`IntraDieDAG` 描述**语义**（必须发生什么），
`IntraDieSchedule` 描述**决策**（怎么发生）。

> **早期草稿的缺陷**：把两者混在一个 `IntraDieGraph` 里——节点上既有 `deps`（语义），
> 又有 `port_id`/`expected_route`/`buffer_ref`（决策）。后果是
> `IntraDiePolicy` 没有干净的函数签名，消融时无法在「同一语义、两种调度」之间对比。

分离后：

- `IntraDiePolicy: IntraDieDAG → IntraDieSchedule` 成为明确的可替换接口（§9）
- 消融 = 同一个 DAG 上比较两个 Schedule，语义完全等价可保证
- 两个后端的 emitter 消费 `(DAG, Schedule)` 二元组，职责良定义：

| Schedule 字段 | JSON 后端 | ISA 后端 |
|---|---|---|
| `placement` | core id | core program index |
| `binding` | `sram_address` label | `SRAM_ALLOC` / `SRAM_BIND` |
| `tags` | `cast` / `recv_cnt` tag | collective key / channel |
| `tokens` | `Dte_async_prim` token | `DTE_ISSUE` / `DTE_WAIT` |
| `order` | worklist 内 prim 顺序 | external record 顺序 |

### 5.1 IntraDieDAG（语义）

```python
NodeOrigin = {kind:FUSED, plan_id, rank, action_id}
           | {kind:ORDINARY, op_id}
           | {kind:STANDALONE, collective_plan_id, action_id}

IntraDieDAG(die_id) {
  nodes: [                             # 每项都含 id 与 origin_ref:NodeOrigin
    {kind: DMA_IN,  value_ref, buffer_ref, src:HBM, bytes, chunk_id, deps}
    {kind: COMP,    op_kind, member_id, region_id, shape, tile,
                    reads:[buffer_ref], writes:[buffer_ref], chunk_id, deps}
    {kind: SEND,    flow_id, region_id, collective_step, chunk_id, src_rank, dst_rank,
                    peer_die, port_id, expected_route, bytes, buffer_ref, logical_channel, deps}
    {kind: RECV,    flow_id, region_id, collective_step, chunk_id, src_rank, dst_rank,
                    peer_die, port_id, expected_route, bytes, buffer_ref, logical_channel, deps}
    {kind: REDUCE,  region_id, reduce_op, dtype, chunk_id, src_buffers, dst_buffer, deps}
    {kind: WAIT | BARRIER, region_id, logical_event_or_group, deps}
    {kind: TRANSIT, flow_id, hop_index, ingress_port_id, egress_port_id,
                    prev_die, next_die, bytes, deps}  # 过境，本 die 不产不消
    {kind: DMA_OUT, value_ref, buffer_ref, dst:HBM, bytes, deps}
  ],
  edges: [(src_node, dst_node)],
  regions: {region_id -> {fusion_ref, lowering:"isa"}}
}
```

SEND 方向由 embedding 的**第一跳**推出，RECV 方向由**最后一跳**推出。
多跳时中间 die 获得带同一 `flow_id` 的 `TRANSIT` 节点。

对应需求图 2 的形状：`recv N → (comp N, send N to W)` 链，首尾接 `HBM→SRAM` / `SRAM→HBM`。

> **需求三图与本方案的差距**（`req.md` 的图 1/2/3 早于本方案定稿，需补充可执行语义）：
>
> | 图 | 现有内容 | 需补充 |
> |---|---|---|
> | 图 1（Swizzling 输入） | mesh 尺寸、等效 D2D BW、mnk、collective 种类 | **phase**（等效带宽按相位而非标量，§4.2.1）、**并发 group**（组间竞争是 `link_load` 的一部分）、`COLL.role`（决定裕度） |
> | 图 2（单 die 计算通信图） | recv/comp/send 链 + 方向 | **chunk_id / collective_step**（分块流水的次序）、**tag / logical_channel**、**port_id**（出口端口可能先于链路饱和）、**buffer + lifetime**（SPM 容量约束）、**REDUCE 与 WAIT/BARRIER 节点**、**TRANSIT**（过境流量） |
> | 图 3（intra-die 架构） | Graph Builder → Optimizer → Schedule Simulator / Physical Mapper → Emitter | 明确 **DAG 与 Schedule 的边界**（§5.1/§5.2）：Optimizer 产出 DAG，Physical Mapper 产出 Schedule；Emitter 消费二元组 |
>

> 因此不能直接作为 IR-2 的规格，只能作为示意。

`region_id != null` 的 COMP/通信/reduce/wait 节点必须作为一个融合 region 整体交给 ISA lowering；
`region_id = null` 的普通计算走 JSON coarse lowering，独立 collective 走 standalone strict lowering。
三类节点以及 TRANSIT 最终进入同一
`CoreCommandStream` 和资源时间线，不能分别运行后再相加。

> **迁移说明**：上表中的 `port_id`、`expected_route`、`buffer_ref`、`logical_channel`
> 属于**决策**而非语义，应迁至 §5.2 的 `IntraDieSchedule`。DAG 节点保留
> `kind`、`op_kind`、`flow_id`、`chunk_id`、`bytes`、`deps`、`region_id`
> 及 value 级的读写关系；物理绑定由 Schedule 提供。
> 二者以 `task_id` 关联。

### 5.2 IntraDieSchedule（决策）

```python
IntraDieSchedule(die_id) {
  placement: {task_id -> core_id},
  binding:   {buffer_id -> BufferBinding},
  routes:    {flow_id  -> {port_id, noc_path, first_hop_dir}},
  tags:      {flow_id  -> tag_id | collective_key},
  tokens:    {task_id  -> token_id},        # async issue/wait 配对
  order:     {core_id  -> [task_id]}        # 每核发射顺序
}

BufferBinding {
  region: str, offset: int, size: int,
  bank: int | [int],                        # SPM banking 决策
  lifetime: (t0, t1)                        # 以 order 中的位置计
}
```

**`BufferBinding.lifetime` 与 `bank` 是 intra-die 编排的核心决策变量**——
前者决定 SRAM 容量是否够用（§3.1 validator 第 10 条的并发 live range 校验在此兑现），
后者决定 bank 冲突。二者都不属于语义，故必须在 Schedule 而非 DAG。

`IntraDiePolicy` 的两个基准实现：

| 实现 | placement | binding | routes | order |
|---|---|---|---|---|
| `naive` | 轮询分核 | 顺序分配、不复用 | 最短路 | DAG 拓扑序 |
| `optimized` | 按数据亲和度 + 端口位置 | 生命周期感知复用 + bank 均衡 | 避让 `TRANSIT` 热点 | 关键路径优先、通信阴影填充 |

## 6. 顶层输入设计

### 6.1 负载输入的三层（训练与推理对称）

训练与推理共用同一套三层结构，**语义对称但底层产物不同**：

| 层级 | 含义 | 推理 | 训练 |
|---|---|---|---|
| **C** | 负载的统计描述 | 生成参数：QPS、到达分布、prompt/output 长度分布 | 数据规格：语料 seq 长度分布、packing 策略 |
| **B** | 具体的工作单元序列 | 请求 trace `[(arrival_ns, prompt_len, output_len)]` | 训练步结构：`global_batch`、`micro_batch`、`grad_accum`、PP schedule |
| **中间** | 展开器 | **调度器**（离线模型 / 仿真器 `config_helper_pds`） | **梯度累积 + PP 调度展开** |
| **A** | 送进 IR-0 的形状 | 形状**分布**：profile + 权重 | **`TrainStructure` spec**（microbatch 数、PP schedule、recompute）——DAG 由其**推导**，不在 IR-0 显式存储 |

```
        推理                                训练
   ┌─ C 生成参数 ─┐                   ┌─ C 数据规格 ─┐
   │ QPS/到达/长度 │                   │ seq 分布/packing │
   └──────┬───────┘                   └───────┬───────┘
          │ 生成                              │ 打包/分桶
          ▼                                   ▼
   ┌─ B 请求 trace ─┐                  ┌─ B 训练步结构 ─┐
   └──────┬─────────┘                  │ gb/mb/ga/PP    │
          │ 调度器                      └───────┬────────┘
   ┌──────┴───────┐                            │ 展开
   ▼              ▼                            ▼
离线调度模型  仿真器 PD 调度器            ┌─ A TrainStructure ─┐
   │              │                     │ (DAG 可由其推导)    │
   ▼              ▼                     └────────────────────┘
┌─ A 形状分布 ─┐  真实时序
│ProfileKey + 权重│  (TTFT/TPOT/排队)
└──────────────┘
```

**用户可从任意一层进入**，未给的下层自动推导。第一阶段推理给层级 A、训练给层级 B 即可。

#### 关键的结构性差异

**推理的 A 是分布，训练的 A 是序列。** 推理里哪个 ProfileKey 出现是随机的，只能给权重后加权聚合；
训练里 microbatch 的顺序与依赖是确定的，展开后是一张 DAG。因此：

- 推理：按 profile 加权聚合，**公式见 §7.3.2**（注意不是「加速比的加权平均」）
- 训练：直接按 DAG 跑一个完整 step，无需加权

**训练的形状动态性远小于推理。** 现代预训练普遍用 **packing**（把多篇文档拼接到定长，
如 8192），打包后**只有一个形状反复出现**——这正是三层结构在训练侧"看起来退化"的原因。
需要形状分布的只有两种情况：SFT/变长微调（按长度分桶）、序列长度 curriculum（按 step 变化）。
两者都可复用同一个 `m_spec`（`kind: histogram` / `kind: schedule`）。

#### 中间层的对应关系

推理的调度器决定 **batch 组成**；训练的 PP schedule 决定 **哪个 microbatch 的 fwd/bwd 在何时执行**。
两者都是"把工作单元序列铺到时间轴上"，因此在本方案里占据同一个位置。

一个值得注意的副作用：1F1B 等调度会让 microbatch `i` 的 backward 与 `i+1` 的 forward 重叠，
这意味着**融合算子的 collective 可以与另一个 microbatch 的计算重叠**，而不只是与自身的 GEMM 重叠。
本方案的 IR 能表达这种重叠（DAG 里就是并行分支），但**PP schedule 本身的搜索不在范围内**——
只接受用户给定的 schedule（见 §1）。

#### 交叉验证

推理侧两个调度器实现消费**同一个 trace**，可交叉验证：离线模型算出的 M 分布应与仿真器
实跑统计一致，不一致说明离线模型的调度策略建错了。
训练侧无此问题——展开是确定性的，直接对拍 microbatch 数与 PP 阶段数即可。

## 7. 动态性的表征边界

**核心原则：IR 表征动态性的「值域与分布」，不表征动态过程本身。**

此原则对训练与推理同样适用，但两者的动态性量级相差悬殊——**训练的动态性主要来自 PP 调度的
时序，形状基本静态**（packing 后单一形状）；**推理的动态性主要来自形状**（M 逐迭代变）。

### 7.0 训练侧

| 动态性 | 类别 | 在 IR 里 | 动态过程由谁产生 |
|---|---|---|---|
| microbatch 序列与 PP 阶段 | 时序 | **IR-0 的 DAG 结构**（确定性依赖，非分布） | PP schedule 展开器 |
| 变长 seq（SFT/微调） | 形状 | `m_spec{kind:histogram}` | 数据规格分桶 |
| 序列长度 curriculum | 形状 | `m_spec{kind:schedule}` | 训练步编号 |
| packing 后的定长预训练 | — | `m_spec{kind:static}` | 无动态性 |
| MoE 专家负载倾斜 | 形状（容量） | `capacity_factor` + `skew` | 仿真器（现为 `rand()`） |

训练的时序动态性**进 IR**（作为 DAG 的依赖边），这与推理相反——因为它是确定的、可展开的，
而不是随机过程。

### 7.1 推理侧

| 动态性 | 类别 | 在 IR 里 | 动态过程由谁产生 |
|---|---|---|---|
| batch 组成逐迭代变 | 形状 | `m_spec.profiles`（多维 `ProfileKey`）+ `weights` | 调度器 |
| 请求间变长 seq | 形状 | 决定 buckets 取值 | trace 统计 |
| KV 传输量随 T 变 | 形状 | `flow_matrix(token_bucket)` | 同上 |
| MoE 路由 | 形状（容量） | `capacity_factor` + `skew` | 仿真器（现为 `rand()`） |
| 请求到达 | 时序 | ❌ | 仿真器 `requests.arrival` |
| decode 长度随机终止 | 时序 | ❌ | 仿真器 `eof_chance` |
| 排队 / credit 背压 | 时序 | ❌ | 仿真器 `idle_decode` |
| 抢占 / KV 驱逐 | 时序 | ❌ | 仿真器亦未建模 |

**推理侧：形状动态性进 IR（分桶），时序动态性不进 IR。**
此二分与工业实践一致——CUDA Graph 按 batch 分桶捕获，serving 循环负责时序。

**与训练侧的分界不同**：训练的时序是确定性的、可展开成 DAG，因此进 IR；
推理的时序是随机过程（到达、EOS、排队），无法展开，只能交给调度器。
判据不是"时序 vs 形状"，而是**"确定可展开 vs 随机需模拟"**。

### 7.2 调度模型（`scheduler_model`）

**定义**：用 Python 复现 serving 调度器的**决策逻辑**，不跑硬件仿真，用于生成 ProfileKey/arrival 序列并闭环查询 surrogate。

> 命名说明：早期草稿称其为「离线模型」，但「offline」在 LLM serving 语境中已指批处理模式
> （相对 online serving），易混淆。统一改称 `scheduler_model`。

| | `scheduler_model` | `simulator`（`config_helper_pds`） |
|---|---|---|
| 模拟范围 | **仅调度决策** | 调度决策 + 每核/每消息/每次访存 |
| 迭代时间来源 | 条件 surrogate；域外走精确 fallback | 统一资源时间线的真实仿真 |
| 单次代价 | 秒级 | 一次完整仿真 |
| 产出 | ProfileKey 分布、带误差边界的 TTFT/TPOT 估计 | 精确时序、`token_record` |
| 工作量 | 约 300 行 | 已有，但受缺口 6（ragged 表达）与 4（独立 `tp_P/tp_D`）限制 |

**算法骨架**：

```python
state = {waiting: [], running: [], t: 0}
while not all_done:
    admit(arrived_requests_by(t))                    # 到达驱动准入
    batch = form_batch(waiting, running, policy)     # ← 调度策略全在这里
    key = ProfileKey.of(batch)                       # ← 多维形状键，见 §3.1/§7.3.1
    record(key)                                      # ← profile 分布的来源
    scenario = RuntimeScenario.of(state, batch)
    dt  = iter_time(key, scenario, config)           # ← 条件 surrogate 或精确 fallback
    t += dt
    for r in batch:
        advance(r)                                   # prefill chunk 完成 / 出 token / EOS
```

`form_batch` 承载全部策略：`max_batch_tokens` / `max_batch_reqs` 上限、chunked prefill 的混合比例、
prefill 与 decode 的优先级、PD 分离时的双队列。**待对比的调度策略差异全部体现在此函数**。

**`iter_time` 的来源（关键设计）**：调度是闭环——batch 决定耗时，耗时决定下一次调度时刻，
进而改变准入、排队和后续 ProfileKey。因此首阶段使用由联合精确仿真标定的条件 surrogate：
`iter_time(key, scenario, config)`；key 是多维 `ProfileKey`，scenario 至少携带 arrival/release、
并发 flow 与内存状态摘要。标定点可复用模式 A 运行，但还必须补充 inter×intra 同时开启的
2×1/2×2 交互样本，不能假定这些样本“免费”或用单 Die 空载 LUT 代替。

**保真度边界**：`scheduler_model` 本身只重放调度状态。若 surrogate 只返回 makespan，它不能动态
复现 NoC/HBM/SPM 争用和跨 region 背压，只能输出带 holdout 误差的 TTFT/TPOT 估计；精确数值必须
来自统一仿真。若顶层事件模型消费 §8.8 的 boundary/resource trace，可提高保真度，但仍受校准域限制。

**验证分两层**：同一请求 trace 对比 scheduler 与仿真器产生的 ProfileKey 序列，验证调度逻辑；
再用未参与拟合的联合精确运行验证 surrogate 的时间误差与候选排序，二者不能混成一次校验。

### 7.2.1 两种模式及其闭环（推理）

**模式 A：静态 profile 编译 + 统一执行**（第一阶段主路径）
每个多维 ProfileKey 严格按 `IR-1 placement → FusionPartition → FusionPlan/per-rank Action DAG
→ ProjectToIR2 → IntraDiePolicy → GlobalActionDAG` 展开。随后普通算子走 JSON coarse
lowering、独立 collective 走 standalone lowering、融合 region 走 ISA lowering，最后链接为一份
完整 `CoreCommandStream` 做一次统一仿真。
桶间聚合先分别累加绝对时间，再求比值：

```text
overall_speedup = Σ_b w_b · T_naive(b) / Σ_b w_b · T_opt(b)
```

优点：同一桶内 inter/intra 资源竞争和计算通信重叠由一条真实时间线给出；
naive/optimized 融合区使用同一 ISA lowering，不混入后端差异。
缺点：静态桶本身拿不到请求排队和尾延迟。

**模式 B：在线调度器驱动**
当前 `config_helper_pds` 仍由 JSON 模板产生请求时序与 batch/ProfileKey 序列，但不能直接调用 strict
ISA region。首阶段把它作为 **trace/profile 产生器**：`scheduler_model` 查询由模式 A 联合精确运行
标定的条件 surrogate（§8.8），对每个候选配置重新闭环推进。
这属于多保真估算；只返回标量 makespan 时尤其不能宣称捕获动态 NoC/端口/HBM/SPM 竞争与背压。

长期路径是在统一 strict helper 中加入 `RegionCall(profile_key)`：运行时选择预链接的 ISA variant，
并与普通 coarse command、跨 die action 共享 buffer/event/tag 命名空间。届时模式 B 才是精确联合仿真。

**闭环**：对每个 placement/policy 候选，用该候选自己的条件 surrogate 或精确标定成本重跑
`scheduler_model`；优化改变迭代时间时，ProfileKey 分布也允许变化，不能固定复用基线 weights。

### 7.3 FusionPlan 按桶编译

`FusionPlan` 以多维 `ProfileKey` 为 guard。模式 A 对每个静态 profile 编译 plan；长期动态模式
保留 `{profile_guard -> FusionPlan/IsaRegion}` 映射，由 `RegionCall` 选择逐维覆盖当前形状的最小
profile；超过覆盖域时走显式 fallback，不能退回标量 M 的“最近桶 + padding”。

与 TRT-LLM 按 profile 选 kernel、vLLM 按 batch 桶选 CUDA Graph 是同一机制。

policy 仍是编译期决策；运行时只做 guard 匹配和 variant dispatch，不在关键路径重新搜索。

### 7.3.1 为什么不能只用 M 分桶

> **早期草稿的缺陷**：把运行形状建模为标量 `M`（`m_spec.buckets`）。
> 该表示只能决定**线性层**的代价，无法决定 attention 与访存代价。

相同的 `M` 可以来自完全不同的负载形态，而它们的 attention 与 KV 代价相差数量级：

| 场景 | M | prefill_tokens | decode_tokens | num_seqs | context_sum | attention 代价 |
|---|---|---|---|---|---|---|
| 一段 prefill chunk | 256 | 256 | 0 | 1 | ~256 | `O(M·ctx)`，小 |
| 256 路 decode，长上下文 | 256 | 0 | 256 | 256 | 256×4096 = 1M | **读 1M token 的 KV**，大三个量级 |
| 混合 batch | 256 | 192 | 64 | 65 | 混合 | 两者叠加 |

三行的**线性层代价完全相同**（`M×K×N` 一致），attention 与 HBM 流量却完全不同。
因此 `iter_time(M, config)` 与 `FusionPlan[m_bucket]` 都不成立，必须换成
§3.1 的多维 `ProfileKey`。

### 7.3.2 profile 选择：支配覆盖，不是「最近桶」

标量 M 下「取最近桶 + padding」是良定义的；多维 key 下**「最近」无定义**（按哪个维度度量？），
而且**任一维度向下 padding 都是错的**——`kv_pages` 取小会导致缓冲不足，
`context_sum` 取小会低估 KV 读取量。

正确语义是**支配（dominance）覆盖**：

```python
def covers(P: ProfileKey, S: ProfileKey) -> bool:
    return all(getattr(P, d) >= getattr(S, d) for d in ProfileKey.dims)

def select(profiles, S):
    candidates = [P for P in profiles if covers(P, S)]
    if not candidates:
        return FALLBACK          # 显式 fallback，不得无条件 padding
    return min(candidates, key=cost)      # 能覆盖当前形状的**最小** profile
```

与 TRT-LLM 的 `min/opt/max` 优化 profile 语义一致：profile 必须在**每个维度**上都不小于
实际形状，才允许使用。无 profile 覆盖时走显式 fallback（重编译或退回 eager），
**不能选一个"接近"的**。

### 7.3.3 聚合公式：加速比不能加权平均

> **早期草稿的数学错误**：曾写 `端到端收益 = Σ_b w_b · speedup_b`。
> 加速比是比值，**比值的加权平均 ≠ 平均的比值**。

正确形式是先分别累加绝对时间，再求比值：

```text
                    Σ_b  w_b · T_base,b
overall_speedup = ─────────────────────
                    Σ_b  w_b · T_opt,b
```

（这等价于以**基线时间占比**为权的调和平均，而非以频次为权的算术平均。）

### 7.3.4 在线场景：weights 不是常量

更根本的问题：**优化本身会改变分布**。迭代变快 → 排队时间变短 → 下一轮 batch 组成改变
→ profile 分布改变。因此**基线测得的 `weights` 对优化配置不成立**，
固定复用会系统性偏置结果。

两种模式的正确做法不同：

| 模式 | 做法 |
|---|---|
| **离线 profile 扫描**（模式 A） | 可用 §7.3.3 公式，但须声明前提：**分布不随配置改变**。仅在固定 profile 集合的敏感性分析中成立 |
| **在线闭环**（模式 B） | **每个候选配置各跑一次 `scheduler_model` 闭环**，用该配置自己标定的 `iter_time` 表。此时两个配置产生**不同的** batch 序列，比较对象直接是 makespan 与延迟分位数，**根本不需要加权** |

这也提高了 `scheduler_model` 的地位：它不再只是"省事的替代品"，
而是在线场景下**保证正确性的必需组件**——因为它足够便宜（秒级），逐候选重跑是可行的。

## 8. 异构算子 lowering 与统一执行后端

本方案不再尝试让 legacy JSON helper 与 Program helper 在一次运行中并列工作，
也不在 `coreconfigs` 层拼接两者的产物。新的原则是：

> **JSON/IR 负责全局规划与普通算子的 coarse model；目标融合区由 ISA 做细粒度 lowering；
> 三类 command 在执行前链接成一个 owned、strict 的命令流，由单一 helper 运行。**

### 8.1 当前实现约束（已核对）

| 约束 | 当前事实 | 设计结论 |
|---|---|---|
| loader 选择 | `npusim.cpp:575` 中 `--program` 与 `--workload-config` 互斥；program 还强制 `SIM_DATAFLOW` | 不能靠删除一条 CLI 检查实现混合执行 |
| 公共数据结构 | `config_helper_base` 有 `coreconfigs`，但 Program 的 owned prim 在私有 `prepared_cores_`，`coreconfigs.worklist` 不是共同可执行表示 | 必须先定义统一的 owned command 表示 |
| wire/ownership | legacy JSON 与 strict Program 使用进程级不同 transport/ownership 约束；SRAM lifecycle、event、ISA endpoint 等是 strict-only | 整次仿真只能选择一种 transport；新主路径统一 strict |
| JSON 普通 worklist | 只接受 compute、`Dte_async`、LSU、`Sram_pipeline`；不能把 `Collective_prim`、Recv/Send 或占位 region 任意插进 `prims` | 需要独立的 `GlobalActionDAG` 与 lowering adapter |
| JSON reduction | `PlanTier0Collective` 是固定 root gather + scatter/broadcast；Tier-0 明确拒绝 FP16/FP32/FP8 reduction | 不能直接执行目标 FP16 RS/AR，也不能消费物理环 Swizzling |
| ISA collective | ISA `core_group` 跨 die 硬失败；但普通 P2P endpoint 可以跨 die | 跨 die collective 由 planner 展开为 P2P endpoint + 本地 FP reduce，不建立跨 die ISA group |
| 动态 PDS | 当前只有 JSON/PDS helper 能按迭代生成 workload；没有 strict `RegionCall`/variant dispatch | 首阶段精确支持静态桶；动态先走多保真，长期再统一 |

因此，“JSON 后端 + ISA 后端”在本文中不再表示两个 runtime 同时启动，而表示
**三种算子 lowering 策略汇入一个执行后端**。

### 8.2 职责边界

| 层次 | 负责什么 | 不负责什么 |
|---|---|---|
| JSON/IR planner | LogicalExpand、placement、FusionPartition、collective algorithm、rank/chunk/phase/peer、`expected_route` 与 FusionPlan | 不生成早于 plan 的 IR-2，也不直接管理 ISA SRAM 地址 |
| ProjectToIR2 / action DAG builder | 从 IR-1 与完整 per-rank FusionAction 确定性物化每 die action、TRANSIT 和跨 die 依赖 | 不重新选择 policy，不模拟尚未 core/route/bank 映射的 DAG |
| IntraDiePolicy | 为 projected IntraDieDAG 决定 core placement、NoC route、SPM banking、buffer lifetime 与 schedule | 不改变 FusionPlan 的 peer/chunk/跨 die依赖 |
| JSON coarse lowering | 将融合区外的普通算子降为快速成本 command | 不执行目标融合区，不参与 naive/optimized 的后端选择 |
| Standalone collective lowering | 将融合区外、已经规划/投影的 collective action 降为 strict command fragment | 不走 legacy `CoreJob`，不重选 canonical algorithm |
| ISA region compiler | 消费 FusionPlan 与 IntraDieSchedule，生成分块 GEMM、P2P、本地 REDUCE、WAIT/BARRIER、SRAM lifecycle | 不重新选择跨 die拓扑、Swizzling 或片上映射 |
| ProgramLinker | relocation、buffer ABI、tag/token/group namespace、跨 region 依赖、所有权和唯一 control envelope | 不改变 policy 或 schedule 决策 |
| unified helper/runtime | 下发一条 `CoreCommandStream` 并产生一条完整 timeline | 不把两次独立仿真结果相加 |

```text
IR-0
  │ LogicalExpand
  ▼
expanded logical view
  │ Placement
  ▼
IR-1 + embedding
  │ FusionPartition → InterDiePolicy / CollectivePlan
  ▼
FusionPlan.rank_programs (per-rank Action DAG)
  │ ProjectToIR2
  ▼
projected per-die IntraDieDAG
  │ IntraDiePolicy: core / NoC route / banking / buffer / schedule
  ▼
scheduled IR-2 → GlobalActionDAG
       ┌────────────┼────────────┐
       ▼            ▼            ▼
 ordinary       standalone      fused
 JSON coarse    collective      ISA region
 lowering       lowering        lowering
       └────────────┼────────────┘
                    ▼
              ProgramLinker
                    ▼
        CoreCommandStream / linked artifact
                    ▼
        single strict helper → one timeline
```

#### GlobalActionDAG

```python
GlobalAction {
  id,
  kind: COARSE_COMPUTE | ISA_REGION | SEND | RECV | REDUCE | WAIT | BARRIER,
  die_id, core_hint, region_id, member_id, chunk_id,
  tensor_slice, buffer_ref, expected_route, port_id,
  logical_channel_or_event, deps: [action_id]
}
```

`GlobalActionDAG` 由 **scheduled IR-2** 构建。普通计算节点成为
`COARSE_COMPUTE`；融合区外、已由 collective plan 投影的 SEND/RECV/REDUCE/WAIT 进入
standalone fragment；同一 `FusionGroup` 的细粒度 COMP/通信/reduce/wait 进入
`ISA_REGION`。lowering 只翻译这些已决定的 action，不得补选 peer/chunk/barrier。
`ISA_REGION` 不是黑盒时间常数：它保留每核 action，因此会与普通 command、TRANSIT、
NoC/HBM/D2D 资源在同一时间线上竞争。

#### 融合区对跨 die 通信的所有权

首版采用“**JSON 决策、ISA 执行整个融合区**”：JSON planner 产生 per-rank `FusionAction`，
ISA compiler 将其中的跨 die collective 降为 P2P endpoint + local reduce。
这不意味着 ISA 自己决定了跨 die 编排；ISA 只是精确执行 JSON 已决定的计划。

```text
ISA MATMUL(chunk0) → P2P SEND/RECV(chunk0) → REDUCE/WAIT(chunk0)
        └────────── ISA MATMUL(chunk1) 可与 chunk0 通信交错 ──────────┘
```

不采用“JSON Recv → 一个整段 ISA → JSON Send”的三明治形式，因为它无法在两个
GEMM chunk 之间插入通信。若未来坚持“ISA 只算 GEMM、通信 command 仍由 coarse lowering 产生”，
则必须把 region 拆成可续接的 chunk fragment，并共享 event/buffer/token ABI；这不是首版路径。

#### Swizzling lowering 契约

为避免实现时重新落回 legacy JSON collective，以下五点是强制契约：

1. **目标融合区绕过旧 planner。** `naive` 与 `swizzle_topo` 的目标 collective 都必须直接消费
   `FusionPlan.rank_programs`，不得再调用 `PlanTier0Collective` 重新生成 peer/phase/barrier。
   旧 planner 只可作为 canonical 行为的 reference/oracle；非目标路径也只能复用其纯规划逻辑，
   不能复用 legacy materialization，更不能覆盖已确定的 Swizzling。

2. **独立 collective 有明确归属。** 融合区外的 AllGather、AllReduce、ReduceScatter 等走
   `StandaloneCollectiveLowering`，生成可重定位的 strict action fragment；可以复用 canonical
   algorithm 的纯规划逻辑，但不得向 legacy `coreconfigs.worklist` 追加独立 `CoreJob`。

3. **planner 只分配逻辑身份。** `FusionPlan`/IR-2 只携带 `logical_channel_or_event`；具体
   tag、async token、group/event ID 统一由 `ProgramLinker` 分配。任何 lowering fragment
   都不得预占全局运行时 ID。

4. **首版 route 是推导量，不是 source-route 指令。** `expected_route` 必须由 placement、peer
   和当前确定性路由规则推导，linker 校验 endpoint 实际路径与其一致。planner 可通过改变
   rank/peer/placement 选择不同路径，但不能声称强制任意 route；若未来支持可编程 source route，
   必须新增独立 capability、schema version 和冲突测试。

5. **时序验收与数值验收分开。** `U3-T` 必须验证 action 顺序、slice/bytes/dtype、流量、资源占用
   和周期；只有实现真实 payload 或等价的确定性 functional oracle 后，`U3-F` 才能宣称 reduction
   数值正确。默认 FP16 SUM 契约为 FP16 输入、FP32 accumulate、round-to-nearest-even cast 到
   声明的输出 dtype；其他累加/舍入语义必须进入 spec 和缓存键。未通过 `U3-F` 时不得作数值正确性 claim。

### 8.3 统一执行表示：`CoreCommandStream`

```python
CoreCommandStream {
  per_core: { core_id -> [Command] },
  owned_prims,
  buffer_table,
  event_table,
  core_group_registry,
  collective_program_image,
  control_envelope
}

Command = CoarseCompute
        | IsaPrim
        | Send | Recv | Reduce
        | Wait | Barrier
```

三个硬约束：

1. **统一 ownership**：命令流拥有所有 prim；`CoreJob` 只保存稳定引用，不再让
   `g_prim_stash` 与多个 fragment 分别负责生命周期。
2. **统一 transport**：整次运行使用 strict wire。普通 JSON coarse op 需要适配为
   stable record 或新增 strict `CoarseCompute` command，不能夹带 legacy-only wire。
3. **单一 helper**：Monitor 只看到一个 helper、一个 group registry、一个 collective image
   和一个 ACK/DONE envelope。是否需要调整 Monitor/Executor 由实现验证决定，本文不再承诺“运行时零改动”。

静态 MVP 中，三类 lowering 先生成**可重定位、未提交**的 command fragment；`ProgramLinker`
再把它们合成一份 `LinkedProgramArtifact`，最后由 finalizer 一次性生成 collective image 并安装，
复用一个 `config_helper_program`。长期动态模式再抽象通用 `config_helper_unified`。
这里的 ISA region lowering 与最终 artifact finalization 是两个阶段：多个 fragment 不能分别调用
`LowerIsaV1CollectiveArtifact` 后再拼 image；plan index、cookie、group ID 会冲突。

### 8.4 Region ABI 与 ProgramLinker

```python
RegionManifest {
  id, target_dies, logical_cores, records,
  inputs:  [BufferBinding],
  outputs: [BufferBinding],
  entry_events, exit_events,
  relocations, resource_requirements
}

BufferBinding {
  logical_tensor, tensor_slice, core,
  region, offset, bytes, alignment,
  dtype, layout, lifetime, ownership,
  producer_event, consumer_event
}
```

字符串 `label_bind` 不能作为边界 ABI：同名 label 不保证地址、大小、layout、生命周期或
producer 完成状态一致。ProgramLinker 必须完成：

1. 按 placement 重定位 die/core/peer ID；
2. 分配全局唯一的 tag、async token、group/event ID；
3. 合并 SRAM region，校验 offset/size/alignment/bank/lifetime；
4. 将已 lowering 的 ISA region fragment 接入各核 command stream，并连接 entry/exit event；
5. 校验每对 SEND/RECV 的 tensor slice、bytes、dtype、逻辑 channel 和 `expected_route`；
6. 校验 ReduceScatter 的 `output_permutation/inverse_permutation` 为双射；region 出口必须
   显式恢复 canonical layout，或证明每个后继的 `consumer_layout_binding` 接受 physical layout；
7. 校验 command DAG 无环、buffer 容量、SAF flow 上限和唯一 ACK/DONE envelope；
8. 所有检查通过后再一次性 finalization/commit，保持强异常安全。

### 8.5 静态模式与动态模式

#### 静态桶：精确主路径

训练 step 和推理模式 A 对每个 profile 生成一份 linked artifact。普通算子仍使用 coarse
成本 command，只有目标融合区展开为细粒度 ISA；二者在一次仿真中共享端口、NoC、HBM、
SRAM 和 D2D 时间线。这是论文主消融的精确路径。

#### 在线 PDS：两阶段支持

**首阶段（多保真）**：`config_helper_pds`/scheduler 产生请求与 ProfileKey/arrival 序列；
`scheduler_model` 查询由静态联合仿真标定的条件 surrogate（§8.8），并为每个候选配置重新闭环。
若只消费预测 makespan，该模式不重放 boundary flow，不能声称捕获同时发生的
NoC/端口/HBM/SPM 竞争与背压；这些属于 surrogate 的明确保真度边界。

**长期（精确）**：统一 strict helper 支持：

```python
RegionCall {
  profile_key,
  variants: {shape_guard -> linked_region},
  buffer_bindings, entry_event, exit_event
}
```

运行时只做 guard 匹配，选择覆盖当前 shape 的最小预链接 variant；所有 command 仍进入同一
`CoreCommandStream`。这要求先解决独立 `tp_P/tp_D`、持久 KV handoff、动态 buffer 和 prim ownership。

### 8.6 融合仍表达成“调度”，不是新 opcode

保留原结论：不新增 `GEMM_REDUCE_SCATTER` opcode，也不使用手工注入 cycle 的
`Gemm_rs_swizzle` 作为稳定实现。变化只在于：目标融合区的 naive 与 optimized
都由同一个 ISA region compiler 产生，而不是 naive 走 JSON、optimized 走 ISA。

```text
naive region:
  MATMUL(whole) → P2P/REDUCE_SCATTER(whole)

optimized region:
  MATMUL(c0) → SEND/RECV/REDUCE(c0)
  MATMUL(c1) 与 c0 通信交错 → WAIT(c0) → ...
```

二者要求相同数学工作量、输入/输出 layout 和 collective 语义，但 record 数、消息数、
buffer 与启动开销可以不同——这正是需要由同一 ISA 成本契约真实计入的优化代价。
普通非目标算子在两组实验中始终走同一 JSON coarse lowering。

### 8.7 必要改动与验收

#### 实现阶段

| 阶段 | 内容 | 验收产物 |
|---|---|---|
| **B0** | FP16/FP32 local reduce + 跨 die P2P endpoint lowering；固定累加/舍入语义，消息按 endpoint/SAF 上限切块 | 2 die × 1 core 的 FP16 RS，分别通过 U3-T/U3-F |
| **B1** | owned `CoreCommandStream`、strict `CoarseCompute`/`StandaloneCollective` adapter、单 helper/control envelope | coarse + 非 reduction standalone collective 与现有 JSON 成本对齐 |
| **B2** | `RegionManifest`/`BufferBinding`、relocation、tag/token namespace、ProgramLinker | 单 die coarse→ISA→coarse mixed stream |
| **B3** | ISA region compiler 消费完整 FusionPlan；生成 chunk GEMM/P2P/reduce/wait | 2 die GEMM+RS naive/optimized |
| **B4** | 多核/多 die collective image、TRANSIT/NoC 资源联动、完整静态桶 | 小规模“全开”精确 timeline |
| **B5** | strict `RegionCall`、动态 variant、PDS/KV buffer ABI | 长期在线精确模式 |

#### 测试阶梯

已有 `program_legacy_compute_diff` 继续作为单核算子成本的 A0 基础，但主验收改为统一命令流：

| 测试 | 覆盖 | 判据 |
|---|---|---|
| **U0** | coarse op 与对应稳定 compute record | 算子顺序、成本和归一化 span 对齐 |
| **U0-P** | PassManager / ProjectToIR2 顺序 | 缺少完整 rank_programs 时拒绝投影；投影节点的 origin_ref 全部可回溯且不得重选 peer/deps |
| **U0-M** | IntraDiePolicy / schedule simulator 前置条件 | 缺 core placement、route、banking 或 buffer binding 的 DAG 不得进入性能模拟 |
| **U0-S** | FusionSemanticValidator 非法/合法图集 | 拒绝 reduction 前 bias/activation、tile/layout 不闭合、危险外部 consumer/effect；接受正确 post-reduction epilogue |
| **U0-R** | FusionPlanValidator owner/buffer 图集 | 拒绝非双射/缺失 inverse permutation 与峰值 SRAM 超限；接受显式 restore 或 layout-aware consumer |
| **U1** | SRAM lifecycle、双缓冲、DTE issue/wait | buffer 生命周期与异步 token 无泄漏 |
| **U2** | `coarse → ISA region → coarse` | entry/exit event、BufferBinding、ownership 正确 |
| **U3-T** | 2 die P2P + FP16 local reduce 的时序路径 | action/deps、bytes/dtype/slice/channel、资源和周期正确 |
| **U3-F** | 同一 case 的 functional payload/oracle | FP32 accumulate、舍入和输出 slice 数值正确；未通过时不得作数值 claim |
| **U4** | 2 die chunk GEMM+RS | trace 证明 chunk0 通信与 chunk1 计算真实重叠 |
| **U5** | naive/optimized 同一 ISA lowering | 除 FusionPlan/Action DAG 外，模型、placement、普通算子 backend 均一致 |
| **U6** | 2×2 含 TRANSIT 的 inter×intra 联合运行 | 无死锁；端口/NoC/D2D 计数守恒 |
| **U6-S** | 条件 surrogate 的 2×1/2×2 holdout | 报告时间/speedup 误差、排序相关性、top-k regret 与域外 fallback；排序不稳定则不得用于选最优 plan |
| **U7** | `RegionCall` 动态 dispatch（长期） | shape guard、variant、动态 buffer 与 PDS 时序正确 |

每个测试须先书面定义允许的归一化差异。CONFIG 下发机制可以归一化；
实际 compute/DTE/reduce 成本、资源占用和 region 边界不得通过放松判据掩盖。

### 8.8 规模过大时的条件 surrogate fallback

统一命令流的静态精确仿真是 ground truth。**surrogate（代理模型）**是用一组联合精确仿真样本
拟合出的快速近似函数，用于大规模候选剪枝或首阶段在线调度闭环；它不是第二个仿真器，也不是
把单 Die 空载时间保存成一个标量后回填满配。

两个技术点共享 C2C port、transit NoC、HBM、SPM/buffer、发包时刻和背压，因此一般有：

```text
T_full(inter_plan, intra_schedule, scenario)
  != T_inter(inter_plan) + T_intra(intra_schedule)
speedup_full != speedup_inter * speedup_intra

T_full = T_base + Δinter + Δintra + Δinteraction
```

单 Die 空载运行只能观察局部计算/搬运，不能恢复 `Δinteraction`：intra schedule 改变 chunk
release time 和突发流量；inter plan 又会反过来改变 RECV 占用、transit、NoC/HBM 竞争与 buffer
backpressure。因此 `LUT[shape] -> time` 不能直接合成为“全开”。

若确需 surrogate，输入必须描述影响交互的条件，而不是只给 shape：

```python
SurrogateKey {
  profile: ProfileKey,
  op_shapes, dtype, tensor_layout,
  fusion_partition,
  plan: {
    collective_algorithm, chunk_slices, chunk_owner,
    phase_peer_deps, expected_routes
  },
  physical: {
    die_and_core_placement,
    ingress_egress_ports, noc_routes, spm_banking
  },
  temporal: {
    release_or_arrival_trace,
    concurrent_flows, background_resource_load
  },
  memory: {
    hbm_load, kv_residency,
    spm_and_buffer_capacity, initial_buffer_occupancy
  },
  d2d_mode
}

SurrogatePrediction {
  region_or_iteration_makespan,
  boundary_flow_trace: [{port, release_time, bytes, duration}],
  resource_occupancy: {C2C, NoC, HBM, SPM_buffer},
  peak_sram, stall_breakdown,
  uncertainty, calibration_domain
}
```

只预测一个 `makespan` 可供 `scheduler_model` 做低保真闭环，但不能再与其他标量时间
相加来模拟共享资源；顶层事件模拟器若要表达竞争，必须消费带时间的 boundary flow/resource
occupancy。任何输出都必须标明训练域与不确定度，超出 `calibration_domain` 时回退精确仿真，
或明确标注为外推结果。

#### 标定与 holdout 验收

标定数据必须来自 **inter-die 与 intra-die 两个优化同时开启** 的统一命令流精确运行，而不是分别
测两张表。至少覆盖 2×1 和 2×2，并包含不同 profile、chunk/owner、端口重叠、arrival trace、
并发流与内存压力。数据按 plan/placement/trace 配置拆分 fit/calibration/holdout，不能把同一
trace 的相邻样本随机拆到训练和 holdout 造成泄漏。

holdout 至少报告：

- makespan 的绝对误差、相对误差及尾部分位误差；
- naive/optimized speedup 的误差；
- 候选排序的 Spearman/Kendall 相关性；
- 预测 top-k 命中率，以及“预测最优方案”相对真实最优方案的 regret；
- 超出校准域的比例和触发精确 fallback 的比例。

论文的静态“全开”主结果仍使用精确联合仿真。surrogate 结果必须单列为多保真/规模扩展结果；
即使平均时间误差较小，只要候选排序不稳定，就不能用于声称找到最佳 Swizzling/片上编排。

## 9. 替换接口与消融矩阵

```python
ShardingDerivation: (IR0.ops, DeviceMesh) -> {value_id -> Sharding}
CollectiveInsertion: {value_id -> Sharding} -> [CollectiveOp]
LogicalExpand:       IR0 -> ExpandedLogicalView
Placement:           (ExpandedLogicalView, PhysicalFabric) -> IR1
FusionPartition:     (IR1, semantic_candidates) -> [FusedOpSkeleton]
InterDiePolicy:      (IR1.embedding, FusedOpSkeleton, profile) -> FusionPlan
ProjectToIR2:        (IR1, {fused_op -> FusionPlan}) -> [IntraDieDAG]
IntraDiePolicy:      IntraDieDAG -> IntraDieSchedule
GlobalActionDAGBuilder: (IR1, [IntraDieSchedule]) -> GlobalActionDAG
CoarseLowering:      ScheduledOrdinaryOp -> CoarseCompute
StandaloneCollectiveLowering: ScheduledCollectiveAction -> StandaloneCollectiveFragment
IsaRegionLowering:   (FusionPlan, IntraDieSchedule) -> RegionManifest
CommandFragment = CoarseCompute | StandaloneCollectiveFragment | RegionManifest
ProgramLinker:       (GlobalActionDAG, [CommandFragment]) -> CoreCommandStream
```

`ShardingDerivation`、`CollectiveInsertion`、`LogicalExpand`、`ProjectToIR2` 与
`GlobalActionDAGBuilder` 是确定性变换，不作为消融变量。三个 policy 接口
`FusionPartition / InterDiePolicy / IntraDiePolicy` 对应三个独立优化维度；其余接口是固定执行基础设施。
尤其 `ProjectToIR2` 必须消费完整 FusionPlan，`IntraDiePolicy` 必须先完成物理映射，
后续 simulation 才有定义。

| 维度 | naive | optimized | 后端约束 |
|---|---|---|---|
| **融合划分** | 候选区内 GEMM 与 collective 串行、有显式 barrier | 成组；可再细分「仅 GEMM+coll」vs「含相邻计算算子」 | 两边都由 ISA region compiler lowering |
| **跨 die 编排** | rank 序、朴素 chunk/phase | 物理环序或搜索得到的 Swizzling | 两边都生成完整 per-rank FusionAction |
| **片上编排** | 朴素核放置 / 路由 / banking | 优化 | 两边都链接到同一 CoreCommandStream |

融合候选区之外的普通算子在所有实验中始终走同一个 JSON coarse lowering。
融合候选区之外的 collective 始终走同一个 `StandaloneCollectiveLowering`。
“不融合”不能通过把 GEMM 退回 JSON、把 optimized 留在 ISA 来实现；
应由同一 ISA compiler 生成带 barrier 的串行 region，从而只比较调度差异。

主消融矩阵仍取跨 die 编排 × 片上编排的 2×2；融合划分作为敏感性分析。
每个格子使用相同模型、placement、profile、普通算子 cost model、transport 和 linker。

## 11. 分阶段计划

分成可并行的**前端/策略线（F）**与**统一执行线（B）**，在 F5/B3 汇合。

### 前端 / 策略线

| 阶段 | 内容 | 依赖 | 产出 |
|---|---|---|---|
| **F0** | `PhysicalFabric`/资源图 + `GroupRegistry`；提供 route/resource-capacity 查询，但不在无 placement 时生成具体 embedding | 无 | fabric/route 单测 |
| **F1** | IR-0 生成 + `LogicalExpand`：层模板、切分、collective 插入、反向代理、语义候选预检 | F0 | `ir0.json` + expanded logical view + CI 断言 |

| **F4** | `ProjectToIR2` 物化 region/flow/TRANSIT，再执行 `IntraDiePolicy` 的 core/NoC/banking/buffer/schedule，最后构建 `GlobalActionDAG` | F3 | 可回溯到 `(plan_id,rank,action_id)` 的 scheduled per-die graph |

| **F7** | 大规模 surrogate/在线 scheduler 闭环；长期接 `RegionCall` | F6；精确在线另依赖 B5 | 多保真结果或在线精确结果 |

### 统一执行线

| 阶段 | 内容 | 依赖 | 产出 |
|---|---|---|---|
| **B0** | 2 die P2P endpoint + FP16/FP32 local reduce + functional oracle + chunk 上限处理 | 无 | 2 die × 1 core FP16 RS 的 U3-T/U3-F |
| **B1** | owned `CoreCommandStream` + strict `CoarseCompute`/`StandaloneCollective` adapter + 单 control envelope | 无 | coarse + standalone non-reduction strict 运行 |
| **B2** | `RegionManifest`/`BufferBinding` + relocation/tag/token + ProgramLinker | B1 | coarse→ISA→coarse 单 die验收 |
| **B3** | ISA region compiler 消费 FusionPlan，生成 GEMM/P2P/reduce/wait | B0、B2 | 2 die chunk GEMM+RS |
| **B4** | 多核/TRANSIT/collective image 集成，完成 U0–U6（含 U3-T/U3-F） | B3 | 静态 unified backend |
| **B5** | strict `RegionCall`、variant dispatch、PDS/KV 动态 buffer | B4、缺口 4–6 | 长期在线精确 backend |


### 依赖要点

- **F3→F4 是硬依赖**：IR-2 的 SEND/RECV/REDUCE/WAIT/TRANSIT 与 chunk deps
  来自完整 per-rank FusionAction；禁止先生成 IR-2 再“补”Swizzling。
- **F4→F6 是物理闭环顺序**：候选 partition/tiling 必须先做 core placement、route、banking、
  buffer 与 schedule，再仿真并反馈；未映射 DAG 的解析下界只能剪枝，不能作为性能结果。
- **F5 必须依赖 F3/F4**：ISA region compiler 消费确定的 FusionPlan 与 IntraDieSchedule，
  不能生成与 inter-die plan 或片上映射无关的 artifact。
- F0/F1 可与 B0/B1 并行；F2/F3 是纯前端决策，不依赖 backend 完成；F5 才与 B2/B3 汇合。
- 静态主结果在 F6 直接运行 linked artifact，不再默认用单 die 标量 LUT 回填。
- F7 的多保真结果必须由 F6/B4 的小规模联合精确运行校准；长期在线精确模式才依赖 B5。
- PD 分离的完整实验还依赖持久 KV handoff；MoE 不阻塞 dense 主线。

## 12. 术语

- **IR-0 / IR-1 / IR-2**：逻辑图 / 物理图 / 单 Die 图，本方案的三个中间表示。
- **DeviceMesh**：多轴逻辑设备网格（`axes = [{name, size}]`），取代早期的单一 `LogicalGroup`；
  一个张量可同时被多个轴切分。
- **Sharding**：张量在某个 mesh 上的切分状态，`dim_map`（张量维→mesh 轴）+ `partial`（该轴上为未归约部分和）。
- **partial**：行并行 GEMM 输出的未归约状态。它是让 §3.3 四条规则**可推导而非硬编码**的关键机制；
  collective 的类型与通信量由 `(in.sharding → out.sharding)` 的差量推导得出。
- **IntraDieDAG / IntraDieSchedule**：IR-2 的语义层与决策层。前者描述必须发生什么，
  后者描述怎么发生（placement/binding/routes/tags/tokens/order）；
  `IntraDiePolicy` 是二者之间的函数。
- **BufferBinding**：buffer 到 `region/offset/size/bank/lifetime` 的绑定，属于 Schedule 而非 DAG；
  `bank` 与 `lifetime` 是片上编排的核心决策变量。
- **embedding**：逻辑 group 到物理 die 网格的静态嵌入，包括 rank→die、route、hop、资源关联矩阵、逐资源容量与过境资源。
- **canonical bandwidth profile**：给定 `(mapping, traffic template, d2d_mode)` 后得到的静态容量签名；mapping 单独不能定义等效带宽。
- **lane_eq_bandwidth**：按约定逻辑 lane/归一化 flow 权重折算的速率，用于和单链路带宽比较。
- **aggregate/logical goodput**：有用逻辑字节除以实际完成区间，可因多链路并行而高于单链路带宽。
- **plan-specific bandwidth / PlanEvaluation**：具体 plan 在给定并发场景下的资源负载、通信区间与 makespan；它不是 group embedding 的固定常数。
- **KvTransferProfile**：由 P/D 分片、placement、token bucket 和 D2D 模式共同确定的逐层 KV flow/resource 静态描述。
- **TRANSIT**：过境流量——某 die 转发它既不产生也不消费的跨 die 数据；以 `flow_id` 链接到统一资源时间线。
- **reshard**：`tp_P ≠ tp_D` 时 KV 在两个不同大小的 group 之间重新分片。
- **ProfileKey**：运行形状的**多维**键（`prefill_tokens/decode_tokens/num_seqs/context_sum/
  context_max/kv_pages/expert_load`），取代早期的标量 M——相同 M 可来自 prefill/decode/混合，
  attention 与 KV 代价相差数量级。
- **支配覆盖（dominance）**：profile P 可服务形状 S，当且仅当 P 在**每个维度**上 ≥ S；
  运行时取满足者中最小的，无覆盖则显式 fallback。区别于标量下的「最近桶 + padding」。
- **m_spec / profile**：运行形状的值域与分布；静态模式逐 profile 编译，动态模式按 shape guard 选择 variant。
- **模式 A / 模式 B**：静态桶统一执行 / 在线调度器驱动；模式 B 首版是多保真，长期才支持精确 `RegionCall`。
- **surrogate / 条件代理模型**：由联合精确仿真标定的快速近似模型；输入必须包含 plan、物理映射、并发与内存状态，输出带不确定度的 makespan/边界资源轨迹。它只用于剪枝或多保真闭环，不是真值。
- **JSON/IR planner**：负责 placement、collective algorithm、rank/chunk/phase/peer 和 FusionPlan，并按确定性路由规则推导 `expected_route`；不负责 ISA 地址或运行时 tag/token 分配。
- **JSON coarse lowering**：将融合区外普通算子转换为快速 `CoarseCompute` command 的适配层。
- **Standalone collective lowering**：将融合区外 collective 转换为 strict SEND/RECV/REDUCE/WAIT fragment 的固定适配层。
- **ISA region**：同一融合区的分块 GEMM、P2P SEND/RECV、本地 REDUCE、WAIT/BARRIER 与 SRAM lifecycle 的细粒度程序。
- **GlobalActionDAG**：三类 lowering 之前的全局 action 与依赖图，是 policy 决策和执行链接之间的边界。
- **CoreCommandStream**：三类 lowering 汇总后的 owned、strict、per-core 执行表示；一次仿真只运行一份。
- **RegionManifest / BufferBinding**：ISA region 的入口/出口、tensor slice、地址、layout、生命周期和 event ABI。
- **ProgramLinker**：在 artifact finalization/commit 前完成 relocation、buffer、tag/token/group、依赖和 control envelope 合并的组件。
- **RegionCall**：长期动态模式下按 shape/profile 选择预链接 ISA variant 的 strict command。
- **归一化契约**：对齐测试中允许哪些 lowering/下发机制差异、为什么允许的显式清单。
- **FusionGroup**：IR-0 中的候选算子分组；“Schema 可容纳任意成员”不代表可任意重排，必须通过语义与资源两阶段校验。
- **FusedOp**：`FusionGroup` 通过语义校验并经 placement 后在 IR-1 中的物化形式，携带仍需资源校验的 `FusionPlan`。
- **FusionPlan**：JSON planner 产出的 collective algorithm、chunk/owner、per-rank Action DAG、`expected_route` 与双向 layout permutation；ISA compiler 原样消费。
- **凸子图**：融合合法性的图论约束之一——成员连通且无“出组再回组”的外部路径；它不能替代 reduction、layout、consumer、副作用、数值和 SRAM 校验。
