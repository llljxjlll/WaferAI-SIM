# 阶段 0 开发报告：能力真相与 Policy Wiring

## 1. 阶段结论

阶段 0 已完成。该阶段没有增加任何 optimized 能力，也没有扩大训练、decode、PD/KV 或
MoE 的支持范围；它把已有 naive baseline 与尚未实现的能力变成可重算、不可冒认的机器
可读事实。

当前结论仍是：

- S1 研究覆盖 3.5/6；
- S1 顶层验收 1/3；
- E1 TP2/L1 和 E2 TP4/L2 为 e2e-timing；
- 单 die 图闭包为 unit-only；
- optimized/swizzle、decode、PD/KV、S2 和 S3 均未因声明或枚举存在而升级状态。

## 2. 需求理解与形式化

CapabilityStatus 的 wire 值固定为 unsupported、schema-only、unit-only、e2e-timing 和
e2e-functional。状态与分数是两个独立维度：GEMM+collective baseline 得 1/2 分表示
对比项已有 naive 一侧，不代表存在 optimized 实现。

CaseMatrix 同时列出当前 baseline case 与开发方案 §6 的 S1、S2、S3 case。没有 evidence
的 case 必须保持 unsupported。CapabilityManifest 只能由 CaseMatrix 和有 digest 的
CaseEvidence 纯函数派生，调用方不能直接填写 claim、score 或 acceptance。

## 3. 软件架构

阶段 0 分为五个可独立验证的切片：

1. 0A：CaseMatrix、CapabilityManifest、显式 Fraction 计分和 exact evidence closure；
2. 0B：PolicySelection 与带版本/实现/config/capability 元数据的 registry；
3. 0C：compile_naive 只经 registry 实例化 inter、standalone 和 intra policy；
4. 0D：selection 进入 N4/N5 context、PassReceipt、NaiveCompilation 与 NaiveRunReport；
5. 0E：持久 E1/E2 证据、checked manifest 和 digest review。

production registry 只激活 naive 实现。swizzle_topo 与 optimized 保持 declared-but-unavailable，
选择后在首个 pass 前失败，且不会创建 runner 输出或遗留 lock。

## 5. 持久证据与重新冻结政策

证据目录：`notes/frontend/baselines/stage0-policy-provenance-v1/`。

每个 E1/E2 子目录保留输入快照、linked manifest、pass receipts、stage digests、ProgramArtifact、
finalizer report、ProgramIo、两次运行日志、解析 marker 和最终 report。顶层另有：

- `case_matrix.json`；
- `capability_manifest.json`；
- `baseline_review.json`。

baseline_review 记录原/新 artifact SHA、report digest、语义 fingerprint、计数、通信量、
makespan、生成命令和审批结论。此前没有持久 report，因此 prior_report_digest 明确为 null，
不伪造旧 digest。后续禁止因测试变红直接更新这些文件；必须通过同一 freeze 工具重建，并
提交版本原因、结构差异和 review。

## 6. 限制与下一阶段

阶段 0 不支持 decode_tokens>0、持久 KV、P/D 分离、training 或 MoE，也没有 optimized
policy。下一阶段 1a 只实现 HBM-backed persistent parameter/KV/state、显式 DMA 和最小
STEP/PERSISTENT lifecycle；地址扩宽、通用 reuse、spill 和 alias 保留到阶段 1b。
