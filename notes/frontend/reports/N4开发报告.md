# N4 开发报告：Naive FusionPartition 与 Inter-die Action DAG

## 1. 阶段结论

N4 已把 N3 的逐 Profile `PlacedIR1Bundle` 转成完整、可校验、可稳定序列化的
`InterDiePlanBundle`。当前实现只提供 deterministic naive baseline：选择数学合法的
`row-parallel GEMM → SUM ReduceScatter` region，并为这些 region 及独立 AllGather 展开逐 rank
Action DAG；不生成 IR-2，也不实现 ring、tree、Swizzling 或优化搜索。

本阶段把“选哪些算子融合”和“这些算子怎样跨 Die 执行”拆成两个独立 pass：

```text
PlacedIR1Bundle
  → FusionPartitionContext + fusion_partition
  → FusionPartitionedIR1Bundle       # skeleton.impl = NONE
  → InterDiePlanningContext + inter_die_plan
  → InterDiePlanBundle               # FusionPlan.impl = NAIVE
```

因此未来替换 Swizzling policy 时，不需要重做语义分区、placement、IR-2 或后端 ABI。

## 2. 需求理解与模型形式化

### 2.1 FusionPartition 边界

`NaiveFusionPartition` 只消费 N3 保留的 `FusionCandidate`，并选择全部合法候选。每个 region 必须：

- 恰为两个成员，顺序为 row-parallel GEMM、SUM ReduceScatter；
- 两成员属于同一 instance、stage、phase 和 execution group；
- 只有一条直接 GEMM partial → ReduceScatter DATA edge；
- partial 没有 region 外 consumer；
- boundary、layout、tile domain、reduction axis 和 numerical policy 与候选完全一致；
- 不包含 bias、residual、activation 或有副作用节点；
- 不与其他已选 region 重叠。

分区产物中的 `FusedOpSkeleton.impl` 固定为 `NONE`。Skeleton ID 只由 region 语义决定，不含
Profile 或 IR-1 ID；相同模型结构在不同 Profile 下得到相同 region ID。任意候选漏选、重排、冒认
ID 或偷偷写入 `NAIVE` 都会被 wrapper 拒绝。

### 2.2 Naive fused GEMM + ReduceScatter

设 TP rank 数为 `P`，RS 逻辑输出为 `[M,N]`，首版要求 `M % P == 0`。计划固定为：

- 沿 M 轴均匀切成 `P` 个 chunk，`chunk_owner[c] = c`；
- physical/logical output layout 相同；forward/inverse permutation 均为 identity；
- 每个 `(rank, chunk)` 恰有一个 chunk-local GEMM `COMP`；
- 非 owner 的贡献通过唯一 `SEND/RECV` channel 发往 owner；
- owner 对每个 remote `RECV` 建显式 `WAIT`；
- owner 按 rank 0..P-1 的固定顺序执行唯一 `REDUCE`；
- reduction 固定为 `SUM FP16 → FP32 accumulate → FP16 RNE`；
- 不同 chunk 之间不伪造依赖，后续 N5 可以保留或收紧 overlap，但不能改变数学顺序。

每条 SEND/RECV 的 peer、route、bytes、dtype、chunk、slice、collective step 和 logical channel
必须完全配对。Route 只读取 N3 `PairRoute` 的 source→destination X-then-Y 路径；policy 不重新选路。

### 2.3 Chunk-local GEMM

N4 修正了“每个 chunk 重复携带并执行整个 rank GEMM”的错误。现在每个 `COMP` 同时携带：

- `ComputeContract.workload`：当前 chunk 的 GEMM workload；
- `ComputeTileBinding.origin_workload`：原始完整 GEMM；
- A 的 M-axis slice；
- B 的完整逻辑 slice；
- partial output 的当前 chunk slice。

若原 row-parallel GEMM 的 logical/rank shape 分别为 `(M,N,K)` 与 `(M,N,K/P)`，每个 chunk 的
shape 为 `(M/P,N)`，则每个 action 的 rank-local work 为：

```text
2 × (M/P) × N × (K/P)
```

全体 `rank × chunk` 的 work 总和严格等于一次全局 GEMM `2MNK`，不会多算 `P` 倍。

### 2.4 Standalone AllGather

未被 fused region 覆盖的 collective 只有 AllGather 可进入首版 standalone policy：

- 沿 workload 声明的 gather tensor axis 均匀切 `P` 个 canonical chunk；
- owner rank 先 `LOCAL_COPY(input shard → output chunk)`；
- owner 按 rank 顺序 fan-out SEND，其他 rank 建匹配 RECV；
- 每个 rank 最后执行一个共享 `PLAN` scope barrier；
- barrier deps 按 chunk 顺序覆盖本地所有 LOCAL_COPY/RECV completion。

未融合 ReduceScatter、AllReduce、AllToAll、Broadcast 等均 fail closed，不会静默转成 AllGather 或旧
JSON collective。

## 3. 软件架构与开发切片

N4 按可独立验证的小切片完成：

1. Action schema：加入 chunk-local GEMM tile/operand slice、`FusionPlan.impl`、显式 WAIT 与 canonical
   fused/AllGather validator，升级到 `v1alpha7`。
2. Provenance schema：加入两个 typed context、partition/profile bundle 和 planning/profile bundle，证明
   Profile、weight、source entry、IR-1、placement/partition/planning context 的完整闭包。
3. Partition policy：实现 `NaiveFusionPartition.run(ir1)`，只输出 `impl=NONE` skeleton。
4. Partition producer：实现 `partition_ir1`、`partition_bundle`，只允许在 N3 placement 结果上增加
   skeleton。
5. Inter-die policy：实现 `NaiveInterDiePolicy` 和 `DirectAllGatherPolicy`，生成 canonical per-rank
   programs。
6. Planning producer：实现 `plan_profile`、`plan_bundle`，按 skeleton 顺序生成 fused plan，按 graph node
   顺序生成 standalone plan。
7. PassManager integration：两个 pass 使用不同 context digest，主 artifact digest 仍保持连续。

所有 producer 依赖 `FusionPartition`、`InterDiePolicy`、`StandaloneCollectivePolicy` Protocol，naive 只是
默认实现；falsey 自定义 policy 不会被默认实现覆盖。optimized implementation 尚未注册，也不会回退到
naive。

## 4. 数值与结构验证

### 4.1 TP=2 / TP=4 policy golden

单个 fused region 的 action 数量：

| TP | COMP | SEND | RECV | WAIT | REDUCE | 总数 |
|---:|---:|---:|---:|---:|---:|---:|
| 2 | 4 | 2 | 2 | 2 | 2 | 12 |
| 4 | 16 | 12 | 12 | 12 | 4 | 56 |

单个 standalone AllGather 的 action 数量：

| TP | LOCAL_COPY | SEND | RECV | BARRIER | 总数 |
|---:|---:|---:|---:|---:|---:|
| 2 | 2 | 2 | 2 | 2 | 8 |
| 4 | 4 | 12 | 12 | 4 | 32 |

TP=2 与 TP=4 均验证了：rank/chunk 完整覆盖、消息数、总 bytes、N3 route、channel 唯一性、WAIT lineage、
rank-major reduction 和共享 AllGather barrier。TP=4 的每个 fused rank program 恰有 14 个 action，
每个 AllGather rank program 恰有 8 个 action。

### 4.2 实际 sample 端到端 N4 golden

使用 `valid_spec` 的单层 TP=2 Dense sample 和真实 `hardware_numa.json`：

- 2 个 fused GEMM+RS plan；
- 2 个 standalone AllGather plan；
- 共 40 个 action；
- 8 个 SEND；
- SEND 总 payload 为 65,536 bytes；
- 两个 fused region 的 chunk-local GEMM work 总和为 12,582,912 FLOPs；
- output layout/permutation 保持 canonical identity；
- JSON round-trip 和重复编译的 bundle/snapshot digest 完全相同。

这一步只验证静态 plan 数学和通信闭包；N0 已单独验证 FP16/FP32/RNE backend functional oracle，N5/N6
才把这些 actions 投影、排程、lower 并执行。

## 6. 当前限制与 N5 边界

N4 明确不支持：

- ring/tree/recursive-doubling/Swizzling 搜索；
- 非 identity chunk owner/permutation；
- standalone 非 AllGather collective；
- 动态 arrival/PDS；
- source routing、非 N3 canonical route；
- IR-2、core mapping、SPM allocation、intra-die schedule、GlobalActionDAG；
- JSON/ISA lowering、manifest linking 或 simulator execution。

N5 必须消费完整 `InterDiePlanBundle`，新增逐 Profile 的 projection/schedule provenance wrapper；不能把
multi-profile bundle 降成无来源的单份 raw `(ir1, plans)`。`ProjectToIR2` 只能翻译 N4 已决定的 action，
不得重新选择 peer、route、chunk、owner、reduction 顺序或 barrier。

## 7. N4 退出条件

N4 的退出条件已经满足：

- fusion region 只含数学合法的 partial GEMM + RS；
- partition 与 inter-die planning 是两个显式、可 digest 的 pass；
- TP2/TP4 per-rank Action DAG 完整，SEND/RECV 一一配对；
- chunk GEMM work、collective bytes、layout、permutation 和 numerical order 可重算验证；
- standalone AllGather 完整且不依赖旧 JSON planner；
- optimized policy 缺失时 fail closed；
- 输出仍停在 N4，不提前产生 IR-2 或调度结果。
