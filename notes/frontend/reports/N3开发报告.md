# N3 开发报告：固定 Placement 与 IR-1

## 1. 阶段结论

N3 已把 N2 的逐 Profile Dense IR-0 绑定到确定的物理 Die mesh，并生成可独立校验、可稳定序列化的
`PlacedIR1Bundle`。当前输出只包含 placement、pair route、资源容量和 canonical traffic profile；它保留
全部普通算子、TensorValue、GraphEdge 和 `FusionCandidate` 的逻辑 ID，不包含 `FusionPlan`、Action
DAG、IR-2 或已选择的 `FusedOpSkeleton`。

这条边界保证 N4 才开始选择融合候选和 collective 算法，不会在 placement 阶段偷做 Swizzling 决策。

## 2. 需求理解与模型形式化

### 2.1 输入与输出

- 主输入：`ExpandedIR0Bundle`，每个 `ProfileKey` 拥有一份独立 IR-0。
- 显式上下文：`PlacementContext(PhysicalFabric, PlacementSpec, traffic_templates)`。
- 输出：`PlacedIR1Bundle`，每个输入 Profile 恰好对应一份 IR-1。

`PassManager` 将主输入 digest 与 placement context digest 分开记录。因此只修改 hardware 或
placement 时，N2 产物保持可复用，N3 及其下游失效；placement 不能通过未记录的闭包读取 hardware。

### 2.2 Placement

首版只支持单 instance、单 replica、单个一维 TP mesh：

- `compact`：rank 按 `die_id` 的 row-major 顺序映射到前 `TP` 个 Die；
- `explicit`：用户给出的 Die 列表顺序就是 rank 顺序；
- Die 数不足、重复、越界、group key/size 不匹配均 fail closed。

TP=1 仍产生一个 placement group，但 embedding 的 route、capacity 和 bandwidth profile 为空；本地组的
跨 Die 带宽不是 `0` 或 `∞`，而是“不适用”。

### 2.3 路由与资源模型

对每个有序 rank pair `src != dst`，按照 backend-v1 的 X-then-Y 规则生成唯一 `PairRoute`。每跳资源为：

```text
source egress port resource
+ directed D2D link resource
+ optional directed (src_die,dst_die,link_group) cut resource
```

目的端 ingress port 不与源端 egress 混成同一资源；反向 D2D link 和反向 link group 也不共享容量账本。
这与仿真器“每个方向一个独立 `D2DLinkUnit`”的 full-duplex 事实一致。

当前 canonical template 固定为 `direct_a2a_unit_chunk/v1`：所有有序 rank pair 的权重均为 1。对被该
group 使用的资源计算：

```text
W[r] = Σ_f A[r,f] · w[f]
lane_eq_bandwidth = min_{W[r] > 0} C[r] / W[r]
```

该数值只描述当前 group 和具名 traffic template 的静态容量签名，不代表某个 N4 Swizzling plan 的实际
通信时间，也不混入其他不相交 group 的热点。

## 3. 软件架构

N3 分成四个可独立验证的组件：

1. `load_fabric.py`：严格解析 simulator hardware JSON 和 identity `mapping.spec`，生成
   `PhysicalFabric`。
2. `placement.py` schema：冻结 `PlacementContext`，使 hardware、placement 和 traffic template
   成为显式、可 digest 的 pass 输入。
3. `group_registry.py`：生成并重算验证 rank placement、ordered pair routes、used capacities 和
   canonical bandwidth profile。
4. `placed_ir1.py` + placement producer：证明逐 Profile 来源闭包，复制逻辑字段，只增加
   `execution_group_ref` 和物理 group。

核心 API：

```text
load_physical_fabric(hardware_path, mapping_path) -> PhysicalFabric
build_group_registry(ir0, context) -> tuple[PhysicalGroup, ...]
validate_group_against(ir0, context, group)
place_ir0(ir0, context) -> IR1
place_bundle(expanded_bundle, context) -> PlacedIR1Bundle
validate_placement_against(result, source, context)
```

`validate_placement_against` 不信任 artifact 内保存的带宽值，而是重新运行 GroupRegistry 推导；因此
“结构自洽但数值伪造”的 `lane_eq_bandwidth` 和缺失 ordered pair route 都会被拒绝。

## 4. 分片开发与验证结果

### 4.1 最小实现

- 先冻结 `PhysicalFabric`、有向资源语义和严格 hardware loader；
- 再冻结 `PlacementContext` 与 explicit placement schema；
- 独立完成 GroupRegistry 数值闭包；
- 独立完成 `PlacedIR1Bundle` 跨 Profile 来源闭包；
- 最后实现 placement producer 和 PassManager 集成。

每一片均先有 focused 单测，绿灯后才进入下一片；没有提前实现 N4 collective plan。

### 4.2 单元测试

覆盖：

- hardware JSON 重复键、单位、端口编号、SRAM/HBM 与不支持模式；
- compact/explicit placement、Die 越界、错误 mesh/group；
- routes 缺失、增加、重排和错误 hop/resource incidence；
- capacity、resource work、bottleneck、lane bandwidth 篡改；
- IR0→IR1 node/value/edge/candidate 精确保真；
- Profile 缺失、重复、换序、权重和来源冒认；
- N3 输出提前出现 skeleton/cross route 的负例；
- canonical JSON round-trip、稳定 ID 和输入不可变。

完整 frontend Python 门禁：`272/272 PASS`。

### 4.3 数值验证

以单向 port/link/cut 容量 `C=16 B/cycle` 为基准：

- 2×1、TP=2：正反流占用完全独立的有向资源，`W=1`，结果 `16 B/cycle`；
- 2×2、TP=4、direct all-to-all：瓶颈有向资源 `W=2`，结果 `8 B/cycle`；
- explicit `[3,0]`：rank0→rank1 路径为 `3→2→0`，反向为 `0→1→3`。

真实 `llm/test/sram/hardware_numa.json` 的单位换算门禁：

- 128-bit logical packet = 16 B；
- NoC `4 packet/cycle = 64 B/cycle`；
- C2C `1 packet/cycle = 16 B/cycle`；
- HBM `8 GB/s × 2 ns = 16 B/cycle`；
- 真实 TP=2 canonical lane 为 `16 B/cycle`。

### 4.4 集成测试

真实流水线执行：

```text
ExperimentSpec
→ build_ir0
→ logical_expand
→ load_physical_fabric + PlacementContext
→ placement
→ PlacedIR1Bundle JSON round-trip
```

PassManager 到达 `IR1_PLACED`，三张 receipt 连续，placement receipt 同时记录主输入和 context digest。
CMake 注册门禁：`frontend_python_unit` 与 `frontend_n0_backend_gate` 共 `2/2 PASS`。

## 5. 重构与性能

- producer 复用 GroupRegistry，不复制 route 或 bandwidth 算法；
- verifier 预建 owner/group 映射并使用集合检查，避免在 node 循环中重复线性查找；
- route 构造复杂度为 `O(P² · H)`，其中 `P` 为 TP rank 数、`H` 为 XY hop 数；这是显式 all-pair
  embedding 的必要输出规模；
- resource work 在单次 route 扫描中累计，不做 flow×resource 的笛卡尔重复计算；
- 所有输出使用 immutable tuple 和稳定 ID，重复编译得到相同 artifact 与 pipeline snapshot。

## 6. 明确限制与 N4 入口

N3 MVP 对以下情况 fail closed：多 instance、多 replica、多维 mesh、非 TP axis、非 identity legacy
`mapping.spec`、fractional/implicit HBM、非 strict D2D mode、hardware JSON 中的 shared `link_group`。
IR-1 schema 已能表示有向 shared cut，但当前 loader 在没有受测 backend fixture 前不会猜测转换。

N4 只可从 IR-1 中已保留且通过语义校验的 `FusionCandidate` 选择
`row-parallel GEMM → ReduceScatter`；它必须复用 N3 的 peer placement 与 `PairRoute`，不得改写
placement，也不得把 canonical static bandwidth 当成 plan-specific makespan。
