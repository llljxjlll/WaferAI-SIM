# N5 开发报告：IR-2 投影、Naive Intra-die Schedule 与 GlobalActionDAG

## 1. 阶段结论

N5 已把 N4 的逐 Profile `InterDiePlanBundle` 转成可独立校验、稳定序列化的语义 IR-2、物理
intra-die schedule 和 `GlobalActionDAG`：

```text
InterDiePlanBundle
  → ProjectToIR2Context + project_to_ir2
  → ProjectedIR2Bundle
  → IntraDieSchedulingContext + intra_die_schedule
  → ScheduledIR2Bundle
  → global_action_dag
  → GlobalActionBundle
```

当前实现是 deterministic naive baseline。它完整保留 N4 已选择的 ordinary、fused 和 standalone
语义及 route，不在投影或调度阶段重选 collective 算法、chunk owner、permutation 或 reduction 顺序。
语义 DAG 与物理 schedule 分离；`GlobalActionDAG` 只是“一项 `SemanticTask` 对应一项
`GlobalAction`”的无损 scheduled quotient，还没有生成 backend record、linked manifest 或
`program.npup`。

因此 N5 已到达 `GLOBAL_DAG_BUILT`，但没有声称 N6 lowering、backend 联合执行或 simulator E2E 已完成。

## 2. 需求理解与模型形式化

### 2.1 ProjectToIR2 的唯一翻译

`NaiveProjectToIR2` 只消费完整的 `(IR1, fusion_plans, standalone_plans)`：

- 未被计划覆盖的 ordinary op 在每个 placement rank 上生成一个 `JSON_COARSE` `COMP`；
- fused plan 的每个 rank/action 原样投影为 `ISA_REGION` 中的
  `COMP/SEND/RECV/WAIT/REDUCE`；
- standalone AllGather 的 action 原样投影为 `STRICT_ACTIONS` 中的
  `LOCAL_COPY/SEND/RECV/BARRIER`；
- 每条多跳 SEND 在 route 的每个中间 Die 上生成一个 `TRANSIT`；
- fused/standalone endpoint 保留 `(plan_id, rank, action_id)`，ordinary task 保留
  `(op_id, rank)`；TRANSIT 继承源 SEND 的 origin、region、flow、slice、bytes、dtype 和 hop route。

本地 `task.deps` 只表达 N4 action dependency 和 IR-1 graph 在同一 Die 上的 dependency。跨 Die
SEND→RECV 因果不伪造成另一个 Die DAG 中的 task ID，而由同一个 canonical `SemanticFlow`、logical
channel、完整 `PairRoute` 和 endpoint sync contract 表达。

每个 local value 都保留 IR-1 source value。Fused GEMM tile 的 operand temp 与 IR-1 source value ID
分离：A 使用 M chunk 的全局坐标 slice，B 使用完整 logical slice，partial output 使用当前 chunk
slice；RECV/contribution temp 绑定到 GEMM partial source 和相同 chunk domain。投影 validator 会重算
这些 origin/domain，而不相信 artifact 自报 metadata。

### 2.2 Canonical order

N5 把所有 tuple 顺序纳入可重算语义，而不只检查集合相等：

- projection 的 fusion/standalone plan ID 必须与输入 plan tuple 完全一致；
- per-die DAG 必须严格跟随 `ir1.fabric.dies`；每个 DAG 的 local plan ID 是输入 plan 按本地
  endpoint/transit 过滤后的子序列，ordinary ID 是 IR-1 node order 按 placement 过滤后的子序列；
- task key 为 `unit node/anchor index`，ordinary 再按 placement rank；planned endpoint 再按
  `rank_program index, action index, sub=0`，TRANSIT 使用源 SEND 的 rank/action key 和 `sub=1`；
- `values` 按 canonical task tuple 中 `read_values + write_values` 的首次出现顺序；
- `flows` 按其唯一 local task key；`regions` 按 unit、ordinary rank；
- `IntraDieScheduleSet.schedules` 与 projection DAG tuple 同序；
- `GlobalActionDAG.actions` 与 projection 的 DAG/task 二重 tuple 同序。

因此 reverse plan、reverse DAG、reverse value/flow/region 或交换两个没有依赖的 task，都不会因为
“集合仍相同”而被接受。

### 2.3 Naive intra-die schedule

`NaiveIntraDiePolicy` 的固定算法为：

1. 使用 source tuple position 作为 tie-break，执行 canonical Kahn topological sort；
2. 将 executable task 的无向 dependency component 整体放到同一 core；普通 component 与通信
   component 分别 round-robin，通信 component 优先选择 SRAM profile 同时允许
   `COMPUTE/DTE/NOC_RX` 的 core；
3. `TRANSIT` 不分配 core；其他 task 恰有一个 runtime core placement 和一个 core-local 顺序；
4. endpoint/core 到 C2C port 的 intra-die NoC route 使用 deterministic X-then-Y；source、destination、
   transit 分别绑定正确的 egress、ingress 或 ingress+egress leg；
5. buffer key 固定为 `(runtime core, value)`，同一 core 上同一 value 只能有一个 root backing；每个
   `TaskBufferUse.tensor_slice` 是该 backing 上的显式 operand view，而不是另一次 allocation。root 是所有
   use view 的最小矩形 cover，采用 tight dense row-major 布局；其 lifetime 是全部 use 的区间并集，
   ownership 则由该 storage 的本地 use 是否存在 writer 推导；
6. allocator 按 named SRAM region 做单调顺序 allocation，校验 initiator、alignment、bank、root byte span、
   lifetime 和 capacity。当前不做 alias 或 lifetime reuse；遇到 alias fail closed；
7. DIRECT AllGather 的完整输出只分配一个 full root backing：LOCAL_COPY 与 RECV 写入互不重叠的 axis-0
   contiguous subview，后继 COMP 读取 full view。若 collective axis 对 tight row-major root 不是连续 view，
   当前 naive policy fail closed；
8. LOCAL_REDUCE 的 input 按 contribution rank 排列，所有 input/output 强制进入同一个 named region，
   以 FP16 2-byte stride 紧密 staging；
9. schedule 返回前与 semantic DAG、fabric、route 和 SRAM profile 做完整交叉校验。

当前调度 policy contract 固定为 `naive_component_rr_xy_sequential/v2`。与本次 breaking buffer-view
语义对应的 schema 版本为：IR-2 DAG `v1alpha8`、`IntraDieScheduleSet` `v1alpha3`、`GlobalAction`
`v1alpha2`、`GlobalActionDAG` `v1alpha4`。`TaskBufferUse.tensor_slice` 会被 Global builder 原样复制为
`ActionBufferUse.tensor_slice`，validator 对该字段做 exact reconstruction，而不是只校验 binding ID。

### 2.4 Runtime event closure

`LogicalRuntimeBinding` 只覆盖 `SEND/RECV/WAIT/BARRIER`，每项都有确定且非空的 frontend token symbol：

- SEND 与 RECV 保存相同 logical channel，但各自保存自己的 task completion event；
- 每个 fused remote RECV 对应的同 rank WAIT 不携带 flow/channel，其 `event_symbol` 必须精确等于
  `WAIT.sync.wait_event`；该 wait event 又必须精确等于所依赖 RECV 的 completion event；
- BARRIER 不携带 flow/channel，event 精确等于 barrier completion event；
- token 是按 `(dag_id, task_id)` 生成的稳定逻辑 symbol，不是提前分配的 backend runtime ID。

也就是 runtime closure 明确固定为：

```text
RECV completion_event == WAIT wait_event
```

改变 RECV event、WAIT event、channel、flow 或漏配/多配 runtime binding 都会 fail closed。

### 2.5 GlobalActionDAG

Global builder 不增加调度策略。每个 action 精确保留 source task 的 origin、lowering region、compute/
reduction/sync、flow、route、runtime binding 和 buffer uses；core 使用稳定的 `(die_id, local_core_id)`，
不把 backend `runtime_core_id` 当作可移植身份。

Global dependency 为：

```text
source SemanticTask deps
+ 同一 core 上紧邻的前驱 action
→ ordered unique action deps
```

每项 action 都保留精确 `(dag_id, schedule_id, task_id)` source，Global validator 从 projection 与
schedule 重新构造整个 action tuple、字段和 dependency，拒绝丢 action、重排、重复 source 或伪造
physical binding。

## 3. 软件架构与开发切片

N5 按可独立验证的正确性切片完成：

1. IR-2 schema：冻结 `SemanticTask/Flow/Value/Region`、route/buffer/runtime schedule schema 和
   cross-validator。
2. Raw projection policy：先 ordinary TP1，再 fused TP2、standalone AllGather，最后 TP4 2×2
   TRANSIT；每一片均在 producer 返回前 `validate_against`。
3. Projection provenance：实现 `ProjectToIR2Context`、`ProjectedProfileIR2`、
   `ProjectedIR2Bundle` 与 `project_profile/project_bundle`。
4. Naive scheduler：依次实现 topology/core order、route、buffer/staging、runtime symbols 和
   `IntraDieScheduleSet`。
5. Scheduling provenance：实现 `IntraDieSchedulingContext`、`ScheduledProfileIR2`、
   `ScheduledIR2Bundle` 与 `schedule_profile/schedule_bundle`。
6. Global quotient：实现 `GlobalAction`、`GlobalActionDAG`、`build_global_action_dag`，再增加
   `GlobalActionProfile/Bundle` wrapper。
7. Canonical closure：把 plan、DAG、local ID、task、value、flow、region、schedule 和 action 的 tuple
   顺序全部升级为 exact validation contract。
8. PassManager：加入 `IR2_PROJECTED → INTRADIE_SCHEDULED → GLOBAL_DAG_BUILT` 固定状态迁移；projection
   和 scheduling receipt 必须记录显式 immutable context digest。

三个策略边界分别使用 `ProjectToIR2`、`IntraDiePolicy` 和 `GlobalActionDAGBuilder` Protocol。默认实现是
naive，但 profile/bundle producer 支持显式注入，并验证返回类型、producer、source 和 provenance；不会
因为传入 falsey policy 而静默替换为默认实现。

## 4. Provenance 与多 Profile 闭包

N5 的每层 wrapper 都嵌入完整 payload，并保留上游链：

```text
source partitioned entry/bundle
→ source planned entry/bundle
→ source projected entry/bundle
→ source scheduled entry/bundle
```

同时保留 `source_ir1_id`、placement/partition/planning/projection/scheduling context ID、完整 profile
manifest、profile order、`ProfileKey` 和 weight。每个 bundle 必须按 source entry tuple 恰好调用一次
policy，所有 profile 共享相同 fabric、group 和 fusion partition；缺 entry、换序、重复 source、篡改
weight/context 或把另一个 profile 的 graph/projection/schedule 冒充当前输入都会被拒绝。

`GlobalActionProfile.lowering_context()` 只在当前 graph、plans、projection、schedule 和 global DAG
全部交叉验证后才构造 N6 输入，因此不会把一组彼此不匹配的 raw artifacts 交给 lowering。

## 5. 数值与结构 Golden

### 5.1 单层 TP=2 完整投影

对当前单层 Dense TP=2 fixture：

- 2 个 fused GEMM+ReduceScatter plan、2 个 standalone AllGather plan，加上其余 ordinary op；
- 总计 `56` 个 semantic task，两个 Die 各 `28` 个；
- direct route 没有中间 Die，总计 `16` 个 per-die flow replica；
- 每个 N4 endpoint action 恰投影一次，ordinary `(node, rank)` 也恰覆盖一次；
- fused region 为 ISA、standalone 为 strict actions、ordinary 为 JSON coarse，没有 lowering 混写。

### 5.2 Synthetic 64 MiB SRAM 调度

把 fixture 的 SRAM profile 和各 named region 扩为 `64 MiB` 后，完整 TP=2 schedule 成功：

- 每个 Die `29` 个 `BufferBinding`；
- 每个 Die 的最大 `region_offset_bytes + size_bytes` 为 `1,441,792` bytes；
- GEMM tile use 精确保持 A chunk、完整 B、partial output view；binding 则表示覆盖这些 use 的唯一 root
  backing；
- standalone AllGather 的 full output 每 core/value 只有一个 root backing，LOCAL_COPY/RECV 通过显式
  subview 写入各自分片，后继 COMP 读取 full view；
- LOCAL_REDUCE input 为 rank-major tight stride，output 位于全部 input 之后；
- 每个 SEND/RECV/WAIT/BARRIER 都有 runtime token，且 RECV completion→WAIT wait event 精确闭合。

这些数值验证的是当前无 alias、无 lifetime reuse 的顺序 allocator 对 root backing 的确定性容量需求，
不代表经过 N6 lowering 后的最优 SRAM 占用，也不是性能预测。

### 5.3 真实 hardware_numa 的容量负例

真实 `llm/test/sram/hardware_numa.json` 的 named `comm` region 只有 `4096` bytes，而当前 TP=2
计划的首个通信 chunk 需要 `8192` bytes。Naive scheduler 在第一次越界分配处以
`SRAM capacity exceeded for named region 'comm'` fail closed；它不会 spill、切小 chunk、借用其他
region 或静默忽略容量。

这个负例是 N5 的正确结果：IR-2 semantic projection 可以成功，因为 semantic projection 不应提前应用
schedule capacity；物理 schedule 必须在真实 named SRAM capacity 上拒绝不可执行计划。

### 5.4 TP=4 2×2 TRANSIT

TP=4 2×2 fixture 验证每条多跳 flow 在每个中间 Die 恰有一个 canonical TRANSIT，并保留 route 的
ingress/egress leg 与 intra-die XY port path。TRANSIT 不是该 Die 上的可执行 compute/runtime task：

- 无 core placement 和 core order；
- 无 buffer binding/use；
- 无 runtime binding；
- GlobalAction 中也保持 coreless，但保留 flow 和 flow route。

## 7. 明确限制

N5 naive baseline 当前明确不做：

- 不做 intra-die tiling 搜索、core mapping 搜索、通信/计算 overlap、double buffering 或 bank 优化；
- 不做 SRAM lifetime reuse；遇到 IR-2 value `alias_set` 时 scheduler fail closed，不推断 alias，也不复用
  alias storage；
- 不做 spill、HBM staging 或因容量不足自动重切 collective chunk；
- TRANSIT 虽保留 ingress/egress route leg，但没有 core、buffer 或 runtime binding；当前资源模型也没有独立
  ingress capacity 账本/预留，因此不能据此声称 transit ingress/backpressure 已被物理调度；
- 不增加跨 Die task dependency；跨 Die 因果仍由 flow/channel/route/sync 表达；
- 不支持 N4 之外的新 collective、非 identity permutation 或 optimized Swizzling plan；
- 不把 logical token/event/channel 分配成 backend 最终整数 ID。

尤其是 synthetic 64 MiB 成功只证明 schema、allocator 和 schedule 闭包；真实 4096-byte comm region
失败说明当前 N4 chunk plan 与该硬件不兼容，不能把 synthetic 成功误写成真实硬件可执行。

## 8. N6 边界与 N5 退出条件

N6 必须从 `GlobalActionProfile.lowering_context()` 消费已经验证的 N5 决策，并按 region lowering 分成：

- ordinary `JSON_COARSE` → coarse compute/cost records；
- standalone `STRICT_ACTIONS` → 已决定的 AllGather actions；
- fused `ISA_REGION` → chunk GEMM、raw-byte endpoint、WAIT 和 LOCAL_REDUCE records。

N6 不得重新选择 N4 route/chunk/owner，也不得重做 N5 core、buffer、flow route 或 schedule。N6 仍需完成
fragment lowering、manifest linking、symbol/relocation、最终 tag/token/group/event ID 分配、artifact finalization、
单一 `npusim --program` 执行和 functional/timing oracle。

N5 与 N6 的 buffer 地址边界已经明确：N5 输出唯一 root `BufferBinding` 及每项
`ActionBufferUse.tensor_slice` view；N6 从 root binding 派生 `BufferABI`，并在 linked schema 中用与
`buffer_abi_ids` 同序的
`AddressOperandBinding.tensor_slices` 保存 operand view，并令 ABS relocation 的 addend 等于 tight dense
row-major root 内的 view byte offset。`SRAM_ALLOC_AT/FREE` 仍只作用于 root，生命周期各一次。这里描述的
只是 N6 artifact/manifest 地址闭包合同，不表示 C++ runner 已消费该字段，也不据此声称 simulator 已执行。

N5 的退出条件已经满足：

- ordinary/fused/standalone/TRANSIT 均有 exact、canonical IR-2 投影；
- schedule 与 semantic DAG 分离，core/route/buffer/runtime binding 可重算验证；
- TP2 任务、flow、SRAM golden 和 TP4 TRANSIT golden 通过；
- 真实 hardware_numa 容量不足按物理边界 fail closed；
- GlobalAction 对 source task、schedule 和 provenance 是一一无损映射；
- multi-profile profile/weight/upstream context 闭包完整；
- 输出严格停在 `GLOBAL_DAG_BUILT`，未提前宣称 N6 lowering、backend artifact 或 simulator E2E。
