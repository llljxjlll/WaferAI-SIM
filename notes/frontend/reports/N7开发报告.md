# N7 开发报告：Naive Dense 一键编译、执行与 Baseline

## 1. 阶段结论

N7 已把 N0–N6 的离散能力收口为一个事务化 production runner。对固定的 E1/E2
timing case，单次调用会从严格 YAML 和真实 hardware/mapping 输入开始，完成十个
frontend pass、C++ finalization、ProgramIo 装载、两次 simulator 运行，并只在全部
门禁通过后原子发布完整结果目录。

    ExperimentSpec + PhysicalFabric
      → 10-pass naive frontend
      → LinkedProgramManifest v1alpha6
      → npusim_program_finalizer
      → one ProgramArtifact
      → ProgramIo timing contract
      → npusim × 2
      → strict NaiveRunReport + atomic SUCCESS

当前结论精确限定为：

- E1/E2 的 schema/provenance、地址、root/view、SRAM lifecycle、transport、barrier、
  ACK/DONE、drain、D2D byte accounting 和 timing makespan 已端到端跑通；
- E0 的非零 FP16→FP32→FP16 RNE reduction 数值 oracle 仍由独立 N0 backend gate
  验收，不能复用 timing sidecar；
- timing-only compute primitive 不写 Dense 数值输出，所以本阶段不声称完整 Dense
  functional correctness，不声称 swizzling 或 optimized policy 收益。

## 2. 生产入口

公共 Python API 为 run_naive(request: NaiveRunRequest) -> NaiveRunResult。
公共 CLI 示例：

    python -m llm.frontend.wafer_frontend.cli run \
      --case E1 --validation timing \
      --spec notes/frontend/examples/naive_dense_tp2.yaml \
      --hardware notes/frontend/examples/hardware_2x1.json \
      --simulation llm/test/sram/simulation.json \
      --mapping llm/test/default/mapping.spec \
      --out build/frontend-naive-tp2 \
      --npusim build/npusim \
      --finalizer build/npusim_program_finalizer

E2 使用 --case E2、naive_dense_tp4.yaml 和 hardware_2x2.json。runner 固定执行
两次 simulator；output 目录必须不存在。多 profile 输入必须显式提供 --profile-id。

runner 对 spec、fabric、simulation、mapping、工具路径、case identity、profile、超时和
output ownership 全部 fail closed。它使用同目录 lock 和 sibling temporary directory；
失败时默认删除临时结果，--keep-failed 才保留诊断目录。只有 report 完成严格自校验后才
通过一次 rename 发布目标目录，不会留下部分成功的正式输出。

## 3. 固定编译链与 provenance

compile_naive 的 phase 链固定为：

    build_ir0 → logical_expand → placement → fusion_partition
      → inter_die_plan → project_to_ir2 → intra_die_schedule
      → global_action_dag → lowering → manifest_link

最终 snapshot 必须包含十个连续 receipt；每项 input_digest → output_digest 必须精确
对应相邻 artifact，placement 到 scheduling 使用的五个 immutable context digest 也必须
与 receipt 一致。runner 保存：

- 原始 experiment、hardware、simulation 和 mapping 副本及 digest；
- 十个 pass receipt 与十一个 stage digest；
- linked manifest、manifest ID 和 canonical digest；
- finalizer report、ProgramArtifact SHA-256 和 ProgramIo contract；
- 两次 simulator 的 stdout/stderr 与解析后的 machine-readable markers；
- strict wafer_frontend.naive_run_report/v1alpha1 和 SUCCESS。

报告 ID 对全部语义字段 content-addressed。工具二进制 SHA-256 也进入报告，因此重建工具后
report ID 可以变化；integration 冻结 ProgramArtifact digest 和关键 invariant，不硬编码
由工具哈希派生的 report ID。

## 4. Runtime 证据

runner 不用普通日志中的模糊文本推断成功。每次运行必须同时满足：

1. ProgramIo 恰好经历 resolved → applied → verify；
2. 每个 probe 都 valid，且 exact/timing comparison 通过；
3. 每个 active core 的 ACK/DONE 数量精确，terminal core 与 envelope 一致；
4. P2P、timing、collective、router 和 D2D drain residual 全部为零；
5. SIM_RESULT 恰好出现一次，且 makespan_cycles > 0；
6. D2D_TYPE.data_in == data_out；
7. 每条有向 link 恰好一个 D2D_LINK record，packet count 非零且总和闭合；
8. observed bytes = packet count × 16 B，且等于 canonical flow route 重算的 bytes；
9. 两次运行的 makespan、ACK/DONE、probe、drain 和 D2D marker 完全相同。

SIM_RESULT 在 sc_start() 返回后、ProgramIo verify/cleanup 前输出一次，cycle 使用
SystemC 整数 tick 除以固定 CYCLE，避免浮点换算。

## 5. E0 / E1 / E2 Baseline

### 5.1 E0：独立非零 reduction oracle

E0 使用 CTest frontend_n0_backend_gate，覆盖 2-die TP2 dual-owner ReduceScatter，
使用非零 FP16 输入、FP32 rank-major accumulation 和 FP16 RNE 输出。
NaiveRunRequest(case=E0) 会明确拒绝并指向该 independent gate，避免把 E1/E2 的零值
timing sidecar 冒充 functional oracle。

## 6. 能力声明

成功报告固定写入：

    timing=pass
    address_lifecycle=pass
    transport_control=pass
    compute_functional=unsupported
    reduction_u3f=unsupported
    end_to_end_functional=unsupported

ProgramIo zero timing probes 证明 root/view 地址、ALLOC_AT/FREE 生命周期、通信和控制闭包，
不是 Dense 输出数值 oracle。当前 Attention/RMSNorm/SwiGLU/Residual/Matmul manual timing
路径发布 cost，但没有产生完整 Dense payload。未来实现 functional compute 时必须新增
非零 input image、逐 op reference kernel 和输出 probe，禁止把 unsupported 改名为 pass。

## 7. CI、nightly 与运行成本

默认 CI 包含 frontend_python_unit、frontend_n0_backend_gate 和真实
naive_n7_e1_runtime。配置 -DBUILD_N7_NIGHTLY_TESTS=ON 后额外注册
naive_n7_e2_runtime，timeout 900 秒。

E2 原始十阶段编译基线约 251 秒，瓶颈是 N6 重复 intermediate validation。当前生产 wrapper
只对三个内置 naive lowerer 启用安全 fast path：leaf 中间结果不重复全链 validate，最终
LoweredProgramProfile/Bundle.validate_against 仍完整执行。公共 lowerer、lifecycle API 和
所有显式 Protocol 注入仍逐层严格校验。优化后本机完整 E2 integration（含 finalizer 和
simulator × 2）约 120 秒。

## 8. 后续 optimized policy 接口

Naive baseline 冻结 schema 与 pass 边界，不冻结实现类：

- placement、fusion partition、inter-die plan、ProjectToIR2、intra-die schedule、
  lowering 和 linker 通过已公开 Protocol/typed context 接入；
- 新 policy 返回现有 typed artifact，并通过现有 validate_against 和 provenance；
- 不得为 optimized path 修改 IR schema、绕过 canonical order、让 finalizer 重选策略，
  或接受无法重算的 route/buffer/runtime 声明。

production run 当前故意固定 naive policy。未来暴露 policy selection 时，必须把实现名、
版本和 factory digest 纳入 context、receipt 和 report，不能复用 naive ID。

## 9. 退出状态与限制

N7 已满足从 checked-in YAML/hardware 一键生成并执行统一 ProgramArtifact；E1 连续运行
byte-stable、marker-stable、无死锁和 residual；E2 多层/TP4/TRANSIT/D2D bytes 守恒；
所有配置、阶段 digest、artifact、runtime 和 validation 进入严格报告；失败不发布半成品。

仍明确不支持 timing runner 中的 E0、完整 Dense functional output、decode/KV cache functional
execution、swizzling、optimized collective、alias-aware allocator、lifetime reuse、非连续
tensor-axis collective view、动态 shape 或运行时策略搜索。

因此本阶段的准确表述是：Naive Dense 静态前向 timing E2E baseline 已跑通，而不是 Dense
数值模型或优化策略已经验证。
