# Stage 3 开发报告：S1 静态 Prefill、Decode 与 Ragged Profile

## 1. 阶段状态

《S1–S3 后续开发方案》的阶段 3 已完成。PREFILL、DECODE、MIXED 三种静态 profile
均从 typed request/profile 经过 IR0、IR1、placement、Action/IR2、schedule、GlobalAction、
lowering、linking、ProgramArtifact、ProgramIo 到 npusim 双跑；解析 Attention/KV/HBM work 与
observed runtime evidence 已闭合。checked baseline 已发布到
`notes/frontend/baselines/stage3-static-profile-v1`。

这里的 “Stage 3” 是 S1-N 依赖链中的第三阶段，不是 S3 MoE-N 完成声明。它只把
F-P1、F-D1、F-M1 提升为 `e2e-timing`；PD fused/separated、跨 instance KV handoff/reshard、
training forward、S2/S3 workload 与 optimized policy 仍未实现。`compute_functional` 和
`model_functional` 均保持 false。

## 2. 需求与完成边界

本阶段解决 Stage 2 仍缺失的静态推理形状语义：

- 同样的线性 token 数 `M=8` 必须区分 pure prefill、pure decode 和 mixed/ragged；
- 每个 request 必须携带 exact prefill/decode token、context 和不重叠 KV page span；
- Attention record 必须编码 mode、query tokens、context sum/max、query-key pairs 与 rank KV bytes；
- prefill KV 是 write-first，decode KV 是 read-existing + append-write；
- profile selection 必须使用 exact domination 与唯一 Pareto-minimal 选择，不能按 aggregate `M`
  猜测，也不能隐式 fallback；
- 每个静态 profile 是一个统一 ProgramArtifact 和一条 simulator timeline，禁止拆分后相加。

阶段外能力保持 fail closed：动态 request trace/RegionCall、online batching、TTFT/TPOT、KV
抢占/驱逐、prefix cache、speculative decode、PD 多 instance、KV reshard、训练和大模型
reuse/spill 均不在本阶段。

## 3. Profile 与选择合同

新增版本：

- `wafer_frontend.stage3_static_profile/v1alpha1`；
- `wafer_frontend.stage3_profile_selection/v1alpha1`；
- `wafer_frontend.stage3_dense_inference_oracle/v1alpha1`；
- `wafer_frontend.stage3_static_profile_runtime_report/v1alpha1`；
- runtime marker `wafer_frontend.stage3_static_profile_runtime_markers/v1`。

`Stage3StaticProfile` 保留 canonical ordered requests。每个 `StaticRequestShape` 的
`KvPageSpan(page_start,page_count,page_size_tokens)` 必须以最少页覆盖 context，所有 span
互不重叠。Profile aggregate key 精确等于 requests 的求和/最大值，不能由调用方自报。

Profile selection 只接受同 mode 且逐维支配 request 的候选，并要求唯一 Pareto-minimal；
duplicate ID、空集合、无 dominating profile、mode substitution 和 incomparable minima 均有
machine negative。`REJECT` 是当前唯一可执行 fallback；`EAGER`、`RECOMPILE` 明确声明但抛出
`StageNotImplementedError`，没有静默回退。

## 4. 解析式与 tiny profile

统一模型为 `V=32,H=16,I=32,NH=4,KVH=4,DH=4,L=2,FP16,TP1`。三个 profile 的
总线性 token 数均为 8，因此 embedding/GEMM/RMSNorm/RoPE/SwiGLU/residual work 相同；差异
必须只来自 request-aware Attention 与 KV state。

```text
prefill pairs(request) = q * (q + 1) / 2
decode  pairs(request) = q * context
KV read bytes/layer    = 2 * sum(decode_context) * KVH * DH * sizeof(FP16)
KV write bytes/layer   = 2 * query_tokens * KVH * DH * sizeof(FP16)
KV reserved/layer      = 2 * kv_pages * page_size * KVH * DH * sizeof(FP16)
```

| Profile | Requests | Aggregate key | Pairs/layer | KV read/write total | Reserved total |
|---|---:|---|---:|---:|---:|
| PREFILL | 1 | `P=8,D=0,S=1,ctx=8/8,pages=1` | 36 | 0 / 1,024 B | 2,048 B |
| DECODE | 8 | `P=0,D=8,S=8,ctx=144/32,pages=12` | 144 | 18,432 / 1,024 B | 24,576 B |
| MIXED | 6 | `P=4,D=4,S=6,ctx=44/16,pages=6` | 47 | 5,120 / 1,024 B | 12,288 B |

Oracle 中两层 Attention pair 分别为 72、288、94。对应 QK 与 PV matmul FLOPs 各为
2,304、9,216、3,008；softmax elements 为 288、1,152、376。三案 parameter bytes 均为
12,448，collective 与 D2D 均严格为零。

## 5. 编译链与 backend

Stage 3 直接扩展 Stage 2 的单一 typed carrier，没有复制第二套 IR、allocator、linker 或 runner：

- IR0/IR1 分别升至 `v1alpha7` / `v1alpha11`，完整保存 static profile 与 per-request state；
- ProjectToIR2 contract 升至 `exact_naive_projection_dense_forward/v5`；
- projected/scheduled/global/lowered/linked wrapper 与 Command/Region/Linked manifest 按 breaking
  载荷链统一升版；
- `ATTENTION_EXACT` 保留固定 record opcode，但 ISA 1.2 增加 exact PREFILL/DECODE/MIXED mode
  与 context/KV 字段约束；旧 ISA 1.1 artifact 不冒充新语义；
- 每个 request、每层 K/V 都有独立 persistent state declaration/access；decode read 生成真实
  LSU_LOAD 与 ProgramIo HBM seed/probe，prefill 保持 write-first 且不伪造 seed；
- fixed record relocation、finalizer、ProgramIo resolver、config helper 与 thin prim 均保持
  strict enum、width、address、byte-span 和 state closure；
- Program ISA 为 1.2，Program Format 仍为 1.0。

## 12. 证明边界与下一阶段

本阶段证明 static request/profile 语义、解析 work、KV/HBM traffic、artifact/ProgramIo 地址边界、
control/drain 与 deterministic timing execution。它不证明 logits/token 数值、KV payload 数值、
模型质量或在线调度性能。

下一严格依赖是阶段 4：放开多个 prefill/decode instance，生成逐层 K/V cross edge、handoff、
admission 和 `tp_P != tp_D` reshard；只有 fused/separated/reshard 三类 case 完成后，才能提升
PD 与跨 die KV capability。不得用本阶段同一 instance 的 HBM KV read/write 冒充跨 instance
handoff。
