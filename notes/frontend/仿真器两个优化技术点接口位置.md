# 仿真器两个优化技术点接口位置

## 1. 结论

两个优化技术点的主要替换接口都在 Python 前端的 policy/pass 边界，不在 C++ 仿真器执行核中：

| 优化技术点 | 主接口 | 输入 | 输出 | 当前基线 |
| --- | --- | --- | --- | --- |
| 跨 Die 计算通信 Swizzling / GEMM+collective 编排 | `InterDiePolicy.plan(...)` | `IR1` + `FusedOpSkeleton` + `ProfileKey` | `FusionPlan` | `NaiveInterDiePolicy` |
| Die 内数据流编排 | `IntraDiePolicy.schedule(...)` | `IR2ProjectionResult` + `IR1` | `IntraDieScheduleSet` | `NaiveIntraDiePolicy` |

注册表已经预留 `swizzle_topo` 和 `optimized` 名称，但它们目前只处于 declared 状态，尚未绑定生产实现。当前 schema context 也仍然只允许 `naive` 策略。

## 2. 跨 Die Swizzling / GEMM+collective 编排

### 2.1 主策略接口

文件：`llm/frontend/wafer_frontend/policies/interfaces.py`

```python
class InterDiePolicy(Protocol):
    def plan(
        self,
        ir1: IR1,
        fused_op: FusedOpSkeleton,
        profile: ProfileKey,
    ) -> FusionPlan: ...
```

该接口是跨 Die 优化算法的主插入点。

输入已经包含：

- 放置后的物理 Die、Mesh group 与路由信息；
- 已识别的 GEMM+collective 融合区域；
- GEMM 和 collective workload；
- profile、shape 及 instance 信息。

优化算法返回 `FusionPlan`，用于表达：

- GEMM 分块方式；
- collective 动作与路由；
- 计算/通信依赖；
- 计算与通信的交错顺序；
- Swizzling 匹配方式。

### 2.2 Pass 调用入口

文件：`llm/frontend/wafer_frontend/passes/inter_die_plan.py`

函数：

```python
plan_ir1(
    graph: IR1,
    context: InterDiePlanningContext,
    fused_policy: InterDiePolicy | None = None,
    standalone_policy: StandaloneCollectivePolicy | None = None,
)
```

`plan_ir1` 对每个 `FusedOpSkeleton` 调用 `fused_policy.plan(...)`。因此，新 Swizzling 实现只要满足 `InterDiePolicy` 协议，就可在此替换 naive 实现。

### 2.3 当前 naive 参考实现

文件：`llm/frontend/wafer_frontend/policies/naive_inter_die.py`

类：`NaiveInterDiePolicy`

当前实现是 canonical DIRECT row-GEMM + SUM ReduceScatter 编排，可作为新 Swizzling policy 的行为基线和消融对照。

### 2.4 GEMM+collective 融合区域识别接口

如果优化不仅改变融合区域内的编排，还要改变“哪些 GEMM 和 collective 可以组成融合区域”，则需要使用前一级接口：

文件：`llm/frontend/wafer_frontend/policies/interfaces.py`

```python
class FusionPartition(Protocol):
    def run(self, ir1: IR1) -> tuple[FusedOpSkeleton, ...]: ...
```

Pass 调用点：`llm/frontend/wafer_frontend/passes/fusion_partition.py::partition_ir1`

当前实现：`policies/naive_fusion_partition.py::NaiveFusionPartition`

这两级的职责应保持分离：

1. `FusionPartition` 只选择合法融合区域，产生 `FusionImpl.NONE` skeleton；
2. `InterDiePolicy` 才决定可执行的跨 Die 算法和动作顺序。

## 3. Die 内数据流编排

### 3.1 主策略接口

文件：`llm/frontend/wafer_frontend/policies/interfaces.py`

```python
class IntraDiePolicy(Protocol):
    def schedule(
        self,
        projection: IR2ProjectionResult,
        ir1: IR1,
    ) -> IntraDieScheduleSet: ...
```

输入 `IR2ProjectionResult` 已经是按 Die 拆分后的单 Die 任务图，可包含：

- compute task；
- DMA task；
- SEND/RECV/WAIT；
- task dependency；
- buffer 和 state 访问；
- 跨 Die flow 在当前 Die 上的端点。

输出 `IntraDieScheduleSet` 用于决定：

- task 到 core 的放置；
- core 内执行顺序；
- SRAM 区域、地址和生命周期；
- buffer reuse；
- NoC/flow route；
- 计算、DMA 和通信重叠。

### 3.2 Pass 调用入口

文件：`llm/frontend/wafer_frontend/passes/intra_die_schedule.py`

主要函数：

- `schedule_profile(...)`；
- `schedule_bundle(...)`；
- `schedule_stage4(...)`；
- `schedule_train_forward(...)`。

这些函数都通过：

```python
policy.schedule(source.projection, source.graph)
```

产生 `IntraDieScheduleSet`。

### 3.3 当前 naive 参考实现

文件：`llm/frontend/wafer_frontend/policies/naive_intra_die.py`

类：`NaiveIntraDiePolicy`

当前实现是 sequential allocator + component round-robin scheduler，可作为片上数据流优化的 naive 对照。

## 4. 策略注册和选择位置

### 4.1 协议类型与版本

文件：`llm/frontend/wafer_frontend/schema/policy.py`

关键枚举：

```python
RegistryKind.INTER_DIE
RegistryKind.INTRA_DIE
```

当前接口版本：

- `wafer_frontend.policy_interface/inter_die/v1`；
- `wafer_frontend.policy_interface/intra_die/v1`。

### 4.2 注册表

文件：`llm/frontend/wafer_frontend/policies/registry.py`

`production_registry()` 已声明：

```python
(RegistryKind.INTER_DIE, "naive", ...)
(RegistryKind.INTER_DIE, "swizzle_topo", ...)
(RegistryKind.INTRA_DIE, "naive", ...)
(RegistryKind.INTRA_DIE, "optimized", ...)
```

当前只激活了：

- `INTER_DIE / naive`；
- `INTRA_DIE / naive`。

`swizzle_topo` 和 `optimized` 只是预留名称，目前调用 `registry.instantiate(...)` 不能得到它们的生产实现。

### 4.3 编译器选择入口

文件：`llm/frontend/wafer_frontend/compiler.py`

编译器通过：

```python
registry.instantiate(RegistryKind.INTER_DIE, spec.policy.inter_die.value)
registry.instantiate(RegistryKind.INTRA_DIE, spec.policy.intra_die.value)
```

实例化策略，然后将 `PolicySelection` 写入：

- `InterDiePlanningContext`；
- `IntraDieSchedulingContext`。

这使每次编译都可以保留策略身份、配置摘要和 provenance，用于 naive/optimized 比较及消融实验。

## 5. 当前尚未打通的门禁

虽然接口和策略名已预留，当前 context validator 仍硬编码只允许 naive：

1. `schema/n4.py::InterDiePlanningContext.validate()` 要求 `fused_policy.name == "naive"`；
2. `schema/n5.py::IntraDieSchedulingContext.validate()` 要求 `policy.name == "naive"`。

因此，正式接入新算法时不能只写一个新 policy 类，还需要：

1. 为新 policy 增加独立、版本化的 contract；
2. 在 `production_registry()` 中 `activate(...)`；
3. 对 N4/N5 context validator 做 exact allowlist 扩展；
4. 保持 naive contract 和旧 artifact fail-closed；
5. 将策略名、版本、配置摘要写入证据和实验报告。

## 6. 4-Die MoE 当前的专用接入点

当前 4-Die MoE 是为了在固定 2x2/EP4 商定上快速完成的隔离路径，尚未经过通用 `InterDiePolicy` / `IntraDiePolicy` registry。

### 6.1 Mesh、EP4 放置和 N4 路由

文件：`llm/frontend/wafer_frontend/passes/lite_moe_dp4.py`

关键入口：

- `build_lite_moe_dp4_spec(...)`；
- `build_lite_moe_dp4_topology(...)`；
- `build_lite_moe_dp4_ir0_adapter(...)`；
- `place_lite_moe_dp4_adapter(...)`；
- `build_lite_moe_dp4_n4(...)`。

要在当前 MoE 专用路径中快速试验跨 Die Swizzling，可以先在 `build_lite_moe_dp4_n4(...)` 前后替换 topology/route 构造，但输出仍必须满足 `LiteMoeDp4N4IR1` 合同。

### 6.2 单 Die 任务投影

文件：`llm/frontend/wafer_frontend/passes/lite_moe_dp4_execution.py`

入口：`project_lite_moe_dp4(...)`

该阶段将 N4 的 compute/P2P 图转换为按 Die 拆分的 GEMM、SwiGLU、DMA_IN、SEND、RECV 和 WAIT 任务图。

### 6.3 单 Die 放置、SRAM 和执行顺序

同一文件中的入口：`schedule_lite_moe_dp4(...)`

当前 `_schedule_components(...)` 使用：

- 每个 Die 的 canonical core 0；
- 固定 ordinal 顺序；
- 64B 对齐的 sequential SRAM allocator。

因此这里就是当前 4-Die MoE 路径的 Die 内数据流优化替换点。新实现需输出同样可验证的 `LiteMoeDp4Scheduled`。

### 6.4 Global Action 边界

同一文件中的入口：`build_lite_moe_dp4_global(...)`

这是优化结果进入 N6 lowering/manifest/ISA 之前的最后语义边界。只要优化后的 projection/schedule/global carrier 继续满足当前 typed contract，后续 lowering、ProgramIo 和 C++ 仿真器不需要知道使用了 naive 还是 optimized 编排。

## 7. 推荐的新算法接入方式

### 7.1 跨 Die 优化

1. 新增 `SwizzleTopoInterDiePolicy`，实现 `InterDiePolicy`；
2. 输入保持 `IR1 + FusedOpSkeleton + ProfileKey`；
3. 输出保持 `FusionPlan`；
4. 在 registry 中激活 `INTER_DIE / swizzle_topo`；
5. 新增 exact contract 并扩展 `InterDiePlanningContext`；
6. 用同一 ExperimentSpec 分别选择 naive/swizzle，对比 makespan、D2D packets、byte-hop 及计算通信重叠度。

### 7.2 Die 内优化

1. 新增 `OptimizedIntraDiePolicy`，实现 `IntraDiePolicy`；
2. 输入保持 `IR2ProjectionResult + IR1`；
3. 输出保持 `IntraDieScheduleSet`；
4. 在 registry 中激活 `INTRA_DIE / optimized`；
5. 新增 exact contract 并扩展 `IntraDieSchedulingContext`；
6. 用同一 projection 分别选择 naive/optimized，对比 SRAM high-water、NoC 拥塞、core utilization 和 makespan。

## 8. 接口分层图

```text
ExperimentSpec / Mesh / Parallelism
                 |
                 v
             Placed IR1
                 |
                 v
 FusionPartition.run(IR1)
   -> FusedOpSkeleton[]
                 |
                 v
 InterDiePolicy.plan(IR1, skeleton, profile)       <-- 跨 Die Swizzling 插口
   -> FusionPlan / StandaloneCollectivePlan
                 |
                 v
 ProjectToIR2.run(...)
   -> IR2ProjectionResult（单 Die 任务图）
                 |
                 v
 IntraDiePolicy.schedule(projection, IR1)          <-- Die 内数据流插口
   -> IntraDieScheduleSet
                 |
                 v
 GlobalActionDAG -> N6 lowering -> Manifest -> ISA -> npusim
```

## 9. 边界原则

- 优化 policy 不应直接生成 ISA record；
- 不应在 C++ 仿真器内通过 shape/opcode 猜测使用了哪种优化；
- policy 必须输出已有 typed carrier，并通过 stable ID、provenance 和 exact validator；
- naive 和 optimized 应共享同一输入语义和后端 lowering，差异只位于 policy 输出；
- 如果新算法需要新的后端可观测语义，应先扩展 typed action/IR contract，再版本化 lowering ABI，不应复用不相干 opcode 伪装。
