# 编译产物指令集开发计划

> 制定日期：2026-08-11
> 依据文档：`notes/instr/编译产物指令集设计计划.md`
> 状态：待评审、待执行
> 目标版本：NPU ISA v1
> 适用范围：WaferAI-SIM/npusim 编译产物指令集、加载器、执行接入与配套测试

## 1. 文档目的

本文把《编译产物指令集设计计划》中的指令定义、硬件映射、已知缺口和待决问题，转换为可执行的开发计划。计划覆盖：

- 开发阶段及阶段依赖；
- 每阶段的开发目标、任务、交付物和退出条件；
- 单元、组件、集成、端到端、性能和回归测试的详细内容；
- 每阶段必须完成的“计划确认 → 开发 → 自测 → 集成测试 → 评审 → 修改 → 复测 → 验收”闭环；
- v1 范围、暂缓项、风险、兼容策略和最终完成定义。

本计划只安排工作，不在本文中修改 C++ 实现。开发时若发现设计文档与当前代码不一致，必须先形成评审记录并更新契约，不能直接以实现行为替代设计结论。

## 2. 总体目标与范围

### 2.1 v1 必须交付

1. **稳定 ISA 契约**
   - 使用手工分配、跨构建稳定的 8-bit opcode；
   - 保持计算、通信、访存、同步四类编号区间；
   - opcode 一经发布不得改号或复用，删除的指令保留 tombstone；
   - 为每条可用指令冻结操作数、位宽、同步语义、错误行为和对应硬件结构。

2. **稳定编解码与分类**
   - 改造 `PrimFactory`/`REGISTER_PRIM`，显式注册 opcode；
   - 明确区分“外部 ISA record”和“内部 Prim wire”：外部记录稳定、可由编译器生成，内部 `vector<sc_bv<128>>` 可由 loader lowering 后复用；
   - 规范现有 `vector<sc_bv<128>>` 多段线格式，禁止把带进程内 ID 的现有 wire 原样定义成外部 ABI；
   - 完成所有 v1 外部 record 的编解码往返，以及 lowering 后内部 Prim wire 的编解码往返；
   - 增加 `COMM_PRIM`、`MEM_PRIM` 分类位，并支持 `Dte_async_prim` 按 direction 动态分类。

3. **编译产物加载路径**
   - 新增 `config_helper_program : public config_helper_base`；
   - 支持 `npusim --program <path>`；
   - 编译产物可描述多核指令流、core group、符号/重定位、source/start、terminal/DONE 等必要元数据；
   - 保留原 JSON workload 路径，默认行为和既有结果不变。

4. **计算指令接入**
   - 为 v1 支持的 NPU 计算原语分配稳定 opcode；
   - 保持现有 `param_name`、`taskCore`、EXU/SFU/VEC 和 DRAM overlap 成本契约；
   - 保持 `SRAM_BIND` 在计算指令前绑定符号标签的机制。

5. **访存与同步指令接入**
   - LSU 只暴露阻塞式 `LSU_LOAD`/`LSU_STORE`；
   - DTE 暴露异步 issue 及 wait/fence/cancel；`POLL` 仅在 P0 定义了可消费结果后发布；
   - 提供 SRAM region 生命周期指令和 `GROUP_SYNC`；`FENCE_ALL` 与现有无参 `DTE_FENCE` 的去重方式由 P0 冻结；
   - `EVENT_SET`/`EVENT_WAIT` 按评审结论使用专用控制 wire、现有控制协议或薄原语，不能假设现有零长度 DATA 路径可直接复用。

6. **真实通信数据通路**
   - `DTE_SEND`/`DTE_RECV` 不仅计算时延，还要真实搬运 `length` 字节；
   - 源端通过 SRAM `AccessUnit` 读取真实 payload；
   - payload 经过现有 Router/NoC/D2D 通路；
   - 目的端以 `Initiator::kNocRx` 写入 SRAM；
   - 同 die 与跨 die P2P 都具备字节级正确性。

7. **集合通信 lowering 与同步**
   - 实现 3×3 TX×RX 矩阵的九种语义；
   - AllToAll、AllGather、ReduceScatter、AllReduce 在编译期展开，不增加运行时 `COLLECTIVE_CALL`；
   - 普通 Reduce 保持单 root 语义，ReduceScatter/AllReduce 按对称分解实现；
   - core group 只声明一次，通信和 `GROUP_SYNC` 按 `group_id` 引用。

8. **四档 NoC 配置与冲突规避**
   - baseline、broadcast_only、reduce_only、reduce_broadcast 两个正交开关独立生效；
   - multicast 树和 DCA reduce 路径不得静默降级；
   - 对多棵并发广播树实施编译期冲突分析、容量检查和安全分批；
   - ReduceScatter+DCA 仅在专项验证通过后开放。

9. **工程化交付**
   - 自动化测试、独立 oracle、trace、错误诊断、开发日志、评审记录和用户文档齐全；
   - 全部异步 token、barrier、tree、gather/reduce session 和 Router residual 在程序结束时清零；
   - legacy JSON、普通 NoC、DTE、SRAM、D2D 和既有集合通信回归保持通过。

### 2.2 v1 暂不交付

以下能力不进入 v1 可用指令集合；若预留 opcode，也必须在加载期明确报“unsupported”，不能按零成本执行：

- GPU 原语及 GPU ISA；
- `GEMM_REDUCE_SCATTER` 实验性融合原语；
- 未实现的 `BATCHNORM`、`SPLIT_CONV`、`MERGE_CONV`；
- 未接线的 `GLOBAL_SEND`、`GLOBAL_RECV`、`GLOBAL_LOAD`、`GLOBAL_STORE`；
- 旧 `Load_prim`/`Store_prim` 线格式；
- 编译产物可见的异步 LSU issue/wait/poll/fence/cancel；
- core group 严格 lockstep 一致性运行时检查；
- OpenSMART/自适应路由等设计文档未确认的传输能力。

### 2.3 v1 计算指令范围

在 P0 评审后冻结最终清单。按设计文档，候选可用指令为：

- 矩阵/卷积/注意力：`MATMUL`、`MATMUL_MLA`、`MATMUL_PD`、`CONV`、`MAXPOOL`、`ATTENTION`、`ATTENTION_PD`；
- MoE：`GATE`、`MOE_MATMUL`；
- 激活/归一化：`GELU`、`SILU`、`SWIGLU`、`RELU`、`RESIDUAL`、`LAYERNORM`、`RMSNORM`；
- 位置编码：`ROPE`、`ROPE_PD`；
- 拆分/合并和辅助：`SPLIT_MATMUL`、`MERGE_MATMUL`、`DUMMY`。

其中 `MATMUL_MLA`、`MATMUL_PD`、`ATTENTION_PD`、`ROPE_PD` 除了核实成本公式，还必须通过 D-29 的 program 调度上下文 gate；未通过不得以“同族推断”进入正式 opcode 清单。

`load_expert`、`switch_data`、`parse_input`、`parse_output` 虽继承自计算侧基类，但按实际行为划入访存类，分类不能只由 C++ 继承关系决定。

## 3. 总体架构与阶段依赖

目标执行链如下：

```text
编译器后端/测试编码器
        │
        ▼
带版本的 program artifact
（外部 ISA records + 符号/重定位 + core_groups + 控制 envelope）
        │
        ▼
config_helper_program
        │
        ▼
外部 Opcode 解码、完整校验、符号重定位、mode lowering
        │
        ▼
现有/扩展 PrimBase 对象
        │
        ▼
内部 Prim wire（vector<sc_bv<128>>）
        │
        ▼
MemInterface / PrimFactory / WorkerCoreExecutor
        │
        ├── EXU / SFU / VEC
        ├── LSU / DTE / SRAM / HBM
        └── Router / NoC / D2D / collective runtime
```

建议按以下依赖执行：

```text
P0 契约与基线
  └─ P1 Opcode、线格式与分类
       └─ P2 编译产物加载器
            ├─ P3 计算指令 ──────────────────────────────┐
            └─ P4 访存、异步与同步                       │
                 └─ P5 真实字节 P2P 通信                  │
                      └─ P6 通信语义与对称分解             │
                           └─ P7 四档加速与冲突规避         │
                                └──────────────────────────┴─ P8 全系统验收与发布
```

P3 与 P4 可在 P2 通过后由不同开发者并行，但必须分别完成阶段闭环：`SRAM_BIND` 的运行时实现由 P3 唯一负责，P4 负责 region 管理原语，跨能力的“释放后再绑定”用例留到 P8。P5 以后按依赖串行推进；P8 同时依赖 P3 和 P7。真实字节 P2P 未通过前，不得宣称集合通信具备数据正确性。

## 4. 开发前必须关闭的决策

P0 必须形成 ADR/评审记录并关闭下表事项。未关闭的高优先级项会改变线格式、数据通路或集合通信算法，不能留到实现中临时决定。

| 编号 | 决策项 | 建议基线 | 关闭标准 |
|---|---|---|---|
| D-01 | 完整 opcode 清单和编号 | 先清点当前约 51 个 `REGISTER_PRIM`，manifest 拆成三个正交维度：visibility=`public/internal`、lifecycle=`stable/deprecated/reserved/tombstone`、support=`available/unsupported/experimental`；公共候选区间仍以 `0x00–0x3F` 计算、`0x40–0x7F` 通信、`0x80–0xBF` 访存、`0xC0–0xEF` 同步、`0xF0–0xFF` 保留为基线，再评审内部编号；不能假定 16 个保留号足以容纳 GPU/legacy/internal 原语 | 全部仍会经过 8-bit PrimFactory wire 的原语都有唯一身份；三个状态维度可独立校验，公共 opcode、内部 ID、保留位和 tombstone 规则不冲突，确认总数不超过空间 |
| D-02 | `DTE_SEND`/`DTE_RECV` lowering | 保留 loader lowering 方向，但不能假定现有类无需修改：`Send_prim` 缺 src_addr/length，`Recv_prim` 缺 dst_addr/length/src_expect；最小原型必须在“扩展现有类”和“新增薄 DTE 类”之间作结论 | 证明地址、长度、同步/异步、token、mode、真实 payload 和现有 executor 均可表达，形成类/wire 改造清单并评审 |
| D-03 | 外部 ISA 与内部 Prim wire | 冻结两层格式：artifact 使用稳定外部 ISA record；loader 负责符号解析、验证和 lowering，再生成内部 Prim wire。禁止把当前预 serialize 的裸 128-bit 段直接当外部 ABI | 给出两层 opcode/版本/字段映射、lowering 责任、字节级容器、损坏输入行为和 golden fixture |
| D-04 | 操作数位宽 | 审计现有 16-bit 地址、30-bit计算参数、32/64-bit token/地址、region 名称和 group 字段；不允许隐式截断 | 每字段有位宽、单位、范围和溢出错误，最大值 round-trip 通过 |
| D-05 | `EVENT_SET/WAIT` 编码 | 现有 DATA path 要求 `max_packet>0`，不能直接承载零长度 event；在专用控制 wire/薄原语与严格复用 REQUEST/ACK 之间选择，不得伪装成普通 DATA | 明确控制消息格式、`fsm_id`/tag/count、提前到达、重复信号和资源回收规则，正负例通过 |
| D-06 | core group 声明位置和成员规则 | 放入 program artifact 的静态表；允许一个核属于多个 group，但同一 group 内成员唯一；v1 core group 必须位于同一 die，跨 die 只允许显式 P2P | 配置 schema、重复/未知成员/跨 die/重叠 group 规则通过评审 |
| D-07 | `GROUP_SYNC` key 命名空间 | 优先使用显式“纯同步”命名空间或 marker，若沿用 sentinel `collective_id` 则必须有不会碰撞的保留规则 | 连续 epoch、真实 collective 并发和碰撞负例通过 |
| D-08 | 历史计算计费问题 | v1 默认冻结当前行为；若修复 RMSNORM/RELU/MAXPOOL/MERGE_MATMUL，应在 opcode/性能 golden 冻结前单独改动和评审 | 明确“继承”或“修复”，更新 oracle，不允许开发中悄悄改变 |
| D-09 | PD 成本公式 | 已核实：MATMUL_PD 为 EXU/VEC 二选一并依赖 KV/chunk/完成副作用；ATTENTION_PD 为 EXU+SFU+VEC 且读取 KV；ROPE_PD 为 `3*C*sum(token_num)`。发布前仍需运行时上下文 fixture | 三个 PD 指令形成公式、batch/KV/chunk/job_type 副作用说明和 JSON/program 差分测试向量 |
| D-10 | 同 die 广播路由唯一真源 | 当前实现已确认 X-first XY；把 production 树编程的拓扑构建抽成共享纯函数，由树编程、冲突分析和测试共同调用，避免复制路由算法 | 给定 root/group 可重复得到相同 `(router, output)` 集合，静态集合与 production trace 一致 |
| D-11 | ReduceScatter+DCA | 先验证现有 N→1 DCA tree 能否表达多目的归约组；验证前 capability gate 关闭 | 正向数据/时序测试通过后开放；否则启动期明确拒绝，禁止静默 endpoint fallback |
| D-12 | 广播树分批适用对象 | 设计文档 4.7 认为 Scatter 不用 multicast，4.9 又写到 `BROADCAST_TX/SCATTER_TX` 分批；建议只对实际携带 `tree_id` 的 Broadcast 分批 | 修正文档表述，测试证明 Scatter 不进入 `AtomicMulticastFork` |
| D-13 | 批大小 K 策略 | 首版采用“确定性冲突图 + 保守贪心着色 + 容量约束”；固定 K 只作为可配置上限 | 同一输入调度结果稳定，无冲突批次可验证，无法证明安全时串行 |
| D-14 | 兼容策略 | `--program` 与 JSON 路径并存至少一个发布周期；未知版本/opcode fail-fast | 兼容矩阵和废弃策略写入用户文档并有自动化测试 |
| D-15 | 符号与重定位 | `Set_addr`/`Send_prim` 当前 wire 使用运行期 `g_addr_label_table` 数字 ID，外部编译器不可生成；artifact 必须带稳定字符串/符号表，loader 先注册并重定位 | 不同插入顺序、不同进程运行得到相同语义；artifact 中不存在进程内临时 ID |
| D-16 | `SRAM_CLEAR` 语义 | 设计写 targeted `SRAM_CLEAR(label)`，当前 `Clear_sram` 无操作数且清理全部 task-lifetime spillable 标签；决定新增 targeted primitive，或把 v1 语义明确改为 clear-all | 操作数、AccessUnit 时序、RegionTable 生命周期和兼容行为有唯一规格及正负例 |
| D-17 | `DTE_POLL` 可编程语义 | 当前结果只写 `poll_complete`，静态队列无分支/谓词可消费；v1 默认不发布，或仅定义为观测/trace 指令；若要轮询控制流则另立扩展计划 | 后续指令如何读取结果有明确机制；否则从 public manifest 移除且文档不宣称可重试 |
| D-18 | `DTE_FENCE` 与 `FENCE_ALL` | 现有 DTE FENCE 无 token，已 drain 全部 DTE；v1 又无 LSU async，故两者当前等价。建议只发布无参 `DTE_FENCE`，`FENCE_ALL` 作为不占号别名或未来版本能力 | opcode、操作数和 trace 不重复；测试确认 fence 无 token |
| D-19 | `DTE_ISSUE` 与 `DTE_SEND/RECV` 边界 | 为 `SPM_TO_REMOTE`、`REMOTE_TO_SPM`、`SPM_TO_SPM`、`SPM_TO_DRAM`、`DRAM_TO_SPM`、`DRAM_TO_REMOTE` 逐项冻结 public/拒绝状态、源/目的存储体、地址所有者、完成点和唯一 lowering；remote 方向不得与 SEND/RECV 形成两套编码 | 六方向×send/recv mode 互斥/组合表完整；每个发布方向只有一个外部表达、一个 token 和一套字节/计费路径 |
| D-20 | program 模式平台初始化 | `Monitor(config_helper_base*)` 当前会进入带 `assert(0)` 的 GlobalMemInterface 构造；`InitGrid` 又把 workload mode 与平台配置绑定。建议修复/旁路 GlobalMemory，并拆分 `InitPlatform` 与 workload/program 初始化 | 不需要伪 workload JSON 即可加载 hardware/simulation/mapping；program helper 注入不崩溃，GLOBAL_* 仍明确不支持 |
| D-21 | program 控制 envelope | artifact 除 per-core 指令外必须携带 source/start、terminal/DONE、ACK 相关元数据，不能指望 raw segments 自动推导 | 单源/多源、空流、多终点和失败收尾均能驱动现有 host 协议 |
| D-22 | 树的按批 program/erase | 当前 AllGather 加载期一次性编程所有 source tree；只排序运行指令不能降低 64-entry 常驻容量。P7 必须实现按批 program/erase 生命周期，或在加载期按全量常驻容量拒绝 | 批开始前所需树已编程、批释放后表项回收；tree occupancy 峰值满足容量 oracle |
| D-23 | 同步分类 | 设计只新增 `COMM_PRIM/MEM_PRIM`，需决定是否新增 `SYNC_PRIM`，或以 opcode category 独立统计同步指令 | 分类表和 trace 统计唯一，指令总数不因复合 bit 重复计数 |
| D-24 | `SRAM_BIND` 生命周期 | 设计描述为“绑定下一条计算指令”，当前 `Set_addr` 实际持续到下一次 Set_addr。决定采用 one-shot 并消费后失效，或明确采用 persistent binding；loader 校验必须与运行时一致 | 连续两条 compute、有/无第二次 bind、跨同步/访存指令的标签解析均有确定结果 |
| D-25 | 数据准备原语的公共编码 | `load_expert`、`switch_data`、`parse_input`、`parse_output` 被设计归为访存类，但尚无外部 opcode 表；决定发布为访存 opcode、lowering 为更基础访存序列，或仅作 internal primitive | 每个原语有 public/internal 状态、操作数、分类、数据副作用和编译器生成规则 |
| D-26 | `Sram_pipeline/Set_batch` 等 helper 状态 | `Sram_pipeline_prim` 是双缓冲范例/测试资产，`Set_batch` 是运行时上下文 helper；默认列为 internal，不因设计文档引用范例而自动发布 | public manifest 不出现未评审 helper；program envelope/lowering 仍能表达必要 batch 上下文 |
| D-27 | `COLL_BARRIER` 与 `GROUP_SYNC` 边界 | `GROUP_SYNC` 是 public、用户可引用的 group 同步；`COLL_BARRIER` 默认只是 collective lowering 生成的内部 phase barrier，不再占用第二个 public opcode | manifest、trace 和文档分别标注 public/internal；若实现复用同一底层状态机，key/epoch 仍不碰撞且不重复计数 |
| D-28 | collective 中 N 的定义 | 统一 `N=group_size`，每个成员贡献一份；本地贡献不经过网络，root/目标通常接收 `N-1` 份远端消息，再与本地一份合成 N 份逻辑输入 | 每种 mode 都给出逻辑贡献数、本地处理数、远端 send/recv 数和 N=1 行为，lowering 与 oracle 使用同一张独立规格表 |
| D-29 | MLA/PD program 上下文 | 若发布 `MATMUL_MLA`/三个 PD opcode，artifact 和 program helper 必须表达 request/batch_info、job_type、chunk、KV cache 状态及调度生命周期，并避免把通用 helper 非安全强转为 PD/PDS helper；否则这些 opcode 移出 v1 public manifest | program-aware PD/PDS adapter 或 scheduler spike 能运行 golden fixture；没有上下文的 program 确定性失败，未通过则 capability 明确拒绝 |
| D-30 | 普通 Reduce 与对称算法边界 | 按 TX×RX 定义，普通 Reduce 是单 root `UNICAST_TX×REDUCE_RX`；只有 ReduceScatter/AllReduce 使用对称分解，修正设计中把普通 Reduce 也称为对称的冲突表述 | lowering 表、profile 表、数据 oracle 和用户文档均使用同一语义，普通 Reduce 只有一个目标 |
| D-31 | collective 发布与完成协议 | 推荐每 phase 先发布接收状态，再异步 issue 发送，随后等待 receive/token，最后进入内部 phase barrier；禁止所有核先执行可能阻塞的同步 send | 九种语义均有逐核顺序、完成条件、fsm 回收点和有限 buffer 下的 progress 证明；无依赖 watchdog 才能前进的正常路径 |
| D-32 | endpoint reduce 数据与整数语义 | 冻结 sender-rank staging 布局、最终目的可见点、字节序、INT32/INT64 符号解释、SUM 溢出/截断规则和 MAX 负数语义；不能把只计周期的 `Reduce_compute_prim` 当数据实现 | 独立软件 oracle 覆盖负值、边界和溢出；真实 SRAM 读/写与 VEC 周期各只计一次 |

## 5. 各阶段通用开发闭环

每个阶段都必须完整执行以下流程，不能以“代码已合入”代替阶段完成：

1. **计划确认**
   - 明确本阶段范围、非目标、依赖、接口和验收用例；
   - 把设计待决项转成 ADR 或阻塞项；
   - 建立阶段 issue 清单、测试矩阵和可复现 baseline。

2. **按计划开发**
   - 先提交公共契约、纯函数或隔离组件，再接 production path；
   - 每项能力同时增加参数校验、错误信息、trace 和测试；
   - 避免在同一变更中混入历史成本修复、重命名和无关重构。

3. **开发者自测**
   - 编译改动目标；
   - 执行新增 unit/selftest、正负例和 sanitizer 可用范围内的检查；
   - 核对数据值、周期、资源占用和最终 drain，不只检查进程退出码。

4. **集成与回归测试**
   - 从 program artifact 入口执行本阶段能力；
   - 运行受影响的 DTE/SRAM/NoC/D2D/legacy JSON runner；
   - 对照独立 oracle 或 golden trace，禁止实现和测试共用同一错误公式。

5. **评审**
   - 至少包含设计/接口评审、代码评审和测试评审；
   - 重点检查单位、位宽、阻塞语义、时序唯一计费、状态生命周期、错误门禁和兼容性；
   - 所有评审意见按“必须修改/建议修改/已接受风险”分类记录。

6. **问题修改**
   - 必须修改项关闭后重跑新增测试与完整受影响回归；
   - 若修改了契约、wire 或 oracle，重新执行阶段评审；
   - 不得仅更新预期值来掩盖无解释的行为变化。

7. **阶段验收**
   - 代码、测试、oracle、文档、开发日志和已知限制齐全；
   - `git diff --check`、构建和阶段测试全绿；
   - 退出条件逐项有证据；
   - 评审负责人确认后才允许进入依赖本阶段的下一阶段。

每阶段建议在 `notes/instr/log/` 新增 `P<n>_development.md`，使用第 15 节模板记录实际完成情况。

## 7. P1：稳定 opcode、线格式、工厂与分类

### 7.1 开发目标

建立跨编译、跨链接顺序稳定的 ISA 身份与编解码基础，使后续加载器和指令实现只依赖显式 opcode，不依赖 C++ 静态初始化顺序。

### 7.2 开发任务

- 新增 `llm/include/isa/opcode.h`：
  - 外部 public 使用稳定的 `enum class Opcode : uint8_t`；若内部 Prim ID 不与其一一相同，使用不同强类型和显式映射，禁止混用裸整数；
  - 显式编号、类别边界、保留号和 tombstone；
  - opcode 到规范名称/category/capability 的静态表；
- 改造 `llm/include/utils/prim_utils.h`：
  - `REGISTER_PRIM` 显式接收已冻结的内部 Prim 编号；public 原语同时登记外部 Opcode→lowering/内部编号映射；
  - `PrimFactory` 只维护内部 name↔PrimId、PrimId→creator；外部 ISA registry 独立维护 Opcode→规范元数据/lowering，禁止把外部 Opcode 直接当内部 creator key；
  - 重复名称、重复 PrimId、重复 Opcode、越界和保留号注册均在启动期失败；
  - 删除生产路径对 `next_id_` 的依赖；
- 改造全部现存注册点，不只处理 v1 public 原语；按 manifest 三个正交维度登记，并保证内部 Host→WorkerCore wire 仍有稳定唯一编号；
- 在 `llm/include/defs/enums.h` 增加 `COMM_PRIM`、`MEM_PRIM`，明确同步类是否另设位或按“非数据计算控制类”统计；
- 为通信、访存、同步原语在构造、JSON parse 和 deserialize 后设置正确分类；
- 为 `Dte_async_prim` 按 direction 设置 `COMM_PRIM` 或 `MEM_PRIM`；
- 分层规范外部 ISA codec 和内部 Prim codec，建立显式 lowering/重定位接口；内部 codec 不能泄漏进程内标签 ID到外部 ABI：
  - 每个 segment 的 opcode 一致性；
  - 段数可确定或显式编码；
  - 所有 segment 初始化为 0，保留位反序列化时校验；
  - 溢出、截断、额外段和未知 enum 抛出确定性异常；
  - `WorkerCoreExecutor::parse_prim` 在解引用前处理未知 opcode/空 creator；
  - 现有只记录日志后继续的段数错误改为 fail-fast；
- 建立不可修改的外部 ISA golden records、内部 Prim golden wire vectors 和完整 opcode manifest。

### 7.3 详细测试

1. **opcode/factory selftest**
   - manifest 的 visibility/lifecycle/support 组合合法且编号落在已批准区间；public opcode 具备稳定 ABI；
   - 保留区和 tombstone 不可注册；
   - 以正序、逆序和随机顺序注册同一批测试原语，内部 name↔PrimId 及外部 Opcode→lowering 结果分别稳定；
   - 重复 name、重复 PrimId、重复 Opcode、未知 Opcode、未知 PrimId 和未知 name 均给出稳定错误；
   - 所有经过内部 wire 的编号均可由 8 bit 表达；不得只检查 public 最大编号。

2. **codec round-trip**
   - 每条 v1 外部指令至少覆盖最小值、典型值、最大值三组，并验证 lowering 后的内部 segments；
   - 计算参数覆盖 0/1、30-bit 边界和溢出；
   - 地址/size/token/fsm/group/tree 字段覆盖各自最大值；
   - region 名称覆盖 1 字节及 `L-1/L/L+1`，其中 `L` 为 D-04 冻结的最大编码长度，`L+1` 必须拒绝；
   - 绝对地址与 region+offset 必须恰好二选一；
   - serialize→deserialize→serialize 必须逐 bit 相同；
   - 缺段、多段、segment opcode 不一致、保留位非零、非法 enum、长度伪造全部失败。
   - 未知 opcode 不得先返回空指针再被 executor 解引用；
   - 外部符号/字符串重定位后不出现 `g_addr_label_table` 的临时 ID 泄漏。

3. **golden/跨构建稳定性**
   - 同一指令在 release/debug 和至少两次干净构建中生成相同 segments；
   - golden fixture 中记录十六进制位串，变更必须触发显式 ABI 评审；
   - opcode manifest 生成结果可重复，排序不依赖 unordered_map。

4. **分类测试**
   - 每个计算、通信、访存、同步指令分类与清单一致；
   - DTE 六个 direction 分别断言通信/访存分类；
   - `load_expert`、`switch_data`、`parse_input`、`parse_output` 断言为访存类；
   - trace 统计总数等于实际解码指令数，不因多分类位重复计数。

5. **回归**
   - 原 JSON 路径仍能通过 name 创建原语；
   - P0 的 CTest、DTE、SRAM、NoC、D2D baseline 全部重跑；
   - 未使用 `--program` 时周期和关键 trace 不变。

### 7.4 评审、修改与退出条件

**评审重点**：编号不可变策略、所有注册点覆盖、codec 边界、异常而非日志后继续、动态分类是否影响现有统计。

**修改要求**：golden wire 变化必须说明原因；如果字段宽度不足，回到 D-03/D-04 修改 format version，禁止截断。

**退出条件**：

- 工厂不再以链接顺序生成生产 opcode；
- 全部现存注册原语有状态和内部编号；全部 v1 public 指令有稳定外部 manifest、lowering 和 round-trip 测试；
- golden vectors 在重复构建中一致；
- legacy JSON 回归无变化；
- P2 可以只凭外部 record 边界安全解码、重定位并 lowering，WorkerCore 只接收校验后的内部 segments。

   - group id 重复、成员重复、未知 core、空 group、非法跨 die group；
   - artifact 声明 capability 与实际指令不一致；
   - 所有失败均在下发前发生，错误信息包含文件偏移、core id 和 opcode（适用时）；
   - 重定位指向未知符号、重复符号、不合法 UTF-8/长度和越界引用；
   - source/terminal 引用未知 core、DONE 计数不闭合、控制 envelope 自相矛盾。

3. **JSON/program 等价性**
   - 为一组只使用已支持原语的 workload 同时生成 JSON 和 program；
   - 比较每核创建的原语类型、操作数、顺序和 segment；
   - 比较最终完成、关键 trace、周期和 drain；
   - 允许的差异必须登记，不能只比较退出码。

4. **CLI 和生命周期**
   - 仅 `--program`、仅 JSON、两者同时、两者均缺失、文件不存在、权限错误；
   - 重复运行无全局注册表污染；
   - 直接注入 `config_helper_program` 不触发 GlobalMemInterface assert；
   - program 与 JSON 选择不同初始化分支，但公共平台配置和资源实例一致；
   - 若发布 MLA/PD，program request/batch/KV fixture 可启动、迭代并完成；若不发布，相应 opcode/capability 在加载期拒绝；
   - parse 失败后析构无 token/tree/barrier 残留；
   - 默认启动 smoke 和 `playground_legacy_baseline` 保持通过。

5. **健壮性**
   - 对 golden artifact 做固定 seed 的 bit flip、截断、长度篡改和 opcode mutation；
   - parser 不崩溃、不越界、不无限分配，所有异常可诊断；
   - 对记录数、字符串长度和总文件大小设置明确上限并测试。

### 8.4 评审、修改与退出条件

**评审重点**：格式能否前向演进、是否完整校验后再下发、CLI 兼容、资源上限和错误可诊断性。

**修改要求**：任何容器字段变化必须升级未发布草案版本并更新 golden；发布 v1 后只能以新 format/ISA version 演进。

**退出条件**：

- program 可稳定完成符号重定位、lowering，构造多核 `coreconfigs` 和原语队列，并完成 START/ACK/DONE；
- 正负例、mutation 和 JSON/program 等价测试通过；
- 默认 JSON 行为不变；
- P3/P4 的测试可以只通过 `--program` 注入指令。

## 9. P3：计算指令接入与成本模型验证

### 9.1 开发目标

### 9.2 开发任务

### 9.3 详细测试

1. **逐指令功能矩阵**

   - 连续两条 compute 覆盖一次 bind、两次 bind，以及中间穿插访存/同步，验证绑定生命周期；

2. **成本 oracle**

   - `SPLIT_MATMUL` 零独立耗时，`MERGE_MATMUL` 按冻结行为计费；

3. **PD 与 MoE**

   - D-29 允许发布的 MLA/PD opcode 在缺少运行时上下文时明确失败；未发布时由 capability gate 拒绝；
   - MoE selected_experts/frequency 副作用与 JSON 路径一致。

4. **不可用指令门禁**
   - 对 stub/实验/GPU opcode 分别测试加载期拒绝；
   - 错误信息区分“未知 opcode”和“已知但 v1 不支持”；
   - 不允许 stub 以零周期成功完成。

5. **端到端与回归**
   - 选取含 MATMUL、ATTENTION、归一化、激活的短模型片段，由 program 执行；
   - 与等价 JSON 比较指令数、硬件 ops、完成周期和输出标签生命周期；
   - 重跑 compute 相关 legacy workload、CTest 和默认 smoke。

### 9.4 评审、修改与退出条件

**评审重点**：是否忠实复用成本模型、是否发生重复计费、PD 上下文是否完整、stub 是否被错误发布、标签依赖是否可诊断。

**修改要求**：成本变化必须同时给出源码依据、独立公式和 golden 更新；无法解释的性能差异不能通过修改测试阈值关闭。

**退出条件**：

- 每个已发布计算 opcode 有功能、codec 和成本测试；

## 10. P4：访存、异步控制、SRAM 生命周期与同步

### 10.1 开发目标

完成 v1 的内存与依赖控制能力，明确 LSU 阻塞、DTE 非阻塞的架构边界，并建立可供集合通信复用的 core group 和同步机制。

### 10.2 开发任务

- 发布 `LSU_LOAD`/`LSU_STORE`，只映射 `LOAD_BLOCKING/STORE_BLOCKING`；
- decoder 明确拒绝编译产物中的 LSU ISSUE/WAIT/POLL/FENCE/CANCEL；
- 按 D-19 发布规范且不重叠的 `DTE_ISSUE` direction 与 `DTE_SEND/RECV` 边界，并发布 `DTE_WAIT/FENCE/CANCEL`；
- `DTE_POLL` 只有在 D-17 定义可消费结果后才发布，否则仅保留内部观测或从 v1 manifest 移除；
- 按 D-18 只保留一条无参的全 DTE drain 语义；若 `FENCE_ALL` 只是别名则不占独立 opcode；
- 新增 SRAM region 薄封装原语：
  - `SRAM_ALLOC`、`SRAM_FREE`、`SRAM_RESIZE`、`SRAM_RENAME`；
  - 参数逐一映射 `RegionTable`，不重复实现分配器；
- 按 D-16 冻结的 targeted/clear-all 语义接入 `SRAM_CLEAR`；`SRAM_BIND` 由 P3 唯一实现，P4 只验证它与 region 释放/重命名的交互；
- 按 D-25 为 `load_expert`、`switch_data`、`parse_input`、`parse_output` 实现 public 访存 opcode/lowering，或将其明确保持 internal；分类与实际数据副作用一致；
- 按 D-26 保持 `Sram_pipeline_prim`、`Set_batch` 等 helper 的已评审 internal/public 边界；
- 实现 core group 静态注册表及加载期校验；
- 实现 `GROUP_SYNC{group_id,sync_seq}`，复用 `WaitCollectiveBarrier` 的到达计数，不触发树编程/擦除；
- 按 D-05 使用已评审的控制 wire/薄原语实现 `EVENT_SET`/`EVENT_WAIT`，不得直接发送不满足现有 DATA 契约的零长度包；
- 为 token、group barrier、event 和 region 生命周期增加 trace 与最终 residual 统计。

### 10.3 详细测试

1. **LSU 阻塞语义**
   - `LSU_LOAD → COMPUTE`：compute 开始时间不早于 load 完成；
   - `COMPUTE → LSU_STORE`：store 不早于 compute 完成；
   - 尝试编码 LSU async op 必须在加载期失败；
   - HBM↔SRAM 数据内容、地址、size 和耗时与 `CoreLsuUnit` oracle 一致。

2. **DTE 异步语义**
   - `DTE_ISSUE → COMPUTE → DTE_WAIT` 确实发生重叠；
   - `WAIT` 只等待指定 token，无参 `DTE_FENCE` 等待全部 token，且拒绝携带 token；别名不重复产生 trace/计费；
   - 若发布 `POLL`，测试后续指令读取/分支机制；若仅观测，则断言它不被编译器用于正确性依赖；
   - `CANCEL` 回收未完成 token，已完成/未知/重复 cancel 有确定行为；
   - max_outstanding、队列满、RAW/WAR/WAW hazard 和 refill；
   - 按 D-19 对六个 direction 分别验证 public/拒绝状态、必填/禁用地址字段、源/目的存储体、完成点和分类位；remote 方向不能出现第二套外部编码。

3. **SRAM region 生命周期**
   - allocate/allocate-at、读写、resize、rename、free 的正常流程；
   - 重名、重叠、越界、零大小、缩小后访问旧尾部、double free、rename 冲突；
   - 指令引用已释放 allocation 必须失败；
   - metadata 操作本身不产生虚假的 SRAM 数据面周期；
   - `SRAM_CLEAR` 经过 AccessUnit，和纯 `SRAM_FREE` 的时序/语义分开验证；
   - 分别按 D-16 结论验证 targeted clear 或 clear-all，且与旧 `Clear_sram` 兼容行为一致；
   - 对 D-25 中每个发布的数据准备指令验证真实搬运/解析副作用、访存分类和 program/JSON 等价；internal 项不能从外部 artifact 编码；
   - `Sram_pipeline_prim` 若为 internal，仅作为 overlap oracle 资产，不占 public opcode。

4. **同步语义**
   - `GROUP_SYNC` 覆盖 N=1/2/4、非连续成员、重复同步 1000 次和连续 sync_seq；
   - 最快核等待最慢核，最后一个成员到达后全部放行；
   - 重复到达、非成员到达、sync_seq 回退/跳跃、成员永不到达由错误或 watchdog 捕获；
   - 包含跨 die 成员的 core group 在加载期失败，不能进入 GROUP_SYNC 或 group mode DTE；
   - 真实 collective 与 `GROUP_SYNC` 使用同一 group 并发时 key 不碰撞；
   - 高频纯屏障不编程/擦除 multicast/reduce tree；
   - `EVENT_SET/WAIT` 覆盖一对一、多对一、提前 set、先 wait、重复 tag 和 count 不匹配，并断言不进入普通 DATA payload/stripe 校验路径。

5. **流水与收尾**
   - LSU blocking 与 DTE double buffering 使用相同数据，结果一致且只有 DTE 与 compute 重叠；
   - 正常程序尾部 `OutstandingCount()==0`；
   - 故意遗漏 WAIT/FENCE 的 program 由现有 drain gate 确定性拒绝；
   - token、region、barrier、event residual 全部为零。

6. **回归**
   - 全部 SRAM R0～R6 selftest；
   - `run_test_sram_pipeline.py`；
   - DTE V3/V3b/V4 runner；
   - legacy JSON 中已有 `Lsu_mem`/`Dte_async` 行为不变。

### 10.4 评审、修改与退出条件

**评审重点**：LSU/DTE 阻塞边界、token 生命周期、GROUP_SYNC 命名空间、region 元数据与数据面计费分离、死锁和错误路径清理。

**修改要求**：任何新增 wait 都要证明不是重复计费或隐藏死锁；任何新增异步状态都要有容量、backpressure、trace 和 drain。

**退出条件**：

- LSU 不能通过 v1 artifact 发起异步访问；
- DTE overlap 和全部已发布完成控制语义通过；未发布 POLL、重复 fence 别名无法从 artifact 编码；
- region 与 group 表可被后续通信指令稳定引用；
- 高频同步、错误同步和全 drain 测试通过。

## 11. P5：`DTE_SEND`/`DTE_RECV` 真实字节 P2P 数据通路

### 11.1 开发目标

补齐设计文档标出的最高优先级缺口：让核间通信从“时序/协议记账”升级为真实 payload 搬运，同时保持现有 NoC/D2D 时序、信用和拥塞模型的唯一计费责任。

### 11.2 开发任务

- 实现逻辑 `DTE_SEND{SYNC|ASYNC,UNICAST_TX}` 和 `DTE_RECV{SYNC|ASYNC,UNICAST_RX}` lowering；
- 落实 D-02：扩展 `Send_prim/Recv_prim` 的地址、长度、来源和 payload 参数，或新增薄 DTE send/recv 类；同步修改内部 wire、`WorkerCoreExecutor` 和 `workercore/logic.cpp`，不能把本阶段只当 loader 工作；
- 为每个 fsm 定义分配、复用、完成和回收规则，集合通信后续使用同一 allocator；
- 将 DTE remote 三方向从纯时序/资源行为接到本阶段的真实数据通路，并保持 D-19 的唯一外部表达：
  - `SPM_TO_REMOTE`：本地 SRAM→peer memory；
  - `REMOTE_TO_SPM`：peer memory→本地 SRAM；
  - `DRAM_TO_REMOTE`：本地 HBM/DRAM→peer memory；
  - 每条路径的 peer 地址所有者、发起核、ACK/completion 和目标可见点严格使用 D-19 规格；
- 统一 `fsm_id` 的硬件 FSM/channel、token 和收发匹配语义；
- TX 侧：
  - 按 `src_addr` 或 region+offset 检查范围；
  - 使用 `sram::AccessUnit`、`Initiator::kDte`、`Command::kRead` 读取准确 `length` 字节；
  - 删除“固定 16 字节只算延迟且丢弃内容”的生产行为；
- wire/Msg：
  - 设计真实 payload 的分片、seq、tail、总长度和重组规则；
  - 复用现有物理 flit/credit/Router/D2D，不另建绕行数据通道；
  - 解决 DTE streaming 当前用 `Msg.data_[127:0]` 保存时间戳而覆盖业务 payload 的冲突：升级 wire 版本或使用明确 sideband，时间戳与数据不可共用同一位；
  - physical 与 behavioral NoC 分别定义 payload 承载/等价 sideband、分片和可见性契约；
  - behavioral 模式也必须保留可验证的数据内容或明确使用等价 payload sideband，不能恢复为常量；
- RX 侧：
  - 校验来源、fsm/tag、seq、length 和目标范围；
  - 完整重组后以 `Initiator::kNocRx`、`Command::kWrite` 写目的 SRAM；
  - 完成通知只能在最后一字节可见后触发；
- 保持普通 P2P 可跨 die，复用现有 `CrossDieSelectExit/CrossDieStep`；
- 增加 payload checksum、字节数、flit 数、源读/目的写、sync/async completion 和 residual trace；
- 明确 cancel、超时或 wire 错误时部分写入是否回滚；v1 推荐在完整校验后提交目的写，避免暴露半包。

### 11.3 详细测试

1. **字节级数据正确性**
   - pattern：全 0、全 1、递增字节、随机固定 seed、跨 128-bit 边界的非对齐 pattern；
   - length：1、15、16、17、127、128、129、一个物理包边界前后、4 KiB、32 KiB；
   - 源/目的 offset：0、非对齐、region 尾部恰好结束；
   - 目的 SRAM 逐字节等于源 SRAM，传输范围外哨兵字节不变；
   - source checksum、wire checksum、destination checksum 一致；

2. **同 die 与跨 die**
   - physical 与 behavioral 模式对同一 program 得到相同目的字节；
   - 打开 DTE streaming 时间戳后业务 payload 仍完整，时间戳/trace 值也正确；
   - 相邻核、跨多 Router、2D 转弯路径；
   - 跨 die 使用不同出口、stripe 配置和 tail；
   - payload 内容、路由 hop、D2D SAF/credit 和完成时间均可解释；
   - 跨 die 只增加已有 D2D 路径时延，不在 DTE 重复计 hop/link 时延；
   - 对 D-19 中每个发布的 remote direction 做非零字节端到端测试，并核对 HBM/SRAM 源读、peer 目的写和 completion；不发布的 direction 必须有加载期负例。

3. **同步/异步与匹配**
   - SYNC send 仅等本地发送完成，不等对端 ack；SYNC recv 等数据完整落 SRAM；
   - ASYNC issue 后计算可前进，WAIT 后数据才可消费；
   - 同 fsm 配对成功，fsm/tag/source/length 不匹配失败；
   - 多个 fsm 并发、同目的争用、双向 full duplex、backpressure 后恢复；
   - cancel、重复 completion、未知 token、接收先于发送和发送先于接收。

4. **错误与边界**
   - length=0 只允许专门 event 语义，普通数据传输拒绝；
   - fsm 复用只能发生在前一传输完成/取消并回收之后，提前复用明确失败；
   - 源/目的越界、size 溢出、region 已释放、目的重叠写 hazard；
   - 丢 seq、重复 seq、乱序、错误 tail、checksum 错、提前 end；
   - 失败后没有 token、reassembly buffer、credit 或 Router residual 泄漏。

5. **时序与资源 oracle**
   - SRAM 源读、DTE endpoint service、NoC/D2D、目的写各有 trace；
   - 无争用时总时间与分项 oracle 一致；
   - 有争用时只增加实际 queue/link/bank wait；
   - 不允许固定 16-byte Access 和真实 length Access 同时计费；
   - 大 payload 完成时间随 flit/byte 数线性增长。

6. **回归**
   - DTE V0～V4、NoC congestion、D2D V0～V5、SRAM/HBM 相关测试全跑；
   - Msg metadata、streaming timestamp 和业务 payload 的 bit/sideband 互不覆盖；
   - 普通旧 `Send_prim`/`Recv_prim` 若保留兼容模式，输出和时序变化必须有迁移说明；
   - program 与测试 helper 不能使用绕过 Router 的直接 SRAM copy。

### 11.4 评审、修改与退出条件

**评审重点**：真实 payload 是否走 production 数据通路、Send/Recv/DTE 类和 executor 改造是否完整、时间戳与 payload 是否分离、时序是否只计一次、RX 可见性、错误时部分写、跨 die 内容保持和所有有限缓冲的 backpressure。

**修改要求**：发现数据只在测试 side channel 中复制、绕过 Router，或仍使用常量 Msg payload，阶段直接判定不通过；修复后重跑全部长度和跨 die 矩阵。

**退出条件**：

- 同 die、跨 die、同步、异步 P2P 均通过逐字节校验；
- 每个已发布 direction 的实际 source read、wire payload 和 destination write 均有 production trace，远端 SRAM 落点使用 `kNocRx`；
- 时序与 credit 回归可解释，无重复计费；
- 所有错误/完成路径全 drain；
- P6 可以复用同一 payload 数据通路，不另建集合通信专用假数据路径。

## 12. P6：九种通信语义（P2P 与八种集合通信）、core group 与对称分解

### 12.1 开发目标

在真实 P2P 字节通路之上，实现 TX×RX 3×3 矩阵、编译期 collective lowering 和 baseline/endpoint 路径，证明九种通信的值、顺序、阶段同步和生命周期正确。

### 12.2 开发任务

- 扩展 `llm/include/dte/coll_plan.h`：
  - 保留 DIRECT 和必要的单边 root 语义；
  - 新增 AllToAll、AllGather、ReduceScatter、AllReduce 的对称分解；
  - 生成每核 `DTE_SEND`/`DTE_RECV`、`REDUCE_COMPUTE` 和 public `GROUP_SYNC`；collective phase barrier 按 D-27 作为 lowering 生成的 internal 控制，不与 `GROUP_SYNC` 混成第二套 public 语义；
  - 确定性分配 fsm_id、collective_id、phase、group_id；
- 当前内部 `CollAlgorithm`/codec v0 只有 DIRECT/root-scatter/root-broadcast；对称算法优先存在于外部 ISA lowering 层。若必须进入内部 descriptor/wire，则显式升级 codec version，禁止静默改变 v0 数值语义；
- 使用 P5 的统一 fsm allocator，并为每个 collective phase 定义分配、配对、完成和回收点；
- 按 D-31 固定每个 phase 的“先 post receive→异步 issue send→wait receive/token→内部 phase barrier”顺序；若某模式使用同步 send，必须单独证明有限 buffer 下不会循环等待；
- 实现/补齐 mode lowering：
  - TX：UNICAST、SCATTER、BROADCAST；
  - RX：UNICAST、GATHER、REDUCE；
- baseline 阶段不使用 multicast/DCA：
  - Broadcast 退化为多条 unicast；
  - endpoint Reduce 按 D-28 聚合 N 份逻辑贡献（本地 1 份、远端 `N-1` 份）后执行独立 `REDUCE_COMPUTE`；
  - Gather 使用 reorder buffer 按 rank/chunk 写入正确偏移；
- 按 D-32 实现 endpoint reduce 的真实数据路径：定义 sender-rank staging SRAM 布局，从 N 份 operand 读取数据，执行 SUM/MAX，将结果写入最终 region，最后一字节可见后才完成；
- 扩展现有仅做周期计费的 `Reduce_compute_prim` 或新增数据执行层，VEC 周期与 SRAM AccessUnit 时序分别只计一次；
- 为 UINT8/INT32/INT64 实现已冻结的字节序、符号、溢出/截断和负数 MAX 规则；
- 指令只引用静态 `group_id`，不重复内嵌完整成员表；
- 除 P2P 外的八种集合语义在加载期拒绝跨 die group；
- 明确 public `GROUP_SYNC`、internal phase barrier、epoch、tree/session 的 key、完成与释放次序；
- 编译器/规划库输出稳定的 lowering trace 和每核指令清单。

### 12.3 详细测试

1. **lowering 纯函数测试**
   - 九个 TX×RX 格子分别生成预期发送者、接收者、mode 和数量；
   - 统一 `N=group_size`，覆盖 N=1/2/4、非连续 group、不同 root；
   - 每种 mode 的逻辑贡献、本地处理、远端 send/recv 数与 D-28 规格表一致，root Reduce 在 N>1 时接收 `N-1` 条远端贡献；
   - 同一输入重复 lowering 得到逐条相同的每核指令序列；
   - fsm_id、phase、offset、slice 和 recv count 无碰撞；
   - AllToAll/AllGather/ReduceScatter/AllReduce 不生成运行时 `COLLECTIVE_CALL`；
   - phase 完成前不得复用 fsm，完成/取消/异常后必须可回收；
   - 外部对称算法 lowering 不改变内部 codec v0；若启用新版 codec，v0/v1 互解码必须按版本拒绝或兼容；
   - endpoint reduce 恰好生成必要的 `REDUCE_COMPUTE`，无 DCA 时不能省略。

2. **九种模式的真实数据测试**
   - P2P：目标等于源；
   - Scatter：每个目标得到不同且正确的 slice；
   - Broadcast：每个目标 exactly once 得到相同数据；
   - Gather：root 按 sender rank/offset 拼装；
   - Reduce：检查 sender-rank staging 布局、每份真实 operand、本地+远端贡献数、最终目的可见性，SUM/MAX 结果与独立软件 oracle 一致；
   - ReduceScatter/AllReduce 的每个归约目标同样读取真实 N 份逻辑贡献，不能只修改 trace 中的结果；
   - AllToAll：每个目标得到来自每个源的对应 slice；
   - AllGather：每核按固定顺序得到全组数据；
   - ReduceScatter：每核得到不同 slice 的正确归约结果；
   - AllReduce：每核得到相同最终归约结果；
   - 所有测试检查逐字节内容、传输范围外哨兵、发送/接收次数和 checksum。

3. **dtype、大小和尾部**
   - UINT8、INT32、INT64 的 SUM/MAX exact，覆盖 0、负数、最小/最大值和多次累加溢出，并按 D-32 断言符号、字节序及截断规则；
   - 范围外输入/输出哨兵不变，staging 读、最终写和 VEC 计费各自与 oracle 一致；
   - FP 只按现有 backend 已支持的 value mode 测试，timing-only 不做伪 exact 断言；
   - count 覆盖单元素、非整 flit tail、1 KiB、8 KiB、32 KiB；
   - N=1 的 reduce/allreduce bypass 不产生远端消息或多余归约，按规格执行本地 copy/alias。

4. **同步、并发与错误**
   - 同一 group 连续 epoch、两个不同 collective key 并发、普通 P2P 与 collective 并发；
   - 快核在 barrier 等待，release 后所有成员继续；
   - 在每 endpoint/Router/credit/reassembly buffer 均有限且接近满载时，验证 receive-post/send-issue/wait 顺序持续前进；
   - 故意生成“全部核先阻塞 send”的非法 schedule，planner 或 loader 必须拒绝，不能只依赖 watchdog；
   - group 不一致、rank 重复/缺失、root 非成员、count/stride 不合法、跨 die group 均启动期失败；
   - sender 缺失、重复到达、recv count 不符由 watchdog/协议校验捕获；
   - 完成后 gather/reduce buffer、barrier、endpoint、fsm/token、Router residual 全为零。

5. **路径不变量**
   - baseline 下不编程 multicast tree、不产生 DCA issue；
   - Scatter/Gather/AllToAll 不进入 multicast/DCA；
   - endpoint Reduce 目的端收到 `N-1` 份远端消息，与 1 份本地贡献组成 N 份逻辑输入并执行真实 VEC/数据运算，不能伪装成网内归约；
   - 所有真实数据复用 P5 通路，禁止 `self_rank+1` 等假数据验证路径。

6. **回归**
   - NoC collective V0～V6/R0～R8 现有 selftest 和 runner；
   - DTE、SRAM、D2D 和普通 NoC 回归；
   - JSON collective 与 program lowering 的同语义结果对比。

### 12.4 评审、修改与退出条件

**评审重点**：矩阵语义、普通 Reduce 的单 root 与 ReduceScatter/AllReduce 的对称边界、外部 lowering 与内部 codec 版本边界、slice/offset、收发发布顺序、fsm 分配/回收、endpoint reduce 的真实数据与计费、跨 die gate、barrier/epoch 生命周期。

**修改要求**：任何死锁通过扩大无界 buffer 或插入不可解释 wait 解决都不接受；必须修正依赖、有限容量和 progress 逻辑并重跑压力用例。

**退出条件**：

- 九种模式的 lowering、真实值、exactly-once 和 drain 全部通过；
- ReduceScatter/AllReduce 使用对称分解；
- baseline 不触发 multicast/DCA；
- 非 P2P 跨 die 被明确拒绝；
- P7 只需切换正交加速能力，不重写语义指令序列。

## 13. P7：四档 NoC 加速、DCA 与广播树冲突规避

### 13.1 开发目标

在同一语义指令序列上独立启用 multicast broadcast 和 DCA reduce，并通过编译期冲突/容量调度消除多广播树整段占锁带来的不可控尾延迟。

### 13.2 开发任务

- 复用 D-10 从 production X-first XY 树编程抽出的共享 topology/path 纯函数，禁止冲突分析复制另一套路由算法；
- 为每棵 tree 计算 `(router, output_direction)` 资源集合；
- 构建树冲突图：共享任一 Router output 即冲突；
- 使用确定性贪心着色/分批，并同时满足：
  - 批内无资源冲突；
  - 每个 Router 的 `CollectiveTreeTable` 容量；
  - 可配置 K 上限；
  - 无法证明安全时保守串行；
- 批间插入 `GROUP_SYNC`，sync_seq 由 lowering 确定性分配；
- 按 D-22 实现批级 tree 生命周期：批开始前 program 本批树，批完成后 erase/release，再进入下一批；若运行期 program/erase 不可行，则按全量常驻占用在加载期拒绝，不能声称指令分批降低容量；
- 修改当前 AllGather “加载期一次性编程所有 source tree”的路径，使实际表项生命周期与批次一致；
- 将 tree occupancy 峰值、每批 program/erase 数量和 release 原因加入 trace；
- `broadcast_backend=MULTICAST` 时仅实际可组播的 `BROADCAST_TX` 携带 tree_id；Scatter 保持 unicast 展开；
- `reduce_backend=DCA_OFFLOAD` 时 `REDUCE_RX` 携带 DCA/tree 配置，成功路径不生成 endpoint `REDUCE_COMPUTE`；
- ReduceScatter+DCA 按 D-11 结论开放或 fail-fast；
- 四 profile 只改变 tree/DCA 配置，不改变高层 collective 语义；
- 输出实际 profile/backend、批次、冲突边、tree 容量、DCA issue 和降级/拒绝原因；禁止静默 fallback。

### 13.3 详细测试

1. **冲突图与批调度纯函数测试**
   - 两棵无共享 output 的树在同一批；
   - 两棵共享 output 的树必须分批；
   - 链式、环形、完全冲突图的颜色数和批次合法；
   - 输入顺序变化后规范化调度结果稳定；
   - K=1、K=2、K≥N；
   - Router tree entry 剩余容量不足时，实际按批 program/erase 后拆批；若采用全量常驻策略则在加载期明确失败；
   - 未知/非确定路径按保守冲突处理；
   - 每批程序化验证任意两棵树资源集合不相交。

   - 静态 path 集合与 production tree 编程/Router trace 逐项一致；
   - 调度分成多批时实测 tree occupancy 峰值等于 oracle，而不是仍常驻全部 source tree。
2. **profile 作用矩阵**
   - P2P：四档完全相同；
   - Scatter、Gather、AllToAll：四档数据通路相同；
   - Broadcast、AllGather：baseline/reduce_only 为 unicast，broadcast_only/reduce_broadcast 为 multicast；
   - Reduce：baseline/broadcast_only 为 endpoint+VEC，reduce_only/reduce_broadcast 为 DCA；
   - ReduceScatter：按 D-11 只产生两种已支持行为，未支持配置明确拒绝；
   - AllReduce：四档对应 broadcast 开关×reduce 开关的四种不同路径；
   - trace 中实际 backend 必须与配置严格一致。

3. **multicast 数据与生命周期**
   - 源 SRAM 只读一次，网络内复制，每个目标 exactly once；
   - 多 tree 同批无冲突时并行，冲突 tree 按批和 `GROUP_SYNC` 顺序执行；
   - 第一 flit 加锁、tail 解锁，批结束无方向锁残留；
   - tree_id collision、重复 program、容量超限、release mismatch 和未知 tree 负例；
   - 每批开始前只存在本批树，批 release 后表项回收，再允许下一批进入；
   - AllGather 多 source 分批时，未到批次的 source tree 不提前占表项；
   - 连续 epoch、多 group、多 tree 完成后表项为零。

4. **DCA reduce 数据与时序**
   - 目的 SRAM 只收到最终结果一份，不生成 endpoint `REDUCE_COMPUTE`；
   - N=1 bypass、N=2、N=3/4 pairwise stages；
   - SUM/MAX、tail mask、不同 dtype/value mode；
   - DCA latency 与 initiation interval 分离，issue/completion 符合独立 oracle；
   - DCA 与 core compute、normal traffic、multicast result 竞争时公平前进；
   - queue/result backpressure 解除后无重复 result。

5. **压力与性能可解释性**
   - group N 接近/超过单 Router 64 tree entry 风险边界；
   - 1、4、16、32、40、64 chunks 和 1～32 KiB payload；
   - 多棵共享链路树、完全串行兜底和最大安全并行批；
   - 对比无冲突理论时间、实际 queue/stall、批间同步和尾部 drain；
   - 不要求所有场景一定快于 baseline，但性能拐点必须能由 trace/oracle 分解。

6. **回归与禁止项**
   - 四 profile 全矩阵、现有 R0～R8/V0～V6、NoC congestion、DTE、D2D 全跑；
   - Scatter trace 中不得出现 `AtomicMulticastFork`；
   - 未通过 DCA 能力验证的 ReduceScatter 不得静默使用 endpoint；
   - 未启用 collective 时普通 NoC 路径关键周期保持 frozen baseline。

### 13.4 评审、修改与退出条件

**评审重点**：静态路径与 production Router 唯一真源、冲突图充分性、tree 按批 program/erase 的真实生命周期与容量峰值、批间屏障、两个加速开关正交、DCA capability gate 和无静默 fallback。

**修改要求**：若实际 trace 出现静态分析未预测的共享 output，立即阻塞发布；先修正路由模型或降为保守串行，再重跑全部冲突矩阵。

**退出条件**：

- 所有批次均可证明无 tree output 冲突，且实际 tree occupancy 峰值不超容量；
- 四 profile 的实际路径、值、时序和 trace 与 oracle 一致；
- AllReduce 四种组合独立生效；
- tree/DCA/barrier/token/Router 全 drain；
- 32 KiB 和多 tree 压力无 watchdog、死锁或不可解释尾延迟。

## 17. 主要风险与控制措施

| 风险 | 影响 | 控制措施 |
|---|---|---|
| opcode 或 wire 发布后变更 | 编译器产物不可重放 | P0/P1 冻结、golden fixture、版本化、禁止改号/复用 |
| 外部 ISA 与内部 Prim wire 混为一层 | 编译器无法表达 lowering/符号且内部变化破坏 ABI | 两层格式、独立版本、明确 lowering/重定位责任 |
| artifact 固化进程内标签 ID | 跨进程或插入顺序变化后标签错绑 | 稳定字符串/符号表、loader 重定位、不同顺序差分测试 |
| DTE streaming 时间戳覆盖 payload | 数据在网络中被元数据破坏 | wire 版本或独立 sideband、physical/behavioral 双模式逐字节测试 |
| program helper 注入触发 assert 或依赖伪 JSON | `--program` 无法启动 | 拆平台初始化、修复/旁路 GlobalMemory 构造、独立 program smoke |
| MLA/PD 缺少 program 调度上下文或 helper 被错误强转 | program 路径崩溃或成本/副作用失真 | D-29 capability gate、专用 adapter/scheduler fixture、未通过则不发布 |
| endpoint reduce 仍只计周期 | SUM/MAX trace 正确但 SRAM 数据错误 | sender-rank staging、真实 operand 读写、独立整数 oracle |
| collective 全员先阻塞发送 | 有限 buffer 下循环等待 | receive-first 发布协议、planner 负例、满载 progress 测试 |
| 现有字段位宽不足且静默截断 | 地址/shape/长度错误 | 全字段范围审计、边界 round-trip、溢出 fail-fast |
| 通信仍只模拟时序不搬字节 | 模型数据流验证失真 | P5 独立阶段、逐字节 oracle、必须出现 kDte read/kNocRx write trace |
| DTE/NoC/D2D/SRAM 重复计费 | 性能结果失真 | 明确各组件唯一责任、分项 trace 和无争用 oracle |
| 对称分解引入死锁 | AllGather/AllReduce 无法完成 | 有限状态、显式 phase、先隔离 lowering，再 production 压力和全 drain |
| 多广播树整段锁冲突 | 尾延迟不可控 | 路由确定性 gate、冲突图、容量检查、保守分批、批间 GROUP_SYNC |
| 树虽分批但加载期全部常驻 | 仍超过 64-entry 容量，分批门禁形同虚设 | 批级 program/erase 或按全量常驻 fail-fast，实测 occupancy 峰值 |
| ReduceScatter+DCA 不兼容 | 错误归约或静默走错路径 | capability 默认关闭、专项验证、未通过即启动期拒绝 |
| GROUP_SYNC 与 collective key 碰撞 | 错误释放/永久等待 | 独立命名空间或严格保留值、连续 epoch 和并发负例 |
| 历史成本 bug 混入 ISA 开发 | 回归无法归因 | P0 明确继承/修复，修复使用独立变更和 oracle |
| loader 解析半途下发 | 错误状态难以清理 | 两阶段解析/提交、输入上限、mutation 和失败后 residual 测试 |
| POLL/FENCE/EVENT 规格与现状不匹配 | 结果不可消费、重复 opcode 或非法零长度 DATA | P0 收口 public 语义，未定义能力不发布，控制 wire 专项测试 |
| 测试 runner 共享 events/VCD/log | 并发测试相互覆盖并产生假阳性/假阴性 | CTest `RUN_SERIAL` 或独立输出目录，CI 串行执行共享 runner |
| 为解决 deadlock 扩大成无界队列 | 掩盖真实硬件约束 | 所有队列有限、容量满可恢复、occupancy/pressure trace |
| JSON 兼容被破坏 | 现有用户无法运行 | 双入口至少保留一周期、legacy CTest/runner 每阶段回归 |

## 18. 完成定义

本项目只有同时满足以下条件才算完成，而不是“已经能解析几条指令”或“仿真能够跑完”：

1. 外部 program artifact、外部 opcode/操作数 ABI 与内部 Prim wire 分层版本化并冻结，符号经稳定重定位；
2. v1 已发布指令均有稳定 codec、明确硬件映射和 program 入口；
3. 计算成本、LSU/DTE 阻塞语义、同步依赖符合设计契约；
4. P2P 和集合通信真实搬运并验证数据字节，不使用常量/假数据代替；
5. 九种 TX×RX 语义、普通 Reduce 的单 root 边界、ReduceScatter/AllReduce 的对称分解和四档配置均有独立 oracle；
6. 广播树冲突和容量由编译期安全调度，批级 tree program/erase 或全量容量 gate 的实际 occupancy 已验证，不依赖不可控运行时抢占；
7. 正常、异常、取消、连续 epoch 和压力场景最终全部 drain；
8. JSON legacy 路径和既有 DTE/SRAM/NoC/D2D 测试保持通过；
9. 代码、测试、oracle、trace、文档、开发日志和评审记录同时交付；
10. 未完成能力被明确拒绝，不存在零成本 stub、静默 fallback 或未记录的兼容变化。
