# 编译产物指令集设计计划

> 整理日期：2026-08-10
> 状态：设计阶段（未实现，供评审）
> 关联文档：`notes/overall_contents.md`（项目总览）、`notes/extensions/NoC/NoC集合通信重构计划.md`、`notes/extensions/DTE/DTE建模计划.md`、`notes/extensions/SRAM/SRAM能力扩展实现计划.md`

## 1. 背景与目标

WaferAI-SIM/npusim 目前完全由启动时一次性解析的 JSON workload config 驱动：`chips → cores → worklist → prims` 的静态结构在 `InitGrid` 阶段一次性装配完成，运行期不再变化。本计划的目标是把仿真器改造成**可以被编译产物调用**的形态——在现有原语（`PrimBase`/`CompBase`/`NpuBase` 及 `norm_prims`/`comp_prims`/`dte` 家族）之上，抽象出一层**稳定的指令集（ISA）**，使得未来的编译器后端可以把程序"编译"成这套指令序列去驱动仿真器执行，而不是手写/生成 JSON worklist。

指令按四类组织：**计算指令、通信指令、访存指令、同步指令**（后两者常被笼统称为"访存"，但本计划按用户要求把"数据搬运"和"顺序/依赖控制"分开设计，见第 6 节）。

本轮为**纯设计阶段交付**：给出指令列表、每条指令背后对应的具体硬件结构、以及把现有原语体系改造成稳定 ISA 所需的跨切面机制，不修改任何 C++ 代码。已知的代码缺口（部分算子未实现或存在计费 bug）如实标记，不在本轮修复。

## 2. 设计原则

仿真器已经具备四条统一的能力契约，只是没有被组织成 ISA：

- **计算侧**：`NpuBase::taskCore(context, name, dram_time&, exu_ops&, sfu_ops&, vec_ops&)` 是所有计算算子的统一成本模型入口，`NpuBase::writeOutputData`（`llm/src/prims/base/npu_base.cpp:629-710`）把 `(exu_ops, sfu_ops, vec_ops, dram_time)` 统一换算成周期数：`cycle = max(exu_cycle, sfu_cycle, vec_cycle)`，再与 `dram_time` 取重叠。
- **通信侧**：TX×RX 组合模型（`{Unicast,Scatter,Broadcast} TX × {Unicast,Gather,Reduce} RX`），`CollDescriptor`（`llm/include/dte/coll_types.h`）作为算子描述符，`PlanTier0Collective`（`llm/include/dte/coll_plan.h`）已经是一个能把整体集合通信展开成底层动作序列的编译期库函数。
- **访存侧**：`Lsu_mem_prim`/`Dte_async_prim` 已经收敛到统一的 `{绝对地址 | (region_name, offset), size_bytes, token（异步 issue/wait/poll/fence/cancel）}` 操作数约定。
- **加载侧**：`config_helper_base`（`llm/include/monitor/config_helper_base.h`）已经是一个抽象的"程序构建器"接口，`MemInterface` 已支持注入自定义实现（`mem_interface.cpp:35-38`），`PrimBase::serialize()/deserialize()` 已经是可复用的 128-bit 线格式编解码。

设计原则：**加三样东西，不改现有执行模型**——
1. 稳定的手工编号 opcode，替代 `PrimFactory` 当前的链接顺序自增 ID；
2. 补全通信/访存/同步类的 `prim_type` 分类位（目前只有计算类原语携带非零 `prim_type`）；
3. 一个读取"编译产物"而非 JSON 的 `config_helper_base` 新实现。

已确认的取舍：
- **计算指令粒度**：每个现有计算原语对应一个 opcode，不做合并抽象，最大化复用现有 `param_name`/`param_value`/`taskCore` 成本模型契约。
- **通信指令粒度**：所有通信（点对点和集合通信）由每个核的 DTE 统一发起，wire 级 opcode 只到 `DTE_SEND`/`DTE_RECV`（各带 `mode` 区分 Unicast/Scatter/Broadcast/Gather/Reduce）以及 `COLL_BARRIER`/`REDUCE_COMPUTE` 这一层级；`AllReduce`/`ReduceScatter` 等整体集合通信是编译器 IR 层语义，由编译器在编译期展开为 `DTE_SEND`/`DTE_RECV` 指令序列，不引入运行时自解释的 `COLLECTIVE_CALL` 指令。Reduce 相关集合通信（Reduce/ReduceScatter/AllReduce）按对称分解方式展开，需要同时体现四档 NoC 硬件加速配置的独立生效效果——完整设计、已知风险与解决方案见第 4 节（4.6-4.9）。
- **已知代码缺口如实标记，不在本轮修复**（详见第 3、7 节各处标注）。
- **Core group 同步语义**：同步信号仅作**到达屏障**（等组内全部核到齐即放行，不携带数据）；组内如需真正的数据交换（reduce/broadcast/…），由编译产物显式发出第 4 节的集合通信指令完成，不把两者合并成一条指令。详见 6.2 节。

## 2.1 硬件结构映射总览

每条指令必须标明**由哪个被仿真的硬件结构产生耗时**，而不是止步于"映射到哪个 C++ 类"。下表是仿真器中实际建模了时延/资源争用的硬件单元清单，第 3-6 节的每张指令表都依据此表填写"对应硬件结构"列：

| 硬件结构 | 建模位置 | 说明 |
|---|---|---|
| **EXU**（脉动阵列/MAC Array） | `ExuConfig{x_dims,count}`（`hardware.json` 的 `exu_x`/`sa_cnt`），成本换算见 `npu_base.cpp:629-710` | `exu_cycle = exu_ops / (x_dims² × 2 × count × HW_COMP_UTIL) × CYCLE` |
| **SFU**（超越函数单元） | `SfuConfig{x_dims}`（`sfu_x`） | `sfu_cycle = sfu_ops / x_dims × CYCLE` |
| **VEC**（向量 ALU） | `VectorConfig{x_dims,count}`（`vec_x`/`vec_cnt`） | `vec_cycle = vec_ops / (x_dims × count) × CYCLE` |
| **Router/NoC**（`RouterUnit`） | `llm/include/router/router.h`；含 `AtomicMulticastFork`（多播树单周期 fork）、`RouterReduceStreamEngine`+`DcaComputePool`（DCA 归约计算池，latency/II 分离） | 通信数据面 |
| **LSU**（`CoreLsuUnit`） | `llm/include/memory/core_lsu_unit.h` | 驱动 SRAM AccessUnit + DRAM/HBM 通路的同步引擎 |
| **DTE**（`DteMemoryBridge`+`DteAsyncTracker`） | `llm/include/dte/dte_memory_bridge.h`、`dte_async.h` | 驱动同一套 SRAM/HBM 通路的异步引擎；remote 方向额外经 Router/NoC |
| **SRAM 数据面**（`sram::AccessUnit`） | `llm/include/memory/sram/sram_access_unit.h` | bank/port 阵列，byte 级读写/清除排队仲裁 |
| **DRAM/HBM** | legacy `DCache` 或 `CoreMemAdapter→MemEndpointUnit→HBMBackend`（Behavioral/DRAMSys） | `LSU_*`/`DTE_*` 的 HBM 侧访问 |
| **ComputeTimeline**（手工周期注入） | `llm/include/memory/sram/compute_timeline.h`，`RunTile`/`RunCycles` | **不经过 exu/sfu/vec 模型**，直接消耗调用方指定的 cycle 数；目前仅 `Gemm_rs_swizzle`（实验性原语）与 `Sram_pipeline_prim` 使用，见 3.2 节说明 |
| **ChipGlobalMemory**（未接线 stub） | `llm/include/link/chip_global_memory.h` | 时延来源目前无法确认 |
| **纯控制面 / 无独立硬件耗时** | `SramPosLocator`（标签表元数据）、`sram::RegionTable`（分配元数据）、`WaitCollectiveBarrier`（协议状态机） | 元数据写入，不排队、不占用任何计时资源 |

**核对结论**：写本文档时逐条打开了 `llm/src/prims/comp_prims/*.cpp` 与 `moe_prims/*.cpp` 的 `taskCore` 实现（而非仅凭 `param_name` 或注释推断），发现现有实现里同属"逐元素"语义的算子并**没有**统一走同一个硬件单元——例如 `Residual_f` 走纯 VEC，`Relu_f` 却把开销计入 **EXU**（`exu_ops = N`），`Max_pool` 把开销计入 **SFU**（`sfu_ops = B·oC·oH·oW·kX·kY`）。这不是本文档的笔误，是现有代码的真实计费方式；ISA 设计原样继承（第 3 节表格逐条标出），但作为已知的历史实现不一致点提醒读者，不应被误认为是"逐元素算子=VEC"的通用规律。

## 4. 通信指令表（DTE 为中心的重构设计）

### 4.1 设计原则

无论点对点还是集合通信，硬件层面都是由**每个核的 DTE** 发起的——因此指令集不再按"是不是集合通信"区分成 `SEND`/`RECV`/`COLL_BARRIER`/`COLL_DATA`/`REDUCE_COMPUTE` 这些独立 opcode，而是收敛成两条指令（各带同步/异步两种触发方式），所有通信语义统一通过 `mode` 参数表达。参照 DTE 硬件寄存器接口的通用形态（`direct_dte_send_async`/`direct_dte_send_sync`：配置源地址、目的、长度、模式、触发方式后发起，配置耗时几十 ns 量级）设计。

### 4.2 指令定义

| 指令 | 操作数 | 语义 | 映射到的现有类（lowering 目标） | 对应硬件结构 | 备注 |
|---|---|---|---|---|---|
| `DTE_SEND{op=ASYNC\|SYNC}` | `fsm_id`, `mode`∈{UNICAST_TX,SCATTER_TX,BROADCAST_TX}, `src_addr`\|region+offset, `length`, `dst`（UNICAST_TX：全局端点 id / SCATTER_TX,BROADCAST_TX：`group_id`+可选 `tree_id`） | 配置 DTE 寄存器（源地址/长度/模式/目的）后触发发送 | `Send_prim`（UNICAST_TX）/ `Collective_data_prim{mode=BROADCAST_TX}`（BROADCAST_TX）/ `Collective_data_prim` 按目的展开的 N 条 `Send_prim`（SCATTER_TX，见 4.4） | **Router/NoC**；`BROADCAST_TX` 给 `tree_id` 时额外用 Router 的 `AtomicMulticastFork` | `op=ASYNC`：配置+触发后立即返回（几十 ns），本核指令流不阻塞，可与后续指令重叠，配合 `fsm_id` 用 6.1 节的 `DTE_WAIT`/`POLL`/`FENCE`/`CANCEL` 追踪完成；`op=SYNC`：阻塞直到**本地发送动作本身完成**（不是等对端收到 ack），未完成会一直等待 |
| `DTE_RECV{op=ASYNC\|SYNC}` | `fsm_id`, `mode`∈{UNICAST_RX,GATHER_RX,REDUCE_RX}, `dst_addr`\|region+offset, `length`, `src_expect`（UNICAST_RX：期望发送方 id/tag / GATHER_RX,REDUCE_RX：`group_id`），`reduce_op`（仅 REDUCE_RX，SUM/MAX） | 配置接收描述符后触发 | `Recv_prim`（UNICAST_RX）/ `Collective_data_prim{mode=REDUCE_RX/GATHER_RX 对应现有 mode}` + `Reduce_compute_prim`（REDUCE_RX 非 DCA 路径，见 4.11） | **Router/NoC**；`REDUCE_RX` 给 `tree_id`/DCA 配置时额外用 `RouterReduceStreamEngine`/`DcaComputePool` | 语义同 `DTE_SEND` 的 `op` |

`fsm_id` 身兼两职：既是 DTE 上实际占用的硬件 FSM/channel 资源编号（对应现有 `token` 概念），也是配对 TX/RX 指令的匹配键（对应现有 `tag_id`）——一次传输的收发两端必须用同一个 `fsm_id`。

`dst`/`src_expect` 里的 `group_id` 复用 6.2 节新设计的 core group 静态注册表（`group_id → core_ids[]`），运行时按 `group_id` 查成员列表/`group_size`，指令里不必每次内嵌完整核 id 数组——这是 core group 注册表的第三个受益方（另两个是 `GROUP_SYNC` 和下面 4.8 节的对称分解）。`tree_id` 复用现有 `CollectiveTreeTable`/`ProgramCollectiveTreeEntry` 机制；不给 `tree_id` 时运行时把 `SCATTER_TX`/`BROADCAST_TX`/`REDUCE_RX` 退化为若干条 Tier0 unicast 收发的组合，指令本身对是否有硬件加速透明（详见 4.8）。

**lowering 策略待确认**：上表"映射到的现有类"一栏是推荐的落地方式——`DTE_SEND`/`DTE_RECV` 只是 ISA/wire 层面的逻辑 opcode，实际由加载器/编译器后端根据 `mode` 在反序列化时构造出对应的现有 C++ 原语对象（`Send_prim`/`Recv_prim`/`Collective_data_prim`/`Reduce_compute_prim`），`WorkerCoreExecutor` 内部的 `typeid` 分派、`worker_core_execute` 调度逻辑都不需要改动。另一种做法是真的新增 `Dte_send_prim`/`Dte_recv_prim` C++ 类、让调度器认识新类型——工作量更大，本轮不推荐，留在第 8 节作为待决问题。

### 4.3 TX×RX 组合矩阵：集合通信语义由谁来

不是 TX 单向决定 RX，而是**参与通信的核组，各自选择的 TX 模式和 RX 模式组合起来**决定整体是哪种集合通信：

| RX＼TX | Unicast TX | Scatter TX | Broadcast TX |
|---|---|---|---|
| **Unicast RX** | Send/Recv（P2P） | Scatter | Broadcast |
| **Gather RX** | Gather | AllToAll | AllGather |
| **Reduce RX** | Reduce | ReduceScatter | AllReduce |

矩阵第一行/第一列（root 参与其中一侧）是**单边角色**：只有 root 用非 Unicast 模式，其余核只用 Unicast 模式补另一侧。右下角四个格子（AllToAll/AllGather/ReduceScatter/AllReduce）是**全员对等**：组内每个核同时用两种非 Unicast 模式，既发又收——本文档称后者为**对称分解**（symmetric decomposition），区别于"先全部汇总到 root、再由 root 分发"的**顺序 root 中转分解**（现有 `PlanTier0Collective` 已实现的 `REDUCE_ROOT_SCATTER`/`REDUCE_ROOT_BROADCAST` 算法就是顺序分解的例子，只用在单边角色格子）。

### 4.4 九种模式的指令发放方式

| 集合通信 | TX×RX | 谁发 `DTE_SEND`，什么 mode | 谁发 `DTE_RECV`，什么 mode |
|---|---|---|---|
| Send/Recv (P2P) | Unicast×Unicast | 1 个源核：`UNICAST_TX` | 1 个目的核：`UNICAST_RX` |
| Scatter | Scatter×Unicast | root：1 条 `SCATTER_TX`（引用 `group_id`，向 N 个目的核分发不同切片） | 其余 N 个核各发 `UNICAST_RX` |
| Broadcast | Broadcast×Unicast | root：1 条 `BROADCAST_TX`（引用 `group_id`，可选 `tree_id` 走硬件组播） | 其余 N 个核各发 `UNICAST_RX` |
| Gather | Unicast×Gather | N 个源核各发 `UNICAST_TX`（发给 root） | root：1 条 `GATHER_RX`（引用 `group_id`，等 N 份到齐并拼装） |
| Reduce | Unicast×Reduce | N 个源核各发 `UNICAST_TX` | root：1 条 `REDUCE_RX`（引用 `group_id`+`reduce_op`，归约 N 份） |
| AllToAll | Scatter×Gather | **组内每个核**都发 `SCATTER_TX`（给组内其他每个核发不同切片） | **组内每个核**都发 `GATHER_RX`（收齐来自其他每个核的不同切片） |
| AllGather | Broadcast×Gather | 组内每个核都发 `BROADCAST_TX`（把自己那份广播给全组） | 组内每个核都发 `GATHER_RX`（收齐全组各自广播出来的一份） |
| ReduceScatter | Scatter×Reduce | 组内每个核都发 `SCATTER_TX`（给组内每个核发不同切片） | 组内每个核都发 `REDUCE_RX`（把收到的、来自每个核的切片归约成自己那份最终结果——每核结果不同） |
| AllReduce | Broadcast×Reduce | 组内每个核都发 `BROADCAST_TX`（把自己完整数据广播给全组） | 组内每个核都发 `REDUCE_RX`（把收到的全组数据归约成最终结果——每核结果相同） |

### 4.5 跨 Die 约束

只有 `UNICAST_TX`+`UNICAST_RX` 这一对可以跨 die；`SCATTER_TX`/`BROADCAST_TX`/`GATHER_RX`/`REDUCE_RX` 只能同 die。已核实的代码依据：`config_helper_core.cpp` 里 `ProgramCollectiveTopology()`（Tier1 多播/归约树编程前）显式 `throw std::invalid_argument("Tier1/Tier2 collective cannot cross dies")`（约 112-113 行）以及构造函数里的等价检查（约 722-726 行）；而普通 `Send_prim`/`Recv_prim` 没有任何跨 die 限制，Router 自动判定 `des_die != my_die` 并路由，D2D 场景下只是多算一段 SAF 缓冲深度（`config_helper_core.cpp:1090-1104`），不会拒绝。

### 4.6 已知风险 A：现有通信原语不搬运真实字节，完整数据通路尚未打通

**已核实的现状**（逐行读了 `send_prim.cpp`/`recv_prim.cpp`/`logic.cpp` 的 `send_logic`/`recv_logic`，以及 `execute_collective_data()`）：现有 `Send_prim`/`Recv_prim`/`Collective_data_prim` **全部是纯时序/协议记账，不搬运真实字节**：
- `Send_prim::taskCoreDefault`（`send_prim.cpp:91-137`）只为了算延迟发起一次固定 16 字节的 `sram_access->Access()`，返回的 payload 直接丢弃；真正发到网络上的 `Msg` 数据字段是硬编码常量 `sc_bv<128>(0x1)`（`logic.cpp:263-265`，默认值见 `msg.h:79`）。
- `Recv_prim::taskCoreDefault`（`recv_prim.cpp:46-51`）SRAM 侧什么都不做（写回逻辑被注释掉）。
- `execute_collective_data()`（`workercore.cpp:578-869`）全程不碰 `sram_access`/`AccessUnit`：`REDUCE_TX` 直接拿 `self_rank+1` 编造假数据验证归约正确性（约 783 行），`BROADCAST_TX`/`RX` 只收发 `CollDataHeader` 元数据（约 830-865 行），没有任何真实 payload 字节。
- `WorkerCoreExecutor`/`RouterUnit` 之间没有专门命名的"core-router 接口"模块，就是 `monitor.cpp:256-293` 里的裸 SystemC 端口直连（`channel_i`/`channel_o` 等）。

**但有一个强烈的验证信号**：`sram::AccessUnit` 的 `Initiator` 枚举里已经有 `kNocRx`（跟 `kCompute`/`kDte`/`kLsu` 并列，`llm/include/memory/sram/sram_types.h`）——SRAM 访存栈的设计者已经预留了"NoC 接收端写 SRAM"的接入点，只是从未真正接到 `Send_prim`/`Recv_prim`/`Collective_data_prim` 上。

**这意味着按本节设计实现 `DTE_SEND`/`DTE_RECV`，不只是 ISA 重新命名，还需要补上一段真实但目前完全缺失的数据通路**，具体到 SRAM2SRAM 场景（起点/终点都是 SRAM）：

> DTE 从源核 SRAM 中读数（新增：通过 `sram::AccessUnit::Access({initiator=kDte, command=kRead, address=src_addr, size_bytes=length})` 真读，而不是现在这种只为算延迟的固定 16 字节访问）→ 经过 core-router 端口（现状即可，不需要新组件）→ 经过 NoC（Router 现有的带宽/拥塞/信用建模已经是时序精确的，缺的是 flit 里要真正携带 `length` 字节 payload，而不是现在的硬编码常量——`max_packet`/`packet_scale`/`packets_in_last_group` 目前只管包数计时，不管内容，需要新增/扩展字段真正携带数据）→ 如果跨 die，走现有 D2D/`CrossDieSelectExit`/`CrossDieStep` 通路（这部分是时序精确的，只需要确认 payload 字节能一起带过去）→ 到目的核的 Router → 写到目的核 SRAM（新增：用 `Initiator::kNocRx` 发起真实 `Command::kWrite`）。

**验证方法**：实现完成后，应该能构造一个测试——源核 SRAM 某地址写入已知 pattern，触发 `DTE_SEND`/`DTE_RECV` 配对指令，检查目的核 SRAM 对应地址读出的字节跟源 pattern 完全一致（类似 `hbm_r4_selftest.cpp` 对跨 die HBM 访问的验证方式）。在这条通路补上之前，`DTE_SEND`/`DTE_RECV` 的时序模型是可信的，但字节级正确性不可信，不能用来验证真正跑一个模型时数据流是否正确，只能用来测吞吐/延迟。

### 4.7 指令与数据通路的对应关系

4.2 节指令定义表的"对应硬件结构"列和 4.6 节的数据通路描述都比较粗——前者只写到"Router/NoC"级别，后者只针对 SRAM2SRAM 这一种通用场景论证"现有原语不搬字节"这个风险。本节按 4.3 节 TX×RX 矩阵的 9 个格子逐一给出：分解方式（复用 4.4 节结论）、数据通路配置、以及硬件加速开启/关闭时路径的具体差异——用于指导后续验证测试（发了某条指令，应该断言数据经过了哪几个部件、以什么顺序），不能一套断言套用到所有 mode。

已核实的四档配置作用范围决定了：`broadcast_backend` 只影响 Scatter/Broadcast 侧，`reduce_backend` 只影响 Reduce 侧，两者独立生效——所以**不是所有 9 种模式都对四档配置同等敏感**：AllToAll 完全不受影响，ReduceScatter 只受 `reduce_backend` 影响（`broadcast_backend` 不生效），Gather/Reduce（非对称格）里 Gather 侧恒定不加速。

| RX＼TX | Unicast TX | Scatter TX | Broadcast TX |
|---|---|---|---|
| **Unicast RX** | 分解：1 源核 `UNICAST_TX`+1 目的核 `UNICAST_RX`。<br>路径：源 SRAM 读(`kDte`)→core-router 端口→Router/NoC→(跨 die：C2C)→目的 Router→目的 SRAM 写(`kNocRx`)。<br>加速差异：**无**——P2P 不参与四档配置，路径恒定。 | 分解：root 发 1 条 `SCATTER_TX`（引用 `group_id`，N 个目的地不同切片），其余 N 核各发 `UNICAST_RX`。<br>路径：对 N 个目的地**各自独立重复**上面的 UNICAST 路径（源 SRAM 每次都重新读一遍不同切片）。<br>加速差异：**无**——Scatter 从不使用组播（不同目的地数据不同，`AtomicMulticastFork` 的"网内复制"机制天然不适用），`broadcast_backend=MULTICAST` 对这一格不生效。 | 分解：root 发 1 条 `BROADCAST_TX`（引用 `group_id`，可选 `tree_id`），其余 N 核各发 `UNICAST_RX`。<br>路径（`broadcast_backend=UNICAST`）：退化成 N 次独立 UNICAST，源 SRAM 读 N 次。<br>路径（`broadcast_backend=MULTICAST`，需 `tree_id`）：源 SRAM 读**一次**→core-router 端口→首个 Router 查 `CollectiveTreeTable`→`AtomicMulticastFork` 在多个输出方向复制 flit→沿树逐跳继续复制→到达 N 个目的 Router→N 个目的 SRAM 写。<br>加速差异：数据是"源端重复读 N 次"还是"网内复制一次"——这是唯一的路径级差异，验证测试要按这两种情况分别断言。 |
| **Gather RX** | 分解：N 个源核各发 `UNICAST_TX`（发给 root），root 发 1 条 `GATHER_RX`。<br>路径：N 个源核各自源 SRAM 读→Router/NoC→目的 Router；目的核侧每份到达先进 `GatherReorderBuffer` 按 rank/chunk 重排→目的 SRAM 写（N 次，各自偏移）。<br>加速差异：**无**——Gather 从不加速，四档配置里没有对应的 Gather 加速后端，四档下路径完全一样。 | 分解：**组内每个核**都发 `SCATTER_TX`（给其他每个核发不同切片）和 `GATHER_RX`（收齐来自其他每个核的不同切片）。<br>路径：组内 N×(N-1) 条独立数据流，每条都是"源 SRAM 读→Router/NoC→目的 SRAM 写（进 `GatherReorderBuffer` 按 sender rank 重排）"——跟单纯 Scatter/Gather 的路径形态相同，只是同时在 N 个方向上发生。<br>加速差异：**无**——Scatter、Gather 两侧都不支持加速，AllToAll 是**唯一一个四档配置完全不影响其数据通路的模式**。 | 分解：组内每个核都发 `BROADCAST_TX`（把自己那份广播给全组）和 `GATHER_RX`（收齐全组广播出来的各自一份）。<br>路径（`broadcast_backend=UNICAST`）：每个核的广播各自退化成 N-1 次 unicast，目的核侧收 N-1 次到达进 `GatherReorderBuffer`。<br>路径（`broadcast_backend=MULTICAST`）：每个核各自的 `BROADCAST_TX` 走**自己的**组播树（需要 N 棵树同时/分批存在，见 4.9 节冲突问题），源端各自只读一次、网内复制到 N-1 个目的地；**但目的核侧仍然是收 N-1 次到达**——硬件加速减少的是源端重复读和网络流量，不改变"目的核要收 N-1 次、需要重排"这个事实。<br>加速差异：`broadcast_backend` 独立作用在每个核各自的 `BROADCAST_TX` 上；这是 4.9 节风险场景的直接来源（N 棵树同时发起）。 |
| **Reduce RX** | 分解：N 个源核各发 `UNICAST_TX`，root 发 1 条 `REDUCE_RX`（`reduce_op`）。<br>路径（`reduce_backend=ENDPOINT`）：N 份数据各自送到目的 Router→目的核 N 次 SRAM 写（各自操作数）→额外一条 `REDUCE_COMPUTE` 在目的核 VEC 读 N 份、算归约、写回 SRAM。<br>路径（`reduce_backend=DCA_OFFLOAD`）：N 份数据在**汇聚路径的中间 Router** 上被 `RouterReduceStreamEngine`/`DcaComputePool` 逐步两两归约→目的 Router 只收到**已经算好的最终结果一份**→目的 SRAM 写一次，**不需要发 `REDUCE_COMPUTE`**。<br>加速差异：归约发生在目的核 VEC，还是发生在网络中间节点——决定了目的核收到 1 次写还是 N 次写，验证测试要分场景断言。 | 分解：组内每个核都发 `SCATTER_TX`（给组内每个核发不同切片）和 `REDUCE_RX`（把收到的、来自每个核的切片归约成自己那份最终结果——每核结果不同）。<br>路径（`reduce_backend=ENDPOINT`）：N×(N-1) 条 Scatter 式独立数据流各自送达，每个核收 N-1 份**不同切片**操作数→`REDUCE_COMPUTE` 在各自 VEC 归约成自己那份结果。<br>路径（`reduce_backend=DCA_OFFLOAD`）：**待确认**——现有 `RouterReduceStreamEngine`/`DcaComputePool` 是围绕"多个源向同一目的地送同位置操作数"设计的（标准 Reduce 的 N→1 结构），ReduceScatter 里每个核同时是 N-1 个不同"归约组"的参与者（作为不同目的地的一份切片），这个模式能否直接复用现有 DCA 归约树机制、还是需要新的树编程方式，本轮未核实，见第 8 节待决问题。<br>加速差异：`broadcast_backend` 对这一格**不生效**（Scatter 恒定不加速），所以 `BASELINE`/`BROADCAST_ONLY` 两档下 ReduceScatter 路径相同，`REDUCE_ONLY`/`REDUCE_BROADCAST` 两档下路径相同（如果上面的"待确认"项验证通过）——四档实际只产生 2 种不同行为，不是 4 种。 | 分解：组内每个核都发 `BROADCAST_TX`（把自己完整数据广播给全组）和 `REDUCE_RX`（把收到的全组数据归约成最终结果——每核结果相同）。<br>路径：`broadcast_backend`（是否网内复制源数据）和 `reduce_backend`（是否网内归约）两个开关**独立叠加**，四档各自对应一种组合，是这张表里**唯一一个两个开关都真正生效、四档路径两两不同**的模式。`REDUCE_BROADCAST`（两者都加速）是最复杂的情况：N 棵组播树 + 网内归约流同时存在，也是 4.9 节冲突风险最严重的场景。<br>加速差异：四种组合分别对应四档配置，验证测试理论上需要覆盖全部 4 种路径。 |

两点补充说明：
- **跨 die 约束（4.5 节）对这张表里除 P2P 外的所有格子都适用**——只有左上角 P2P 那一格能跨 die，其余 8 格（含 Scatter/Broadcast/Gather/Reduce 及 4 个对称格）都限同 die，不在每格里重复写，但每格都要遵守。
- **ReduceScatter 的 DCA 加速路径是本表唯一标了"待确认"而不是直接给结论的格子**——现有 DCA 归约树的设计前提（N→1 结构）跟 ReduceScatter 里"每个核同时扮演多个归约组角色"这个模式是否兼容，没有把握确认，落地前需要专门验证，不能直接照抄 Reduce 格子的结论（见第 8 节待决问题）。

### 4.8 Reduce 相关集合通信：对称分解 + 四档 NoC 硬件加速配置独立生效

**已确认的决定**：Reduce/ReduceScatter/AllReduce 按 4.3 节矩阵右下角对应的**对称分解**实现（组内每核同时发 Broadcast/Scatter TX + 收 Reduce RX），不再走现有的顺序 root 中转算法。

**四档配置的本质是两个独立开关的组合**（已读 `llm/include/dte/coll_config.h` 核实）：
```
NocCollProfile::BASELINE          = broadcast_backend:UNICAST  × reduce_backend:ENDPOINT
NocCollProfile::BROADCAST_ONLY    = broadcast_backend:MULTICAST × reduce_backend:ENDPOINT
NocCollProfile::REDUCE_ONLY       = broadcast_backend:UNICAST  × reduce_backend:DCA_OFFLOAD（或 LEGACY_ROUTER_ALU）
NocCollProfile::REDUCE_BROADCAST  = broadcast_backend:MULTICAST × reduce_backend:DCA_OFFLOAD（或 LEGACY_ROUTER_ALU）
```
"要不要给 broadcast 加速"和"要不要给 reduce 加速"是分开控制的两个开关。对称分解要体现四档配置的不同效果，靠的是：`BROADCAST_TX`/`SCATTER_TX` 指令是否携带 `tree_id`（有则尝试走 `AtomicMulticastFork` 硬件组播，否则运行时退化为逐核 unicast）独立决定 broadcast 是否加速；`REDUCE_RX` 指令是否携带 DCA 归约配置（有则走 `RouterReduceStreamEngine`/`DcaComputePool`，否则退化为逐条到达后调用 `REDUCE_COMPUTE` 端点 ALU 归约，见 4.11 节）独立决定 reduce 是否加速——**两者是同一条指令序列上的两个正交开关，不是四条不同的指令序列**，编译器不需要为四档配置生成不同的代码，只需要在构造 `DTE_SEND`/`DTE_RECV` 时决定要不要传 `tree_id`/DCA 配置，指令本身对能力降级透明。

**需要新增的 lowering 工作（已确认，不是简单复用）**：现有 `PlanTier0Collective`（`llm/include/dte/coll_plan.h`）只实现了 `DIRECT`/`REDUCE_ROOT_SCATTER`/`REDUCE_ROOT_BROADCAST` 三种**顺序**算法，没有对称分解算法——要支持本节的决定，需要给这个规划库新增一个"对称分解"的展开逻辑（组内 N 个核 × 2 条指令，而不是 root 中转的 1 次 reduce + 1 次 broadcast），这是新写的编译期规划代码，不是现成的。

### 4.9 已知风险 B：对称分解中 Broadcast 侧的树冲突问题，及解决方案

**风险机制（已逐行读 `coll_multicast.h`/`router.cpp` 核实，非推测）**：

对称分解要求组内 N 个核**同时**各发一条 `BROADCAST_TX`——如果都想用硬件组播加速（都带 `tree_id`），N 棵组播树会在 Mesh 里走到同一批 Router。但 `AtomicMulticastFork` 的加锁状态是**按（树, Router 输出方向）持有一整段传输**的，不是逐 flit：
- `Commit`（`coll_multicast.h:150-160`）在 `first`（第一个 flit）时给对应输出方向上锁，直到 `tail`（`is_end` flit）才解锁——中间过程既不释放也不能被抢占。
- 多棵树抢同一个输出方向时，谁赢完全由跟树身份无关的**通用 ingress 端口轮转**决定（`router.cpp:613-614` 的 `collective_rr_start`，成功后在 `router.cpp:724` 等处推进），**没有任何面向集合通信树的公平性/优先级机制**（`NocCollDcaArbitration` 那个仲裁配置是给 DCA 归约计算池用的，跟组播锁无关）。
- `CollectiveTreeTable` 每个 Router 只有 `COLL_TREE_ENTRIES_PER_ROUTER=64` 个树条目容量，N 棵并发树可能逼近甚至超过这个上限。

后果：两棵树一旦在某条链路上撞上，输家要等赢家的**整个传输**跑完才能继续，且这个"谁赢"不可预测、不可调度——如果放任 N 个核同时触发硬件加速的 `BROADCAST_TX`，会产生不可控的尾延迟，而不是预期的加速效果。**Reduce 侧没有这个问题**：`DcaComputePool` 本身就是按多请求源排队+仲裁设计的（`core_pending_`/`dca_pending_` 两个队列 + round-robin/优先级仲裁），N 个核同时发 `REDUCE_RX` 争用同一 DCA 资源会正常排队处理，只受 `initiation_interval` 限速，不会出现上述整段独占的问题。

**解决方案：不依赖 Router 的临时仲裁，靠编译期把 `BROADCAST_TX`/`SCATTER_TX` 排到无冲突的批次里**：
1. 把对称分解里"组内 N 核同时发 Broadcast/Scatter TX"这一步拆成 ⌈N/K⌉ 批（批大小 K 可调），批间用 6.2 节的 `GROUP_SYNC` 做屏障顺序执行；批内的 K 棵树在编译期需要保证互不冲突。
2. **冲突判定**：基于确定性路由（Mesh 内广播路由若采用 XY dimension-order 这类确定性算法，可以在编译期静态算出每个 root 的组播树会经过哪些 Router 的哪些输出方向——**此路由确定性假设在本轮未针对同 die 广播场景重新核实，落地前需要专门确认**，之前的调研只确认了 D2D 跨 die 路由是"先 die 级 XY 选出口、再 die 内 XY"这种确定性方式），构建"冲突图"（两个 root 的树共享至少一个 Router 输出方向就连一条边），对图做贪心分组/图着色，同色（无内部边）的 root 放进同一批，可以安全并行。
3. **容量约束**：批大小同时受路径上任意 Router 当前剩余 `CollectiveTreeTable` 容量的限制，跟冲突图分组一起算。
4. **保守兜底**：算不清楚或有疑虑的 root 对，编译器默认分到不同批（宁可少并行，不猜）——跟 `CollectiveTreeTable::Program` 对冲突编程直接 `throw` 的行为一致，宁可编译期拒绝也不依赖运行时纠错。

**当前状态**：这套冲突图分批机制是全新的编译期工具（拓扑建模 + 冲突分析 + 批调度），**是让对称分解在四档硬件配置下都能正确工作的必要组成部分，不是可选的后续优化**——因为对称分解已经是既定方向（4.8 节），如果不做冲突规避，`BROADCAST_ONLY`/`REDUCE_BROADCAST` 两档配置下的对称 Broadcast/AllGather/AllReduce 会有不可控的尾延迟风险。批大小 K 的具体取值策略（固定小批 vs 精确图着色）留在第 8 节作为待决问题，先把"必须做冲突规避，不能假设 Router 会自己处理好"这个结论定下来。

### 4.10 片外/全局内存收发（不属于 DTE 核间通信，单独保留）

`GLOBAL_SEND`/`GLOBAL_RECV`（type,enable,des_id,des_offset,local_offset,max_packet,tag_id,end_length / type,tag_id,recv_cnt，映射到 `Send_global_memory`/`Recv_global_memory`，硬件结构=`ChipGlobalMemory`）是核到片外/host 全局内存的访问，跟本节重构的"核间"通信（无论 P2P 还是集合通信，两端都是核）是不同的东西，不纳入 `DTE_SEND`/`DTE_RECV` 的 mode 分类。现状不变：`taskCore()` 是 `LOG_ERROR("not implemented")` 桩，真实 TLM 收发逻辑被注释掉，**不进入可交付 v1 opcode 空间**，作为独立前置任务（跟第 5 节 `GLOBAL_LOAD`/`GLOBAL_STORE` 共享同一前置依赖）。

### 4.11 `REDUCE_COMPUTE` 与 `COLL_BARRIER` 的关系

`REDUCE_COMPUTE`（映射到现有 `Reduce_compute_prim`，硬件结构=VEC）保留为独立指令，跟 `REDUCE_RX` 配套使用：`REDUCE_RX` 负责收数据（不管是否 DCA 加速），如果**没有**用 DCA 硬件归约（`REDUCE_RX` 未带 DCA 配置，Tier0/baseline 路径），接收核在收齐 N 份数据后需要额外发一条 `REDUCE_COMPUTE` 在自己的 VEC 单元上做实际的归约运算——这跟之前"通信开销和计算开销分离计费"的设计原则一致，`REDUCE_RX` 只计通信/收数的时延，归约算子本身的计算时延单独用 `REDUCE_COMPUTE` 计。如果 `REDUCE_RX` 用了 DCA 加速，归约在网内已经做完，不需要再发 `REDUCE_COMPUTE`。

`COLL_BARRIER`（第 6 节）不是数据传输指令，保持独立，用于集合通信内部的阶段同步（跟服务于 lockstep 调度的 `GROUP_SYNC` 是两回事，见 6.2 节）。

## 5. 访存指令表

统一操作数约定（与 `Lsu_mem_prim`/`Dte_async_prim` 已收敛的形态一致）：SRAM 侧用**绝对地址**或**命名 region + offset** 二选一，均带显式 `size_bytes`；异步指令带 `token`。

## 5.1 LSU 与 DTE 的阻塞/非阻塞语义（已核实并据此收紧设计）

**结论先行**：如果把 `Lsu_mem_prim{op=ISSUE/WAIT/POLL/FENCE/CANCEL}` 也当作 v1 ISA 的可用 opcode，LSU 就会表现得和 DTE 完全一样——非阻塞、可与计算重叠，这与"LSU 访存必须阻塞、不能与计算并行；只有 DTE 能与计算并行"的架构意图相冲突。第 5 节已经把这几个 op 排除在编译产物可见的 v1 opcode 空间之外。下面是逐行读源码确认的具体机制，不是推测。

**LSU_LOAD/LSU_STORE 为什么真的会阻塞（已核实）**：
1. `Lsu_mem_prim` **没有被 `WorkerCoreExecutor::worker_core_execute` 特判分派**（`llm/src/workercore/workercore.cpp:402-576`）——该函数只对 `Collective_data_prim`/`Collective_prim`/`Dte_async_prim`/`Send_prim`/`Recv_prim` 五种类型走专门分支，其余类型（包括 `Lsu_mem_prim`）一律落进通用的"计算"分支：`ev_comp.notify(CYCLE, SC_NS); ... wait(prim_block.negedge_event());`。
2. `Lsu_mem_prim::taskCoreDefault`（`llm/src/prims/norm_prims/lsu_mem.cpp:188-229`）对 `LOAD_BLOCKING`/`STORE_BLOCKING` 调用的是 `CoreLsuUnit::Load`/`Store`（`llm/include/memory/core_lsu_unit.h:90-92`）——这两个函数与返回 token 就走的 `IssueLoad`/`IssueStore`（`core_lsu_unit.h:75-79`）不同，是真正同步的调用，会在函数内部等待完整传输时延才返回。
3. 两者叠加：核心单线程的 `prim_queue` 在 `LOAD_BLOCKING`/`STORE_BLOCKING` 执行期间被整体卡住——不只是这条访存指令本身耗时，该核**任何后续指令（含计算指令）都无法开始**，必须等传输完成。这精确对应"LSU 不能与计算并行"的要求。

**但 `CoreLsuUnit` 引擎本身其实支持异步（这正是需要在 ISA 层面主动收紧的原因）**：`Lsu_mem_prim{op=ISSUE}` 走的是同一条 `taskCoreDefault` 路径，但它调用的 `CoreLsuUnit::Issue`（`core_lsu_unit.h:73-74`）内部只是把描述符塞进 `sc_fifo` 队列（`queue_`，`core_lsu_unit.h:123`）就返回，不做同步等待——真正的传输由 `CoreLsuUnit` 自己的后台 `Worker()` 线程（`core_lsu_unit.h:118`）完成，通过 token 追踪，行为上和 `DteMemoryBridge`/`DteAsyncTracker` 完全对称。也就是说，**"LSU 必须阻塞"不是 `CoreLsuUnit` 这个引擎的固有限制，而是我们要在 ISA 层面主动做出的设计选择**——如果不把 `ISSUE`/`WAIT`/`POLL`/`FENCE`/`CANCEL` 从编译产物可见的 opcode 集合里剔除，编译器完全可以（意外或故意地）让 LSU 访存也变得能和计算重叠，破坏预期的硬件模型边界。

**DTE_ISSUE 为什么真的不阻塞（已核实）**：`Dte_async_prim` **有**被 `worker_core_execute` 特判分派（`workercore.cpp:456-465`），该分支只调用 `execute_dte_async(async_prim)`，**不**调用 `wait(prim_block.negedge_event())`——核心指令流几乎立即（一拍之内）继续处理 `prim_queue` 里的下一条指令，可以是计算指令，真正的数据搬运在 `DteMemoryBridge` 的后台 worker 线程里异步进行。`DTE_WAIT`/`DTE_FENCE` 会真正阻塞（语义上就是要等结果），`DTE_ISSUE`/`DTE_POLL`/`DTE_CANCEL` 不阻塞。

**设计收紧（已在第 5 节表格体现）**：v1 编译产物可见的 LSU opcode 只保留 `LSU_LOAD`/`LSU_STORE`（映射到 `Lsu_mem_prim{op=LOAD_BLOCKING/STORE_BLOCKING}`），不暴露 `LSU_ISSUE`/`LSU_WAIT`/`LSU_POLL`/`LSU_FENCE`/`LSU_CANCEL`。所有需要与计算重叠的异步访存都必须显式走 `DTE_*`。这也意味着第 6 节 `FENCE_ALL`（"清空本核 LSU+DTE 全部在途 token"）在 v1 下 LSU 那一半永远是空操作——因为编译产物根本不会产生任何在途的 LSU token——保留该指令是为未来万一重新开放 LSU 异步路径做前向兼容，不是当前必需。

## 6. 同步指令表

已通过阅读 `llm/src/workercore/workercore.cpp:402-576`（`worker_core_execute` 完整调度循环）、`llm/include/link/instr/wait_event.h`、`llm/include/dte/coll_runtime.h` 核实现状：

- **核内顺序执行即隐式同步**：`prim_queue` 由单个 SC_THREAD 顺序消费，计算指令（`ev_comp`）与同步式 `Send_prim`/`Recv_prim`（`ev_send`/`ev_recv`）在返回前都会 `wait(prim_block.negedge_event())`——即**默认模式下每条指令天然阻塞直至完成**，同核内指令间的先后依赖不需要额外同步指令。
- **异步引擎（DTE）已有 token 级同步，但缺一个"主动 drain"入口**：`Dte_async_prim` 已提供 `WAIT`/`POLL`/`FENCE`/`CANCEL`（按 token）。当前唯一的"漏检"防线是 `worker_core_execute` 在 `prim_queue` 排空时才检查 `dte_async->OutstandingCount()`/`lsu_memory->OutstandingCount()` 是否为零，不为零就 `throw`（`workercore.cpp:407-415`）——这是运行时兜底，不是编译产物可以主动插入的同步点。新增 `FENCE_ALL` 填补这个空白。**LSU 侧不再单独讨论**：按 5.1 节的设计约束，v1 ISA 只暴露 `LSU_LOAD`/`LSU_STORE`（阻塞），不暴露 `Lsu_mem_prim` 的 `ISSUE`/`WAIT`/`POLL`/`FENCE`/`CANCEL`，因此编译产物永远不会产生在途的 LSU token，`FENCE_ALL` 里对 LSU 的清空调用恒为空操作，只是为未来保留的前向兼容位。
- **集合通信屏障（`COLL_BARRIER`）功能完整但代价较重**：`WaitCollectiveBarrier(key, phase_id, rank, group_size, release_tree_id)` 要求先有一个 `CollectiveKey{group_id, collective_id, epoch}`，且同一 epoch 不能重叠在途（V1 限制）。适合"多核参与的阶段性屏障"，**不适合编译产物频繁插入的细粒度两核间生产者/消费者同步**。
- **`chip_instr_base`/`Wait_event`（`llm/include/link/instr/wait_event.h`）是死端，不可复用**：`taskCoreDefault` 无条件立即返回 0，`event` 字段从未被真正消费；它是芯片级、未接线的脚手架，**不是**一个可用的通用跨核同步原语。
- **提议新增轻量级 `EVENT_SET`/`EVENT_WAIT`**：填补"隐式核内顺序"与"重量级集合屏障"之间的空档，用于任意两核（或多核）间的一次性/高频生产者-消费者信号，不需要声明 collective group。落地方式：**不引入新的运行时状态机**，而是直接复用现有 `Send_prim`/`Recv_prim` 的 tag 匹配机制（`tag_id`/`recv_cnt`），定义为 `Send_prim{type=SEND_DATA, end_length=0}`/`Recv_prim{tag_id, recv_cnt}` 的编译器语法糖。
- **`GROUP_SYNC`（新增）：预先声明的 core group 内的到达屏障**——为支持"单 die 上多个核提前按 core id 划分为 core group，组内所有核执行相同指令、并靠一个同步信号互相对齐"这种调度模式而设计，只做纯到达屏障，不携带任何数据；组内如需数据交换，由编译产物另外显式发出第 4 节的通信指令（`DTE_SEND`/`DTE_RECV`/`REDUCE_COMPUTE`），两者不合并。详细设计见 6.2 节。

| 指令 | 操作数 | 语义 | 映射到的现有能力 | 对应硬件结构 | 备注 |
|---|---|---|---|---|---|
| `DTE_WAIT`/`DTE_POLL`/`DTE_FENCE`/`DTE_CANCEL` | token | 等待/轮询/清空/取消 DTE 异步操作 | `DteAsyncTracker::WaitToken/PollToken/Fence/CancelToken`（经 `Dte_async_prim`） | 无独立硬件耗时 | 已在访存表出现，此处作为同步类复列；LSU 侧无对应指令，v1 ISA 里 LSU 只有阻塞的 `LSU_LOAD`/`LSU_STORE`，见 5.1 节 |
| `FENCE_ALL`（新增） | — | 主动清空本核 DTE 全部在途 token（LSU 侧恒为空操作，见 5.1 节） | 新增薄封装，调用 `DteAsyncTracker::Fence()`（+ 预留的 `lsu_memory->Fence()` 前向兼容位） | 无独立硬件耗时，纯组合 | 无新仿真行为 |
| `COLL_BARRIER` | descriptor, phase_id, release_tree_id | 声明的 collective group 内跨核屏障（为单次集合通信操作服务） | `Collective_prim` → `WaitCollectiveBarrier`（已在通信表出现） | 无独立硬件耗时（协议状态机） | 每次调用都要内嵌完整 `group` 向量，不适合高频复用；`GROUP_SYNC` 是为高频场景专门做的精简版，两者语义相近但操作数/使用场景不同 |
| `EVENT_SET`/`EVENT_WAIT`（新增） | dest_id+event_tag / event_tag+count | 任意两核（或多核）间轻量级一次性信号，无需声明 collective group | 提议：作为 `DTE_SEND{mode=UNICAST_TX, length=0}`/`DTE_RECV{mode=UNICAST_RX}` 的编译器语法糖实现，复用其 tag/`fsm_id` 匹配机制 | **Router/NoC**（与 `DTE_SEND`/`DTE_RECV` 的 Unicast 模式相同，因为就是同一对底层指令） | 明确区别于不可用的 `chip_instr_base::Wait_event` 死端脚手架；点对点/多对一信号，语义上不同于 `GROUP_SYNC` 的 N 核互等 |
| `GROUP_SYNC`（新增） | group_id, sync_seq | 等待**预先声明的** core group 内全部成员到达此点后统一放行，纯屏障、不带数据 | 提议：复用 `WaitCollectiveBarrier` 的到达计数逻辑（见 6.2 节） | 无独立硬件耗时（协议状态机，与 `COLL_BARRIER` 共享底层实现） | 操作数只有 `group_id`+`sync_seq`，不内嵌成员列表——依赖 6.2 节新增的 core group 注册表 |

## 6.1 DTE 同步指令的作用（`WAIT`/`POLL`/`FENCE`/`CANCEL` 分工）

`DTE_ISSUE` 是"发出去就不管"的——它几乎立即返回、不阻塞核心指令流（见 5.1 节）。这意味着如果没有配套的同步指令，编译产物就**没有任何办法知道这次异步搬运什么时候真正完成**，也没法限制同时在途的传输数量，更没法保证核在退出前所有传输都已经落地。`DTE_WAIT`/`DTE_POLL`/`DTE_FENCE`/`DTE_CANCEL` 就是补上这个手段，四者分工不同：

- **`DTE_WAIT{token}`——真正的同步点**：阻塞本核指令流，直到指定 token 对应的那次传输完成。这是把"异步搬运"和"需要用到这份数据的后续指令"之间建立**依赖关系**的唯一方式——例如双缓冲流水线里，`DTE_ISSUE` 发起下一块 tile 的加载后，核可以先去跑当前 tile 的计算指令（真正重叠），但在要读取新 tile 数据之前，必须先发一条 `DTE_WAIT{token}` 确保数据确实已经到位，否则就是读到未就绪的数据（`Sram_pipeline_prim` 里手写的双缓冲模式就是这个用法的现成范例，见第 5 节 `SRAM_PIPELINE` 行）。这条指令会真正消耗仿真时间等待结果，语义使然。
- **`DTE_POLL{token}`——非阻塞查询**：不等待，立即返回这个 token 有没有完成（`Dte_async_prim::poll_complete`）。用于编译产物想尽量榨取重叠度的场景：先查一下"好了没"，没好就继续安排别的指令，而不是傻等——比 `WAIT` 更灵活，但需要编译器自己写轮询/重试逻辑。
- **`DTE_FENCE{}`——批量清空，不针对单个 token**：等本核所有在途的 DTE 传输都完成。用在比较粗的边界上，比如一个计算阶段结束、核准备上报 DONE、或者核的指令流要收尾之前。这直接对应仿真器现有的一条运行时安全网——`worker_core_execute` 在 `prim_queue` 排空时会检查 `dte_async->OutstandingCount()` 是否为零，不为零就直接 `throw`（`workercore.cpp:407-415`）。`FENCE` 让编译产物能**主动**满足这个不变量，而不是等仿真器在末尾报错。
- **`DTE_CANCEL{token}`——放弃一次还没完成的传输**：用于回收资源，例如一次推测性预取后来发现用不上了。DTE 引擎有 `max_outstanding` 限制（同时在途传输数上限，见 `DteMemoryBridge`/`DteAsyncTracker` 的队列配置），如果只发 `ISSUE` 不发 `WAIT`/`CANCEL`，在途 token 会一直占着槽位，后续 `ISSUE` 可能被阻塞或报错——`CANCEL` 是在不需要等结果的情况下把槽位让出来的手段。

一句话总结：`DTE_ISSUE` 负责"发起重叠"，这四条同步指令负责"正确地结束重叠"——`WAIT` 建立正确性所需的依赖顺序，`POLL`/`CANCEL` 提供非阻塞的灵活控制，`FENCE` 兜底保证收尾时不留在途操作。`WAIT`/`FENCE` 会真正阻塞（消耗仿真时间等待结果，语义使然），`POLL`/`CANCEL` 不阻塞——这一点已经体现在第 5、6 节表格的"备注"列里。

## 6.2 Core Group 声明与 `GROUP_SYNC`（新增能力）

**需求**：未来调度要支持——单 die 上的多个核提前按 core id 划分为若干 **core group**；组内所有核执行相同指令（SPMD 复制，不需要新指令，是编译器/生成阶段的复制职责，见下）；组内有一个**到达屏障**同步信号，等组内全部核到齐再统一放行；组内数据交换（reduce/broadcast/…）通过显式调用第 4 节的集合通信指令完成，不混进同步信号里。

**调研结论（已核实，非推测）**：

1. **没有持久化的 core group 抽象**：全代码库搜索 `core_group`/`CoreGroup`/`core_set`/`group_members`/`GroupTable` 等词，**零匹配**。现有的"group"只有 `CollDescriptor::group: vector<uint16_t>`（`llm/include/dte/coll_types.h:59`）——它是**每个描述符自带的完整核 id 列表**，`CollectiveKey.group_id` 只是复合 key/哈希用的字段，不是指向某个已注册成员表的索引。也就是说，今天每发一次 `COLL_BARRIER`/`DTE_SEND{SCATTER_TX/BROADCAST_TX}`/`DTE_RECV{GATHER_RX/REDUCE_RX}`（底层仍落到 `CollDescriptor`），都要在指令里重新内嵌一遍完整核 id 列表，没有"声明一次、之后按 id 引用"的机制。
2. **JSON 集合通信管线的高频复用限制是管线自己的限制，不是 `WaitCollectiveBarrier` 底层机制的限制**：`config_helper_core.cpp` 里有 `"V1 collective requires core loop=1; express epochs as declarations"` 的强制检查，每个 epoch 都要单独声明并触发一次组播/归约树编程（`ProgramCollectiveTopology`）。但 `WaitCollectiveBarrier(key, phase_id, rank, group_size, release_tree_id=0)`（`llm/include/dte/coll_runtime.h`）的 `release_tree_id` 默认就是 0，只有 `release_tree_id != 0` 时才会在释放时触发树擦除（`coll_runtime.cpp:84-93`，`EraseCollectiveTree`/`EraseCollectiveReduceTree`）——纯屏障（不挂组播/归约树）路径本身理论上没有这层开销。真正的限制是 JSON 管线的 `loop=1` 检查和"每次都要重新声明+展开"的生成方式，我们的编译产物本来就计划绕开这条管线直接构造原语（见第 7 节"加载路径"），所以卡脖子的是下一条。
3. **真正的缺口是"组成员要在每次调用里重复内嵌"**：如果一个 core group 有几十个核、程序里要反复同步几百次（比如按你说的"组内所有核执行相同指令"这种逐指令对齐的调度模式），每次都在 `GROUP_SYNC`/`COLL_BARRIER` 指令里重复一遍完整核 id 列表，既浪费线格式空间，也和"提前划分好、之后复用"的用法不匹配。

**设计方案**：

- **新增一个配置层的静态声明**（不是运行时指令，地位类似现有的 mapping/hardware config）：`core_groups: [{group_id, core_ids: [...]}]`，在加载期注册一次；仿真器内部按 `group_id` 查 `group_size`/成员集合，之后所有引用同一个 `group_id` 的 `GROUP_SYNC`（以及第 4.2 节末尾说明的 `DTE_SEND`/`DTE_RECV`）都不用再带完整核列表。具体挂在哪个配置文件（新建专用 section，还是并入 hardware/mapping config）留待实现阶段决定，见第 8 节待决问题。
- **`GROUP_SYNC{group_id, sync_seq}` 的推荐落地方式：最大化复用现有 `WaitCollectiveBarrier`，不新写运行时状态机**——ISA 层是一个精简描述符（只有 `group_id`+`sync_seq`，没有 `CollDescriptor` 里跟数据搬运相关的 `op`/`dtype`/`reduce_op`/`algorithm`/`chunk_bits` 等字段），加载器/运行时把它展开成 `Collective_prim{marker_kind=BARRIER, descriptor.key={group_id, collective_id=RESERVED_SYNC_ID, epoch=sync_seq}, group_size=<从 core group 注册表查>, release_tree_id=0}`，直接调用现成的 `WaitCollectiveBarrier`。`RESERVED_SYNC_ID` 是一个保留的 `collective_id` 哨兵值，专门留给"纯同步、不搬数据"的调用，避免和同一 `group_id` 下真正的集合通信操作在 `CollectiveKey` 命名空间里撞车（这个哨兵值的具体分配方式留待实现阶段定，见第 8 节）。
- **"组内所有核执行相同指令"本身不需要新指令**：这是编译器/生成阶段的复制职责——把同一份计算/访存指令序列发到组内每个核各自的指令流里，跟现在 TP 切分时把同一份原语序列发给一组核是同一回事（`config_helper_core.cpp` 已经在这么做）。如果需要仿真器**运行时校验**"这些核这一步确实在跑同一条指令"（严格 lockstep 一致性检查），那是一个全新的、可选的调试能力，本轮不涉及，需要单独决定要不要做。

## 7. 跨切面机制

- **稳定 opcode 编码**：新增 `include/isa/opcode.h`，手工编号 `enum class Opcode : uint8_t`，按类别分段：

  | 区段 | 用途 |
  |---|---|
  | `0x00–0x3F` | 计算指令（第 3 节，约 20 条，预留到 64） |
  | `0x40–0x7F` | 通信指令（第 4 节） |
  | `0x80–0xBF` | 访存指令（第 5 节） |
  | `0xC0–0xEF` | 同步指令（第 6 节；`DTE_*` 的 opcode 与访存表复用同一编号，不重复分配；LSU 侧无异步指令，见 5.1 节） |
  | `0xF0–0xFF` | 保留 |

  改造 `REGISTER_PRIM` 宏支持显式传入 `Opcode` 而非依赖 `PrimFactory::next_id_` 的静态初始化顺序自增（已核实：当前 `next_id_` 从 1 自增，注册顺序依赖链接期静态初始化次序，不可跨构建稳定复现）。不改变现有 128-bit 线格式的 8-bit opcode 字段宽度。

- **分类位扩展**：`PRIM_TYPE`（`llm/include/defs/enums.h:121-128`，已核实当前 5 个位：`NORM_PRIM=0,COMP_PRIM=1,GPU_PRIM=2,NPU_PRIM=4,PD_PRIM=8,MOE_PRIM=16`）新增 `COMM_PRIM=1<<5`、`MEM_PRIM=1<<6`；为当前 `prim_type` 恒为 `NORM_PRIM=0` 的通信/访存/同步类（`Send_prim`/`Recv_prim`/`Collective_*`/`Lsu_mem_prim`/`Dte_async_prim`/`Clear_sram`/`Set_addr` 等——即 `DTE_SEND`/`DTE_RECV` 按 4.2 节 lowering 策略反序列化出的底层类）在构造/`parseJson`/`deserialize` 时补上分类位；`Dte_async_prim` 按 `direction` 动态判定分类（见第 5 节）。

- **调度**：`WorkerCoreExecutor::worker_core_execute`（`llm/src/workercore/workercore.cpp:402-576`）的 `typeid` 分派结构保持不变（已核实：计算指令与同步式 `Send`/`Recv` 均通过 `wait(prim_block.negedge_event())` 阻塞至完成；异步 token 仅在 `prim_queue` 排空时被动检查，不为零即 `throw`）；仅建议在现有兜底分支中按新的 `MEM_PRIM` 位区分 trace 事件标签（`"Mem_prim"` vs `"Comp_prim"`），使指令构成统计准确，不改变调度语义。

- **统一寻址/操作数约定**：所有访存类操作数统一到 `Lsu_mem_prim`/`Dte_async_prim` 已收敛的形态（绝对地址或 region+offset、显式 `size_bytes`、异步指令带 `token`），明确排除计算指令的张量操作数（继续走 `Set_addr`/`SramPosLocator` 符号标签机制，本轮不重构）。

- **加载路径**：新增 `config_helper_program : public config_helper_base`（已核实该接口为纯虚基类：`fill_queue_config`/`fill_queue_start`/`parse_ack_msg`/`parse_done_msg`/`generate_prims`/`printSelf`/`clone`），读取编译产物（建议直接是预先 `serialize()` 好的 128-bit 段，编译器负责编码，加载器只需重放），通过 `MemInterface(name, event_engine, config_helper_base*)` 现有构造函数注入；`unittest/npusim.cpp` 的 `sc_main` 增加 `--program <path>` CLI 分支选择使用该实现而非 JSON 路径；`WorkerCoreExecutor::parse_prim`/`PrimFactory::createPrim`/SystemC 执行进程均不需要改动。

## 8. 待决问题清单

- opcode 空间是否会超过 255（触及 8-bit 线格式宽度）。
- `SRAM_ALLOC`/`SRAM_FREE`/`SRAM_RESIZE`/`SRAM_RENAME` 新增薄封装原语的具体字段设计（`RegionTable::Allocate/AllocateAt/Free/ResizeAllocation/RenameAllocation` 的参数需要一一对应到 ISA 操作数）。
- `Dte_async_prim` 双重分类（按 `direction` 动态判定）是否需要下游工具链支持"按 direction 拆分统计"。
- `Send_global_memory`/`Recv_global_memory`（`GLOBAL_SEND`/`GLOBAL_RECV`/`GLOBAL_LOAD`/`GLOBAL_STORE`）补全 TLM 收发逻辑，作为独立前置任务的排期。
- `EVENT_SET`/`EVENT_WAIT` 是作为独立 opcode 还是纯粹的编译器语法糖（不占用新 opcode，编译器直接吐出对应的 `Send_prim`/`Recv_prim`）。
- `FENCE_ALL` 是否需要覆盖未来可能新增的第三类异步引擎（当前 v1 只有 DTE 一个异步引擎，LSU 被限制为阻塞-only，见 5.1 节）。
- 是否需要在后续版本重新开放 `Lsu_mem_prim{ISSUE/WAIT/POLL/FENCE/CANCEL}` 作为编译产物可见的 opcode（例如需要一条比 DTE 更轻量、不经过 Router/NoC remote 方向判定的核内异步访存路径时）——v1 判断为不需要，只保留 DTE 一条异步路径，以保证 LSU/DTE 的架构边界清晰。
- `BATCHNORM`、`SPLIT_CONV`/`MERGE_CONV` 是否在本轮预留 opcode 编号但不发布为可用指令，还是干脆排除出 v1 opcode 空间，留到实现该算子后再分配编号。
- `RMSNORM` 的 `sfu_ops` 恒零 bug、`Relu_f`/`Max_pool` 计费单元与同族算子不一致——是否需要在实现阶段一并修正，还是继续作为"已知的历史计费选择"由 ISA 如实继承。
- `MATMUL_PD`/`ATTENTION_PD`/`ROPE_PD` 的具体成本公式本轮未逐行核实（仅通过与非 PD 版本的同族推断），实现前需要补充核实 `pd_prims/*.cpp`。
- `core_groups` 静态声明具体放在哪个配置文件（新建专用 section / 并入 hardware config / 并入 mapping config），以及是否要支持一个核同时属于多个 core group（比如既是 TP group 成员又是某个更大 pipeline stage group 的成员）。
- `GROUP_SYNC` 复用 `WaitCollectiveBarrier` 时，`RESERVED_SYNC_ID`（哨兵 `collective_id`）具体怎么分配才能保证不和同一 `group_id` 下真正的集合通信操作撞车——是留一个固定保留值，还是在 `CollectiveKey` 里单独加一个 bit 区分"纯同步"和"数据搬运"。
- `release_tree_id=0` 的纯屏障路径在高频复用（例如逐指令 lockstep 对齐）下的实际性能开销，本轮只读代码确认了"理论上不触发树编程/擦除"，还没有做实际的仿真基准测试，实现阶段需要验证。
- 是否需要仿真器运行时校验 core group 内成员确实在执行相同指令（严格 lockstep 一致性检查）——本轮判断为超出当前范围的可选调试能力，需要用户确认要不要做。
- `DTE_SEND`/`DTE_RECV` 的 lowering 策略最终选哪种（4.2 节）：反序列化时按 `mode` 构造现有 `Send_prim`/`Recv_prim`/`Collective_data_prim`/`Reduce_compute_prim`（推荐，改动小），还是新增 `Dte_send_prim`/`Dte_recv_prim` C++ 类、让 `WorkerCoreExecutor` 认识新类型（改动大）。
- **（高优先级前置依赖）** 4.6 节确认的"现有通信原语不搬运真实字节"缺口需要实际补齐：TX 侧要读改成真实 `sram::AccessUnit::Access`（不是现在只为算延迟的固定 16 字节访问），`Msg`/wire 格式要能携带真实 `length` 字节 payload（不是硬编码常量），RX 侧要接上预留但从未使用的 `Initiator::kNocRx` 真实写 SRAM——这是 `DTE_SEND`/`DTE_RECV` 具备字节级正确性的必要前提，本轮判断为独立的、优先级较高的前置任务（不完成的话，指令的时序模型可信但数据搬运结果不可信）。
- `PlanTier0Collective`（`llm/include/dte/coll_plan.h`）目前只实现顺序算法（`DIRECT`/`REDUCE_ROOT_SCATTER`/`REDUCE_ROOT_BROADCAST`），4.8 节确定的对称分解需要新增一套编译期展开逻辑，这部分是全新代码，需要单独排期设计（组内 N 核 × TX+RX 指令的生成规则、`fsm_id`/`group_id`/`tree_id` 的分配方式）。
- 4.9 节冲突图分批方案里，**同 die 广播路由是否为确定性 XY dimension-order 路由**这一假设本轮未重新核实（只核实了 D2D 跨 die 路由的确定性），落地冲突图分析前必须专门确认，如果路由是自适应/非确定性的，整套冲突图方案需要重新设计。
- 4.9 节的批大小 `K` 具体取值策略未定：固定小批（简单，牺牲部分并行度）vs 精确图着色（复杂，最大化安全并行度）——两者都需要先做前一条的路由确定性验证才能评估。
- 4.7 节数据通路表里标注为"待确认"的 ReduceScatter+DCA 加速路径：现有 `RouterReduceStreamEngine`/`DcaComputePool` 的 N→1 归约树设计能否直接支持"每个核同时是多个归约组参与者"的模式，需要专门验证，不能假设跟普通 Reduce 一样直接可用。
